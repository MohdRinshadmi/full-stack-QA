# SECTION Frontend Incidents | "The app is slow / broken" — diagnose out loud, mitigate, then fix.

### The React app becomes unusably slow after a customer adds 3,000 rows to a table. What do you do?
@short
Confirm it is a render problem rather than a data problem, then profile: 3,000 rows means 3,000 mounted components plus their children, which is tens of thousands of DOM nodes. The fix is virtualisation so only the visible rows are mounted, plus server-side pagination if the client does not genuinely need all the data.
@deep
The diagnostic sequence is: open the Profiler, record the interaction, and look at commit duration and the number of components rendering. If one commit takes 800ms across 3,000 `Row` components, it is render volume. If the commit is fast but the interaction is slow, it is a long task elsewhere — often a filter or sort running on every keystroke.

The secondary cause is re-render amplification: a state change at the page level re-rendering every row because rows are not memoised and receive new callback identities.
@code tsx The three-step fix, in order of leverage
// 1. VIRTUALISE — 3,000 rows becomes ~25 mounted nodes
const v = useVirtualizer({ count: rows.length, getScrollElement: () => ref.current,
                           estimateSize: () => 48, overscan: 10 });

// 2. STOP RE-RENDER AMPLIFICATION — memoised row + stable callbacks
const Row = memo(function Row({ row, onSelect }) { … },
                 (a, b) => a.row.updatedAt === b.row.updatedAt);
const onSelect = useCallback((id) => setSelected(id), []);

// 3. STOP RECOMPUTING ON EVERY KEYSTROKE
const deferredQuery = useDeferredValue(query);
const visible = useMemo(() => filterAndSort(rows, deferredQuery, sort),
                        [rows, deferredQuery, sort]);

// AND ASK: does the client need 3,000 rows at all?
// Server-side pagination + filtering removes the payload, the parse and the render.
@end
@senior
The order matters: virtualisation is the structural fix and gives the biggest win, memoisation only helps once the row count is bounded, and `useDeferredValue` addresses input responsiveness rather than raw render cost. But the question I would ask before any of them is whether the client should have 3,000 rows — server-side filtering and pagination removes the transfer, the JSON parse and the render together, and is usually both simpler and faster. Virtualisation is the right answer when the user genuinely needs to scroll a large local dataset.
@followup
The customer says they need to see all rows to search across them. Now what?
@answer
Move the search to the server so it operates on the full dataset and returns matches, with the client showing a virtualised result list — that satisfies the requirement without shipping everything. If offline access is genuinely needed, store the data in IndexedDB with indexes and query it in a worker, so the main thread never holds or scans the full set. Either way "see all rows" is a user goal, not a technical requirement, and the goal is usually satisfied by search rather than by rendering.
@red
- Reaching for `React.memo` before addressing the row count.
- Accepting "we need all the data on the client" without questioning it.

### Users report the page flashes wrong content then corrects itself. What is happening?
@short
Almost certainly a hydration mismatch: the server rendered one thing, the client's first render produced something different, and React replaced that subtree. The usual causes are a theme or locale read from `localStorage`, a timestamp formatted with the local timezone, or a value that differs between server and client.
@deep
React logs a hydration error in development and, in production, silently re-renders the mismatched subtree — which is exactly the visible flash. The most common instances are theme (server does not know the user's preference), dates (server and browser timezones differ), and any use of `Math.random()` or `Date.now()` during render.

Invalid HTML nesting is the sneakier cause: a `<div>` inside a `<p>` is silently corrected by the parser, so the DOM no longer matches what React produced.
@code tsx The cause and the correct fix, per case
// ❌ theme from localStorage → server renders light, client corrects to dark → FLASH
const theme = typeof window !== 'undefined' ? localStorage.getItem('theme') : 'light';

// ✅ store it in a COOKIE so the server knows and renders it correctly first time
const theme = (await cookies()).get('theme')?.value ?? 'light';
<html data-theme={theme}>

// ❌ timezone-dependent formatting during render
<span>{new Date(order.paidAt).toLocaleString()}</span>
// ✅ format on the server with an explicit timezone, or after mount
<span suppressHydrationWarning>{formatIn(order.paidAt, user.timezone)}</span>

// ❌ invalid nesting silently corrected by the browser
<p><div>…</div></p>
// ✅ valid markup — check the console; React 19 shows a diff

// Verify: React DevTools console warning names the mismatched element in dev.
@end
@senior
The cookie solution for theme is the pattern worth generalising: rather than suppressing the mismatch, make the server aware of the state so there is no mismatch. That eliminates both the flash and the hydration cost, and it works for locale, feature flags and anything else the server could know. `suppressHydrationWarning` is a genuine escape hatch for unavoidable cases like a live clock, but using it broadly hides real bugs — and the flash is the visible symptom of a subtree being thrown away and re-rendered, which is also a performance cost.
@followup
The mismatch only happens for some users. How do you find it?
@answer
It will correlate with something environmental — timezone, locale, a feature flag, an A/B bucket, or a browser extension injecting markup. I would capture the hydration error in production with the component stack via the error boundary or Sentry, and attach the user's timezone, locale and flag state to the report. Extensions are the frustrating case: a password manager injecting attributes into inputs causes mismatches you cannot fix, which is one legitimate use of `suppressHydrationWarning` on the affected element.
@red
- Adding `suppressHydrationWarning` globally.
- Not knowing that the flash is React discarding server HTML.

### Your bundle grew from 180KB to 620KB after a sprint. How do you find out why and fix it?
@short
Run the bundle analyser and compare against the previous build to see which modules appeared. The usual causes are a large dependency imported for one function, a whole icon set, a date or charting library pulled into a shared chunk, or a barrel file defeating tree-shaking.
@deep
The comparison matters more than the absolute view — you want the diff, not the total, because it names the change responsible. `source-map-explorer` or `rollup-plugin-visualizer` on both builds gives you that.

Barrel files are the subtle cause: importing from an `index.ts` that re-exports fifty modules can pull all of them in if the bundler cannot prove they are side-effect free.
@code js Finding it, fixing it, and preventing the next one
// 1. FIND IT
// npx source-map-explorer 'dist/assets/*.js' --json > after.json
// diff against the previous build's report → which modules are new?

// 2. COMMON CAUSES AND FIXES
// ❌ whole library for one function
import _ from 'lodash';                    // 70KB
import moment from 'moment';               // 65KB + locales
import * as Icons from 'react-icons/fa';   // the ENTIRE set
// ✅
import debounce from 'lodash-es/debounce'; // or write it — it is 8 lines
import { format } from 'date-fns';         // or Intl.DateTimeFormat — free
import { FaUser } from 'react-icons/fa';   // individual imports

// ❌ barrel file drags in everything
import { Button } from '@/components';     // index.ts re-exports 50 modules
// ✅ import from the module directly, and set "sideEffects": false in package.json

// ❌ a heavy library in a shared chunk
import { Chart } from 'recharts';          // used only on /analytics
// ✅ route-level split
const Analytics = lazy(() => import('./pages/Analytics'));

// 3. PREVENT IT — budget in CI, and a bundle-diff comment on every PR
// .size-limit.json: [{ "path": "dist/assets/index-*.js", "limit": "200 KB" }]
@end
@senior
The prevention step is the one that matters, because this will happen again otherwise: a size budget that fails the pull request, plus a bot comment showing the delta, means the cost is visible at the moment someone adds the dependency rather than discovered a sprint later. In my experience that single feedback loop changes behaviour more than any amount of guidance. And I would check whether the growth is actually in the initial bundle or in a lazily loaded chunk, because 620KB split across routes with 180KB initial is a completely different situation from 620KB on first load.
@followup
The large dependency is genuinely needed. What now?
@answer
Load it only where it is used — route-level or interaction-triggered dynamic import — so it does not affect initial load. If it is needed on the critical path, look for a lighter alternative, use a subset entry point if the library provides one, or check whether a browser API now covers it (`Intl` replaces most date and number formatting libraries entirely). If none of those work, I would raise the budget deliberately for that route with the reason recorded, which is a decision rather than a drift.
@red
- Looking at the total bundle rather than the diff.
- No CI budget, so the growth was invisible until someone noticed.

### The dashboard shows stale data after a user makes a change. Where do you look?
@short
Work outward through the caching layers: the query cache key, the client router cache, the CDN, and the server-side data cache. The most common cause is a mutation that invalidated one key while the list uses a different one, or a Next.js router cache serving a prefetched segment.
@deep
Cache-key drift is the usual culprit: one component uses `['orders', page]` and another `['orders', { page }]`, so invalidating one leaves the other stale. A key factory prevents it.

In the App Router the layered caches make this harder — a server-side `revalidateTag` does not clear the browser's router cache, so a client-side navigation can still show the old render.
@code ts The checklist, layer by layer
// 1. QUERY CACHE — are the keys identical? Use a factory, never inline keys.
qc.invalidateQueries({ queryKey: orderKeys.lists() });   // prefix-invalidates all list queries
// Debug: qc.getQueryCache().getAll().map(q => q.queryKey)  ← look for near-duplicates

// 2. MUTATION — did it invalidate everything derived?
onSuccess: (data, id) => {
  qc.setQueryData(orderKeys.detail(id), data);
  qc.invalidateQueries({ queryKey: orderKeys.lists() });     // lists
  qc.invalidateQueries({ queryKey: statsKeys.all });         // ← and the derived stats
}

// 3. NEXT.JS ROUTER CACHE — server revalidation does NOT clear the browser's copy
router.refresh();                       // after a mutation that changes server-rendered data

// 4. SERVER DATA CACHE — was the fetch tagged, and was that tag revalidated?
fetch(url, { next: { tags: [`orders:${userId}`] } });
revalidateTag(`orders:${userId}`);

// 5. CDN — is an authenticated response being cached publicly? (worse than stale:
//    it is a cross-user leak). Check Cache-Control and Vary.
@end
@senior
Checking step five is not optional even when the symptom is only staleness, because "user A sees old data" and "user A sees user B's data" have the same first symptom and very different severity. A `Cache-Control: public` on an authenticated response with a CDN in front is a data-exposure incident. Beyond that, the systematic fix for this class of bug is a query-key factory plus a rule that mutations invalidate by prefix rather than by exact key — most staleness bugs are someone forgetting one derived query, and prefix invalidation makes that structurally unlikely.
@followup
The data is correct on refresh but stale on navigation. Which layer is it?
@answer
The client router cache, almost certainly — a full refresh bypasses it while a client-side navigation serves the prefetched segment. `router.refresh()` after the mutation clears it, or reducing the prefetch staleness for that route. If a full refresh is also stale, the problem is server-side: the data cache, the CDN, or a replica lag issue where the read went to a replica that had not caught up.
@red
- Invalidating only the exact key that was mutated.
- Not checking whether an authenticated response is publicly cached.

### A user reports "I clicked save and nothing happened, then it saved twice." Diagnose.
@short
No pending state on the button plus a non-idempotent endpoint. The user clicked, saw no feedback, clicked again, and both requests succeeded. The fix is disabling the control while in flight and making the endpoint idempotent, because client-side prevention alone is not sufficient.
@deep
Client-side protection handles the common case: disable the button, show a spinner, and ignore submissions while a mutation is pending. But a double-submit can also come from a slow network causing a client retry, a page restored from the back-forward cache, or a user with a flaky trackpad producing a double click.

Server-side idempotency is the only complete answer, and for anything creating a record it needs a client-supplied key.
@code tsx Both halves — UI feedback and server idempotency
// CLIENT: disable while pending, and send a stable idempotency key per submission
const idemKey = useRef(crypto.randomUUID());
const { mutate, isPending } = useMutation({
  mutationFn: (body) => api.post('/orders', body, { headers: { 'Idempotency-Key': idemKey.current } }),
  onSuccess: () => { idemKey.current = crypto.randomUUID(); },   // new key for the NEXT submission
});

<button onClick={() => mutate(values)} disabled={isPending} aria-busy={isPending}>
  {isPending ? 'Saving…' : 'Save'}
</button>

// SERVER: the key makes a replay a no-op, whatever the client does
// INSERT INTO idempotency_keys (key, request_hash, status) VALUES ($1,$2,'in_progress')
//   ON CONFLICT (key) DO NOTHING RETURNING key
// 0 rows → return the stored response (or 409 if still in progress)
@end
@senior
Generating the idempotency key once per form submission rather than per request is the detail that makes this work: a key regenerated on each retry defeats the purpose, while a key that never rotates would make a legitimate second order impossible. The other point is that the missing pending state is a real bug in its own right — users who get no feedback assume failure, and that assumption drives the double submit. So the fix is genuinely both halves: the UI stops most of it, the server makes the rest harmless.
@followup
The endpoint is a PUT that is already idempotent. Why did it still duplicate?
@answer
Then the duplication is probably not from the two clicks but from something downstream — a side effect that is not idempotent, such as sending an email or publishing an event, running on each request even though the record update converged. The fix is to make the side effect conditional on an actual state change, or to route it through an outbox keyed on the transition rather than on the request. It is a good illustration that "idempotent" must cover observable effects, not only the database row.
@red
- Fixing only the client-side double-click.
- Assuming an idempotent write means idempotent side effects.

### The app works on desktop but is unusably slow on mid-range Android. What do you investigate?
@short
JavaScript execution time, because a mid-range Android device has roughly a quarter of the CPU performance of a developer laptop. Throttle to 4× CPU slowdown and Fast 3G in DevTools, record a performance trace, and look for long tasks — usually parsing and executing a large bundle, then hydration.
@deep
The costs that dominate on low-end mobile are script parse and execute, hydration, and main-thread contention from third-party scripts. Network is usually secondary once assets are compressed and cached.

The measurement to trust is field data segmented by device memory and connection type, because the aggregate p75 hides that a large share of users are on much slower hardware.
@code js Reproduce, measure, then fix the right thing
// REPRODUCE
// DevTools → Performance → CPU: 4× slowdown, Network: Fast 3G
// Or better: a real ₹12,000 Android device on the office wifi

// SEGMENT THE FIELD DATA — the aggregate hides the problem
onINP(m => beacon({ ...m, deviceMemory: navigator.deviceMemory,
                    hardwareConcurrency: navigator.hardwareConcurrency,
                    conn: navigator.connection?.effectiveType }));
// Then chart p75 for deviceMemory <= 4 separately. It is usually 2–3× worse.

// TYPICAL FIXES, IN ORDER OF IMPACT ON LOW-END DEVICES
// 1. ship less JavaScript — route splitting, remove heavy deps, server components
// 2. reduce hydration — Server Components / islands: don't hydrate static content
// 3. defer third-party scripts — they compete for the same single main thread
// 4. break long tasks — yield with scheduler.yield() or setTimeout between chunks
// 5. images: AVIF at the right size; a 2MB hero is worse on a slow connection
@end
@senior
The point I would make is that reducing JavaScript beats optimising JavaScript on these devices — hydration cost is proportional to how much of the tree is interactive, so moving static content to Server Components removes work rather than making it faster. I would also insist on testing on a real low-end device rather than only throttling, because throttling models CPU but not memory pressure, thermal throttling or a slower storage subsystem, and those are what produce the worst real-world experiences. Buying two cheap Android phones for the team is the highest-value performance investment I know.
@followup
Marketing insists on keeping three analytics scripts. How do you handle it?
@answer
Quantify the cost — remove them locally and measure the INP and LCP difference — so the conversation is about a number rather than a preference. Then offer mitigations before removal: load them with a lazy strategy after interaction, move them into a worker with Partytown so they do not occupy the main thread, or self-host to remove connection overhead. Usually one of those satisfies both sides. If not, the decision belongs to the business with the cost stated explicitly, and I would want it recorded.
@red
- Testing only on a developer laptop.
- Optimising React rendering when the problem is bundle execution.

### Your Next.js page suddenly serves one user's data to another. What went wrong?
@short
A response that should be private was cached — either a `fetch` with the user's credentials cached in the Data Cache, a route incorrectly treated as static, or a `Cache-Control: public` reaching a CDN. This is a data-exposure incident, so the first action is to stop serving the cached content.
@deep
The mechanism is that caches key on the URL and configured options, not on identity. If a per-user response is cached under a URL that other users request, they receive it.

The specific Next.js causes are: a `fetch` with an auth header and default caching, a page that should be dynamic being statically rendered because it never reads `cookies()` or `headers()`, and a route handler returning a personalised response without `no-store`.
@code ts Immediate mitigation, then the structural fix
// IMMEDIATE (in this order)
// 1. purge the CDN for the affected paths
// 2. deploy with no-store on the affected routes / redeploy to invalidate the Data Cache
// 3. assess: which users, what data, how long — this determines disclosure obligations

// ROOT CAUSES AND FIXES
// ❌ per-user fetch, cached by default (Next 14 and earlier)
const me = await fetch(`${API}/me`, { headers: { cookie } });
// ✅
const me = await fetch(`${API}/me`, { headers: { cookie }, cache: 'no-store' });

// ❌ a page that renders per-user data but never reads request data → treated as static
export default async function Page() { return <Profile user={await getUser()} />; }
// ✅ make the dynamic dependency explicit
export const dynamic = 'force-dynamic';
// or read cookies()/headers(), which marks it dynamic automatically

// ❌ route handler with a cacheable response
return NextResponse.json(data);
// ✅
return NextResponse.json(data, { headers: { 'Cache-Control': 'private, no-store' } });

// STRUCTURAL PREVENTION
// - a lint rule / wrapper: any fetch carrying a cookie or Authorization header
//   MUST set cache: 'no-store'
// - a CI test that asserts Cache-Control on every authenticated route
@end
@senior
The structural prevention is what I would push hardest, because this is a one-word mistake with catastrophic consequences and it will recur otherwise. A wrapper around `fetch` that refuses to cache any request carrying credentials makes the unsafe version impossible to write, and a CI test asserting `Cache-Control: private` on every authenticated route catches the response side. I would also treat this as a security incident with the full process — contain, preserve, assess scope from access logs, then notify as required — rather than as a caching bug, because that is what it is.
@followup
How do you determine how many users were affected?
@answer
From CDN and application access logs: which paths were served from cache, over what period, to how many distinct clients, and what the cached payload contained. The CDN's cache-hit logs are the authoritative source for edge-cached content. That analysis determines the disclosure obligation, which is why it must happen before you purge everything — purging is necessary for containment, but capture the log evidence first. If the logs cannot answer it, you must assume the worst case, which is the argument for having them.
@red
- Treating it as a caching bug rather than a security incident.
- Purging and redeploying before capturing the evidence of scope.

### The frontend works locally but fails in production with CORS errors. Walk through it.
@short
CORS errors are almost always a server configuration difference, not a client bug. Check the actual response headers on the preflight and the real request: is the production origin in the allow-list, is `credentials` handled correctly, and is the failing request actually a CORS failure or a 500 that the browser reports as CORS because the error response lacks the headers.
@deep
The most misleading case is the last one: if the server throws before the CORS middleware sets headers, the browser reports a CORS error even though the real problem is a 500. Checking the network tab for the actual status code resolves it immediately.

The second most common is a wildcard origin combined with credentials, which the specification forbids — it works without credentials in development and fails in production once cookies are involved.
@code bash Diagnose from the outside, not from the browser console
# 1. What does the preflight ACTUALLY return?
curl -i -X OPTIONS https://api.acme.com/v1/orders \
  -H "Origin: https://app.acme.com" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: content-type,authorization"

# Expect:
#   Access-Control-Allow-Origin: https://app.acme.com    ← the EXACT origin, not *
#   Access-Control-Allow-Credentials: true               ← if cookies are used
#   Access-Control-Allow-Headers: content-type,authorization
#   Access-Control-Max-Age: 86400

# 2. Is it really CORS, or a 500 with no CORS headers on the error path?
curl -i https://api.acme.com/v1/orders -H "Origin: https://app.acme.com"
#   → a 500 here means the error middleware runs BEFORE/INSTEAD OF cors()

# 3. Common causes
#   • production origin missing from the allow-list (staging worked, prod did not)
#   • Access-Control-Allow-Origin: * WITH credentials → forbidden by spec
#   • a proxy/CDN stripping or overwriting the headers
#   • a redirect (http → https, or trailing slash) — the preflight does not follow it
@end
@senior
Ordering the CORS middleware before the error handler is the fix people miss, and it produces the most confusing version of this problem — an intermittent "CORS error" that only appears when the endpoint fails, so it looks like a CORS configuration issue and is actually a 500. The redirect case is the other one: a preflight to `http://` that redirects to `https://` fails silently because preflights do not follow redirects. And I would state the security point: the fix is never to reflect the incoming origin with credentials enabled, because that allows every site to make authenticated requests as your users.
@followup
Why does it work in Postman but not the browser?
@answer
Because Postman is not a browser and does not enforce the same-origin policy — there is no `Origin` header and no preflight. That difference is the clearest demonstration that CORS is a browser-side protection for users, not an access control on your API: the endpoint is fully reachable by any non-browser client regardless of the headers. It is a useful thing to say in an interview because it shows you understand what CORS is for rather than treating it as an obstacle.
@red
- Setting `Access-Control-Allow-Origin: *` with credentials to make it work.
- Not checking the actual response status behind the CORS message.

### A memory leak in the SPA crashes long-lived browser tabs. How do you find it?
@short
Reproduce by navigating repeatedly between routes, take heap snapshots before and after, and compare — look for detached DOM nodes and component instances that grow linearly. The retainer path names the holder, which in a React app is usually an uncleaned listener, a timer, or a module-level cache.
@deep
Dashboards left open all day are where this hurts. The signature is a tab consuming gigabytes after hours of use, or becoming progressively slower as garbage collection works harder.

The method is deterministic: snapshot, perform the suspect interaction twenty times, force garbage collection, snapshot again, and use the comparison view sorted by delta.
@code js The reproduction and the four causes to check
// REPRODUCE
// DevTools → Memory → take snapshot 1
// navigate into and out of the suspect route ×20
// click the trash icon (force GC) → take snapshot 2
// Comparison view, sort by "# Delta". Look for:
//   Detached HTMLDivElement ×3,400   → DOM retained by JS
//   FiberNode ×12,000                → component instances retained
//   Closure ×8,200 retained by Timeout → an interval holding a closure

// THE FOUR CAUSES, AND THEIR FIXES
useEffect(() => { const id = setInterval(poll, 5000); return () => clearInterval(id); }, []);
useEffect(() => {
  const ac = new AbortController();
  window.addEventListener('resize', onResize, { signal: ac.signal });
  ws.addEventListener('message', onMsg, { signal: ac.signal });
  return () => ac.abort();                       // one teardown for everything
}, []);
// 3. module-level cache that only grows → bound it (LRU) or let the query cache own it
// 4. a third-party SDK that never cleans up → isolate it, or reinitialise on route change

// GUARD: track it in production
setInterval(() => {
  performance.memory && beacon({ heapMb: performance.memory.usedJSHeapSize / 1e6,
                                 route: location.pathname, uptimeMin: uptime() });
}, 60_000);
@end
@senior
The `AbortController` with `{ signal }` is the idiom I would recommend as the standard pattern, because it unifies teardown for listeners, fetches and any signal-aware API — one cleanup path instead of four, and it is much harder to forget one. On the production side, beaconing heap size with route and uptime is what lets you detect this from real usage rather than waiting for a support ticket, and the correlation with a specific route usually identifies the culprit before you take a single snapshot.
@followup
The leak is in a third-party charting library. What are your options?
@answer
Confirm it with a minimal reproduction, check the issue tracker for a known fix or a documented `destroy()` call you are not making, and if there is none, contain it: mount the widget in an iframe that is discarded on navigation, or reinitialise it in a way that releases the previous instance. Longer term I would weigh replacing the library, because a leak in a long-lived SPA is a recurring support cost. Reporting it upstream with the reproduction is worth doing regardless.
@red
- Concluding "React leaks memory" without a heap snapshot.
- Adding a page reload on navigation as the fix.

### Search-as-you-type shows results for a previous query. Why, and how do you fix it?
@short
A race: an earlier request resolved after a later one, so its results overwrote the newer ones. The fix is to cancel in-flight requests when a new one starts, or to discard responses that do not match the current query — and a query library does this for you by keying the cache on the query.
@deep
Debouncing reduces the frequency of requests but does not fix ordering: two requests in flight can still return out of order, and on a variable mobile network that is common.

The robust fixes are `AbortController` to cancel superseded requests, and keying the cache by the query so a stale response lands under its own key and is simply not the one being displayed.
@code tsx Three correct fixes, best last
// ❌ debounce alone — still races
useEffect(() => { const t = setTimeout(async () => setResults(await search(q)), 300);
                  return () => clearTimeout(t); }, [q]);

// ✅ 1. abort the previous request
useEffect(() => {
  const ac = new AbortController();
  const t = setTimeout(async () => {
    try { setResults(await search(q, { signal: ac.signal })); }
    catch (e) { if (e.name !== 'AbortError') setError(e); }
  }, 300);
  return () => { clearTimeout(t); ac.abort(); };
}, [q]);

// ✅ 2. ignore stale responses explicitly
const latest = useRef(0);
const id = ++latest.current;
const r = await search(q);
if (id === latest.current) setResults(r);      // discard if superseded

// ✅✅ 3. let the cache key handle it — no race is possible by construction
const deferred = useDeferredValue(q);
const { data } = useQuery({
  queryKey: ['search', deferred],
  queryFn: ({ signal }) => search(deferred, { signal }),   // library aborts superseded requests
  enabled: deferred.length >= 2,
  placeholderData: keepPreviousData,                        // no flicker between queries
});
@end
@senior
The third option is the one I would ship, because keying the cache on the query makes the race structurally impossible rather than handled — a late response for "lap" lands under the key for "lap" and simply is not what the component is reading. That is a better property than cancellation, which is a mitigation. The wider lesson is that most hand-rolled data fetching reimplements cancellation, deduplication and ordering badly, and this bug is one of the standard symptoms; the library exists precisely because these are easy to get subtly wrong.
@followup
The server is doing expensive work for requests the user has already abandoned. How do you stop that?
@answer
Propagate the cancellation server-side: `AbortController` on the client closes the connection, and the server should detect the disconnect (`req.on('close')` or the request's `AbortSignal`) and abort the downstream work — cancel the database query, abort the search request, stop the LLM generation. Without that, cancelling on the client only saves the client's rendering, while the backend continues doing work nobody will read, which under load is a significant waste and can be a denial-of-service vector against yourself.
@red
- Debouncing and assuming the race is fixed.
- Cancelling on the client but continuing the work server-side.

# SECTION Backend & Node Incidents | Latency, memory, crashes and the pool. Diagnose in order, mitigate first.

### The API p99 jumped from 200ms to 4s at 09:00 with no deploy. What do you do?
@short
Mitigate first if there is an obvious lever, but with no deploy to revert I would go straight to the trace: split the latency into database, outbound calls, event-loop lag and pool wait time. A 09:00 onset with no deploy usually means a traffic pattern change, a scheduled job, or a dependency degrading.
@deep
The 09:00 timing is the strongest clue: it is when users arrive, or when a cron job runs. A batch job saturating the database or the connection pool degrades every request without any code change.

The diagnostic order is mechanical: event-loop lag distinguishes "we are CPU-bound" from "we are waiting"; pool wait time distinguishes "the database is slow" from "we have no connections"; and a trace attributes the remainder.
@code text The triage sequence, with what each answer means
  1. WHAT CHANGED?  deploys (none) · feature flags · config · traffic volume ·
     scheduled jobs at 09:00 · dependency status pages · database maintenance window

  2. EVENT-LOOP LAG
     high  → CPU-bound in JS. Take a CPU profile. (Big JSON? sync crypto? regex?)
     low   → we are waiting on something. Continue.

  3. POOL WAIT TIME / active connections
     high  → pool exhaustion. WHY? one slow query holding connections, a leak,
             or a batch job consuming the pool. Check pg_stat_activity.
     low   → continue.

  4. TRACE BREAKDOWN (p99 traces specifically, not p50)
     one wide DB span     → plan regression? check auto_explain, ANALYZE staleness
     many small DB spans  → N+1 newly triggered by a data-shape change
     wide external span   → third party degraded → breaker + fallback
     unexplained gap      → GC, or waiting for the pool (back to 3)

  5. MITIGATE while diagnosing
     kill the batch job · raise the pool cap if the DB can take it ·
     shed low-priority traffic · scale out if the bottleneck is app CPU
@end
@code sql The two queries that resolve most of these in 60 seconds
-- Is one query suddenly dominating?
SELECT left(query,80), calls, round(mean_exec_time,1) avg_ms, round(total_exec_time) total_ms
  FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- Is something holding connections?
SELECT state, wait_event_type, count(*), max(now()-xact_start) AS oldest
  FROM pg_stat_activity GROUP BY 1,2 ORDER BY 3 DESC;
-- many 'idle in transaction' → a code path forgot to commit
-- many 'active' with a long oldest → one query is blocking everything
@end
@senior
The insight I would offer is that "no deploy" does not mean "nothing changed" — data volume crosses a threshold and a plan flips, a cron job starts overlapping with peak traffic, or a third party degrades. The p99-versus-p50 distinction is the other key move: if p50 is unchanged and only p99 moved, the cause is contention (pool waits, lock waits, GC) rather than a uniformly slower path, and that points you at a completely different set of checks. Mitigating before fully understanding — killing the batch job, shedding load — is correct here because users are affected now.
@followup
The trace shows most time in a database span but the database CPU is fine. What is it?
@answer
Lock waiting or connection-pool waiting rather than query execution. Check `pg_stat_activity` for `wait_event_type = 'Lock'` and find the blocker with `pg_blocking_pids` — a long-running transaction or a migration holding a lock will make every query on that table slow while the database looks idle. It could also be that the "database span" includes time waiting to acquire a pooled connection, in which case the fix is on your side: a leaked client, a slow query holding connections, or a pool too small for the concurrency.
@red
- Restarting instances without diagnosing.
- Looking only at averages rather than at the p99 trace.

### Node memory grows steadily and the container is OOM-killed every six hours.
@short
Confirm it is a leak rather than normal sawtooth by watching the post-GC heap floor, then take two heap snapshots under load and diff them. In Node the cause is nearly always an unbounded cache, listeners added per request, a timer holding a closure, or streams not destroyed on error.
@deep
The distinction between heap and RSS growth directs the search. Growing heap with growing object counts is a JavaScript retention problem. Growing RSS with a flat heap points at buffers or native memory — a file upload path, an image library, or many open sockets.

The OOM kill itself is silent because SIGKILL cannot be caught, which is why the first task is often just establishing that this is what is happening.
@code bash Establish, then find, then fix
# 1. CONFIRM it is the OOM killer (nothing in the app logs)
dmesg -T | grep -i 'killed process'
kubectl describe pod api-xxx | grep -i oomkilled
# ECS: check the task's stopped reason

# 2. MAKE IT CATCHABLE instead of silent — heap limit BELOW the container limit
node --max-old-space-size=1536 dist/index.js      # container limit 2Gi
# → now you get a JS heap out of memory error WITH A STACK instead of SIGKILL

# 3. INSTRUMENT so the shape is visible
setInterval(() => logger.info({
  rssMb: process.memoryUsage().rss/1e6,
  heapUsedMb: process.memoryUsage().heapUsed/1e6,
  externalMb: process.memoryUsage().external/1e6,   # Buffers live here
  handles: process._getActiveHandles().length,      # growing = socket/timer leak
}), 30_000).unref();

# 4. SNAPSHOT AND DIFF under load
kill -USR2 $(pgrep -f node)     # with v8.writeHeapSnapshot on SIGUSR2
# ...30 minutes...
kill -USR2 $(pgrep -f node)
# Chrome DevTools → Load both → Comparison → sort by # Delta
@end
@senior
Setting `--max-old-space-size` below the container limit is the first thing I would do, because it converts an undiagnosable silent kill into a JavaScript heap-out-of-memory error with a stack trace — which frequently identifies the culprit immediately. Tracking the active handle count is the other cheap signal: a steadily rising count means sockets, timers or streams are not being cleaned up, and it moves before memory becomes critical. As a temporary mitigation a rolling restart is acceptable, but I would be explicit that it is a stopgap and the snapshot diff is the actual work.
@followup
The heap looks flat but RSS keeps growing. What now?
@answer
That points outside the V8 heap: `Buffer` allocations, native module memory, or a large number of open handles. `process.memoryUsage().external` and `arrayBuffers` tell you if it is buffers — common in upload, image or compression paths where streams are not destroyed on error. Native modules like `sharp` have their own allocators and can leak independently of V8. And thousands of open sockets consume kernel and userspace memory that a heap snapshot will not show, which is why the handle count matters.
@red
- Concluding "memory leak" from RSS alone.
- Scheduled restarts as the permanent fix.

### Every request starts timing out. The database is healthy. What happened?
@short
Almost certainly connection-pool exhaustion. Every request is queued waiting for a connection while the database itself is idle. The cause is either a leaked client that is never released, one slow query holding connections, or a burst of parallel work exceeding the pool.
@deep
The signature is distinctive: application latency at the timeout value, database CPU low, and `pg_stat_activity` showing few active queries but the pool reporting zero idle connections.

The three causes have different fixes. A leak means a code path that does not release in `finally`. A slow query means a missing index or a lock wait. A burst means unbounded `Promise.all` fan-out or a batch job sharing the pool.
@code ts Detect, mitigate, and prevent recurrence
// DETECT — instrument the pool, or you are guessing
setInterval(() => logger.info({
  total: pool.totalCount, idle: pool.idleCount, waiting: pool.waitingCount,
}), 10_000).unref();
// waiting > 0 sustained = exhaustion

// MITIGATE NOW
// 1. find and kill the offender
//    SELECT pid, now()-xact_start age, state, left(query,80) FROM pg_stat_activity
//     WHERE state <> 'idle' ORDER BY age DESC;
//    SELECT pg_cancel_backend(pid);
// 2. restart instances to release leaked clients (blunt, but it works)

// PREVENT — the three fixes
// a) ALWAYS release. A helper makes it impossible to forget.
export async function withClient<T>(fn: (c: PoolClient) => Promise<T>) {
  const c = await pool.connect();
  try { return await fn(c); } finally { c.release(); }     // ← the missing finally
}

// b) BOUND the concurrency of fan-out work
const limit = pLimit(10);
await Promise.all(ids.map(id => limit(() => repo.get(id))));   // not 5,000 at once

// c) FAIL FAST rather than queue, and cap query time
new Pool({ connectionTimeoutMillis: 5_000, statement_timeout: 10_000 });
// separate pool (or PgBouncer) for batch jobs so they cannot starve the API
@end
@senior
Failing fast on connection acquisition rather than queueing indefinitely is the change that turns this from a total outage into a degradation: requests return 503 quickly, health checks stay meaningful, and the system recovers on its own when the offending query completes. Without it, everything queues, health checks time out, the orchestrator restarts instances, and the reconnection storm makes it worse. The separate pool for batch work is the other structural fix — a nightly job should not be able to starve the API of connections, and that is a bulkhead applied to the database.
@followup
How do you find the code path that leaks connections?
@answer
Set `application_name` per code path on checkout so `pg_stat_activity` shows which part of the application holds each connection, and log a stack trace when a client is held beyond a threshold — most pool libraries support a hook for that. The pattern is almost always an early return or a thrown error between `connect()` and `release()` without a `finally`, so a code search for `pool.connect()` not inside the helper usually finds it in minutes.
@red
- Increasing the pool size as the fix without finding the cause.
- No connection timeout, so requests queue instead of failing.

### A background job queue has 200,000 pending jobs and is falling behind. What now?
@short
Establish whether it is a throughput problem or a stuck-job problem: look at oldest job age, failure rate and per-job duration. Then mitigate by scaling workers if the downstream can take it, shedding or deferring low-priority job types, and fixing whatever is causing retries.
@deep
Queue depth alone is misleading. A deep queue draining quickly is fine; a shallow queue where the oldest job is two hours old means something is stuck. Oldest-job age is the metric that maps to user impact.

Common causes of falling behind: a downstream dependency slowed so each job takes longer, a poison job failing and retrying forever, worker concurrency capped by a database pool, or a burst of enqueues from a backfill.
@code ts Diagnose by job type, then act
// 1. WHERE is the backlog? Aggregate by job type and age.
const stats = await Promise.all(TYPES.map(async t => ({
  type: t,
  waiting: await queue.getWaitingCount(t),
  active: await queue.getActiveCount(t),
  failed: await queue.getFailedCount(t),
  oldestMs: Date.now() - (await queue.getOldestWaiting(t))?.timestamp,
})));
// One type dominating → that handler or its dependency is the problem.
// Failed count climbing → retries are consuming capacity. Find the poison job.

// 2. MITIGATE
// a) scale workers — ONLY if the bottleneck is worker CPU, not the database
//    (more workers against an exhausted DB pool makes it worse)
await worker.setConcurrency(30);
// b) pause low-priority types so critical work drains
await queue.pause('analytics-rollup');
// c) quarantine the poison job — do not let it retry forever
if (job.attemptsMade > 3 && isPermanent(err)) throw new UnrecoverableError(err.message);

// 3. PREVENT
//   • separate queues per priority; workers weighted, never FIFO across everything
//   • alert on OLDEST JOB AGE, not just depth
//   • bound enqueue rate from backfills (they are the usual cause of a sudden spike)
//   • classify errors: permanent → DLQ immediately, transient → backoff
@end
@senior
Alerting on oldest-job age rather than depth is the change I would make permanently, because depth without age is not actionable — 200,000 jobs draining in ten minutes is healthy, and 200 jobs where the oldest is three hours old is an incident. The other point is that scaling workers is the reflex and is often wrong: if the constraint is the database connection pool or a rate-limited third party, more workers increases contention and makes throughput worse. Establishing where the time goes per job before scaling is what prevents that mistake.
@followup
Users are complaining that emails from two hours ago have not arrived. How do you prioritise?
@answer
Separate the queues by user impact and drain the user-facing one first — password resets and order confirmations before analytics rollups and report generation. If they share a queue, that is the structural fix to make afterwards. For the immediate backlog, I would also consider whether some of it is now worthless: a two-hour-old "your order is being prepared" notification may be better dropped than delivered late, and deciding that with product rather than silently delivering stale notifications is the right call.
@red
- Scaling workers without knowing the bottleneck.
- Alerting on queue depth alone.

### A single endpoint is pinning one CPU core at 100%. Find it.
@short
Capture a CPU profile from the running process and read the flame graph for the widest frame. In Node the usual culprits are a large synchronous `JSON.parse` or `stringify`, synchronous crypto, catastrophic regex backtracking, or an accidental quadratic loop over a larger-than-expected dataset.
@deep
The profile is decisive and takes two minutes, which is why guessing is never justified. `--cpu-prof`, the inspector via SIGUSR1, or a continuous profiler all produce the same flame graph.

Regex backtracking deserves special attention because it is both a performance bug and a denial-of-service vulnerability: a crafted input against a pattern with nested quantifiers can take exponential time.
@code js Capture the profile, then the four things to look for
// CAPTURE (no restart needed)
// start with: node --inspect=127.0.0.1:9229 dist/index.js   ← localhost ONLY
kill -USR1 <pid>      // opens the inspector; port-forward, attach DevTools, record 30s

// Or programmatically, bounded and safe to leave in:
const s = new inspector.Session(); s.connect();
await s.post('Profiler.enable'); await s.post('Profiler.start');
await sleep(15_000);
const { profile } = await s.post('Profiler.stop');
fs.writeFileSync(`/tmp/cpu-${Date.now()}.cpuprofile`, JSON.stringify(profile));

// WHAT THE WIDE FRAME USUALLY IS
// 1. JSON.parse / stringify on a large payload  → stream it, or bound the size
// 2. sync crypto (bcrypt.hashSync, pbkdf2Sync)  → async variants; move off the path
// 3. RegExp with nested quantifiers             → ReDoS. Rewrite linear + bound input.
const bad  = /^(\s*\w+\s*)+$/;          // exponential on crafted input
const good = /^\w+(?:\s+\w+)*$/;
if (input.length > 256) throw new BadRequest('TOO_LONG');
// 4. an accidental O(n²): .find() inside .map() over a list that grew
const byId = new Map(users.map(u => [u.id, u]));   // O(n+m) instead of O(n×m)
@end
@senior
If the wide frame is a regex, this is a security incident as well as a performance one, because it means a single crafted request can consume a core — and an attacker who discovers it can take the service down cheaply. So the mitigation is both bounding the input length and rewriting the pattern, plus checking whether the pattern came from a dependency. More generally, the correct fix for genuinely CPU-heavy work is relocation rather than optimisation: a worker pool if it must return in the request, a queue if it need not.
@followup
The wide frame is inside a dependency you cannot change. Options?
@answer
Bound what reaches it — input size limits, a timeout, and a concurrency cap so it cannot occupy every core — and move the call into a worker thread so the main event loop stays responsive. If it is on a hot path and there is a lighter alternative, replacing the dependency is worth the effort. Reporting the issue upstream with a reproduction is also worthwhile, but the mitigation cannot wait for that.
@red
- Guessing at the cause instead of profiling.
- Exposing the inspector on a public interface.

### After scaling from one instance to four, users are randomly logged out. Why?
@short
Session state is in process memory, so a request routed to a different instance does not find the session. The same class of bug affects rate limiters, in-memory caches, WebSocket registries and scheduled jobs. The fix is to move all shared state to Redis or to make it stateless.
@deep
This is the canonical failure when scaling horizontally, and it is worth being able to enumerate the whole list rather than fixing only the symptom you noticed.

Sticky sessions appear to fix it and are a trap: they mask the underlying statefulness, break during deploys as instances drain, and prevent even load distribution.
@code ts Everything that breaks when instance count goes from 1 to N
// 1. SESSIONS — in memory → Redis (or a signed JWT)
app.use(session({ store: new RedisStore({ client: redis }), secret: env.SESSION_SECRET,
                  cookie: { httpOnly: true, secure: true, sameSite: 'lax' } }));

// 2. RATE LIMITING — per-instance counters mean N× the intended limit
rateLimit({ store: new RedisStore({ sendCommand: (...a) => redis.call(...a) }) });

// 3. CACHES — N inconsistent copies with N different expiry times
//    → shared Redis, or a short-TTL local cache + pub/sub invalidation

// 4. WEBSOCKETS — a message published on instance 1 never reaches instance 3
//    → Redis pub/sub fan-out; presence via TTL keys

// 5. SCHEDULED JOBS — cron now runs 4×
//    → DB-backed scheduler with FOR UPDATE SKIP LOCKED, or a distributed lock

// 6. IN-PROGRESS UPLOADS / temp files on local disk → S3

// 7. IDEMPOTENCY / dedup keys held in memory → Redis or Postgres

// ⚠️ Sticky sessions "fix" #1 but hide 2–7 and break on every deploy.
@end
@senior
The valuable part of this answer is the enumeration, because a team that fixes only sessions will hit the other six over the following weeks, each presenting as a separate mysterious bug. I would run through that list as a checklist before any horizontal scaling. And I would argue against sticky sessions explicitly: they make the system appear to work while leaving it stateful, which means deploys disconnect users, load distribution is uneven, and the real fix is deferred indefinitely. The exception is WebSockets, where connection-level affinity is legitimate.
@followup
Cron now runs four times. What is the cleanest fix?
@answer
A database-backed scheduler where workers claim due jobs with `SELECT ... FOR UPDATE SKIP LOCKED`, so exactly one instance runs each occurrence and a crashed worker's claim is reclaimed after a timeout. Idempotency should key on the scheduled occurrence — "the 09:00 run on this date" — so a retry after a crash does not execute twice. A distributed lock in Redis also works but is weaker, and dedicating one instance as the scheduler reintroduces a single point of failure.
@red
- Sticky sessions as the fix.
- Fixing sessions and not auditing the other shared state.

### An external API you depend on starts taking 30 seconds instead of 200ms. What happens to your service, and what should?
@short
Without protection, your service degrades or fails entirely: every request calling that dependency holds a connection and a worker for 30 seconds, the pool and the event loop fill, and unrelated endpoints start timing out. With protection, the calls fail fast, a breaker opens, and a fallback or a clear error is returned.
@deep
A slow dependency is more dangerous than a dead one precisely because it consumes your resources while you wait. The controls are a timeout shorter than your own caller's timeout, a concurrency cap so the dependency cannot occupy your whole pool, and a circuit breaker so you stop calling once it is clearly failing.

The fallback is a product decision made in advance: cached data, a degraded feature, or an honest error.
@code ts What should happen, in code
const breaker = new CircuitBreaker(
  (id: string) => http.get(`${VENDOR}/enrich/${id}`, { timeout: 800, agent: keepAliveAgent }),
  { timeout: 800,                       // ← shorter than OUR caller's budget
    errorThresholdPercentage: 50,
    volumeThreshold: 20,
    resetTimeout: 15_000 });

breaker.fallback(async (id) =>
  (await redis.get(`enrich:${id}`).then(v => v && JSON.parse(v))) ?? DEFAULT_ENRICHMENT);

const limit = pLimit(20);               // bulkhead: cap concurrent calls to this dependency
const data = await limit(() => breaker.fire(id));

breaker.on('open', () => {
  metrics.increment('breaker.open', { dep: 'enrich' });
  logger.warn('enrich breaker OPEN — serving cached/default');
});

// IMMEDIATE MITIGATION IF THIS IS HAPPENING NOW AND THERE IS NO BREAKER:
//   feature-flag the integration off → the feature degrades, the service survives
@end
@senior
Having a feature flag that disables a third-party integration entirely is the mitigation I would want available before the incident, because it works in seconds and requires no deploy. That is the practical version of designing for failure. The other point is timeout budgeting across the chain: if the client times out at 5 seconds and this call has a 30-second timeout, the work continues after nobody is waiting — so timeouts must decrease as you go deeper, and each layer should pass a deadline rather than starting a fresh budget.
@followup
The dependency is on the critical path and there is no meaningful fallback. Now what?
@answer
Then the honest options are to fail fast with a clear message so users are not left waiting, to queue the operation and complete it asynchronously if the product allows, or to accept the degradation while communicating it — a status banner is better than an unexplained failure. What I would avoid is retrying aggressively into an already-struggling dependency, which makes their recovery slower and can turn a partial outage into a total one. Afterwards, the design question is whether a genuinely critical path should have a single vendor with no alternative.
@red
- No timeout on outbound calls.
- Retrying hard into a degraded dependency.

### Requests are being duplicated in your database after a network blip. Explain and fix.
@short
Clients retried requests whose responses were lost, and the endpoint was not idempotent, so each retry created a new record. The fix is a client-supplied idempotency key recorded in the same transaction as the effect, plus a unique constraint so a duplicate is impossible even if the logic is bypassed.
@deep
This is inherent to networks: the client cannot distinguish "the server never received it" from "the server processed it and the response was lost", so it must retry, and the server must make retries safe.

The layered defence is: idempotency key at the API, provider idempotency key for external calls, and a database constraint as the backstop.
@code sql Clean up, then make it structurally impossible
-- 1. FIND the duplicates
SELECT user_id, created_at::date, count(*), array_agg(id)
  FROM orders
 WHERE created_at > now() - interval '2 days'
 GROUP BY user_id, created_at::date, total_minor, payment_intent
HAVING count(*) > 1;

-- 2. CLEAN UP carefully — keep the one with downstream effects (payment, shipment)
--    Never a blind DELETE. Review, then a reversible correction script.

-- 3. PREVENT — a constraint the application cannot bypass
ALTER TABLE orders ADD CONSTRAINT orders_intent_unique UNIQUE (payment_intent);
CREATE UNIQUE INDEX one_open_cart ON orders (user_id) WHERE status = 'pending';

CREATE TABLE idempotency_keys (
  key text PRIMARY KEY, request_hash text NOT NULL, status text NOT NULL,
  response_code int, response_body jsonb, created_at timestamptz DEFAULT now());
@end
@code ts And the API-level handling
const key = req.header('Idempotency-Key');
if (!key) return res.status(400).json({ error: 'IDEMPOTENCY_KEY_REQUIRED' });

const result = await withTransaction(async (tx) => {
  const claimed = await tx.query(
    `INSERT INTO idempotency_keys (key, request_hash, status)
     VALUES ($1,$2,'in_progress') ON CONFLICT (key) DO NOTHING RETURNING key`,
    [key, sha256(JSON.stringify(req.body))]);

  if (!claimed.rowCount) {
    const prior = await tx.query('SELECT * FROM idempotency_keys WHERE key=$1', [key]);
    if (prior.rows[0].request_hash !== sha256(JSON.stringify(req.body)))
      throw new Conflict('KEY_REUSED_WITH_DIFFERENT_BODY');
    if (prior.rows[0].status === 'in_progress') throw new Conflict('IN_PROGRESS');
    return { code: prior.rows[0].response_code, body: prior.rows[0].response_body };
  }
  const order = await createOrder(req.body, tx);
  await tx.query(`UPDATE idempotency_keys SET status='completed', response_code=201,
                  response_body=$2 WHERE key=$1`, [key, order]);
  return { code: 201, body: order };
});
@end
@senior
The unique constraint is what I would add first, because it makes the failure impossible rather than merely handled — a race that slips past the application logic becomes a caught constraint violation instead of corrupt data. The idempotency-key table is the mechanism that lets the client get the right answer on retry rather than an error. And the cleanup step deserves care: deleting duplicates blindly can remove the row that has a payment or a shipment attached, so it needs review and a reversible script, not a one-line DELETE run in a hurry.
@followup
The client is a mobile app that cannot be updated quickly. How do you fix this server-side only?
@answer
Derive a deduplication key server-side from the request's natural identity — user, amount, and a short time window, or a business key like the cart id — and reject or return the existing record for a repeat within that window. It is less precise than a client key and can theoretically block a legitimate rapid duplicate, so the window must be short and chosen with product input. Meanwhile the database constraint prevents the worst outcome regardless, and I would ship the client-side key in the next release.
@red
- Deleting duplicates without adding a constraint.
- Assuming clients will not retry.

### A deploy went out and error rates tripled. Walk me through the next ten minutes.
@short
Roll back first, then diagnose. With a recent deploy as the obvious correlate, reverting restores service in a minute or two, and understanding can happen with the system healthy. Then reproduce from the error signatures and the diff.
@deep
The instinct to understand before acting is wrong when there is an obvious, fast, safe mitigation. Every minute spent diagnosing is a minute of user impact that a rollback would have ended.

After recovery, the investigation is straightforward: the new error signatures in the tracker, the diff, and whether the deploy included a migration that constrains the rollback.
@code text The first ten minutes, in order
  T+0   ALERT: 5xx rate 0.3% → 1.1%, p99 400ms → 2.4s. Deploy 4 minutes ago.
  T+1   DECLARE. One commander. Incident channel. Post in #status.
  T+2   CAN WE ROLL BACK?
          • did the deploy include a migration? → additive only? then YES, roll back code
          • destructive migration? → cannot roll back cleanly → fix forward, carefully
  T+3   ./deploy.sh --rollback prod            (previous image tag, ~90s)
  T+5   VERIFY: error rate and p99 returning to baseline. Confirm in the dashboard,
          not by assumption.
  T+6   COMMUNICATE: "mitigated by rollback, investigating cause".
  T+8   DIAGNOSE with the system healthy:
          • new error signatures in Sentry, grouped, with the release tag
          • the diff: what changed? config? flags? a dependency bump?
          • reproduce in staging with the same input
  T+30  Fix, add a regression test, redeploy behind a flag, ramp gradually.
  LATER Post-mortem: why did CI not catch it? why did canary metrics not stop it?
@end
@senior
The "can we roll back" question at T+2 is the one that determines everything, and its answer is decided long before the incident by whether migrations are additive and whether the previous image is still available. Teams that cannot answer it quickly end up fixing forward under pressure, which is how a five-minute incident becomes an hour. I would also emphasise verifying recovery rather than assuming it — a rollback that did not take effect because a canary task remained on the old revision is a real and confusing scenario, and the dashboard is the arbiter.
@followup
The deploy included a migration. How does that change the plan?
@answer
It depends on the migration's nature. If it was additive — a new nullable column, a new index — the old code is unaffected and rolling back the code is safe. If it was destructive or constraining, rolling back the code may break against the new schema, so you fix forward with a targeted patch or disable the feature with a flag. That asymmetry is exactly why destructive migrations are deferred to a later release than the code that stops using the old structure; it preserves the ability to roll back, which is the most valuable property you have during an incident.
@red
- Diagnosing before mitigating when a rollback is available.
- Not knowing whether the deploy included a migration.

### Your service passes health checks but users report errors. How is that possible?
@short
The health check is too shallow — it returns 200 as long as the process is running, without verifying that the dependencies the service actually needs are working. The fix is a readiness check that reflects the ability to serve, kept distinct from a liveness check that only says the process is alive.
@deep
The opposite failure is also common: a readiness check that verifies every dependency will fail across the whole fleet when one shared dependency blips, turning a partial degradation into a total outage.

The right design distinguishes critical dependencies (without which you cannot serve) from optional ones (which degrade a feature), and reports both.
@code ts Health checks that reflect reality without causing correlated failure
// LIVENESS — is the process wedged? Failing this means RESTART me.
app.get('/healthz', (_req, res) => res.status(200).json({ ok: true }));

// READINESS — should I receive traffic? Failing this means ROUTE AWAY.
app.get('/readyz', async (_req, res) => {
  const [db, cache, queue] = await Promise.allSettled([
    withTimeout(pool.query('SELECT 1'), 1000),
    withTimeout(redis.ping(), 500),
    withTimeout(queueClient.ping(), 500),
  ]);

  const critical = db.status === 'fulfilled';          // cannot serve without the DB
  const degraded = cache.status !== 'fulfilled' || queue.status !== 'fulfilled';

  if (shuttingDown || !critical)
    return res.status(503).json({ db: critical, cache: !degraded, shuttingDown });

  res.status(200).json({ db: true, cache: cache.status === 'fulfilled',
                         queue: queue.status === 'fulfilled', degraded });
});

// ⚠️ Do NOT make readiness depend on every dependency — a Redis blip would then
// remove 100% of the fleet from the load balancer and turn degradation into an outage.
@end
@senior
The correlated-failure warning is the senior point here: a "thorough" readiness check that verifies six dependencies means any one of them failing takes the entire fleet out of rotation simultaneously, which is strictly worse than serving degraded. So the check should depend only on what is genuinely required to serve *some* traffic, with optional dependencies reported but not fatal. I would also add a deeper synthetic check — an actual request through the critical path, run externally on a schedule — because that catches the case where every component is individually healthy and the composition is broken.
@followup
What would have caught this before users did?
@answer
A synthetic monitor exercising the real user journey — log in, load the dashboard, create a test order — from outside the infrastructure, on a schedule. Component health checks verify parts; synthetic checks verify the whole. Combined with alerting on the business metric (orders per minute dropping) rather than only on technical metrics, that closes the gap where everything looks healthy and nothing works. The business metric is often the fastest signal of all.
@red
- One endpoint used for both liveness and readiness.
- Readiness depending on every dependency.

### Logs show a spike in 401s from one customer's integration. What do you check?
@short
Distinguish an expired token from a revoked one from a misconfigured client. Check whether the 401s are `TOKEN_EXPIRED` (their refresh flow is broken), `TOKEN_INVALID` (wrong credential or wrong environment), or a rate-limit-adjacent rejection — the error code tells you which conversation to have.
@deep
This is why distinct error codes matter: a single generic 401 makes it impossible to tell whether the client should refresh, re-authenticate or fix its configuration.

The common causes are a client that never implemented refresh and is using an expired token until it fails, a key rotated on your side without notice, a sandbox credential in production, and clock skew on the client causing premature expiry rejection.
@code ts What to look for, and what to make visible
// 1. SEGMENT the 401s by reason code and client
SELECT error_code, client_id, count(*), min(at), max(at)
  FROM api_errors
 WHERE status = 401 AND at > now() - interval '2 hours'
 GROUP BY 1,2 ORDER BY 3 DESC;

// error_code tells you the conversation:
//   TOKEN_EXPIRED        → their refresh flow is broken or not implemented
//   TOKEN_INVALID        → wrong key, wrong environment, or we rotated
//   TOKEN_REVOKED        → we revoked it — was that intentional?
//   SIGNATURE_INVALID    → webhook secret mismatch (did they rotate?)
//   CLOCK_SKEW           → their server's clock is wrong; we allow ±5s tolerance

// 2. CHECK OUR SIDE FIRST before contacting them
//    - did we rotate a signing key or a secret recently?
//    - did a deploy change token validation (issuer, audience, algorithm)?
//    - is the clock tolerance too tight?
jwt.verify(token, key, { algorithms: ['RS256'], issuer: ISS, audience: AUD, clockTolerance: 5 });

// 3. MAKE IT SELF-SERVICE so this is not a support ticket next time
//    - a per-client dashboard showing recent auth failures with the reason
//    - last-used timestamp per API key, so rotation is verifiable
@end
@senior
Checking our own side first is the discipline, because the most common cause of a sudden spike from one integration is a change we made — a key rotation, a validation change, a tightened clock tolerance — and contacting the customer to tell them their integration is broken is embarrassing when it was our deploy. The self-service dashboard is the durable fix: showing customers their own recent auth failures with reasons converts a support round trip into something they resolve in a minute, and it also gives you the data to spot a systemic problem across clients.
@followup
It turns out you rotated a signing key without notice. How do you handle it?
@answer
Restore service first by accepting both the old and new keys during an overlap window — a JWKS with both keys, or accepting either secret — then notify affected customers with the timeline and the new rotation schedule. Afterwards, fix the process: rotation should always have an overlap period, customers should be notified in advance, and the change should be visible in a changelog. Key rotation without overlap is a self-inflicted outage for every integration, and it is entirely avoidable.
@red
- Blaming the customer before checking your own changes.
- Generic 401s with no reason code.

# SECTION Database Incidents | Where the API outage usually actually is.

### A query that ran in 20ms yesterday takes 5 seconds today. Nothing changed in the code.
@short
The plan changed. Data volume or distribution crossed a threshold, statistics went stale, or an index became less useful. Run `EXPLAIN (ANALYZE, BUFFERS)`, compare estimated to actual rows, and `ANALYZE` the table before doing anything more elaborate.
@deep
The most common cause is stale or insufficient statistics: the planner's estimate diverges from reality, so it picks a nested loop over what it thinks is a handful of rows and is actually two hundred thousand.

The second cause is correlated columns, where the planner multiplies independent selectivities and underestimates by orders of magnitude. Extended statistics fix that without an index change.
@code sql The sequence, and what each result means
-- 1. What plan is it using NOW, with real numbers?
EXPLAIN (ANALYZE, BUFFERS) SELECT …;
-- estimated rows=421  actual rows=184213   ← 400× off. The plan choice was rational
--                                             given wrong information.

-- 2. Cheapest fix first: refresh statistics
ANALYZE orders;
-- did the plan change? Often that alone resolves it.

-- 3. Still wrong? The columns are probably correlated.
CREATE STATISTICS orders_status_created (dependencies, ndistinct, mcv)
  ON status, created_at FROM orders;
ANALYZE orders;

-- 4. Skewed column? Raise the sample size.
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;

-- 5. Only then consider an index, chosen to serve the predicate AND the sort
CREATE INDEX CONCURRENTLY ON orders (user_id, status, created_at DESC);

-- 6. Also check: has the table bloated? Bloat makes scans read more pages.
SELECT n_live_tup, n_dead_tup, last_autovacuum FROM pg_stat_user_tables WHERE relname='orders';
@end
@senior
Checking bloat at step six catches a case people miss: a table with 60% dead tuples requires reading far more pages for the same rows, so a query degrades with no plan change at all. The cause is usually autovacuum falling behind on a high-churn table, or a long-running transaction preventing cleanup. The broader point is to fix the planner's information rather than force its decision — `enable_seqscan = off` proves the index plan is better but is a diagnostic, not a fix, because the right plan changes as the data changes.
@followup
`ANALYZE` fixed it, but it will come back. How do you prevent recurrence?
@answer
Tune autovacuum for that table specifically — the default `autovacuum_analyze_scale_factor` of 10% means a large table waits far too long between analyses, so lowering it to 1–2% keeps statistics fresh. If the underlying issue is correlated columns, the extended statistics object is the durable fix. And I would add `auto_explain` so the next occurrence captures the plan automatically, rather than needing to be reproduced.
@red
- Adding an index before checking statistics.
- Forcing a plan with `enable_*` settings.

### The database CPU is at 95% and everything is slow. What do you do in the first five minutes?
@short
Identify what is consuming it — `pg_stat_statements` ranked by total time, and `pg_stat_activity` for currently running queries — then mitigate by killing the offender, throttling the source, or shedding load. Do not restart the database.
@deep
The usual causes are a new expensive query (a report, a backfill, a missing index after a data growth threshold), a plan regression, a lock storm causing retries, or simply more traffic than capacity.

Killing a runaway query is safe and immediate; restarting the database is not, because recovery replays WAL and can take far longer than the incident.
@code sql The five-minute triage
-- 1. What is running RIGHT NOW, and for how long?
SELECT pid, now()-query_start AS runtime, state, wait_event_type, wait_event,
       left(query, 100)
  FROM pg_stat_activity
 WHERE state <> 'idle' ORDER BY runtime DESC LIMIT 20;

-- 2. Kill the runaway (gentle first)
SELECT pg_cancel_backend(12345);          -- cancel the query
SELECT pg_terminate_backend(12345);       -- if cancel does not work

-- 3. What is expensive in AGGREGATE (may be many cheap queries, not one big one)
SELECT left(query,80), calls, round(total_exec_time) total_ms, round(mean_exec_time,1) avg
  FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;
-- 10,000 calls × 40ms is worse than 1 call × 30s, and needs a different fix

-- 4. Lock storm? (high CPU can be retry churn)
SELECT count(*) FROM pg_stat_activity WHERE wait_event_type = 'Lock';

-- 5. MITIGATE while fixing
--    • pause the batch job / reporting workload
--    • shed low-priority API traffic
--    • route read-only traffic to a replica
--    • statement_timeout to stop anything running away again
@end
@senior
Distinguishing one expensive query from ten thousand cheap ones is the diagnostic that determines the fix — the first needs an index or a rewrite, the second needs caching or a batch. Both look identical on a CPU graph. I would also set a `statement_timeout` immediately if there is not one, because it prevents recurrence during the incident itself. And restarting the database is the thing not to do: it does not fix the cause, it drops every connection, and crash recovery can take longer than the original problem.
@followup
The expensive query is a customer-facing report that they genuinely need. What now?
@answer
Move it off the transactional path: run it against a read replica, precompute it into a rollup refreshed on a schedule, or make it asynchronous with a job and a download link. In the immediate term, a per-tenant concurrency limit stops one customer's report from consuming the whole database. The general principle is that analytical queries and transactional traffic should not compete for the same resources, and this incident is the evidence for making that change.
@red
- Restarting the database.
- Ranking queries by mean time rather than total time.

### A migration is running and the whole application is down. What happened?
@short
The migration is holding — or waiting for — an `ACCESS EXCLUSIVE` lock. If it is waiting behind a long-running query, every subsequent query on that table queues behind the pending lock request, so the table becomes unavailable even before the migration runs. Cancel it immediately.
@deep
This is one of the fastest ways to take an application down, and it is entirely preventable with `lock_timeout`.

The lock queue is the surprising part: a pending exclusive request blocks new shared locks, so readers that would otherwise be fine start queueing. That is why a "harmless" `ALTER TABLE` can take out reads.
@code sql Immediate mitigation, then prevention
-- 1. FIND the migration and what it is waiting for
SELECT a.pid, now()-a.query_start AS waiting_for, left(a.query,80) AS migration,
       pg_blocking_pids(a.pid) AS blocked_by
  FROM pg_stat_activity a
 WHERE a.wait_event_type = 'Lock' ORDER BY waiting_for DESC;

-- 2. CANCEL IT. Recovery is immediate once the lock queue clears.
SELECT pg_cancel_backend(<migration_pid>);

-- 3. If a long report is the blocker and the migration must run, cancel that too.

-- 4. PREVENT — every migration, always
SET lock_timeout = '3s';
SET statement_timeout = '10min';

-- 5. Use the non-blocking forms
ALTER TABLE orders ADD COLUMN region text;                    -- instant (nullable)
CREATE INDEX CONCURRENTLY idx_x ON orders (region);           -- no write lock
ALTER TABLE orders ADD CONSTRAINT c CHECK (region IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT c;                      -- validates without a write lock

-- 6. Rehearse on a restored production-size snapshot. Record the timing in the PR.
@end
@senior
`SET lock_timeout` before every migration is the single control that converts this incident into a non-event: the migration fails after three seconds, nobody notices, and you retry during a quieter window. I would put it in the migration runner so it cannot be forgotten, and add a lint rule rejecting the dangerous statement forms. The rehearsal against production-sized data is the other half — a statement that takes twelve milliseconds on development data is not evidence about fifty million rows, and treating it as evidence is what leads here.
@followup
The migration is half-applied and you cancelled it. What state are you in?
@answer
In Postgres, DDL is transactional, so a cancelled `ALTER TABLE` rolls back completely and leaves no partial state — that is a real advantage over MySQL, where DDL is not transactional and a cancelled migration can leave the schema half-changed. What can be left behind is an invalid index from a failed `CREATE INDEX CONCURRENTLY`, which you drop and recreate. I would verify the schema state explicitly before retrying rather than assuming, and check the migration tool's own tracking table has not recorded it as applied.
@red
- Waiting for the migration to finish while the site is down.
- Running DDL without a lock timeout.

### The disk on the database server is 95% full. What is filling it and what do you do?
@short
Check three candidates in order: WAL retained by an inactive replication slot, table and index bloat, and log files. The replication slot case is the dangerous one because it grows without bound and will stop the primary accepting writes when the disk fills.
@deep
An abandoned replication slot — from a removed replica or a stopped CDC consumer — makes Postgres retain every WAL segment since that slot's position. It is quiet, it is fast, and it takes the primary down.

Bloat is the slower cause: a high-churn table where autovacuum has fallen behind, often because of a long-running transaction holding an old snapshot.
@code sql Find the cause, in the order they are likely
-- 1. REPLICATION SLOTS — the fast, dangerous one
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
  FROM pg_replication_slots ORDER BY 4 DESC;
-- inactive slot retaining 200GB → drop it (the consumer is gone) or fix the consumer
SELECT pg_drop_replication_slot('dead_replica_slot');
ALTER SYSTEM SET max_slot_wal_keep_size = '64GB';    -- bound it defensively, permanently

-- 2. WAL directory size overall
SELECT pg_size_pretty(sum(size)) FROM pg_ls_waldir();
-- large with no slot issue → archive_command failing? check the logs

-- 3. BLOAT
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum,
       pg_size_pretty(pg_total_relation_size(relid)) AS total
  FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
-- and the usual cause of vacuum falling behind:
SELECT pid, now()-xact_start AS age, state, left(query,60) FROM pg_stat_activity
 WHERE xact_start < now() - interval '5 min' ORDER BY age DESC;

-- 4. Reclaim WITHOUT an exclusive lock
-- ❌ VACUUM FULL locks the table completely
-- ✅ pg_repack, or vacuum aggressively and let the space be reused
@end
@senior
The replication slot is where I would look first because it is the one that goes from healthy to total outage fastest, and because it is invisible on every normal dashboard. Setting `max_slot_wal_keep_size` proactively is the defensive fix: it breaks the abandoned consumer rather than the primary, which is the correct trade. On bloat, the underlying cause is usually a long-running or idle-in-transaction session, so `idle_in_transaction_session_timeout` prevents recurrence more effectively than any amount of vacuum tuning.
@followup
The disk fills anyway before you can act. What happens?
@answer
Postgres stops accepting writes to protect itself, and the application effectively goes down — reads may continue briefly but anything writing fails. Recovery means freeing space urgently: dropping the offending replication slot, removing old log files, or extending the volume if the platform allows online resizing. That is why alerting at 75% and 85% rather than 95% matters — you need time to act, and this failure has no graceful degradation.
@red
- Running `VACUUM FULL` on a live table.
- No alert on replication slot lag or WAL size.

### Users report seeing data that they just deleted. Why?
@short
Read replica lag: the delete committed on the primary and the read went to a replica that had not yet replayed it. The fix is read-your-writes — route a user's reads to the primary for a short window after they write, or check the replica's replay position against the write's log position.
@deep
This is the most user-visible consequence of eventual consistency, and it looks like a broken application rather than a consistency trade-off. The same mechanism causes "I created it and got a 404" and "my edit did not save".

The other possible cause is caching: a deleted record still in Redis or in the client's query cache because the mutation invalidated a different key.
@code ts Distinguish the two causes, then fix
// CAUSE A — replica lag
SELECT client_addr, pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
  FROM pg_stat_replication;
// lag in the megabytes during a backfill → this is it.

// FIX: pin the user's reads to the primary briefly after a write
await primary.query('DELETE FROM items WHERE id=$1 AND user_id=$2', [id, userId]);
await redis.set(`recent-write:${userId}`, '1', 'EX', 5);
// on read:
const db = (await redis.exists(`recent-write:${userId}`)) ? primary : replica;

// PRECISE VARIANT: compare the replica's replay position to the write's LSN
const { rows } = await primary.query('SELECT pg_current_wal_lsn() AS lsn');
await redis.set(`lsn:${userId}`, rows[0].lsn, 'EX', 30);
// choose a replica only if pg_last_wal_replay_lsn() >= that value

// CAUSE B — caching
qc.invalidateQueries({ queryKey: itemKeys.all });     // prefix, not the exact key
await redis.del(`item:${id}`); await redis.incr('ver:items');   // version-namespaced keys
@end
@senior
The five-second primary pin is usually the right engineering trade: it costs a little extra primary load and removes the entire class of "my change disappeared", which is the inconsistency users always notice and report. The precise LSN version is worth it when replica lag is variable or primary capacity is tight. I would also point out that lag spikes are usually caused by something else you are doing — an unthrottled backfill, a large migration — so the durable fix may be throttling that work rather than changing the read path.
@followup
Lag is normally 5ms but spikes to 30 seconds during a nightly job. How do you handle that?
@answer
Throttle the job — batch the writes with pauses between batches, and monitor replication lag as a feedback signal so the job slows itself when lag grows. That is better than accepting large lag windows, because during them every read-your-writes protection has to fall back to the primary, which concentrates load exactly when the system is busiest. I would also schedule such jobs outside peak hours and alert on lag exceeding a threshold, so the interaction between batch work and user-facing consistency is visible rather than discovered from a support ticket.
@red
- Sending all reads to replicas including immediately after writes.
- Assuming replica lag is constant.

### A report query is timing out after the customer's data grew ten times. What are your options?
@short
In order: check the plan and add the index that serves it, reduce the data returned, precompute into a rollup or materialised view, move it to a replica, or make it asynchronous with a job and a download link. Which one depends on whether the work is inherent or accidental.
@deep
The first question is whether the query is slow because of a fixable plan or because it genuinely must process ten times more data. `EXPLAIN ANALYZE` answers it: a sequential scan or a nested loop over a large set is fixable, whereas an efficient scan over fifty million rows is inherent.

For inherent work, the answer is not to optimise the query but to change when and where it runs.
@code sql The ladder, with the decision point at each step
-- STEP 0: is it accidental or inherent?
EXPLAIN (ANALYZE, BUFFERS) <the report query>;
--   Seq Scan / nested loop over millions  → ACCIDENTAL. Fix the plan.
--   Efficient index scan aggregating 50M rows → INHERENT. Change the approach.

-- ACCIDENTAL
CREATE INDEX CONCURRENTLY ON orders (tenant_id, created_at DESC) INCLUDE (total_minor, status);
CREATE STATISTICS … ON status, created_at FROM orders;   -- correlated columns

-- INHERENT — precompute
CREATE MATERIALIZED VIEW tenant_daily AS
SELECT tenant_id, date_trunc('day', created_at) d, count(*) n, sum(total_minor) rev
  FROM orders WHERE status='paid' GROUP BY 1,2;
CREATE UNIQUE INDEX ON tenant_daily (tenant_id, d);
REFRESH MATERIALIZED VIEW CONCURRENTLY tenant_daily;     -- no read lock

-- INHERENT — or make it asynchronous
-- POST /reports → 202 + job id; worker runs it on a REPLICA with a generous
-- statement_timeout; result written to S3; user gets a signed download link.
-- This also removes the request-timeout and the retry problem entirely.
@end
@senior
The 202-plus-job pattern is the answer I would push for any report that can legitimately take more than a few seconds, because a synchronous endpoint fighting a load-balancer idle timeout is a losing battle regardless of how fast you make the query — and it gives you progress, cancellation and retry for free. Running it on a replica with a longer statement timeout is the complementary move, so a big report cannot affect transactional traffic. Those two changes together convert "the report times out" from a recurring incident into a solved architecture.
@followup
The customer wants the report in real time on a dashboard. How do you meet that?
@answer
Incremental rollups rather than on-demand aggregation: maintain the daily and hourly figures as data arrives, so the dashboard reads a few hundred pre-aggregated rows instead of scanning millions. Freshness becomes a function of the rollup interval, which for most dashboards can be a minute without anyone noticing. Where genuinely live numbers are needed — a counter for today — a Redis counter incremented on write, reconciled against the database periodically, gives instant reads with a correctness check.
@red
- Raising the timeout as the fix.
- Optimising a query whose problem is the volume of data.

### Two services deadlock updating the same rows. How do you diagnose and prevent it?
@short
Postgres detects the cycle and kills one transaction with a deadlock error, which appears in the logs with both queries. The cause is almost always inconsistent lock ordering, and the prevention is to always acquire locks in a deterministic order — typically sorted by primary key.
@deep
The deadlock log entry names both processes and both statements, which usually makes the ordering conflict obvious: one path locks A then B, the other locks B then A.

Beyond ordering, deadlock frequency is reduced by shorter transactions, doing the work in a single atomic statement where possible, and retrying on the deadlock error code, because at high concurrency some are unavoidable.
@code sql The log, the cause, and the fix
-- The log entry tells you everything
-- ERROR:  deadlock detected
-- DETAIL: Process 1234 waits for ShareLock on transaction 5678; blocked by process 4321.
--         Process 4321 waits for ShareLock on transaction 5679; blocked by process 1234.
--         Process 1234: UPDATE accounts SET balance = … WHERE id = 'A'
--         Process 4321: UPDATE accounts SET balance = … WHERE id = 'B'

-- ❌ INCONSISTENT ORDER: transfer(A→B) locks A then B; transfer(B→A) locks B then A
-- ✅ ALWAYS lock in a deterministic order
BEGIN;
  SELECT * FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE;   -- ← sorted
  UPDATE accounts SET balance = balance - $2 WHERE id = $3;
  UPDATE accounts SET balance = balance + $2 WHERE id = $4;
COMMIT;

-- ✅ Better still: avoid holding locks across multiple statements
UPDATE accounts SET balance = balance - $2 WHERE id = $3 AND balance >= $2;
-- one atomic statement, no read-then-write window
@end
@code ts And retry, because some deadlocks are unavoidable
async function withDeadlockRetry<T>(fn: () => Promise<T>, attempts = 3): Promise<T> {
  for (let i = 0; i < attempts; i++) {
    try { return await fn(); }
    catch (e: any) {
      if (e.code !== '40P01' && e.code !== '40001') throw e;    // deadlock / serialization
      metrics.increment('db.deadlock_retry');
      await sleep(2 ** i * 25 + Math.random() * 50);            // backoff + jitter
    }
  }
  throw new Error('DEADLOCK_RETRIES_EXHAUSTED');
}
@end
@senior
Sorting the ids before locking is the one-line fix that eliminates the entire class, and it is easy to apply consistently through a repository helper so no individual code path has to remember. The retry wrapper is the complement, because at high concurrency you cannot design deadlocks away entirely and a retry is the correct response. I would also emphasise keeping transactions short and never holding one across a network call, since long transactions widen the window in which a cycle can form and make every deadlock more expensive.
@followup
The two services are separate applications sharing a database. Does that change anything?
@answer
It makes consistent lock ordering a cross-team contract rather than a local convention, which is harder to enforce — and it is a symptom of a deeper problem, since two services writing the same tables means neither owns its data. The tactical fix is the same (deterministic ordering, short transactions, retries), and the strategic fix is to give one service ownership of those tables and have the other go through its API or an event. Shared mutable database access between services is the coupling that causes this and much else.
@red
- Increasing the deadlock timeout as the fix.
- No retry on the deadlock error code.

### You need to add a NOT NULL column to a 200 million row table with no downtime.
@short
Expand and contract across several deploys: add the column nullable, dual-write, backfill in throttled batches, add a `NOT VALID` check constraint, validate it, and only then set `NOT NULL`. Every step is online and reversible.
@deep
Adding `NOT NULL` directly requires a full table scan under an exclusive lock, which on 200 million rows means minutes of total unavailability for that table.

The `NOT VALID` constraint trick is the key: it is added instantly without scanning, and validation takes a weaker lock that does not block reads or writes.
@code sql The full sequence, deploy by deploy
-- DEPLOY 1 — instant, nullable
ALTER TABLE orders ADD COLUMN region text;

-- DEPLOY 2 — application writes the column on every insert/update (dual write)

-- BACKFILL — batched, throttled, resumable. NOT inside a migration transaction.
DO $$
DECLARE n int;
BEGIN
  LOOP
    UPDATE orders SET region = derive_region(shipping_pin)
     WHERE region IS NULL AND id IN (
       SELECT id FROM orders WHERE region IS NULL ORDER BY id LIMIT 5000);
    GET DIAGNOSTICS n = ROW_COUNT;
    EXIT WHEN n = 0;
    COMMIT;                       -- short transactions; vacuum and replication keep up
    PERFORM pg_sleep(0.2);        -- throttle: watch replication lag while this runs
  END LOOP;
END $$;

-- DEPLOY 3 — constraint added INSTANTLY (not validated yet), then validated online
ALTER TABLE orders ADD CONSTRAINT orders_region_nn CHECK (region IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT orders_region_nn;   -- SHARE UPDATE EXCLUSIVE only

-- DEPLOY 4 — optional: promote to a real NOT NULL (PG12+ uses the validated
-- constraint to skip the scan)
ALTER TABLE orders ALTER COLUMN region SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT orders_region_nn;

-- THROUGHOUT: SET lock_timeout = '3s' on every DDL statement.
@end
@senior
Monitoring replication lag during the backfill is the operational detail that matters, because an unthrottled backfill on 200 million rows can push replicas minutes behind, which breaks read-your-writes for every user and can trigger the "my data disappeared" incident elsewhere. The `pg_sleep` between batches is not politeness — it is what keeps the rest of the system healthy. I would also rehearse the whole sequence on a restored snapshot to get real timings, so the plan has hours attached rather than optimism.
@followup
The backfill will take three days. How do you manage that?
@answer
Run it as a supervised job with progress tracking, resumable from a checkpoint, pausable, and rate-adjustable — not as a migration. The application must work correctly in both the pre- and post-backfill states throughout, which the nullable column guarantees. I would monitor lag, dead tuples and disk during the run, and slow it automatically if lag exceeds a threshold. Three days is fine; three days with no visibility and no pause button is not.
@red
- `ALTER TABLE ... SET NOT NULL` directly on a large table.
- An unthrottled backfill that pushes replicas minutes behind.

### Your Postgres instance is running out of connections. Diagnose.
@short
Compute the arithmetic first — instances times pool size plus workers plus tooling against `max_connections` — then look for the anomaly: a leak, an unbounded fan-out, or `idle in transaction` sessions holding connections. The fix is usually PgBouncer plus timeouts, not raising `max_connections`.
@deep
Raising `max_connections` is the tempting fix and usually the wrong one, because each Postgres connection is a backend process with its own memory, and hundreds of them degrade throughput through context switching.

`idle in transaction` is the specific state to look for: a connection that began a transaction and is doing nothing, usually because the application code awaits an external call inside the transaction or forgot to commit.
@code sql Diagnose, mitigate, prevent
-- 1. WHO is holding connections, and in what state?
SELECT state, count(*), max(now()-state_change) AS longest
  FROM pg_stat_activity GROUP BY state ORDER BY 2 DESC;
-- many 'idle in transaction'  → the application forgot to commit, or awaits inside a txn
-- many 'idle'                 → pools are just large; do the arithmetic
-- many 'active' + long        → one slow query is holding everything

-- 2. WHICH application? (set application_name per service — invaluable here)
SELECT application_name, state, count(*) FROM pg_stat_activity
 GROUP BY 1,2 ORDER BY 3 DESC;

-- 3. MITIGATE
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
 WHERE state = 'idle in transaction' AND state_change < now() - interval '5 min';

-- 4. PREVENT
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
ALTER SYSTEM SET statement_timeout = '30s';      -- per role for reporting workloads
-- + PgBouncer in transaction mode: 240 client connections → ~25 server connections
-- + connectionTimeoutMillis so the app fails fast instead of queueing
@end
@senior
`idle_in_transaction_session_timeout` is the setting I would apply proactively rather than reactively, because the pattern that causes it — beginning a transaction and then making a network call to a payment provider or another service — is common, and one hung call otherwise holds a connection and blocks vacuum indefinitely. Setting `application_name` per service is the other habit that pays off precisely in this moment: without it you know connections are exhausted but not which service is responsible, and with it the answer is one query.
@followup
Why not just raise `max_connections` to 1000?
@answer
Because each connection is a separate backend process with its own memory allocation, and throughput typically peaks at a modest number of *active* connections — often a small multiple of the core count. Beyond that, context switching and lock contention make everything slower, so a thousand connections can be worse than two hundred. The correct answer is a pooler in transaction mode, which multiplexes many client connections onto few server connections, plus fixing whatever is holding connections longer than it should.
@red
- Raising `max_connections` as the first response.
- No `application_name`, so you cannot tell which service is responsible.

### A backup restore test fails. What do you check and what does it mean?
@short
Establish whether the backup itself is unusable or the restore procedure is wrong — they have very different implications. Then check the specifics: WAL continuity for point-in-time recovery, extension availability, version compatibility, and whether the restore target has enough disk and memory.
@deep
The reason this matters is that an untested backup is a hypothesis. The failure modes are: archiving silently broken so WAL segments are missing, an extension present in production but not in the restore environment, a version mismatch, and simply not enough disk on the target.

Discovering any of these during a real recovery is the worst possible time.
@code bash What to check, in order
# 1. Is the base backup itself intact?
pg_verifybackup /restore/base

# 2. Is the WAL chain continuous? (gaps break point-in-time recovery)
aws s3 ls s3://acme-wal/ | awk '{print $4}' | sort | \
  awk 'NR>1 && prev_expected != $0 {print "GAP before " $0} {prev_expected=next($0)}'
# simpler: check the archive_command has not been failing
grep -i 'archive command failed' /var/log/postgresql/*.log

# 3. Extensions present on the target?
psql -c "SELECT extname, extversion FROM pg_extension;"   # prod
# vs the restore target — pgvector, postgis, pg_stat_statements must all exist

# 4. Version compatibility — a physical backup restores only to the SAME major version

# 5. Resources — the restore target needs comparable disk AND memory for recovery

# WHAT EACH FAILURE MEANS
#   missing WAL          → RPO is worse than you believe. Fix archiving NOW.
#   missing extension    → restores will always fail. Fix the runbook and the image.
#   version mismatch     → your DR plan is broken; document the exact procedure.
#   too slow             → your RTO is not what you think. Consider a warm standby.
@end
@senior
The most valuable outcome of a failed restore test is discovering that the recovery point objective is not what you believed — broken WAL archiving means you can only restore to the last base backup, which might be twenty-four hours rather than seconds. That is a business-level fact, not a technical detail, and it should be reported as such. I would also treat restore duration as a first-class finding: if restoring takes six hours and the stated RTO is one, the plan does not meet the requirement and needs a warm standby, which is a budget conversation rather than an engineering one.
@followup
How often should you test restores?
@answer
Monthly at minimum, automated, with assertions — restore, check row counts against expectations, boot the application against it, run a smoke test — and after any change to the database version, extensions or backup configuration. Automation is what makes the cadence sustainable; a manual quarterly drill gets skipped. I would also record the restore duration each time, because it grows with the data and is the number your recovery time objective depends on.
@red
- Taking backups and never restoring them.
- Not knowing your actual recovery point and time objectives.

### You discover a table has grown to 800GB and queries are degrading. What now?
@short
Establish what it is: live data, dead tuples from bloat, or history that should have been archived. Then act accordingly — vacuum and repack for bloat, partition and drop for history, and archive cold data to cheaper storage. Retention policy is usually the real fix.
@deep
The three causes need different responses. Bloat means autovacuum has fallen behind, typically because of long-running transactions. Genuine live data of that size means the access pattern needs partitioning. History that nobody queries should not be in the transactional database at all.

Partitioning is the durable answer for time-series growth because it makes retention an instant `DROP TABLE` instead of a slow, bloating `DELETE`.
@code sql Establish the cause, then apply the right fix
-- 1. HOW MUCH IS BLOAT?
SELECT pg_size_pretty(pg_total_relation_size('events')) AS total,
       pg_size_pretty(pg_relation_size('events')) AS heap,
       pg_size_pretty(pg_indexes_size('events')) AS indexes,
       n_live_tup, n_dead_tup, last_autovacuum
  FROM pg_stat_user_tables WHERE relname = 'events';
-- n_dead_tup comparable to n_live_tup → bloat. Find the blocker:
SELECT pid, now()-xact_start age, state FROM pg_stat_activity
 WHERE xact_start < now()-interval '5 min';

-- 2. RECLAIM without downtime
-- pg_repack -t events -d acme      (online rebuild; VACUUM FULL locks completely)

-- 3. IF IT IS GENUINE HISTORY → partition and set a retention policy
CREATE TABLE events_new (LIKE events INCLUDING ALL) PARTITION BY RANGE (created_at);
-- migrate in batches, then swap; from then on:
DROP TABLE events_2025_02;        -- instant retention, no bloat, no WAL storm

-- 4. ARCHIVE the cold partitions before dropping
-- COPY events_2025_02 TO PROGRAM 'gzip | aws s3 cp - s3://archive/…' (FORMAT csv);

-- 5. PREVENT recurrence
ALTER TABLE events SET (autovacuum_vacuum_scale_factor = 0.02);
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
@end
@senior
The retention question is the one I would put to the business, because it is usually the real answer: nobody queries three-year-old event data, but nobody ever decided to delete it either. Partitioning turns that decision into a one-line operation and archiving to object storage keeps it available at a fraction of the cost. I would also flag that a `DELETE` of hundreds of millions of rows is the wrong tool — it is slow, it generates enormous WAL, it bloats the table further, and it leaves the space unavailable until vacuum catches up, which is exactly the situation you are trying to escape.
@followup
Deleting old rows made it worse. Why?
@answer
Because `DELETE` marks rows dead rather than freeing space, so the table stays the same size while accumulating dead tuples that vacuum must process — and the delete itself generates WAL proportional to the rows removed, which stresses replication and archiving. The space is only reused for new rows, not returned to the filesystem. Partition-and-drop avoids all of that: dropping a partition is a metadata operation that returns the space immediately with no WAL storm and no vacuum work.
@red
- `DELETE` for retention on a very large table.
- `VACUUM FULL` on a live table to reclaim space.

# SECTION Payment Incidents | Stripe, PayPal and Razorpay on 2,000+ monthly transactions is real production experience on your CV — so expect these to be the hardest questions you get, and the least forgiving.

### A Stripe webhook was delivered twice and the customer was fulfilled twice. Fix it.
@short
The handler was not idempotent. The fix is a `processed_events` table with the provider's event id as the primary key, inserted in the same transaction as the effect, so the second delivery finds a conflict and exits without acting. Then reconcile the damage and add the constraint that makes it impossible.
@deep
Providers retry until they receive a 2xx, so duplicate delivery is normal rather than exceptional — a slow handler, a deploy during delivery, or a lost acknowledgement all cause it.

The critical detail is that the dedup insert and the effect must be in the same transaction. Recording the event id after committing the effect leaves a window in which a crash causes reprocessing.
@code sql The fix, and the constraint that backs it up
CREATE TABLE processed_events (
  id          text PRIMARY KEY,         -- the PROVIDER's event id, e.g. evt_1P2x…
  provider    text NOT NULL,
  type        text NOT NULL,
  received_at timestamptz NOT NULL DEFAULT now()
);

-- Backstop: even without the table, fulfilment cannot happen twice
CREATE UNIQUE INDEX one_fulfilment_per_order ON shipments (order_id);
@end
@code ts The handler, corrected
async function handleEvent(event: ProviderEvent) {
  await withTransaction(async (tx) => {
    const first = await tx.query(
      `INSERT INTO processed_events (id, provider, type) VALUES ($1,$2,$3)
       ON CONFLICT (id) DO NOTHING RETURNING id`,
      [event.id, event.provider, event.type]);
    if (!first.rowCount) {                       // ← duplicate: exit silently
      logger.info({ eventId: event.id }, 'duplicate webhook ignored');
      return;
    }

    // Guarded transition: also protects against OUT-OF-ORDER delivery
    const r = await tx.query(
      `UPDATE orders SET status='paid', paid_at=now()
        WHERE payment_intent=$1 AND status='pending' RETURNING id`, [event.intentId]);
    if (!r.rowCount) return;                     // already paid, or refunded — do nothing

    await tx.query(`INSERT INTO outbox (id, topic, payload) VALUES ($1,'order.paid',$2)`,
                   [randomUUID(), JSON.stringify({ orderId: r.rows[0].id })]);
  });
}
@end
@senior
Two things beyond the code. First, the remediation: identify the affected orders by looking for duplicate shipments or duplicate outbox entries, and decide with the business how to handle each — recover the goods, absorb the cost, or contact the customer — rather than silently deleting rows. Second, the constraint as a backstop: the `processed_events` table handles the expected case, and the unique index on shipments means that even a future bug in the dedup logic cannot cause double fulfilment. Defence in depth matters most where the failure costs money.
@followup
How do you find all the orders affected?
@answer
Query for the structural signature — orders with more than one shipment, more than one fulfilment event, or duplicated outbox entries for the same order and topic — over the window when the bug was live. Cross-check against the provider's ledger to confirm only one charge occurred, since the duplicate was fulfilment rather than payment. Then produce a reviewed list with the financial impact per order before taking any corrective action, because bulk-correcting financial records without review is how a bug becomes an incident.
@red
- Deduplicating in Redis after committing the effect.
- Silently deleting the duplicate records without assessing impact.

### A payment succeeded at Stripe but the order is still pending. What happened and what do you do?
@short
The webhook was lost, delayed, or failed to process. The customer has paid and has nothing, so this is urgent. Immediate fix is to query the provider directly for that intent and apply the same handler; the durable fix is a reconciliation job that does this automatically for any payment pending beyond a short window.
@deep
The causes are: our endpoint was down or deploying when the webhook arrived and the retries exhausted, the handler threw and returned a non-2xx repeatedly, a signature verification failure (often a body-parsing change), or the provider had a delivery incident.

Reconciliation is the safety net that makes this self-healing rather than dependent on a customer complaint.
@code ts The immediate repair and the permanent safety net
// IMMEDIATE — the provider is authoritative
const intent = await stripe.paymentIntents.retrieve(intentId);
if (intent.status === 'succeeded') {
  await handleEvent({ id: `manual:${intent.id}`, provider: 'stripe',
                      type: 'payment_intent.succeeded', intentId: intent.id });
}

// PERMANENT — continuous reconciliation for recent payments
export async function repairPending() {
  const stuck = await db.query(
    `SELECT intent_id FROM payments
      WHERE status IN ('requires_payment','processing')
        AND created_at < now() - interval '15 minutes'
        AND created_at > now() - interval '7 days'`);

  for (const { intent_id } of stuck.rows) {
    const pi = await stripe.paymentIntents.retrieve(intent_id);
    metrics.increment('reconciliation.repair', { status: pi.status });
    if (pi.status === 'succeeded')  await handleEvent(synthetic(pi, 'succeeded'));
    if (pi.status === 'canceled')   await handleEvent(synthetic(pi, 'canceled'));
    // still processing → leave it; it will be picked up next run
  }
}
// plus a DAILY two-way sweep against the provider's ledger for the previous day

// AND FIND OUT WHY THE WEBHOOK FAILED
// Stripe dashboard → Webhooks → delivery attempts: 400? 500? timeout?
//   400 → signature verification (did express.json() get mounted before the raw route?)
//   500 → our handler threw. Check the logs for that event id.
//   timeout → we processed synchronously and took >10s. Ack first, process async.
@end
@senior
Because the handler is idempotent, replaying it from the provider's data is safe — which is exactly why idempotency is the foundation that makes automated repair possible. Without it, reconciliation would risk double-fulfilling. I would also emphasise the delivery-attempt log in the provider's dashboard as the first diagnostic: it tells you immediately whether we rejected the webhook (signature), errored on it (handler bug), or timed out (synchronous processing), and each of those is a different fix.
@followup
The webhook failed because of a signature error. What causes that?
@answer
Almost always the raw body being consumed or re-serialised before verification — a global `express.json()` mounted before the webhook route is the classic cause, because the signature is computed over the exact bytes. Other causes are the wrong webhook secret (test versus live, or a rotated secret), a proxy modifying the body, and a timestamp outside the tolerance window because of clock skew. I would check the body handling first, since it accounts for most cases and is easy to verify by logging the raw body length.
@red
- No reconciliation, relying entirely on webhooks.
- Processing synchronously inside the webhook handler.

### A customer was charged twice for one order. Walk through your response.
@short
Refund the duplicate immediately — the customer's money comes first — then determine which layer failed: two intents created because of a missing idempotency key, or one intent captured twice. Then add the constraint that makes it structurally impossible.
@deep
The two shapes have different causes. Two charges means two payment intents were created, which points at a client retry with no idempotency key or a missing unique constraint. One intent captured twice points at a capture path without idempotency.

Both are preventable with the layered approach: an API idempotency key, a provider idempotency key derived from the order, and a unique constraint on the payment intent.
@code sql Find the shape, then close the hole
-- Which shape is it?
SELECT order_id, count(*) AS payments, array_agg(intent_id), array_agg(status)
  FROM payments WHERE order_id = $1 GROUP BY order_id;
-- 2 rows, 2 intents  → duplicate INTENT creation
-- 1 row              → duplicate CAPTURE on one intent

-- CLOSE IT
ALTER TABLE payments ADD CONSTRAINT payments_intent_unique UNIQUE (provider, intent_id);
CREATE UNIQUE INDEX one_successful_payment_per_order
  ON payments (order_id) WHERE status = 'succeeded';
@end
@code ts And the three layers of idempotency that prevent it
// 1. API layer — the client's retry does not create a second order/payment
const key = req.header('Idempotency-Key');       // required, stored with the response

// 2. PROVIDER layer — derived from the ORDER, so every retry converges
const intent = await stripe.paymentIntents.create(
  { amount: order.totalMinor, currency: order.currency },
  { idempotencyKey: `intent:${order.id}` });     // NOT a fresh uuid per attempt

// 3. DATABASE layer — the backstop
await db.query(
  `INSERT INTO payments (order_id, provider, intent_id, amount_minor, currency, status)
   VALUES ($1,'stripe',$2,$3,$4,'requires_payment')
   ON CONFLICT (provider, intent_id) DO NOTHING`, […]);
@end
@senior
Deriving the provider idempotency key from the order id rather than generating a fresh UUID is the specific bug this usually is: a retry with a new key creates a genuinely new intent at the provider, and no amount of application logic afterwards can undo that. The unique partial index on successful payments per order is the backstop I would add regardless, because it converts a future logic error into a caught constraint violation rather than a second charge. And I would say plainly that the refund goes out before the investigation — the customer should not wait for our root-cause analysis.
@followup
How do you detect this proactively rather than waiting for a complaint?
@answer
A reconciliation check that looks for more than one successful charge per order in the provider's ledger, run continuously for recent activity and daily over the previous day, with any hit paging immediately. I would also alert on the ratio of charges to orders, because a systemic version of this bug shows up as that ratio drifting above one before individual customers notice. Detecting a double charge before the customer does turns a trust-damaging incident into a proactive refund and an apology.
@red
- Investigating before refunding the customer.
- A new idempotency key generated on each retry.

### Webhooks arrive out of order — a refund event before the payment event. What breaks and how do you handle it?
@short
Nothing, if every state transition is guarded by the current state. The refund event finds no paid order and does nothing harmful; the later payment event finds an order that is no longer pending and does not resurrect it. Unguarded updates are what break, by overwriting the newer state with the older event.
@deep
Providers do not guarantee ordering, and network conditions plus retries make reordering common. So the handler must be written so that any order of arrival converges to the correct state.

The techniques are guarded transitions (`WHERE status = 'expected'`), an event timestamp or sequence check, and buffering an event whose precondition is not yet satisfied.
@code sql Guarded transitions make ordering irrelevant
-- payment_intent.succeeded — only from pending
UPDATE orders SET status='paid', paid_at=$2
 WHERE payment_intent=$1 AND status='pending';
-- arrives AFTER a refund → status is 'refunded' → 0 rows → correctly ignored

-- charge.refunded — only from paid
UPDATE orders SET status='refunded', refunded_at=$2
 WHERE payment_intent=$1 AND status IN ('paid','fulfilled');
-- arrives BEFORE the payment → status is 'pending' → 0 rows → buffer it

-- Buffer the premature event rather than dropping it
INSERT INTO pending_events (intent_id, event_id, type, payload, received_at)
VALUES ($1,$2,$3,$4, now()) ON CONFLICT DO NOTHING;
-- after any successful transition, re-drive the buffer for that intent
@end
@code ts Timestamp guard as a second line of defence
// Ignore any event older than the last one we applied to this entity
const applied = await tx.query(
  `UPDATE orders SET status=$2, last_event_at=$3
    WHERE payment_intent=$1 AND (last_event_at IS NULL OR last_event_at < $3)
    RETURNING id`,
  [intentId, newStatus, new Date(event.created * 1000)]);
if (!applied.rowCount) {
  metrics.increment('webhook.stale_event_ignored', { type: event.type });
}
@end
@senior
Buffering rather than dropping a premature event is the detail that makes this genuinely correct: if the refund arrives first and you simply ignore it, and the payment event then arrives, you end up with an order marked paid that was actually refunded. Re-driving the buffer after each successful transition converges to the right state. I would also always log the ignored transitions rather than silently discarding them, because a rising count of ignored events is a signal that something upstream has changed and you want to notice it.
@followup
How do you test that your handler is order-independent?
@answer
Property-based testing over permutations: generate a set of events for one entity, apply them in every order (or a random sample of orders), and assert the final state is identical. That is exactly the kind of invariant example-based tests miss, and it finds the transitions you forgot to guard. I would pair it with specific regression tests for the orderings you have actually seen in production, since those are the ones customers experienced.
@red
- Unguarded status updates in webhook handlers.
- Dropping events whose precondition is not yet met.

### The user closed the browser during checkout. What state are you in and what should happen?
@short
It depends where they closed it. If before confirmation, no charge occurred and the pending order expires. If after confirmation but before the redirect, the payment succeeded and the webhook must complete the order — which is exactly why the webhook, not the redirect, is authoritative.
@deep
This is the scenario that proves the design. A system that marks orders paid on the success redirect loses every payment where the user closed the tab, refreshed, or lost connectivity at the wrong moment — and those users are charged with no order.

Pending orders also need a lifecycle: an expiry that releases reserved stock and cancels the intent, so abandoned checkouts do not hold inventory forever.
@code ts What happens in each case, and the cleanup job
// CASE A — closed BEFORE confirming
//   no charge; the order stays 'pending'; the intent expires at the provider
//   → expiry job releases the stock reservation

// CASE B — closed AFTER confirming, before the redirect
//   the charge SUCCEEDED. The webhook arrives server-to-server and completes the order.
//   The user receives the confirmation email even though they never saw the page.
//   ← this is the entire reason the webhook is authoritative

// CASE C — closed during a 3DS challenge
//   status is 'requires_action'; it may still complete if they finish elsewhere,
//   or expire. Reconciliation resolves it either way.

// THE EXPIRY JOB — essential, and often missing
export async function expireAbandonedCheckouts() {
  const stale = await db.query(
    `SELECT id, payment_intent FROM orders
      WHERE status='pending' AND created_at < now() - interval '30 minutes'`);

  for (const o of stale.rows) {
    const pi = o.payment_intent ? await stripe.paymentIntents.retrieve(o.payment_intent) : null;
    if (pi?.status === 'succeeded') { await handleEvent(synthetic(pi)); continue; }  // ← check first!
    await withTransaction(async (tx) => {
      await releaseStockReservation(o.id, tx);
      await tx.query(`UPDATE orders SET status='expired' WHERE id=$1 AND status='pending'`, [o.id]);
    });
    if (pi) await stripe.paymentIntents.cancel(pi.id).catch(() => {});
  }
}
@end
@senior
The check inside the expiry job is the detail that prevents a serious bug: expiring an order without first asking the provider whether the payment actually succeeded would cancel an order the customer has paid for. Always consult the authoritative source before a destructive transition. I would also point out the product angle — an abandoned checkout with a valid email is a recovery opportunity, and the same job that expires the order can trigger a reminder, which is a case where the operational mechanism and the business goal align neatly.
@followup
The customer says they were charged but got no order, and reconciliation has not run yet. What do you tell support?
@answer
Give support a tool that queries the provider by email or intent id and shows the authoritative status, so they can answer immediately rather than escalating. If the charge succeeded, the tool should offer a "repair" action that replays the handler — safe because it is idempotent — and record who did it and why. Building that self-service path is worth far more than the individual incident, because this situation recurs and every occurrence otherwise costs an engineer's time and a customer's patience.
@red
- Treating the success redirect as confirmation of payment.
- An expiry job that cancels without checking the provider first.

### Razorpay reports the payment as captured but your database says failed. Diagnose.
@short
Trust the provider's ledger — it is authoritative for money movement — and repair from it. Then find why our record diverged: a webhook we rejected, a handler that errored, a mapping bug between their status vocabulary and ours, or a signature failure after a secret rotation.
@deep
Provider status vocabularies differ meaningfully. Razorpay distinguishes `authorized` from `captured`, and treating `authorized` as final marks orders paid before the money is actually taken. Conversely, mapping a non-terminal status to `failed` produces exactly this divergence.

Signature failures after a secret rotation are the other frequent cause, and they present as webhooks rejected with a 400 in their dashboard.
@code ts The status mapping is where this bug usually lives
// ❌ over-simplified mapping loses meaning and creates divergence
const status = body.payload.payment.entity.status === 'captured' ? 'paid' : 'failed';
// 'authorized', 'created' and 'refunded' all become 'failed'. That is the bug.

// ✅ explicit, exhaustive mapping with a compile-time check
const MAP = {
  created:    'requires_payment',
  authorized: 'authorized',        // money held, NOT captured — do not fulfil yet
  captured:   'succeeded',
  refunded:   'refunded',
  failed:     'failed',
} as const satisfies Record<RazorpayStatus, InternalStatus>;

const internal = MAP[body.payload.payment.entity.status];
if (!internal) {                                  // unknown status: record, do not guess
  metrics.increment('payments.unknown_status', { provider: 'razorpay',
                                                 status: body.payload.payment.entity.status });
  logger.error({ body }, 'unmapped provider status');
  return;                                          // ← never default to 'failed'
}

@end
@senior
Never defaulting an unknown status to a terminal one is the principle I would emphasise: `failed` is a decision with consequences — it can trigger a retry email, release stock, or cancel an order — so guessing it from an unrecognised value is worse than recording the anomaly and alerting. The `satisfies Record<...>` typing means adding a new provider status becomes a compile error rather than a silent misclassification. And the authorized-versus-captured distinction is a real money bug: fulfilling on authorisation means shipping goods for money you have not actually taken.
@followup
How do you catch mapping bugs before they reach production?
@answer
Enumerate every documented provider status in a test and assert the mapping is exhaustive and correct, with the type system enforcing that a new status must be handled. Beyond that, the nightly sandbox contract test catches statuses the provider adds after you wrote the mapping. And in production, an alert on unmapped statuses means the first occurrence is a notification rather than a silent misclassification affecting orders for weeks.
@red
- Defaulting unknown provider statuses to failed.
- Treating authorisation as capture.

### Your payment success rate dropped from 94% to 71% in an hour. Go.
@short
Segment immediately — by provider, method, currency, issuer and card type — because that tells you whether it is us, one provider, or one issuer. Then check recent deploys and the provider's status page in parallel. Mitigate by routing to the alternative provider if it is provider-specific.
@deep
A drop this size is either a change on our side (a deploy, a configuration change, a certificate) or on theirs (an outage, a policy change, an issuer problem). Segmentation distinguishes them in under a minute.

Decline reasons matter as much as the rate: a spike in `do_not_honor` from one issuer is different from a spike in 3DS abandonment, which is usually a frontend regression.
@code sql Segment first — the answer is almost always in the breakdown
SELECT provider, method, currency, decline_code,
       count(*) FILTER (WHERE outcome='succeeded') AS ok,
       count(*) AS total,
       round(100.0 * count(*) FILTER (WHERE outcome='succeeded') / count(*), 1) AS pct
  FROM payment_attempts
 WHERE at > now() - interval '1 hour'
 GROUP BY 1,2,3,4
 ORDER BY total DESC;

-- INTERPRETING THE RESULT
--  one provider down, others fine        → their incident → route traffic away (flag)
--  one method (UPI/3DS) down             → that flow is broken; check our integration
--  one currency/region                   → issuer or regulatory change
--  spike in 'authentication_required'    → 3DS challenge failing → often a FRONTEND bug
--  spike in 'do_not_honor'               → issuer-side; little we can do; monitor
--  everything down uniformly             → US. Check the deploy, config, and keys.
@end
@code ts Mitigation without a deploy
// Provider routing must be configuration, not code, precisely for this moment
await flags.set('payments.route.default', 'razorpay');       // seconds, no deploy
await flags.set('payments.stripe.enabled', false);
// existing in-flight intents at Stripe still complete via webhook — do not cancel them
@end
@senior
Having provider routing behind a runtime flag is the preparation that makes this incident survivable in seconds rather than a deploy cycle, and it is the strongest practical argument for multi-provider support. On the frontend cause: a spike in authentication failures after a deploy is usually a change to the checkout page breaking the 3DS challenge flow, which no backend metric would reveal — which is why the decline-reason breakdown matters more than the aggregate rate. And I would compare against the same period last week rather than an absolute threshold, because success rates vary naturally by time and traffic mix.
@followup
It turns out to be one issuer declining everything. What can you actually do?
@answer

### A refund was issued twice. How did that happen and how do you prevent it?
@short
The refund path lacked the same idempotency discipline as the payment path — an operator clicked twice, or a retry created a second refund at the provider. Prevent it with a unique constraint on refunds per order or per idempotency key, and a provider idempotency key derived from the refund request rather than generated per attempt.
@deep
Refunds are often built after payments and inherit less care, which is why this happens. They need identical treatment: an idempotency key, a guarded state transition, a unique constraint, and asynchronous execution through the outbox rather than an inline provider call.

The amount check must also account for prior refunds, or partial refunds can cumulatively exceed the capture.
@code sql The constraints that make it impossible
CREATE TABLE refunds (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id      uuid NOT NULL REFERENCES orders(id),
  provider_id   text UNIQUE,                       -- the provider's refund id
  idem_key      text NOT NULL UNIQUE,              -- ours, derived from the request
  amount_minor  bigint NOT NULL CHECK (amount_minor > 0),
  status        text NOT NULL,
  actor         text NOT NULL,
  reason        text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now()

-- Total refunded can never exceed captured — enforced, not checked in code
CREATE OR REPLACE FUNCTION assert_refund_total() RETURNS trigger AS $$
DECLARE captured bigint; refunded bigint;
BEGIN
  SELECT captured_minor INTO captured FROM orders WHERE id = NEW.order_id FOR UPDATE;
  SELECT COALESCE(sum(amount_minor),0) INTO refunded FROM refunds
   WHERE order_id = NEW.order_id AND status <> 'failed';
  IF refunded > captured THEN
    RAISE EXCEPTION 'refund total % exceeds captured %', refunded, captured;
  END IF;
  RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE CONSTRAINT TRIGGER refunds_total AFTER INSERT OR UPDATE ON refunds
DEFERRABLE INITIALLY DEFERRED FOR EACH ROW EXECUTE FUNCTION assert_refund_total();
@end

### Payments are working but the confirmation emails are not sending. How do you handle it?
@short
Confirm the payment path is genuinely unaffected, then treat the email failure as its own incident: check the queue depth and failure rate, the provider's status, and whether the failures are permanent or transient. Because the sends are queued, the messages are not lost — they are pending.
@deep
This is exactly the scenario the outbox pattern is designed for: the order is correct in the database, the intent to notify is recorded, and delivery is retried independently. Nothing is lost, and the system converges when the provider recovers.

The risk is a poison message consuming retry capacity, or a permanent failure being retried forever.
@code ts Diagnose, drain, and communicate
// 1. Is it all sends, or a subset?
SELECT error_code, count(*), min(at), max(at)
  FROM email_attempts WHERE at > now() - interval '1 hour' GROUP BY 1 ORDER BY 2 DESC;
//   provider 5xx / timeouts      → their incident → the queue will drain on recovery
//   429                          → we are rate limited → reduce worker concurrency
//   550 / invalid recipient      → PERMANENT for those addresses → dead-letter, do not retry
//   auth failure                 → our API key was rotated or revoked → fix immediately

// 2. Classify so permanent failures do not consume retry capacity
if (isPermanent(err)) throw new UnrecoverableError(err.message);   // → DLQ, no retries
throw err;                                                         // → backoff and retry

// 3. Communicate: the order IS complete even though the email has not arrived
//    - status page note
//    - support macro: "your order is confirmed; the email is delayed"
//    - the order page should show the confirmation regardless of email status

// 4. After recovery: verify the queue drained and nothing sat in the DLQ unnoticed
SELECT count(*), min(created_at) FROM outbox WHERE topic='order.paid' AND published_at IS NULL;
@end
@senior
The point worth making is that this is a low-severity incident precisely because of an earlier design decision: the outbox means the emails are delayed rather than lost, and the order state is correct regardless. If the email send had been inline in the payment handler, a provider outage would have failed payments — that is the difference the pattern makes. On communication, the key move is that the order page shows the confirmation independently of the email, so a delayed email is an inconvenience rather than a customer believing their order did not go through.
@followup
Some emails were sent twice when the queue recovered. Why?
@answer
At-least-once delivery: a send that succeeded at the provider but whose acknowledgement was lost gets retried, and the handler sends again. The fix is a deduplication key passed to the email provider — most support an idempotency or message id — or recording the send before dispatching and checking it on retry. Since a duplicate receipt is annoying rather than harmful, this is a case where at-least-once with occasional duplicates is an acceptable trade, but it should be a decision rather than a surprise.
@red
- Sending emails inline in the payment handler.
- Retrying permanent failures with the same policy as transient ones.

# SECTION Real-Time & Collaboration Incidents | Connections, ordering and convergence under real network conditions — reasoned from the self-initiated Yjs and Redis Pub/Sub system, not from production incidents you were paged for.

### Your WebSocket server crashes and 40,000 clients reconnect simultaneously. What happens?
@short
A thundering herd: every client retries at the same moment, the surviving instances are overwhelmed by handshakes and subscription setup, they degrade or crash, and the cycle repeats. The fix is jittered exponential backoff on the client and admission control on the server.
@deep
The reconnect storm is worse than the original outage because connection establishment is expensive — TLS handshake, authentication, subscription setup, and often a state resync — so forty thousand simultaneous reconnects is far more load than forty thousand established connections.

Without jitter, clients synchronise: they all failed at the same moment, so they all retry at the same offsets forever.
@code ts Client backoff with jitter, and server-side admission control
// CLIENT — jitter is not optional; without it the herd never disperses
function reconnectDelay(attempt: number) {
  const base = Math.min(30_000, 2 ** attempt * 500);
  return base * (0.5 + Math.random());          // ← full jitter across [0.5x, 1.5x]
}
// plus: resume from lastSeq rather than a full resync, so reconnection is CHEAP

// SERVER — admission control so we degrade instead of collapsing
let connecting = 0;
wss.on('connection', async (ws, req) => {
  if (connecting > 200) {                       // cap concurrent handshakes
    ws.close(1013, 'try_again_later');          // 1013 = the client should back off more
    metrics.increment('ws.admission_rejected');
    return;
  }
  connecting++;
  try { await authenticateAndSubscribe(ws, req); } finally { connecting--; }
});

// AND: stagger the resync work rather than doing it all at connect
//   send the shell immediately; deliver missed events lazily from the stream
@end
@senior
Making reconnection cheap is as important as spacing it out: if every reconnect triggers a full state resync, forty thousand clients each pulling a document is a database and bandwidth event on top of the connection storm. Resuming from a sequence id turns that into a few hundred bytes per client. The 1013 close code is worth knowing because well-behaved clients treat it as an explicit instruction to back off further, which converts server-side pressure into client-side spacing rather than a blunt refusal.
@followup
How do you deploy WebSocket servers without causing the same storm?
@answer
Drain gradually rather than restarting everything: take one instance out of rotation, close its connections with a close code that instructs clients to reconnect after a jittered delay, wait for them to redistribute, then move to the next instance. Doing that over several minutes spreads the reconnection load. The alternative — a rolling restart that replaces every instance in ninety seconds — produces exactly the herd you were trying to avoid, and it is a self-inflicted version of this incident on every deploy.
@red
- Immediate reconnection with no backoff or jitter.
- A full state resync on every reconnect.

### Two users edited the same document and one user's changes vanished. Explain.
@short
If the system uses last-write-wins on the whole document, the second save overwrote the first — the changes did not vanish, they were replaced. With a CRDT this cannot happen for text; if it did, the bug is in the integration: an update dropped during a reconnect, or a persistence race, not in the merge algorithm.
@deep
The diagnosis depends on the model. Document-level saving with no version check loses concurrent edits by design. Optimistic concurrency with a version rejects the second save with a conflict. A CRDT merges them.

With a CRDT, "vanished changes" almost always means an update was never delivered or never persisted — a client that edited offline and whose outbox was not durable, a compaction that lost updates, or a reconnect that resumed from the wrong position.
@code ts Distinguishing the causes, and the instrumentation that makes it possible
// A. LAST-WRITE-WINS on the whole document → this is expected behaviour, and wrong

// C. RECONNECT GAP — the client resumed past the updates it had not sent
//    the outbox must be DURABLE (IndexedDB / SQLite), not in memory,
//    and updates must be acknowledged before being removed
const pending = await idb.getAll('pending-updates');
for (const u of pending) { await send(u); await idb.delete('pending-updates', u.id); }  // ack THEN delete

// D. COMPACTION BUG — snapshot written, updates deleted, but the snapshot was
//    computed from an incomplete set. Both must happen in ONE transaction.
@end
@senior
Acknowledging before deleting from the client outbox is the detail that causes case C, and it is the same at-least-once discipline as anywhere else: delete only after the server has confirmed receipt, and accept that a duplicate send is harmless because CRDT updates are idempotent. The compaction case is the other one I would check, because it is a data-loss bug that only manifests weeks later when the document is reloaded. Instrumenting the update path with client id and sequence is what makes any of this diagnosable — without it, "my changes vanished" is unfalsifiable.
@followup
The user was offline for two days. Should their edits still merge?
@answer
With a CRDT, yes — that is the property it provides, and offline edits from two days ago merge cleanly with everything that happened since. The practical limits are storage on the device and whether the server retained enough history, which is why compaction must preserve the ability to merge older updates rather than discarding state the algorithm needs. What will feel surprising to users is the *result*: their two-day-old edits interleave with everyone else's, which may be semantically odd even though it is technically correct — so a "this was edited while you were away" indicator is worth having.
@red
- Blaming the CRDT for losing data without checking delivery and persistence.
- A client outbox held in memory rather than durable storage.

### Redis goes down and your real-time features stop. What should have happened?
@short
Real-time delivery degrades — messages published during the outage are not fanned out — but connections stay up, the application keeps working, and clients detect the gap and resync on recovery. What must not happen is the whole service failing because Redis is unavailable.
@deep
Redis pub/sub is fire-and-forget, so an outage loses messages published during it. That is acceptable for cursors and presence and unacceptable for anything durable, which is why the durable path writes to Postgres and the stream, not only to pub/sub.

The failure to design for is a readiness check that includes Redis, which would take the whole fleet out of rotation for a degraded feature.
@code ts What the degraded mode should look like
// 1. Redis failure must NOT fail readiness — it degrades a feature, it does not
//    make the service unable to serve

  const cache = await redis.ping().then(() => true).catch(() => false);
  if (!db) return res.status(503).json({ db, cache });
  res.status(200).json({ db: true, cache, degraded: !cache });     // ← still serving
});

// 2. Fan-out failure is logged and surfaced, not thrown at the user

    // the DURABLE record already exists in Postgres — clients will resync
  }
}

// 3. Clients detect the gap and resync rather than silently diverging
if (msg.seq > expected) await resync(lastSeq);
// resync reads from POSTGRES, not Redis → works during the outage

// 4. Presence degrades gracefully: show a stale list with an indicator,
//    never show everyone as offline (which alarms users unnecessarily)
@end
@senior
The critical design decision is that the durable record lives in Postgres and Redis is the delivery accelerator, not the source of truth — which means an outage costs freshness rather than data. The readiness-check point is the one I would emphasise most: making readiness depend on Redis converts a degraded feature into a total outage across every instance simultaneously, which is a much worse failure caused by well-intentioned thoroughness. And resync reading from the database rather than the Redis stream is what makes recovery possible during the outage rather than only after it.
@followup

@answer
It is misleading, which is worse than being stale. Showing the last known presence with a subtle "reconnecting" indicator is better, because users interpret "everyone is offline" as a product failure or as colleagues having left. Caching the last presence snapshot locally and displaying it with an appropriate visual state is a small amount of work that substantially changes how the outage is perceived. It is a good example of degraded mode being a design decision rather than whatever falls out of the code.
@red

- Presence collapsing to "everyone offline" during a cache outage.

### Messages are arriving out of order in a chat application. Diagnose.
@short
Ordering is only guaranteed within a single publisher and a single delivery path. If sequence numbers are assigned per instance, or if fan-out crosses instances without a single sequencing authority, ordering is lost. Assign a monotonic sequence per room at one authority and have clients order by it.
@deep
The common mistakes are ordering by the client's timestamp (device clocks are wrong), ordering by arrival (which is what you are trying to fix), and assigning sequence numbers per server instance (which produces per-instance ordering, not per-room).

A single `INCR` per room in Redis, or the natural ordering of a Redis Stream id, gives one authority.
@code ts One sequencing authority per room, ordering on the client
// SERVER — one authority per room, whichever instance handles the message
const seq = await redis.incr(`room:${roomId}:seq`);
const envelope = { seq, id: msgId, userId, body, at: Date.now() };   // server time, not client
await redis.xadd(`stream:room:${roomId}`, 'MAXLEN', '~', 1000, '*', 'e', JSON.stringify(envelope));
await pub.publish(`room:${roomId}`, JSON.stringify(envelope));

// CLIENT — buffer and order; never render by arrival
const buffer = new Map<number, Msg>();
let nextExpected = lastRenderedSeq + 1;

function onMessage(m: Msg) {
  if (m.seq < nextExpected) return;               // duplicate or stale → ignore
  buffer.set(m.seq, m);
  while (buffer.has(nextExpected)) {              // render only contiguous runs
    render(buffer.get(nextExpected)!);
    buffer.delete(nextExpected);
    nextExpected++;
  }
  // a gap that persists means we missed one → fetch it
  if (buffer.size > 0) scheduleGapFill(nextExpected);
}

async function scheduleGapFill(from: number) {
  await sleep(500);                               // give it a moment to arrive naturally
  if (nextExpected !== from) return;              // it arrived; nothing to do
  const missed = await api.get(`/rooms/${roomId}/messages?since=${from - 1}`);
  missed.forEach(onMessage);
}
@end
@senior
The gap-fill with a short delay is the detail that makes this feel right in practice: most out-of-order arrivals resolve within a few hundred milliseconds naturally, so fetching immediately on every gap produces unnecessary requests, while never fetching means a genuinely lost message blocks rendering forever. Buffering with a timed fallback handles both. I would also insist on server-assigned timestamps rather than client ones for display ordering, because device clocks are wrong often enough that messages appear hours in the past — which users notice immediately and report as a bug.
@followup
The gap never fills because the message was genuinely lost. What then?
@answer
After a bounded number of attempts, fall back to a full resync from the server's authoritative history for that room and reset the client's expected sequence — correctness over elegance. I would also record the loss as a metric, because a rising rate of unfillable gaps means something is dropping messages upstream, and that is a defect worth chasing rather than papering over with resyncs. The user-visible behaviour during a resync should be a brief loading state rather than messages silently rearranging.
@red
- Ordering by client-supplied timestamps.
- Rendering messages in arrival order.

### A collaborative document has become 50MB and takes 30 seconds to load. What happened?
@short
Tombstone accumulation with no snapshot compaction. Every deletion leaves a marker the CRDT needs for positional references, so an actively edited document grows with edit history rather than with content length. The fix is periodic compaction into a snapshot plus lazy loading.
@deep
Yjs collapses tombstones when you encode the current state, so a snapshot is dramatically smaller than the accumulated update log. Without compaction, loading means applying tens of thousands of incremental updates.

The secondary cause is embedded content — images or files stored inside the document rather than referenced — which is a modelling problem rather than a CRDT one.
@code ts Compaction, and the loading path afterwards
// COMPACT — collapse the update log into a snapshot, in ONE transaction
async function compact(docId: string) {
  const rows = await db.query(
    `SELECT seq, update FROM doc_updates WHERE doc_id=$1 ORDER BY seq`, [docId]);
  if (rows.rowCount < 500) return;                       // not worth it yet

  const doc = new Y.Doc();
  for (const r of rows.rows) Y.applyUpdate(doc, r.update);
  const snapshot = Y.encodeStateAsUpdate(doc);           // tombstones collapsed here

  await withTransaction(async (tx) => {
    await tx.query(`INSERT INTO doc_snapshots (doc_id, seq, snapshot) VALUES ($1,$2,$3)`,
                   [docId, rows.rows.at(-1)!.seq, snapshot]);
    await tx.query(`DELETE FROM doc_updates WHERE doc_id=$1 AND seq <= $2`,
                   [docId, rows.rows.at(-1)!.seq]);
  });
  metrics.gauge('doc.size_bytes', snapshot.length, { docId });
}

// LOAD — snapshot + the few updates since; large snapshots live in object storage
const snap = await snapshots.latest(docId);              // from S3 if > 1MB
const doc = new Y.Doc();
if (snap) Y.applyUpdate(doc, snap);
for (const u of await updatesAfter(docId, snap?.seq ?? 0)) Y.applyUpdate(doc, u);

// AND: images/files should be REFERENCES, not embedded bytes
// { type: 'image', assetId: 'a_123' }  ← not a base64 blob inside the document
@end
@senior
Embedded binary content is the cause I would check first, because a document containing base64 images grows far faster than any amount of text editing and no amount of compaction helps — the fix is to store assets separately and reference them, which also makes them cacheable by the CDN. On compaction, running it as a background job triggered by update count keeps it off the user-facing path, and monitoring document size as a gauge means you see growth before a user complains about a thirty-second load. I would also cap document size with a warning, because a genuinely unbounded document is a product problem as well as a technical one.
@followup
Compaction lost some updates. How do you prevent that?
@answer
The snapshot insert and the update deletion must be in the same transaction, so a crash between them cannot leave a snapshot that omits updates you have deleted. I would also keep the previous snapshot rather than deleting it immediately, so there is a recovery point, and verify after compaction that the reconstructed document matches what it was before by comparing a hash. Data loss in a compaction job is silent and discovered late, so the verification step is worth its cost.
@red
- Storing binary content inside CRDT documents.
- Compaction that deletes updates outside the snapshot's transaction.

### Users on mobile keep dropping their connection every 30 seconds. Why?
@short
Something between the client and your server is closing idle connections — a NAT gateway, a corporate proxy, or a load balancer idle timeout. The fix is application-level heartbeats more frequent than the shortest timeout in the path, plus correct proxy configuration.
@deep
Mobile carrier NATs commonly drop idle mappings after thirty to sixty seconds, and load balancers default to sixty seconds of idle timeout. TCP keepalive defaults are far too slow to help (typically two hours).

The other mobile-specific cause is the OS suspending the app when it backgrounds, which tears down sockets — that is expected behaviour and must be handled with reconnection rather than prevented.
@code ts Heartbeats, timeouts and detecting dead connections
// SERVER — ping regularly and terminate connections that stop responding
const HEARTBEAT_MS = 20_000;                    // shorter than any timeout in the path
setInterval(() => {
  for (const ws of wss.clients) {
    if (ws.isAlive === false) { ws.terminate(); continue; }   // missed the last pong
    ws.isAlive = false;
    ws.ping();
  }
}, HEARTBEAT_MS);
wss.on('connection', (ws) => {
  ws.isAlive = true;
  ws.on('pong', () => { ws.isAlive = true; });
});

// CLIENT — application-level heartbeat too (some proxies ignore protocol pings)
setInterval(() => ws.readyState === ws.OPEN && ws.send('{"t":"ping"}'), 20_000);

// INFRASTRUCTURE — the timeouts that must be longer than the heartbeat
// ALB: idle_timeout.timeout_seconds = 300
// Nginx:
//   location /ws {
//     proxy_read_timeout 3600s;    ← default 60s kills every idle socket
//     proxy_send_timeout 3600s;
//     proxy_set_header Upgrade $http_upgrade;
//     proxy_set_header Connection "upgrade";
//   }

// MOBILE — backgrounding tears the socket down. Expected. Reconnect on foreground,
// and use push notifications for anything that must reach a backgrounded app.
@end
@senior
Nginx's default `proxy_read_timeout` of sixty seconds is the specific cause I would check first, because it produces exactly this symptom and the configuration looks correct otherwise. The broader point for mobile is that you cannot keep a socket alive through backgrounding, so the architecture must assume disconnection is normal: cheap reconnection with sequence-based resume, and push notifications as the channel for anything that must reach a backgrounded app. Fighting the OS on this is a losing strategy and drains battery.
@followup
Heartbeats keep the connection alive but drain the battery. What is the trade-off?
@answer
Each heartbeat wakes the radio, which is one of the most power-hungry components, so a twenty-second interval on mobile is genuinely costly. The mitigations are lengthening the interval when the app is backgrounded or the user is inactive, closing the connection entirely when backgrounded and relying on push, and aligning heartbeats with other network activity so the radio wakes once rather than repeatedly. For a mobile-first product I would default to closing the socket on background rather than holding it open.
@red
- Relying on TCP keepalive to detect dead connections.
- Default proxy read timeouts on WebSocket routes.

### Presence shows users who left an hour ago. Fix it.
@short
Presence is tracked by explicit join and leave events, and the leave never arrived — because the instance crashed, the connection dropped without a clean close, or the network partitioned. Replace it with TTL-based presence refreshed by heartbeats, so absence of a heartbeat is the signal.
@deep
Explicit-removal presence is fragile because it depends on a message that may never be sent. TTL-based presence is self-healing: entries expire on their own, so a crashed instance's users disappear within the TTL with no cleanup process.

A sorted set scored by last-seen timestamp gives you both membership and staleness handling in one structure.
@code ts From fragile to self-healing
// ❌ FRAGILE — depends on a leave event that may never arrive
ws.on('close', () => redis.srem(`room:${roomId}:online`, userId));
// instance crashes → the set keeps the user forever

// ✅ SELF-HEALING — heartbeat refreshes a score; stale entries are pruned on read
setInterval(async () => {
  const pipe = redis.pipeline();
  for (const [roomId, users] of localRoomUsers)
    for (const userId of users) pipe.zadd(`presence:${roomId}`, Date.now(), userId);
  await pipe.exec();
}, 20_000);

async function onlineIn(roomId: string) {
  const cutoff = Date.now() - 60_000;                       // 3 missed heartbeats
  await redis.zremrangebyscore(`presence:${roomId}`, 0, cutoff);
  return redis.zrange(`presence:${roomId}`, 0, 199);        // cap the returned list
}

// Clean close is still an optimisation — it removes them immediately
ws.on('close', () => redis.zrem(`presence:${roomId}`, userId));
// but correctness no longer DEPENDS on it
@end
@senior
The design principle is that presence should be derived from evidence of liveness rather than maintained as a fact, because the fact can only be wrong. Keeping the explicit removal as an optimisation is right — it makes the common case instant — but correctness must not depend on it. The trade-off to state is the staleness window: a sixty-second TTL means a user who closes their laptop appears online for up to a minute, and shortening it costs more heartbeat traffic. Sixty seconds is usually imperceptible for a collaboration product.
@followup
Users complain that they appear offline while actively typing. Why?
@answer
The heartbeat is failing while the connection appears fine — often because the heartbeat runs on a timer that the browser throttles in a background tab, or because it is sent on a connection that has silently died and not yet been detected. Browsers aggressively throttle timers in hidden tabs, so a twenty-second interval can become a minute. The fix is to treat any inbound activity from the client as a heartbeat, so typing itself refreshes presence, and to use the visibility API to adjust behaviour deliberately rather than being surprised by throttling.
@red
- Presence maintained by explicit add and remove only.
- No cap on the returned member list for large rooms.

### Your fan-out is delivering messages to the wrong rooms. Diagnose.
@short
A subscription bookkeeping bug: an instance is subscribed to a channel it no longer has clients for, or the local room map was not cleaned up on disconnect, so messages are delivered to sockets that have left. Check the subscribe and unsubscribe paths and the socket-to-room mapping.
@deep
The usual causes are: unsubscribing on the last local client leaving but the count being wrong because a disconnect path did not decrement, a socket left in the room set after close, or channel name construction differing between publisher and subscriber.

The security consequence is serious — delivering a message to a user who is not in the room is a data exposure, not just a bug.
@code ts The bookkeeping that must be exactly right
const rooms = new Map<string, Set<WebSocket>>();

async function join(ws: WebSocket, roomId: string) {
  if (!(await acl.canRead(ws.user, roomId))) throw new Forbidden();   // ← authorise EVERY join
  let set = rooms.get(roomId);
  if (!set) { set = new Set(); rooms.set(roomId, set); await sub.subscribe(`room:${roomId}`); }
  set.add(ws);
  (ws.rooms ??= new Set()).add(roomId);
}

async function leave(ws: WebSocket, roomId: string) {
  const set = rooms.get(roomId);
  if (!set) return;
  set.delete(ws);
  ws.rooms?.delete(roomId);
  if (set.size === 0) { rooms.delete(roomId); await sub.unsubscribe(`room:${roomId}`); }
}

// ⚠️ THE BUG IS USUALLY HERE — close must clean up EVERY room, not just the current one
ws.on('close', async () => {
  for (const roomId of ws.rooms ?? []) await leave(ws, roomId);
  ws.rooms?.clear();
});

// DEFENCE IN DEPTH — verify membership at delivery time, not only at subscribe time
sub.on('message', (channel, raw) => {
  const roomId = channel.slice('room:'.length);
  for (const client of rooms.get(roomId) ?? []) {
    if (client.readyState !== client.OPEN) continue;
    if (!client.rooms?.has(roomId)) continue;          // ← belt and braces
    client.send(raw);
  }
});
@end
@senior
The close handler iterating every room the socket joined is where this bug almost always lives, because the code that handles leaving one room is written first and the disconnect path is written later against a simpler mental model. The delivery-time membership check is worth the cost precisely because the failure is a data exposure rather than a glitch — a message delivered to a user who should not see it is a security incident, so a redundant check is justified. I would also add a test that joins several rooms, disconnects abruptly, and asserts the maps and subscriptions are empty.
@followup
How would you detect this in production before a user reports it?
@answer
Invariant checks on a schedule: assert that every subscribed channel has at least one local socket, that every socket in a room map is open, and that every socket's room set matches the room maps. Any divergence is a bug and should alert. I would also log and alert on any delivery to a socket whose membership check fails, since that is the exact moment a message would have gone to the wrong person — turning a silent exposure into a detected one.
@red
- Cleaning up only the current room on disconnect.
- No authorisation check on subscribe.

### Your RAG assistant confidently gives a wrong answer citing a real document. Diagnose.
@short
Separate retrieval failure from generation failure: check whether the correct chunk was retrieved. If it was not, the problem is chunking or ranking. If it was and the model still answered wrongly, the problem is generation — usually a conflicting chunk, an outdated document, or a prompt that permits inference beyond the sources.
@deep
The distinction determines the fix entirely, which is why the trace must record the retrieved chunks, their scores and the exact prompt.

The most common real cause is an outdated document that is still in the index — the model answered correctly from a source that is no longer true, which is a content problem rather than a model problem.
@code ts The trace that makes this diagnosable, and the triage
// LOG EVERY INTERACTION — without this, "the AI was wrong" is unfalsifiable

  conversationId, question, tenantId,
  retrieved: chunks.map(c => ({ id: c.id, docId: c.docId, score: c.score, section: c.section })),
  rerankScores, promptTokens, model: MODEL_VERSION, answer, citations,
});

// TRIAGE
// 1. Was the correct chunk retrieved at all?
//    NO  → retrieval problem: chunking, embeddings, hybrid weighting, or reranking
//    YES → continue
// 2. Was it ranked highly enough to be in the top-k sent to the model?
//    NO  → reranking problem; increase candidates, tune the reranker
//    YES → continue
// 3. Does the retrieved chunk actually support the wrong answer?
//    YES → the SOURCE is wrong or outdated. Content problem. Fix the document,
//          and check for other stale documents in the index.
//    NO  → generation problem: the model inferred beyond its sources.
//          Tighten the prompt, lower temperature, enforce citation checking.

// 4. ADD IT TO THE EVALUATION SET as a regression case, whatever the cause.
@end
@senior
Step three is the one people skip and it is frequently the answer: the model faithfully reported what an outdated policy document said, and the failure is that the document was never removed from the index when it was superseded. That points at a content lifecycle problem — documents need versions, expiry and a removal path — rather than at anything in the AI pipeline. I would also insist that every reported wrong answer becomes a regression case in the evaluation set, because that is the mechanism that stops the same failure recurring after the next change.
@followup
The model cited a document that does not exist. What does that mean?
@answer
The citation was hallucinated, which means citation enforcement is missing. The fix is mechanical: parse the citations from the answer, check every one against the ids actually supplied in the context, and refuse to display an answer whose citations do not resolve. That converts a confidently wrong answer into a graceful failure. It is also a strong signal to check the prompt, because models fabricate citations more often when the context does not contain the answer and the prompt does not give them an explicit way to say so.
@red
- Treating every wrong answer as a prompt-engineering problem.
- No logging of retrieved chunks, so the failure cannot be diagnosed.

### RAG retrieval quality has degraded since you added 100,000 new documents. Why?
@short
More documents means more competition for the top-k slots, so precision drops even though recall of the index is unchanged. The likely causes are near-duplicate documents crowding out the best match, a filter that is now too broad, and an approximate index whose recall degrades at larger scale.
@deep
Three specific effects. Duplicate or near-duplicate content occupies several of the top slots with the same information. The HNSW `ef_search` parameter that was adequate at ten thousand vectors returns worse candidates at a million. And metadata filtering interacts badly with approximate search when the filtered subset is a small fraction of the index.

Reranking becomes more valuable as the corpus grows, because the first-stage retrieval is noisier.
@code sql Diagnose against the golden set, then fix
-- 1. MEASURE — has recall@k actually dropped, or does it just feel worse?
--    Run the golden set before and after. Numbers, not impressions.

-- 2. NEAR-DUPLICATES crowding the top-k

  FROM chunks c1 JOIN chunks c2 ON c1.id < c2.id
 WHERE c1.tenant_id = $1 AND c1.embedding <=> c2.embedding < 0.05
 LIMIT 100;
-- → deduplicate at ingestion, or diversify results (MMR) at retrieval

-- 3. APPROXIMATE INDEX RECALL at the new scale
SET hnsw.ef_search = 200;          -- was 40; higher = better recall, slower
-- rebuild with a higher m if the corpus grew by an order of magnitude
-- verify: compare ANN results against an exact scan on a sample

-- 4. FILTER + ANN interaction: if the tenant filter leaves 0.1% of the index,
--    the ANN search finds global neighbours that the filter then removes
CREATE INDEX chunks_hnsw_t1 ON chunks USING hnsw (embedding vector_cosine_ops)
  WHERE tenant_id = '…';           -- partial index per large tenant

-- 5. RERANK — retrieve 50, rerank to 5. The larger the corpus, the more this matters.
@end
@senior
The filter-plus-approximate-index interaction is the subtle one and it is easy to miss: HNSW finds the nearest neighbours globally, so if one tenant's chunks are a tiny fraction of a million-vector index, the top fifty candidates may be almost entirely other tenants' content that the filter then discards, leaving you with three results instead of fifty. Partial indexes per large tenant, or over-fetching aggressively, is the fix. And I would emphasise measuring against the golden set rather than trusting the impression that quality dropped — sometimes it has not, and the complaint is about a specific document type that was never covered.
@followup
Deduplicating loses genuinely distinct documents with similar content. How do you handle it?
@answer
Do not deduplicate destructively at ingestion for near-duplicates — diversify at retrieval instead, using maximal marginal relevance so the top-k covers distinct information rather than the same point five times. That keeps every document available while preventing crowding. For exact duplicates — the same file uploaded twice — deduplicate on a content hash at ingestion, which is unambiguous and saves storage and embedding cost.
@red
- Judging retrieval quality by impression rather than by measurement.
- Ignoring how metadata filters interact with approximate search.

### The AI feature is timing out for long documents. What are the options?

### Embedding generation is taking hours for a customer's document upload. Fix it.
@short
Batch the embedding calls rather than making one per chunk, parallelise with bounded concurrency respecting the provider's rate limits, deduplicate unchanged chunks by content hash, and make the whole thing an asynchronous job with progress rather than a request.
@deep
The naive implementation is one API call per chunk, sequentially — for a hundred thousand chunks at two hundred milliseconds each that is over five hours of pure round-trip time.

Embedding APIs accept batches, which collapses that by two orders of magnitude, and content hashing means a re-upload of a mostly unchanged document costs almost nothing.
@code ts From hours to minutes
// ❌ one call per chunk, sequential
for (const c of chunks) c.embedding = await embed(c.text);        // ~5 hours for 100k

// ✅ batch + bounded parallelism + dedup by content hash
const BATCH = 100;                                                 // provider limit
const limit = pLimit(8);                                           // respect rate limits

// 1. skip chunks whose content has not changed
const hashes = chunks.map(c => sha256(c.embedText));
const known = await db.embeddingsByHash(hashes);                    // Map<hash, vector>
const todo = chunks.filter((_, i) => !known.has(hashes[i]));
metrics.gauge('embed.reused', chunks.length - todo.length);

// 2. batch the rest
const batches = chunk(todo, BATCH);
await Promise.all(batches.map((b, i) => limit(async () => {
  const vectors = await embedBatch(b.map(c => c.embedText));        // ONE call for 100
  await db.insertEmbeddings(b, vectors);
  await progress.update(jobId, (i + 1) / batches.length);
})));

// 3. handle rate limits properly: respect Retry-After, back off, do not spin
// 4. the whole thing is a JOB with progress, not a request
@end
@senior
Content hashing is the change with the largest practical effect for the recurring case, because customers re-upload documents with small edits constantly, and re-embedding an unchanged chunk is pure waste of both time and money. Combined with batching, a document re-upload goes from hours to seconds. I would also make ingestion resumable from a checkpoint, because a multi-hour job that fails at 90% and restarts from zero is a much worse experience than the original slowness — and it will fail, because provider rate limits and transient errors are normal at that volume.
@followup

@answer
Respect the `Retry-After` header, back off, and reduce concurrency adaptively rather than retrying immediately — spinning against a rate limit makes the window longer. The job pauses and resumes from its checkpoint, and the user sees progress stalled with an explanation rather than a failure. For large customers I would also spread ingestion over time deliberately rather than attempting maximum throughput, since the goal is completion rather than speed, and a job that finishes reliably in two hours beats one that fails after twenty minutes.

Row-level security is the control I would put in place, because it makes the isolation impossible to bypass from application code — a forgotten filter, a raw query, an ad-hoc script all become harmless. Application-level filtering depends on every developer remembering on every code path forever, which is not a control. On the incident side, the interaction log is what determines the scope and therefore the notification obligation, so it must be preserved before anything is redeployed, and its existence is the difference between "we can confirm three conversations were affected" and "we cannot rule out anything".
@followup
The customer asks whether their data was used to train the model. What do you say?
@answer
Answer precisely from the actual configuration: whether the provider's terms include training on API inputs (most enterprise terms exclude it, but this must be verified, not assumed), whether you fine-tuned on customer data, and whether any shared artefacts — few-shot example pools, shared caches — could contain their content. Vagueness here destroys trust faster than a bad answer. If the honest answer is that you do not know, find out before responding, and treat the gap as a finding in its own right.
@red
- Filtering by tenant after retrieval rather than in the query.
- Redeploying before preserving the interaction logs.

### Your streaming AI responses cut off halfway for some users. Diagnose.
@short
Something in the path is buffering or timing out: a proxy without streaming configuration, a load-balancer idle timeout during a long pause between tokens, or a client that lost connectivity. Check the proxy configuration first, then add heartbeats and resumability.
@deep
Streaming is fragile because it depends on every intermediary passing bytes through immediately and tolerating long-lived connections with irregular data. Nginx buffers by default, CDNs may buffer or transform, and load balancers close idle connections.

Resumability is what makes it robust on mobile: persisting tokens as they are generated means a reconnect continues rather than restarting.
@code ts The full set of fixes
// 1. HEADERS — tell every intermediary not to buffer or transform
res.writeHead(200, {
  'Content-Type': 'text/event-stream',
  'Cache-Control': 'no-cache, no-transform',
  'Connection': 'keep-alive',
  'X-Accel-Buffering': 'no',                    // Nginx
});

// 2. NGINX
// location /api/chat/stream {
//   proxy_buffering off;  proxy_cache off;  proxy_read_timeout 3600s;
// }
// ALB: idle_timeout.timeout_seconds = 300  (a long "thinking" pause must not close it)

// 3. HEARTBEATS during silence — a model thinking for 40s looks idle to a proxy
const hb = setInterval(() => res.write(': ping\n\n'), 15_000);
req.on('close', () => { clearInterval(hb); abort.abort(); });

// 4. RESUMABILITY — persist tokens as they are produced
for await (const token of llm.stream(prompt, { signal: abort.signal })) {
  await store.appendToken(conversationId, i, token);
  res.write(`id: ${i}\ndata: ${JSON.stringify({ t: token })}\n\n`);
  i++;
}
// on reconnect, the client sends Last-Event-ID and we replay from there

// 5. DIAGNOSE WHO IS AFFECTED — log completion vs disconnection by
//    connection type, region and client version. "Some users" usually means
//    one network path or one client build.
@end
@senior
`proxy_buffering off` plus `X-Accel-Buffering: no` is the specific fix for the most common cause, and the symptom is distinctive: users see nothing for thirty seconds and then the whole answer at once, which looks like a slow model rather than a proxy problem. Heartbeats during long pauses are the second, because a model that thinks for forty seconds before emitting a token looks idle to a load balancer. And persisting tokens is what makes mobile usable at all — on a mobile network the connection *will* drop, and resuming from token 340 rather than regenerating is both a cost saving and a much better experience.
@followup
Users on one corporate network never see streaming at all. Why?
@answer
Almost certainly a corporate proxy buffering the response — many enterprise proxies inspect and buffer content and cannot be configured by you. The pragmatic mitigation is a fallback: detect that no tokens have arrived within a threshold and switch that client to polling a completion endpoint instead, so they get the answer in one piece rather than nothing. It is a worse experience but a working one, and it is the kind of environmental constraint you cannot fix from your side.
@red
- Streaming through a proxy with default buffering.
- No resumability, so a dropped connection means regenerating from scratch.

### Your evaluation scores are good but users are complaining. What is the disconnect?
@short
The evaluation set does not reflect real usage: it was written by the team rather than derived from actual questions, it measures the wrong thing, or the complaints are about latency, tone or refusals rather than accuracy. Sample real conversations and find out what users are actually experiencing.
@deep
The classic gap is a golden set of well-formed questions when real users ask ambiguous, misspelled, multi-part questions with implicit context from earlier turns.

The second gap is metric choice: accuracy on answerable questions says nothing about the rate of confident wrong answers on unanswerable ones, which is what damages trust.
@code ts Close the gap between evaluation and reality

  FROM (SELECT *, row_number() OVER (PARTITION BY category ORDER BY at DESC) rn
          FROM ai_feedback WHERE rating = 'bad' AND at > now() - interval '30 days') t

// wrong_answer · too_slow · refused_incorrectly · wrong_tone · missing_context

// 2. REBUILD the golden set from REAL questions
//    cluster actual user questions → sample representatively → annotate
//    include the messy ones: typos, multi-part, follow-ups with pronouns
//    include OUT-OF-SCOPE questions — refusal behaviour is part of quality

// 3. MEASURE what users actually care about, not just accuracy
//    • confident-wrong rate  ← the trust killer
//    • incorrect refusal rate ← the frustration driver
//    • p95 time-to-first-token ← "too slow" is usually THIS, not total time
//    • follow-up rephrase rate ← a proxy for "it did not understand me"

// 4. Sample real conversations for human review weekly. Automated metrics
//    catch known dimensions; humans catch the unknown ones.
@end
@senior
The follow-up rephrase rate is the proxy metric I would add first, because it needs no labelling and correlates strongly with dissatisfaction — a user who immediately asks the same thing differently did not get what they wanted, and that is measurable across all traffic rather than on a sample. On latency, "too slow" almost always means time to first token rather than total generation time, so streaming with a fast first token beats a faster total response — which is a good example of the evaluation metric and the user experience diverging in a way that only real feedback reveals.
@followup
How do you build a golden set from real conversations without exposing customer data?
@answer
Sample with consent where the terms allow it, anonymise thoroughly — replace names, identifiers and any embedded personal data — and keep the annotated set in a controlled store with the same access restrictions as production data. Where anonymisation is not sufficient, synthesise questions modelled on real clusters rather than using the originals verbatim: the distribution of intents and phrasings is what matters, not the specific content. And I would be explicit in the privacy policy about how interaction data is used, because a golden set built quietly from customer conversations is a compliance problem waiting to surface.
@red
- A golden set written by the team rather than derived from real usage.
- Measuring accuracy while users are complaining about latency.

### Your vector search latency jumped from 30ms to 800ms. Investigate.
@short
Check whether the index is still being used, whether `ef_search` was raised, whether the table has grown past what fits in memory, and whether a filter is now defeating the approximate index. An HNSW search falling back to a sequential scan is the most common cause of a jump of that size.
@deep
The index can silently stop being used after a large ingestion if statistics are stale, or if a filter makes the planner prefer a scan. It can also become slow if the graph no longer fits in memory and every search hits disk.

A raised `ef_search`, often set during a recall investigation and never reverted, is another frequent cause.
@code sql The diagnostic sequence
-- 1. Is the index still being used?
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, content FROM chunks
 WHERE tenant_id = $2 ORDER BY embedding <=> $1 LIMIT 10;
-- want: "Index Scan using chunks_hnsw"    ← if you see a Seq Scan, that is the problem
-- Buffers: shared read=…  ← large disk reads mean the index no longer fits in cache

-- 2. Did ef_search get raised and never reverted?
SHOW hnsw.ef_search;                       -- 40 → 400 is a 10× latency change

-- 3. Has the table outgrown memory?
SELECT pg_size_pretty(pg_relation_size('chunks_embedding_hnsw_idx'));
SHOW shared_buffers;
-- index larger than the cache → every search reads from disk

-- 4. Is the filter defeating the index?
--    a very selective tenant filter + ANN → the planner may prefer a scan
CREATE INDEX chunks_hnsw_t1 ON chunks USING hnsw (embedding vector_cosine_ops)
  WHERE tenant_id = '…';                   -- partial index for large tenants
ANALYZE chunks;

-- 5. Did the index need rebuilding after a large ingestion?
REINDEX INDEX CONCURRENTLY chunks_embedding_hnsw_idx;

-- 6. Reduce the vector size if memory is the binding constraint
ALTER TABLE chunks ALTER COLUMN embedding TYPE halfvec(1536);   -- half the memory
@end
@senior
The memory constraint is the one that surprises people: HNSW performance depends on the graph being in memory, and once the index exceeds `shared_buffers` plus the OS cache, every search becomes disk-bound and latency degrades by an order of magnitude. That is a capacity decision — more memory, `halfvec` to halve the size, or partial indexes so each search touches a smaller graph. I would also check that `ef_search` has not been left elevated from an earlier tuning session, because that is a one-line cause with a large effect and it is easy to miss.
@followup
Would moving to a dedicated vector database fix this?
@answer
It would move the problem rather than remove it — dedicated vector databases have the same memory-versus-recall trade-off, they just manage it with sharding and tiering. The honest assessment is whether the corpus has genuinely outgrown a single Postgres instance's memory budget, in which case a distributed store is the right answer, or whether the fix is `halfvec`, partial indexes or more memory, which is far cheaper than adding a datastore. I would make that decision with the numbers rather than by reputation.
@red
- Assuming the ANN index is being used without checking the plan.
- Leaving `ef_search` elevated after a tuning exercise.

# SECTION DevOps, Cloud & Security Incidents | Production is on fire. What do you do in the first five minutes?

### Your Docker container restarts every few minutes with no error in the logs. Why?
@short
The kernel OOM killer, almost certainly. It sends SIGKILL, which cannot be caught, so the process gets no chance to log anything. Confirm it in `dmesg` or the orchestrator's stopped reason, then either raise the limit or fix the memory usage — and set the Node heap limit below the container limit so the failure becomes catchable.
@deep
The other candidates are a failing health check causing the orchestrator to restart a healthy process, an unhandled promise rejection terminating Node, and a liveness probe with too short a timeout during startup.

Each has a distinct signature: OOM shows in the kernel log and the exit reason, a failing probe shows in the orchestrator's events, and an unhandled rejection usually leaves a stack trace.
@code bash Distinguish the causes in under a minute
# 1. OOM KILLER — silent, no application logs
dmesg -T | grep -i 'killed process'
kubectl describe pod api-xxx | grep -A3 'Last State'      # → Reason: OOMKilled
aws ecs describe-tasks --tasks … --query 'tasks[0].containers[0].reason'

# 2. HEALTH PROBE killing a healthy process
kubectl describe pod api-xxx | grep -A5 Events
#   "Liveness probe failed" → probe too aggressive, or startup slower than the
#   initialDelaySeconds. Use a startupProbe rather than a long initial delay.

# 3. UNHANDLED REJECTION / uncaught exception
#   Node 15+ exits on unhandled rejection by default. There WILL be a stack.
process.on('unhandledRejection', (r) => { logger.fatal({ r }); process.exit(1); });

# 4. MAKE OOM DIAGNOSABLE — heap limit BELOW the container limit
#   container: 2Gi   →   node --max-old-space-size=1536
#   now you get "JavaScript heap out of memory" WITH A STACK instead of SIGKILL

# 5. RIGHT-SIZE from evidence, not guesswork
kubectl top pod api-xxx --containers          # observe actual usage over a day
@end
@senior
Setting the Node heap limit below the container limit is the change I would make first, because it converts an undiagnosable silent kill into a JavaScript error with a stack trace that usually names the culprit. The liveness-probe case is the other one worth knowing: a probe that fails during a slow startup causes a restart loop where the process never gets far enough to become healthy, and the fix is a startup probe rather than a longer liveness delay. Both are configuration mistakes that look like application bugs.
@followup
Raising the memory limit fixed it. Is that enough?
@answer
Only if the usage is genuinely legitimate — a service that needs more memory than it was allocated. If memory grows without bound, raising the limit only lengthens the interval between restarts and the leak remains, so I would confirm the shape: does the post-GC floor rise over time, or does usage plateau at a higher level? A plateau means right-sizing was correct; a rising floor means a leak, and the heap-snapshot diff is the actual work.
@red
- Not knowing about the OOM killer.
- Raising memory limits without checking whether usage plateaus.

### Nginx starts returning 502 Bad Gateway. Diagnose.
@short
502 means Nginx could not get a valid response from the upstream. The candidates are: the application is down or crashing, it is too slow and Nginx timed out, the upstream address is wrong, or Nginx has exhausted its connections to it. Check the Nginx error log first — it names the reason.
@deep
The error log distinguishes the cases precisely: `connect() failed (111: Connection refused)` means nothing is listening; `upstream timed out` means the application is slow; `no live upstreams` means health checks removed them all.

Under load, a common cause is the upstream keepalive connection pool being too small, so Nginx opens and closes connections constantly and hits ephemeral port limits.
@code bash Read the error log, then act on what it says
tail -100 /var/log/nginx/error.log
#  "connect() failed (111: Connection refused)"  → app not listening (crashed? wrong port?)
#  "upstream timed out (110)"                    → app too slow → proxy_read_timeout,
#                                                   but the REAL fix is the app
#  "no live upstreams"                           → all backends failed health checks
#  "upstream sent too big header"                → increase proxy_buffer_size
#  "worker_connections are not enough"           → raise worker_connections

# Is the app actually up and listening?
ss -tlnp | grep 3000
curl -sS -o /dev/null -w '%{http_code} %{time_total}\n' http://127.0.0.1:3000/healthz

# Upstream keepalive — without this, Nginx opens a NEW connection per request
upstream api {
  server 127.0.0.1:3000;
  keepalive 64;                       # ← reuse connections; big win under load
  keepalive_requests 1000;
  keepalive_timeout 60s;
}
location / {
  proxy_pass http://api;
  proxy_http_version 1.1;             # required for keepalive
  proxy_set_header Connection "";     # required for keepalive
  proxy_connect_timeout 5s;
  proxy_read_timeout 60s;
}
@end
@senior
The `proxy_http_version 1.1` and empty `Connection` header are required for upstream keepalive to work at all, and their absence is a common silent performance problem — Nginx opens a fresh TCP connection per request to the application, which under load causes ephemeral port exhaustion and a flood of TIME_WAIT sockets that presents as intermittent 502s. On timeouts, raising `proxy_read_timeout` masks a slow application rather than fixing it, so I would treat it as a temporary mitigation while addressing the actual latency.
@followup
The 502s are intermittent and correlate with deploys. Why?
@answer
Because the application is being replaced without connection draining: old instances stop accepting while Nginx still routes to them, or new instances receive traffic before they are ready. The fix is a readiness check that Nginx or the load balancer honours, a deliberate delay between failing readiness and closing the listener so routing propagates, and graceful shutdown that finishes in-flight requests. That sequence is what makes a deploy invisible to users rather than a brief error spike.
@red
- Raising timeouts instead of diagnosing why the upstream is slow.
- Upstream keepalive configured without HTTP/1.1 and the Connection header.

### A CI/CD pipeline that worked yesterday fails today with no code change. What do you check?
@short
Something outside your repository changed: a floating dependency version, a mutable base image tag, an expired credential, a runner image update, or a third-party service. Compare the failing job's logs against the last successful run to find which step and which version differ.
@deep
The root cause is almost always non-determinism in the pipeline: `latest` tags, unpinned actions, and dependency ranges resolved at install time rather than from a lockfile.

Expired credentials are the other frequent cause, and they fail in confusing ways — a push rejected as unauthorised rather than as expired.
@code yaml Find it, then remove the non-determinism
# WHAT CHANGED, IF NOT YOUR CODE?
#  • base image `node:22-alpine` moved (mutable tag)
#  • an action `@v4` moved (mutable major tag)
#  • a dependency range resolved to a new version (no lockfile / npm i)
#  • the runner image was updated by the provider
#  • a credential expired
#  • a third-party registry or service had an incident

# MAKE IT DETERMINISTIC
- uses: actions/checkout@8ade135a41bc03ea155e62e844d188df1ea18608   # pin by SHA, not @v4
- run: npm ci --ignore-scripts                                      # lockfile, no install scripts
# FROM node:22-alpine@sha256:abc123…                                # pin the image by DIGEST

# CREDENTIALS: prefer short-lived OIDC over stored secrets — nothing to expire silently
permissions: { id-token: write, contents: read }
- uses: aws-actions/configure-aws-credentials@v4
  with: { role-to-assume: arn:aws:iam::123:role/deploy, aws-region: ap-south-1 }

# DIAGNOSE: diff the two runs
#   which step failed? what versions were resolved? compare `npm ls` output
#   re-run the last successful commit — does it still pass?
#     still passes → your change after all
#     now fails    → external drift confirmed
@end
@senior
Re-running the last known-good commit is the decisive diagnostic and it takes two minutes: if a commit that passed yesterday fails today, the change is external and you can stop looking at your diff. Pinning actions by SHA rather than by tag is the fix people resist as excessive until a supply-chain incident makes it obvious — a mutable tag means someone else can change what your pipeline executes. Digest-pinned base images with a scheduled rebuild give you the same determinism while still getting security updates deliberately rather than accidentally.
@followup
The failure is a flaky test, not an environment change. How do you handle it?
@answer
Quarantine it immediately so it stops blocking merges, open a ticket with an owner, and fix it rather than adding a retry — a retried flaky test trains the team to ignore red builds, which is how a real failure gets dismissed. I would also track the flaky rate as a metric, because a rising rate is a signal about test-suite health that individual quarantines hide. The usual causes are shared state between tests, timing assumptions, and ordering dependence, all of which are fixable.
@red
- Re-running the pipeline until it passes.
- Mutable tags for actions and base images.

### Your AWS bill doubled last month. Find out why.
@short
Use Cost Explorer grouped by service, then by usage type, comparing month over month to find the delta. The usual causes are data transfer through NAT gateways, log and metric volume, storage that nobody expires, an over-provisioned instance change, or a new feature with an unbudgeted cost profile.
@deep
The bill rarely doubles because of one obvious thing — it is usually a specific usage type within a service, which is why grouping by usage type matters more than grouping by service.

NAT gateway data processing is the classic hidden cost: every byte a private-subnet service sends to S3, ECR or the internet is billed per gigabyte, and a VPC gateway endpoint for S3 eliminates it for free.

@end
@senior
The S3 gateway endpoint is the specific item I would check first, because it is free, it eliminates a per-gigabyte charge that many teams pay unknowingly, and the traffic is often large — every container image pull and every S3 read from a private subnet. Beyond the immediate fix, the durable improvement is cost allocation tags plus a dashboard by service and environment, so cost is visible to the engineers who can change it rather than arriving as a finance question a month later. Anomaly alarms on daily spend catch the next one within a day instead of a month.
@followup
The increase is legitimate growth. How do you make it sustainable?
@answer
Shift from absolute cost to unit economics — cost per request, per tenant, per order — because that tells you whether growth is efficient or whether the architecture is scaling worse than linearly. If cost per request is flat, the increase is just success and the conversation is commercial. If it is rising, something is scaling badly and there is engineering work to do. Presenting it that way also makes the discussion with finance far more productive than defending a total.

### A secret was committed to a public repository. What do you do, in order?
@short
Rotate first — assume it is already compromised, because automated scrapers find public repository secrets within minutes. Then check for unauthorised use in the provider's audit logs, then decide whether to rewrite history, then fix the process that allowed it.
@deep
Removing the commit does not help: it remains in the history, in every clone and fork, in GitHub's dangling-commit storage accessible by SHA, and almost certainly in a scraper's database.

The scope assessment matters more than the cleanup: what could this credential access, and was it used?
@code bash The response, in the correct order
# 1. ROTATE IMMEDIATELY. Do not investigate first.
aws secretsmanager rotate-secret --secret-id prod/stripe
aws iam delete-access-key --access-key-id AKIA…      # revoke the old one entirely

# 2. WAS IT USED? The provider's audit log answers this.
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIA… \
  --start-time 2026-08-01
# unfamiliar source IPs, regions or API calls → this is now a breach investigation

# 3. SCOPE: what could that credential reach? (least privilege pays off here)
aws iam list-attached-user-policies --user-name …

# 4. HISTORY REWRITE — only after 1 and 2, and coordinate with the whole team
git filter-repo --path .env --invert-paths
git push --force-with-lease --all
# ⚠️ this does NOT recall forks, clones, caches or scraper copies

# 5. PREVENT — the actual fix
#   pre-commit: gitleaks protect --staged
#   CI:         gitleaks detect --redact --exit-code 1   (over full history)
#   GitHub secret scanning + push protection enabled
#   short-lived OIDC credentials instead of static keys wherever possible
@end
@senior
Rotation before investigation is the ordering that matters, and it is counter-intuitive to engineers who want to understand first — but a public key is being used within minutes, so every minute spent investigating is exposure. The history rewrite is largely theatre and I would say so: it is worth doing for hygiene, but it does not undo the exposure, and treating it as the remediation is a mistake. The real lesson is preventive: push protection and pre-commit scanning make this nearly impossible, and short-lived federated credentials mean there is often nothing durable to leak in the first place.
@followup
The credential was used by someone else. Now what?
@answer
It becomes a security incident with the full process: contain by revoking, preserve the audit evidence before changing anything else, determine what was accessed and whether data was exfiltrated, engage legal and communications because notification obligations may apply, then remediate and review. The scope determination depends entirely on having detailed audit logs, which is why they matter — the difference between "we can confirm these three API calls" and "we cannot rule out anything" is the difference between a contained incident and a disclosure event.
@red
- Removing the commit and considering it resolved.
- Investigating before rotating.

### Someone is scraping your API at 10,000 requests per minute. Respond.
@short
Rate limit at the edge immediately to stop the resource consumption, then identify the pattern — authenticated or not, sequential ids or search queries, distributed or single-source — and apply proportionate controls. Blocking outright often just moves them to a different address.
@deep
The response depends on whether this is abuse, a misconfigured customer integration, or a legitimate high-volume user. The access pattern distinguishes them: sequential id enumeration is scraping, uniform intervals with the same query is usually a broken retry loop, and varied realistic usage at high volume is a large customer.

Blocking is a blunt instrument; progressive friction and cost-based limits are more effective and less likely to affect legitimate users.
@code text Triage and the proportionate response
  IDENTIFY THE PATTERN
   sequential ids (/orders/1, /orders/2…)   → enumeration / scraping
   same query at uniform intervals          → a broken client retry loop (talk to them)
   many IPs, one user agent, one endpoint   → distributed scraping
   varied realistic usage, high volume      → a large legitimate customer

  IMMEDIATE (edge, seconds)
   • WAF rate rule on the source / ASN / user agent
   • per-account rate limit if authenticated

  PROPORTIONATE CONTROLS
   • progressive friction: captcha or delay rather than a hard block
   • cost-based quotas: expensive endpoints consume more budget
   • cursor pagination + non-sequential ids (UUIDv7) → enumeration becomes useless
   • per-endpoint response caps: no ?limit=100000
   • authentication required for bulk read endpoints

  IF AUTHENTICATED
   • contact the customer first — it is usually a misconfiguration, not malice
   • throttle rather than revoke; revoking breaks their production too

  MEASURE THE FALSE-POSITIVE RATE: how many blocked clients later succeed after
  friction? A control that blocks real users to stop a scraper is a bad trade.
@end
@senior
Non-sequential identifiers are the structural fix worth mentioning, because enumeration only works when ids are guessable — moving to UUIDv7 makes scraping by id enumeration impossible regardless of rate limits, and it costs nothing on a new system. For the immediate response, I would contact an authenticated customer before throttling them hard, because in my experience high-volume traffic from a known account is a misconfigured integration far more often than malice, and breaking their production to stop an accident is a poor outcome. And I would track how much of your traffic and cost this represents, because that determines how much effort the response justifies.
@followup
They are scraping data that is public on your website anyway. Does it matter?
@answer
It matters for cost and availability rather than for confidentiality: they are consuming your compute and bandwidth and potentially degrading service for real users. The proportionate response is therefore rate limiting and caching rather than blocking — serving the public content from a CDN makes scraping cheap for you and removes most of the harm. If the aggregate data has commercial value, that becomes a terms-of-service and legal question rather than a technical one, and engineering controls will only ever raise the cost rather than prevent it.
@red
- Hard-blocking an authenticated customer before contacting them.
- Sequential integer ids on publicly addressable resources.

### Your Kubernetes pods are stuck in CrashLoopBackOff. Debug it.
@short
Read the previous container's logs and the pod events — those two almost always contain the answer. The usual causes are a missing configuration or secret, a failed dependency at startup, an OOM kill, or a probe that fails before the application is ready.
@deep
CrashLoopBackOff means the container exits and the kubelet restarts it with increasing delay. The exit reason distinguishes the causes: a non-zero exit with logs is an application error, `OOMKilled` is memory, and a restart with a healthy-looking process points at the liveness probe.

Configuration is the most common: a missing environment variable or secret means the process fails validation at boot, which is correct behaviour but presents as a crash loop.
@code bash The three commands that resolve most of these
# 1. What did the PREVIOUS container say before it died?
kubectl logs api-xxx --previous            # ← the current one may have no logs yet

# 2. What does the orchestrator think happened?
kubectl describe pod api-xxx
#   Last State: Terminated, Reason: OOMKilled       → memory
#   Last State: Terminated, Exit Code: 1            → application error (see logs)
#   Events: "Liveness probe failed"                 → probe too aggressive
#   Events: "secret 'api-secrets' not found"        → configuration
#   Events: "ErrImagePull"                          → registry auth or wrong tag

# 3. Get inside without the entrypoint fighting you
kubectl debug -it api-xxx --image=busybox --target=api

#  OOM                      → right-size, and set --max-old-space-size below the limit

@senior
`kubectl logs --previous` is the command that resolves this fastest and the one people forget, because the current container may not have produced any output yet. The startup-probe point is worth making: a slow-starting application killed by a liveness probe enters a loop where it never gets far enough to become healthy, and lengthening the liveness delay is the wrong fix because it also delays detection of a genuinely wedged process later. A separate startup probe handles the boot period without weakening the ongoing check.
@followup
The application exits because a dependency is not ready. Should it retry or fail?
@answer
Retry with bounded backoff for transient unavailability — a database that is still starting — because failing fast there just produces a crash loop that resolves itself noisily. But fail fast for configuration errors, because retrying a missing environment variable will never succeed and a crash loop is the correct, visible signal. The distinction is whether the condition can plausibly resolve on its own, and encoding that judgement in the startup path is what makes the failure mode informative rather than confusing.
@red
- Reading only the current container's logs.
- Lengthening the liveness probe delay instead of adding a startup probe.

### An engineer accidentally deleted production data. Walk through the response.
@short
Stop further damage, determine exactly what was deleted and when, restore from point-in-time recovery to a separate instance, extract the affected records, and merge them back carefully. Then fix the access control and the process that made it possible — blamelessly.
@deep
The critical decision is not to restore over production, because that would discard everything written since the incident. You restore to a parallel instance, extract, and merge.

Point-in-time recovery is what makes this survivable at all, which is why WAL archiving matters more than snapshot frequency.
@code bash The recovery, step by step
# 0. STOP further damage — disable the code path or revoke the access used
# 1. ESTABLISH SCOPE precisely: what, when, how many rows?
#    audit_log is authoritative if you have it; otherwise the WAL/logs
SELECT * FROM audit_log WHERE action LIKE '%delete%' AND at > now() - interval '2 hours';

# 2. RESTORE TO A SEPARATE INSTANCE at a point just BEFORE the deletion
#    ⚠️ NEVER restore over production — you would lose everything written since
pg_basebackup -D /restore -h primary -X stream
cat > /restore/recovery.signal <<'CONF'
restore_command = 'aws s3 cp s3://acme-wal/%f %p'
recovery_target_time = '2026-08-18 14:22:00+05:30'
recovery_target_action = 'promote'
CONF

# 3. EXTRACT only the affected rows from the restored instance
pg_dump -h restore-host -t orders --data-only \
  --where="id IN (SELECT id FROM deleted_ids)" > recovered.sql

# 4. MERGE into production, into a staging table first, then reconcile
CREATE TABLE orders_recovered (LIKE orders INCLUDING ALL);
-- \i recovered.sql into orders_recovered, then INSERT … ON CONFLICT DO NOTHING
-- verify counts and spot-check before committing

# 5. VERIFY with the business that the data is correct and complete
@end
@senior
Restoring to a separate instance rather than over production is the decision that determines whether this is a recoverable incident or a much larger one, and it is the thing people get wrong under pressure. The other point is the follow-up: the fix is not "be more careful" but structural — least-privilege roles so the application cannot execute a bulk delete, soft deletes so a mistake is reversible, a confirmation requirement for destructive operations in admin tooling, and separate credentials for migrations. And the post-mortem must be genuinely blameless, because the engineer encountered a system that permitted the mistake.
@followup
There was no point-in-time recovery, only nightly snapshots. What are the options?
@answer
Restore the snapshot to a separate instance and recover what you can, accepting the loss of everything between the snapshot and the deletion — and then be honest with the business about that gap. Depending on the data, some may be reconstructible from other sources: event logs, the outbox, a downstream analytics warehouse, or a payment provider's records. The lasting outcome should be enabling WAL archiving, because this incident demonstrates that the recovery point objective was not what anyone assumed, and that is a business-level finding rather than a technical one.
@red
- Restoring over the production database.
- A post-mortem action of "be more careful with delete statements".

### Your load balancer marks all instances unhealthy at once and the site goes down. Why?
@short
A correlated failure: the health check depends on a shared dependency, so when that dependency blipped every instance failed simultaneously. The fix is a readiness check that reflects the ability to serve *some* traffic rather than verifying every dependency.
@deep
This is the failure mode caused by well-intentioned thoroughness. A readiness endpoint that checks the database, the cache, the queue and a third party will fail across the whole fleet when any of them has a moment of unavailability — converting a degraded feature into a total outage.

The second cause is a health check that is too slow or too strict: a check with a one-second timeout against a database that occasionally takes 1.2 seconds will fail intermittently across all instances.
@code ts The correct shape, and what to check on each dependency
// ❌ CORRELATED FAILURE — any one dependency takes the whole fleet out
app.get('/readyz', async (_req, res) => {
  await pool.query('SELECT 1');
  await redis.ping();
  await queue.ping();
  await fetch(THIRD_PARTY_HEALTH);      // ← someone else's outage becomes yours
  res.sendStatus(200);
});

// ✅ ONLY what is required to serve. Everything else is reported, not fatal.
app.get('/readyz', async (_req, res) => {
  const [db, cache] = await Promise.allSettled([
    withTimeout(pool.query('SELECT 1'), 2000),      // generous timeout
    withTimeout(redis.ping(), 500),
  ]);
  const critical = db.status === 'fulfilled';
  if (shuttingDown || !critical)
    return res.status(503).json({ db: critical, cache: cache.status === 'fulfilled' });
  res.status(200).json({ db: true, cache: cache.status === 'fulfilled',
                         degraded: cache.status !== 'fulfilled' });
});

// LB configuration that avoids flapping
//   healthy threshold 2, unhealthy threshold 3, interval 10s, timeout 5s
//   → a single slow response does not remove an instance
@end
@senior
The design rule is that readiness should answer "can I serve traffic?" rather than "is everything perfect?" — and for most services the honest answer is that a Redis outage means slower but working, so it should not remove the instance. I would also raise the recovery dynamic: when every instance is marked unhealthy and then recovers, they all reconnect to the database simultaneously, which can keep the database saturated and prolong the outage. Staggered recovery and connection limits matter for that reason.
@followup
The database genuinely was down. Should the instances have been marked unhealthy?
@answer
It makes no difference to availability — if the database is down, every instance fails whether or not the load balancer knows, so removing them all achieves nothing except returning a load-balancer error instead of an application error. What is better is returning a meaningful 503 from the application with a clear message and a `Retry-After`, so clients back off appropriately and users see something intelligible. Marking instances unhealthy is useful when *some* instances are bad; it is pointless when the shared dependency is the problem.
@red
- Readiness checks that verify every dependency.
- Health check timeouts tighter than normal dependency latency.

### You suspect an active intrusion. What are your first actions?
@short
Contain without destroying evidence: revoke the suspected credentials and sessions, block the vector, and snapshot the affected systems before rebuilding. Then assess scope from the audit logs, engage legal and communications early because notification clocks may already be running, and only then remediate.
@deep
The instinct is to fix immediately, and that destroys the evidence needed to determine what was accessed — which is what determines your legal obligations and what you tell customers.

Containment and evidence preservation are compatible: revoking credentials and blocking an IP does not destroy logs or disk state, whereas redeploying and rotating everything does.
@code text The first hour, in order
  T+0   DECLARE an incident. One commander. A dedicated channel.
        Assume the attacker may be watching — consider an out-of-band channel.

  T+5   CONTAIN (without destroying evidence)
        • revoke the suspected credentials and ALL sessions for affected accounts
        • block the source at the WAF; disable the vector (endpoint, feature flag)
        • do NOT redeploy, do NOT rotate everything, do NOT rebuild yet

  T+15  PRESERVE
        • EBS/disk snapshots of affected instances
        • export the relevant logs to a write-once location BEFORE retention expires
        • capture the current audit trail and access logs

  T+30  ASSESS SCOPE — this determines everything downstream
        • what was ACCESSIBLE vs what was ACCESSED (audit logs answer the second)
        • which customers, which data categories, what volume, over what period

  T+60  ENGAGE legal, communications, leadership. Notification clocks may already
        be running (72 hours under several regimes).

  THEN  REMEDIATE: fix the vulnerability, rotate everything, rebuild from known-good
        images, verify no persistence (new IAM users, keys, scheduled tasks, webhooks)

  LATER Blameless post-mortem, with equal weight on WHY DETECTION TOOK SO LONG.
@end
@senior
The distinction between accessible and accessed is the one that matters commercially and legally, and it depends entirely on having audit logs that record data access rather than only authentication. Being able to say "we can confirm these forty records were read and no others" versus "we cannot rule out access to the entire customer table" is the difference between a contained incident and a company-defining one. That is why I treat audit logging as a control worth building before you need it, and why the post-mortem should weight detection latency as heavily as the vulnerability itself.
@followup
You cannot determine what was accessed. What do you do?
@answer
Assume the worst case and communicate accordingly, because that is the only defensible position — and accept that it will be far more expensive than a precise disclosure would have been. Then make that gap the top follow-up: data-access audit logging, shipped to a separate account with object-lock retention. I would present it to leadership in exactly those terms, because the cost of this incident's uncertainty is the clearest possible business case for the control.
@red
- Rebuilding compromised systems before capturing evidence.
- Delaying legal and communications engagement.

### Design an e-commerce platform.
@short
Clarify scale and scope first, then design around the three hard parts: inventory correctness under concurrency, payment integration with webhook-driven state, and catalogue read performance. Everything else — users, carts, addresses — is straightforward CRUD.
@deep
The requirements I would establish: catalogue size, traffic shape (steady or flash sales), how many orders per day, whether inventory is single-warehouse or multi, and whether it is multi-tenant. Those change the design materially.

The read path and the write path have opposite characteristics — catalogue reads are enormous and cacheable, order writes are modest and must be exactly right — so they get different treatment.
@arch The architecture, with the design decision at each layer
  CDN (catalogue pages, images, static)      ← absorbs the read traffic
   │  s-maxage + stale-while-revalidate, tag-invalidated on price/stock change
  ALB → API (stateless, autoscaled)
   ├── Redis: session, cart, hot product cache, rate limits, stock snapshot (DISPLAY only)
   ├── Postgres (primary): orders, payments, inventory ledger  ← source of truth
   │     read replica: catalogue queries, reporting
   ├── Search (Postgres FTS → OpenSearch when relevance demands it)
   └── SQS/BullMQ → workers: email, invoices, fulfilment, analytics, webhooks
  Payment providers (Stripe / Razorpay / PayPal) → webhooks → order lifecycle

  THE THREE HARD PARTS
   1. inventory: atomic decrement in Postgres, NEVER from a cached value
   2. payments: webhook is authoritative; idempotency at 3 layers; reconciliation
   3. catalogue reads: CDN + Redis; invalidate by tag on price/stock change
@end
@code sql The schema decisions that matter
CREATE TABLE orders (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL, user_id uuid NOT NULL REFERENCES users(id),
  status text NOT NULL CHECK (status IN ('pending','paid','fulfilled','cancelled','refunded')),
  total_minor bigint NOT NULL CHECK (total_minor >= 0),   -- integer minor units, never float
  currency char(3) NOT NULL,
  payment_intent text UNIQUE,                              -- ← makes double-charge impossible
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_id uuid REFERENCES orders(id) ON DELETE CASCADE,
  sku text NOT NULL,
  product_name text NOT NULL,           -- DENORMALISED on purpose: historical accuracy
  unit_price_minor bigint NOT NULL,     -- the price AGREED, not the current price
  qty int NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, sku)
);

-- Inventory: atomic, conditional, no read-then-write anywhere
UPDATE products SET stock = stock - $2 WHERE sku = $1 AND stock >= $2 RETURNING stock;
-- 0 rows → out of stock. Reservations with a TTL during checkout.
@end
@senior
The two decisions I would defend hardest are storing the agreed price on the order item rather than joining to the live product, because otherwise a price change rewrites history and produces customer disputes, and never deciding stock availability from a cached value — the cache can display "in stock" but the decrement must be atomic against Postgres. For flash sales I would add counter sharding and a virtual waiting room, because a single hot SKU row is a serialisation point no amount of scaling fixes.
@followup
How do you handle a flash sale with 50,000 people trying to buy 100 units?
@answer
Admission control rather than brute force: a waiting room that admits users at the rate the system can serve, sharded stock counters so the decrement is not a single hot row, aggressive CDN caching of the product page so the read traffic never reaches the origin, and pre-scaling because autoscaling cannot react in seconds. The checkout path is never load-shed; browsing and recommendations are shed first. The honest framing is that 49,900 people will not get one, so the goal is a fair, fast, comprehensible failure rather than a timeout for everybody.
@red
- Deciding stock availability from a cache.
- Joining to the live product price when displaying a past order.

### Design a payment system.
@short
Design around the fact that the money moves in someone else's system: model your side as a state machine driven by signed webhooks, make every operation idempotent at three layers, and reconcile continuously against the provider's ledger because webhooks are best-effort.
@deep
The requirements to clarify: which methods and geographies, one provider or several, whether you hold funds or only orchestrate, whether subscriptions are in scope, and the compliance posture — which determines whether card data ever touches your infrastructure (it should not).

The architecture is not about throughput at typical volumes; it is about correctness under partial failure.
@arch The lifecycle, with the guarantee at each step
  client ─► POST /payments/intent ─► provider.createIntent(idem = "intent:<orderId>")
                                     INSERT payments(provider, intent_id UNIQUE, 'requested')
                                   ← clientSecret          [amount computed SERVER-side]
  browser ─► provider SDK confirms  [card data never touches us → minimal PCI scope]
  provider ─► POST /webhooks/:provider  (RAW body, signature verified)
              INSERT processed_events(event_id) ON CONFLICT DO NOTHING   [idempotent]
              UPDATE orders SET status='paid' WHERE intent=$1 AND status='pending'
                                                                        [order-independent]
              INSERT outbox('order.paid')                                [atomic side effects]
  worker ─► outbox relay → email, fulfilment, analytics                  [at-least-once]
  recon  ─► every 15 min for pending; daily two-way vs the ledger        [self-healing]

  ADAPTER per provider normalises: signature scheme, event vocabulary, currency units
  → the order state machine has NO provider conditionals
@end
@code ts The three layers of idempotency, which are the whole design
// 1. API — the client's retry does not create a second payment
const key = req.header('Idempotency-Key');           // stored with the response

// 2. PROVIDER — derived from the ORDER, so every retry converges on one intent
await stripe.paymentIntents.create({ … }, { idempotencyKey: `intent:${order.id}` });

// 3. DATABASE — the backstop no logic error can bypass
ALTER TABLE payments ADD CONSTRAINT u UNIQUE (provider, intent_id);
CREATE UNIQUE INDEX one_success_per_order ON payments (order_id) WHERE status='succeeded';

// + guarded transitions so out-of-order webhooks cannot regress state
// + reconciliation in BOTH directions against the provider's ledger
@end
@senior
The claim I would make is that at typical volumes this is not a scaling problem at all — it is a correctness problem under partial failure, and the engineering effort belongs in idempotency, guarded transitions and reconciliation rather than in throughput. I would also insist on the adapter boundary from the start, because provider differences (signature schemes, status vocabularies, minor units versus decimal strings) otherwise leak into the order logic and adding a third provider becomes a rewrite. And routing between providers must be runtime configuration, so a provider outage is a flag flip rather than a deploy.
@followup
How do you handle a provider outage during checkout?
@answer
Route to the alternative provider via a runtime flag — which is the operational reason multi-provider support is worth its complexity — while leaving in-flight intents at the original provider to complete via their webhooks rather than cancelling them. Users starting a new checkout use the healthy provider. If there is no alternative, fail clearly and quickly with a suggestion to try another method, rather than leaving users on a spinner, and use a status banner so support is not overwhelmed.
@red
- Treating the client redirect as confirmation.
- Provider-specific logic in the order state machine.

### Design a real-time chat system.
@short
Stateless WebSocket servers holding only their own connections, Redis pub/sub for cross-instance fan-out, Redis Streams for replay after reconnect, and Postgres as the durable history. Ordering is per-room via a single sequencing authority; delivery is at-least-once with client-side deduplication.
@deep
Requirements to clarify: direct messages or large rooms, message history retention, delivery receipts and read state, media, and whether messages must survive a datacentre failure. Large rooms change the fan-out design qualitatively.

The design centres on making reconnection cheap, because on mobile it happens constantly.
@arch The topology and the guarantees
  clients ──► ALB (connection affinity) ──► ws-1 … ws-N   (stateless: own sockets only)
                                              │
                                    Redis: pub/sub  (fan-out, fire-and-forget)
                                           streams  (replay, MAXLEN ~1000 per room)
                                           presence:<room>  ZSET scored by last-seen
                                              │
                                        Postgres (durable history, partitioned by month)
                                              │
                                        Push (APNs/FCM) for backgrounded clients

  GUARANTEES
   ordering   per room, via INCR room:<id>:seq at a single authority
   delivery   at-least-once; client dedupes on message id, detects gaps on seq
   presence   TTL + heartbeat → self-healing when an instance dies
   resume     client sends lastSeq → replay from the stream → full reload if trimmed
@end
@code ts Send, fan out, persist, and resume
async function send(roomId: string, userId: string, body: string, clientMsgId: string) {
  if (!(await acl.canWrite(userId, roomId))) throw new Forbidden();

  const seq = await redis.incr(`room:${roomId}:seq`);          // single authority
  const msg = { id: clientMsgId, seq, roomId, userId, body, at: Date.now() };

  await db.query(                                              // durable, idempotent
    `INSERT INTO messages (id, room_id, user_id, seq, body, at)
     VALUES ($1,$2,$3,$4,$5,to_timestamp($6/1000.0))
     ON CONFLICT (id) DO NOTHING`, [clientMsgId, roomId, userId, seq, body, msg.at]);

  const payload = JSON.stringify(msg);
  await redis.xadd(`stream:room:${roomId}`, 'MAXLEN', '~', 1000, '*', 'e', payload);
  await redis.publish(`room:${roomId}`, payload);              // fan out to all instances
  await push.notifyOffline(roomId, userId, msg);               // backgrounded clients
  return msg;
}

// RESUME after reconnect
const missed = await redis.xrange(`stream:room:${roomId}`, `(${lastSeq}`, '+', 'COUNT', 500);
// if the stream has trimmed past lastSeq → { truncated: true } → full reload from Postgres
@end
@senior
The client-generated message id is the detail that makes the whole thing work: it gives idempotent inserts, lets the sender's optimistic UI reconcile with the server's copy, and makes retries harmless. The other design decision is push notifications as the channel for backgrounded mobile clients — you cannot hold a WebSocket through backgrounding, and attempting to is a battery and reliability disaster. For very large rooms I would change the model entirely: broadcast-oriented fan-out with presence as a count rather than a member list, because per-socket delivery does not scale to a hundred thousand participants.
@followup
How do you implement read receipts without overwhelming the system?
@answer
Store a single high-water mark per user per room — the highest sequence they have read — rather than a receipt per message, which turns an O(users × messages) problem into O(users × rooms). Update it with debouncing on the client and batch the writes. For group chats, showing "read by 12" from those markers is cheap, while showing exactly who read each message is expensive and rarely worth it. That modelling choice is the difference between a feature that scales and one that dominates your write volume.
@red
- Room membership held in process memory.
- Read receipts stored per message per user.

### Design a collaborative document editor.
@short
CRDT on the client for convergence, a dumb relay server that never parses the document, Redis for fan-out and replay, and Postgres plus object storage for persistence with periodic snapshot compaction. Awareness data is ephemeral and separate from the document.
@deep
The requirements that shape it: how many concurrent editors per document, whether offline editing is required, whether version history and comments are needed, and document size limits.

Choosing a CRDT over operational transformation is the decision that makes the server stateless and therefore trivially scalable.
@arch Document, awareness and persistence as three separate paths
  clients (Yjs doc + IndexedDB) ──► ws-1 … ws-N   (relay only; never parses the doc)
        │                              │
        │  DOCUMENT updates            ├─ redis pub/sub  doc:<id>          (fan-out)
        │  (opaque binary)             ├─ redis stream   stream:doc:<id>   (replay)
        │                              └─ Postgres doc_updates → compacted → snapshots
        │                                     (large snapshots → S3, key in the row)
        │
        └─ AWARENESS (cursors, selections, presence)
             separate ephemeral channel · throttled ≤20/s · NEVER persisted
             droppable under load

  OFFLINE: IndexedDB persistence → edits merge on reconnect (the CRDT property)
  COMPACTION: when updates > 500, encodeStateAsUpdate → snapshot, delete collapsed
              updates — in ONE transaction
@end
@code ts The relay, and the compaction that keeps documents loadable
// SERVER — it does not know what a document is
ws.on('message', async (data: Buffer) => {
  if (!(await acl.canWrite(ws.user, docId))) return;          // authorise every update
  await redis.publish(`doc:${docId}`, data);
  await redis.xadd(`stream:doc:${docId}`, 'MAXLEN', '~', 5000, '*', 'u', data);
  debouncedPersist(docId, data);                              // batch writes to Postgres
});

// COMPACTION — atomic, or you lose updates
async function compact(docId: string) {
  const updates = await db.updatesFor(docId);
  const doc = new Y.Doc();
  for (const u of updates) Y.applyUpdate(doc, u.update);
  const snapshot = Y.encodeStateAsUpdate(doc);                // tombstones collapsed
  await withTransaction(async (tx) => {
    await tx.insertSnapshot(docId, updates.at(-1)!.seq, snapshot);
    await tx.deleteUpdatesUpTo(docId, updates.at(-1)!.seq);
  });
}
@end
@senior
Keeping awareness data entirely out of the document is the design decision that prevents unbounded growth — cursors persisted into a CRDT would bloat every document forever with information that is worthless a second later. Compaction is the other essential, and it must be transactional. On the honest limitations, I would say that CRDT convergence guarantees a consistent result rather than a semantically correct one: concurrent edits to the same sentence interleave in a way that may be nonsense, so structured fields need last-write-wins with an indicator or explicit locking rather than merging.
@followup
How do you add comments and suggestions?
@answer
As separate entities anchored to positions in the document using relative positions, which Yjs provides and which survive concurrent edits — an absolute character offset would break as soon as someone types above it. Comments live in their own table with their own permissions and lifecycle, not inside the CRDT, so they can be queried, notified on, and resolved without touching the document. Suggestions, where the edit is proposed rather than applied, are modelled as a separate change set that is applied to the document on acceptance.
@red
- Persisting cursor and presence data into the document.
- A server that parses and validates document content.

### Design an AI assistant over a customer's private documents.

### Design a food delivery backend.
@short

@followup
How do you calculate accurate ETAs?

### Design a URL shortener.
@short
Read-dominated by several orders of magnitude, so the design is a fast key-value lookup behind aggressive caching, with the interesting parts being id generation, redirect latency, analytics without slowing the redirect, and abuse prevention.
@deep
The estimates shape everything: at a hundred million redirects a day that is roughly twelve hundred per second average and perhaps five thousand at peak, with a read-to-write ratio around a hundred to one. The storage is small — a hundred million rows is a few gigabytes — so it fits comfortably in one database with a cache in front.

The design decision people get wrong is doing analytics synchronously in the redirect path.
@arch Read path optimised; everything else asynchronous
  GET /abc123
    → CDN (short TTL, or bypass if analytics must be exact)
    → API: Redis GET url:abc123          ~1ms, >99% hit rate
        miss → Postgres SELECT → populate Redis (negative cache for unknown codes)
    → 301/302 redirect                    ← respond FIRST
    → fire-and-forget: XADD to a Redis stream for analytics   ← never blocks the redirect

  Analytics worker: stream → batch → ClickHouse / Postgres rollups
  Creation: POST /shorten → generate code → INSERT → warm the cache

  301 (permanent, browser caches → fewer requests, LESS analytics)
  302 (temporary, every visit hits us → full analytics, more load)
  ← this is a product decision, not a technical one
@end

  if (cached === 'NX') return res.status(404).send();            // negative cache
  let target = cached;
  if (!target) {

    if (!row) { await redis.set(`url:${req.params.code}`, 'NX', 'EX', 300); return res.sendStatus(404); }
    target = row.target;
    await redis.set(`url:${req.params.code}`, target, 'EX', 86400);

  res.redirect(302, target);                                      // respond FIRST
  void redis.xadd('clicks', '*', 'code', req.params.code,         // then record

@senior
Responding before recording the click is the design point — analytics must never be in the latency path of a redirect, and losing a small fraction of click events during an incident is an acceptable trade for a redirect that never fails because the analytics store is down. Negative caching is the other essential, because unknown codes are a large share of traffic (scanners, expired links) and without it every one is a database query. On id generation, sequential codes are enumerable, which means anyone can walk your entire link database — a real privacy issue for a shortener where links are often semi-private.
@followup
How do you prevent your shortener being used for phishing?
@answer
Check submitted URLs against a reputation service such as Safe Browsing at creation and periodically afterwards, since a benign URL can become malicious later. Rate limit creation per account and per address, require authentication for bulk creation, and show an interstitial warning for links flagged as suspicious rather than blocking outright. A takedown process and an abuse reporting path are also necessary, because you will be used for phishing and the question is how quickly you respond.
@red
- Recording analytics synchronously in the redirect path.
- Sequential, enumerable short codes.

### Design a notification system.
@short
A single service that accepts notification requests, resolves user preferences and channels, deduplicates, renders per channel, and delivers with retries and per-channel rate limits. The design is about preferences, deduplication and delivery guarantees rather than throughput.
@deep
Requirements: which channels (push, email, SMS, in-app, webhook), whether notifications are transactional or marketing (which changes consent requirements), quiet hours, and per-user preferences.

The hard parts are deduplication across channels and events, respecting preferences and regulations, and delivering reliably without spamming.
@arch One pipeline, many channels
  producers (services) ──► notify.send({ userId, type, payload, dedupeKey })
                              │
                        ┌─────▼─────────────────────────────────────────┐
                        │ RESOLVE  preferences · channels · locale ·     │
                        │          quiet hours · consent (marketing)     │
                        │ DEDUPE   on dedupeKey within a window          │
                        │ RENDER   per channel from one template source  │
                        │ SCHEDULE respect quiet hours / digest windows  │
                        └─────┬─────────────────────────────────────────┘
                              │ per-channel queues (isolated: SMS failure
                              │ must not delay push)
        ┌──────────┬──────────┼──────────┬─────────────┐
        ▼          ▼          ▼          ▼             ▼
      push       email       SMS      in-app        webhook
     (FCM/APNs) (SES)     (provider)  (Postgres)   (customer endpoints)
        └────────── delivery status → attempts table → retries/DLQ ──────┘

  ALWAYS: an in-app record even when push/email fail — the user can still find it
@end
@code ts Preferences, dedup and channel selection
export async function send(n: NotificationRequest) {
  // 1. dedupe — one logical event, not one per producer retry
  const first = await db.query(
    `INSERT INTO notification_dedupe (key, user_id, expires_at)
     VALUES ($1,$2, now() + interval '1 hour') ON CONFLICT (key) DO NOTHING RETURNING key`,
    [n.dedupeKey, n.userId]);
  if (!first.rowCount) return { skipped: 'duplicate' };

  const prefs = await prefs.for(n.userId, n.type);
  if (!prefs.enabled) return { skipped: 'opted_out' };

  // 2. transactional notifications ignore quiet hours; marketing does not
  const when = n.priority === 'transactional' ? new Date() : nextAllowed(prefs.quietHours);

  // 3. always write the in-app record — the durable, always-available channel
  await db.notifications.insert({ ...n, readAt: null });

  // 4. queue each enabled channel separately
  for (const ch of prefs.channels) {
    await queues[ch].add(n.type, { ...n, locale: prefs.locale }, {
      jobId: `${n.dedupeKey}:${ch}`,           // per-channel idempotency
      delay: Math.max(0, +when - Date.now()),
      attempts: 5, backoff: { type: 'exponential', delay: 5000 },
    });
  }
}
@end
@senior
Per-channel queues rather than one shared queue is the isolation decision that matters: an SMS provider outage with retries should not delay push notifications, and a marketing burst should not sit in front of a password reset. The in-app record written regardless of channel delivery is the other design point — it means a failed push is a degraded experience rather than a lost notification, and it gives support something to point at. Deduplication on a logical key rather than per producer request is what prevents the classic "user got the same alert four times because four services published the event".
@followup
How do you implement digests — one email instead of twenty?
@answer
Accumulate notifications marked as digestible into a per-user bucket with a scheduled flush at the user's chosen frequency, rather than sending each one. Transactional notifications bypass the digest entirely. The nuance is what to do when the digest window arrives and there is one item — sending a digest of one is worse than sending the individual notification, so the flush should adapt. And the digest must render coherently, which means templates designed for aggregation rather than concatenating individual messages.
@red
- One shared queue for all channels.
- Deduplication per producer request rather than per logical event.

### Design an analytics platform.
@short
High-volume append-only ingestion with a durable buffer, batch loading into a columnar store, pre-aggregated rollups for dashboards, and a clear separation between raw events and derived metrics. The hard parts are ingestion reliability, late-arriving data and query cost.

Requirements: events per second, query latency expectations, retention, and whether the numbers must be exact or can be approximate. Approximation changes the design substantially — sketches and sampling make otherwise impossible queries cheap.

The mistake to avoid is querying raw events for dashboards, which does not survive growth.

@senior
Approximate distinct counts via HyperLogLog are the trade I would make explicitly and early: exact unique-user counts over billions of events require enormous memory, while a sketch gives you roughly 1% error in a few kilobytes and merges across time ranges. Most product analytics questions tolerate that, and the ones that do not — billing, compliance — should be computed differently and separately. The other decision is the trailing recompute window for late data, because mobile clients batch events and can deliver them hours later, and a rollup that never revisits yesterday will silently undercount.
@followup
A customer wants to query two years of raw events ad hoc.
@answer
Tier the storage: recent data in the columnar store for interactive queries, older data in object storage queried through a slower path, with a clear expectation that historical queries are asynchronous — submit, get notified, download. I would also rate limit and cost-cap ad-hoc queries per tenant, because one unbounded scan can consume the cluster and degrade everyone's dashboards. Making the cost visible to the customer, and offering pre-aggregated alternatives, usually resolves the requirement without the full scan.
@red
- Dashboards querying raw events.
- No durable buffer between ingestion and storage.

### Design an IoT / geolocation telemetry platform.
@short
Optimise for write throughput and storage economics: batched ingestion, time-partitioned append-only storage, aggressive downsampling and retention tiers, and a query path that reads rollups rather than raw points. Device connectivity is unreliable by assumption.
@deep
The arithmetic drives everything: ten thousand devices sending a point every five seconds is two thousand writes per second and roughly 170 million rows a day. Storage and write amplification, not query complexity, are the binding constraints.

Devices are intermittently connected, so the ingestion contract must be idempotent batches with client-generated ids.
@arch Ingest, store, downsample, serve
  DEVICES (offline-first: local queue, batched upload, client-generated UUIDs)
     │  POST /v1/telemetry/batch  (≤200 points, gzip, Idempotency-Key)

     │  → durable buffer (Kinesis/Kafka/Redis Stream)
     ▼
  WRITER — COPY into a partitioned table in batches (never row-by-row)

  STORAGE TIERS
     hot   7d   full resolution   · btree (device_id, at DESC) + BRIN(at)
     warm  90d  1 point/minute    · downsampled by a scheduled job
     cold  ∞    hourly rollups    · + raw archived to S3 (Parquet), partition DROPped
     │
  QUERY — dashboards read ROLLUPS; raw access is a job, not a request

@end

@senior
The downsampling policy is the design decision that determines whether this is affordable, and it must be made before launch rather than retrofitted onto a table with a billion rows. Full resolution for a week, one point per minute for ninety days, and hourly rollups forever satisfies every product requirement I have seen while reducing storage by orders of magnitude. On the device side, batching is not only a server-side optimisation — it is what makes the battery last a working day, and battery is the requirement that determines whether users keep the app installed. Those two constraints, storage economics and battery, shape the whole system more than any throughput concern.
@followup
Devices come back online after a week offline and upload everything at once.
@answer
The ingestion path must handle it without falling over: rate limit per device, accept bounded batches, and let the durable buffer absorb the spike so the writer drains at a sustainable rate. The device should also downsample its own backlog — a week of five-second points is rarely needed at full resolution, so uploading one point per minute for older data is both acceptable and far cheaper. Idempotent inserts mean a partially uploaded backlog can be retried safely, which matters because that upload will be interrupted.
@red
- Row-by-row inserts for telemetry.
- No downsampling or retention policy defined before launch.

### Design a multi-tenant SaaS platform.
@short
Shared schema with a `tenant_id` on every table, isolation enforced by row-level security rather than by developer discipline, per-tenant quotas and concurrency limits for fairness, and a documented path to move a large customer onto dedicated infrastructure.
@deep
The three isolation models — shared schema, schema per tenant, database per tenant — trade operational cost against isolation strength. Shared schema scales to thousands of tenants; database per tenant becomes painful past a few dozen because migrations, pools and monitoring all multiply.

Noisy neighbours are the operational reality: one tenant's export or import can starve everyone unless there are per-tenant resource limits, not just request rate limits.

    routing layer resolves tenant → connection, so the move is operational
@end

@followup
A customer requires their data to stay in their country.

### Design a distributed job scheduler.
@short
Schedules in the database, workers claiming due jobs with `FOR UPDATE SKIP LOCKED`, idempotency keyed on the scheduled occurrence rather than the attempt, timezone-aware next-run computation, and observability on lag and failures. No single scheduler instance and no cron in every replica.
@deep
The requirements: how many jobs, what granularity, whether jobs can overlap, timezone handling, and whether missed occurrences should be caught up or skipped.

Timezone correctness is the part that causes real incidents twice a year, when daylight-saving transitions make a daily job run twice or not at all.
@arch Claim-based scheduling with no leader
  scheduled_jobs(id, name, cron, timezone, next_run_at, claimed_by, claimed_at, enabled)
  job_runs(job_id, occurrence, status, started_at, finished_at, error)
      PRIMARY KEY (job_id, occurrence)     ← idempotency on the SCHEDULED time

  every worker, every few seconds:
    ┌──────────────────────────────────────────────────────────────┐
    │ WITH due AS (SELECT id FROM scheduled_jobs                    │
    │   WHERE enabled AND next_run_at <= now()                      │
    │     AND (claimed_at IS NULL OR claimed_at < now()-'5 min')    │
    │   ORDER BY next_run_at FOR UPDATE SKIP LOCKED LIMIT 5)        │
    │ UPDATE … SET claimed_by=$worker, claimed_at=now() …           │
    └──────────────────────────────────────────────────────────────┘
      → INSERT job_runs(job_id, occurrence) ON CONFLICT DO NOTHING
          0 rows → already ran → skip (crash-safe idempotency)
      → execute → record outcome → compute next_run_at IN THE JOB'S TIMEZONE

  OBSERVABILITY: schedule lag (now − next_run_at for due jobs), failure rate,
                 duration percentiles, jobs that have not run when expected
@end
@code ts The parts that are easy to get wrong
// TIMEZONE — compute the next occurrence in the job's zone, not in UTC
import { CronExpressionParser } from 'cron-parser';
const next = CronExpressionParser.parse(job.cron, { tz: job.timezone, currentDate: now }).next().toDate();
// "every day at 02:30 Asia/Kolkata" across a DST transition elsewhere stays correct

// OVERLAP POLICY — declared per job, not assumed

if (job.overlapPolicy === 'queue') { /* allow; the handler must tolerate it */ }

// CATCH-UP POLICY — what if we were down for 3 hours?

else for (const occ of missedOccurrences(job, now)) await enqueue(job, occ);  // backfill

// TIMEOUT — a job that hangs must not hold its claim forever
await withTimeout(run(job), job.timeoutMs ?? 15 * 60_000);
@end
@senior
The catch-up policy is the design question people forget and it produces surprising incidents: after a three-hour outage, does the hourly billing job run three times or once? Both are defensible and the wrong one is expensive — three duplicate billing runs versus a gap in the record. Making it an explicit per-job property forces the decision. The stale-claim reclaim window is the other detail: it must be longer than the longest legitimate run, or a slow job gets claimed a second time while still executing, which is exactly the duplicate execution the design exists to prevent.
@followup
How is this different from just using cron?
@answer
It is highly available with no single point of failure, it survives worker crashes because claims expire and are reclaimed, it records what ran and when so failures are visible, it handles timezones correctly, and the schedule lives in your deployment pipeline as code rather than on one machine's crontab. Cron on one host gives you none of that, and cron in every replica runs everything N times. The cost is a small amount of implementation, which is why I would use a library or a managed scheduler if one fits rather than building it from scratch.
@red
- A designated scheduler instance as a single point of failure.
- Computing the next run in UTC for a timezone-specific schedule.

### Design a feature flag service.
@short
Flags evaluated locally from a cached ruleset so evaluation never blocks a request, streamed updates for near-instant propagation, deterministic bucketing so a user's assignment is stable, safe defaults on failure, and an audit trail of every change.
@deep
The requirements: evaluation latency (must be sub-millisecond, so local), propagation delay (seconds is fine), targeting complexity (percentage, attributes, segments), and whether flags drive experiments, which adds assignment logging and statistics.

The critical property is that a flag service outage must not break the application — evaluation falls back to defaults.
@arch Local evaluation, streamed configuration
  ADMIN UI ──► flag service ──► ruleset store (Postgres) + audit log
                     │
                     ├── SSE/WebSocket stream of ruleset changes
                     └── polling fallback (every 30s) for clients that lose the stream
                                │
                     ┌──────────▼──────────────────────────────────────┐
                     │ SDK in each app instance                         │
                     │  • holds the full ruleset in memory              │
                     │  • evaluates LOCALLY: 0 network calls, <1µs      │
                     │  • falls back to compiled-in defaults on failure │
                     │  • emits evaluation events (sampled) for         │
                     │    experiment analysis                           │
                     └──────────────────────────────────────────────────┘

  BUCKETING: hash(flagKey + unitId) % 10000 → deterministic, stable,
             independent per flag (so 10% of one flag ≠ the same 10% of another)
@end
@code ts Evaluation, bucketing and the safety properties
type Rule =
  | { type: 'default'; value: unknown }
  | { type: 'segment'; segmentId: string; value: unknown }
  | { type: 'percentage'; pct: number; value: unknown; unit: 'user' | 'tenant' | 'session' };

export function evaluate(flag: Flag, ctx: EvalContext, fallback: unknown): unknown {
  try {
    for (const rule of flag.rules) {                       // first match wins
      if (rule.type === 'segment' && matches(segments[rule.segmentId], ctx)) return rule.value;
      if (rule.type === 'percentage') {
        const unitId = ctx[rule.unit + 'Id'];
        if (!unitId) continue;
        // hash includes the FLAG KEY → independent buckets per flag
        const bucket = xxhash32(`${flag.key}:${unitId}`) % 10_000;
        if (bucket < rule.pct * 100) return rule.value;
      }
      if (rule.type === 'default') return rule.value;
    }
    return fallback;
  } catch {
    return fallback;                                       // ← NEVER throw from evaluation
  }
}

// Audit every change: who, what, when, why — flags change production behaviour
// INSERT INTO flag_audit (flag_key, actor, before, after, reason, at)
@end
@senior
Including the flag key in the bucketing hash is the detail that prevents a subtle experimental error: without it, every 10% rollout selects the same 10% of users, so those users experience every new feature and your results are biased. Independent buckets per flag fix that. The other property I would insist on is that evaluation never throws and never blocks — a flag service outage should silently fall back to compiled-in defaults, because a flag system that can take down the application is worse than no flag system. And flags need a lifecycle: an owner and an expiry, or you accumulate untested combinations.
@followup
How do you clean up stale flags?
@answer
Record an owner and an intended removal date at creation, report on flags past their date, and track evaluation data so you can show that a flag has returned the same value for every user for months — which makes removal an easy decision. I would also fail the build or raise a warning when the flag count crosses a threshold, because the real cost is combinatorial: every live flag doubles the number of code paths that theoretically exist and none of the combinations are tested.
@red
- Network calls in the flag evaluation path.
- Percentage bucketing that selects the same users for every flag.

### Design a file storage and sharing service.
@short
Presigned direct uploads to object storage so bytes never pass through your API, metadata and permissions in Postgres, content-addressed keys for deduplication and cacheability, signed URLs with short expiry for downloads, and asynchronous processing for previews and scanning.
@deep
Requirements: file sizes, sharing model (link, user, team), whether versioning is needed, retention, and whether content must be scanned or encrypted with customer-managed keys.

The design principle is that your API handles metadata and authorisation while object storage handles bytes — mixing them is what makes file services expensive and fragile.
@arch Bytes to storage, metadata to your API
  UPLOAD
   client → POST /files/sign  → presigned POST (content-type + size constrained, 60s)
   client → PUT direct to S3  (multipart for large files; resumable per part)
   client → POST /files/commit { key, checksum } → metadata row, ownership, ACL
   S3 event → queue → worker: verify magic bytes, scan, thumbnail, extract text,
                              strip EXIF, transcode → derived assets

  DOWNLOAD
   GET /files/:id → authorise → 302 to a signed URL (5 min)
   or CloudFront signed URL/cookie for private CDN delivery
   ⚠ serve user content from a SEPARATE domain with Content-Disposition: attachment
     and a restrictive CSP → an uploaded SVG cannot execute in your origin

  STORAGE
   key = sha256(content) → deduplication + immutable + cache-forever
   lifecycle: Intelligent-Tiering; expire temp/derived assets; versioning if required
@end
@code ts The upload path, with the constraints that matter
app.post('/files/sign', authenticate, async (req, res) => {
  const { contentType, sizeBytes, filename } = SignSchema.parse(req.body);
  if (!ALLOWED_TYPES.has(contentType)) return res.status(422).json({ error: 'UNSUPPORTED_TYPE' });
  if (sizeBytes > quotaRemaining(req.user)) return res.status(413).json({ error: 'QUOTA_EXCEEDED' });

  const key = `u/${req.user.tenantId}/${randomUUID()}`;        // never the client's filename
  const post = await createPresignedPost(s3, {
    Bucket: env.UPLOAD_BUCKET, Key: key, Expires: 60,
    Conditions: [['content-length-range', 1, sizeBytes],
                 ['eq', '$Content-Type', contentType]],        // ← enforced by S3, not by us
  });
  await db.files.insertPending({ key, ownerId: req.user.id, filename, contentType, sizeBytes });
  res.json({ ...post, key });

// Worker: NEVER trust the declared content type
const type = await fileTypeFromBuffer(head);
if (!ALLOWED_TYPES.has(type?.mime ?? '')) return quarantine(key, 'TYPE_MISMATCH');
await sharp(buf, { limitInputPixels: 50_000_000 })             // decompression-bomb guard
  .withMetadata({ exif: undefined })                            // strip GPS/EXIF
  .resize({ width: 1200 }).avif({ quality: 60 }).toBuffer();

@senior
Serving user-uploaded content from a separate domain is the security decision I would insist on, because an uploaded SVG or HTML file served from your own origin is stored cross-site scripting against every user — and `Content-Disposition: attachment` plus a restrictive CSP on that domain contains it. The presigned-upload pattern is the other one: it removes upload bandwidth, memory and timeout risk from your servers entirely, which is what makes the service scale for free. And the magic-byte check in the worker matters because the declared content type is client-supplied and therefore meaningless.
@followup
How do you handle very large files and resumable uploads?
@answer
S3 multipart upload with presigned part URLs: the client uploads parts in parallel, retries only the failed parts, and calls your API to complete — which gives resumability and parallelism without any bytes touching your servers. The client tracks completed parts locally so an interrupted upload resumes rather than restarting. I would use an established client library rather than implementing the part bookkeeping by hand, because the edge cases around part ordering and completion are fiddly and already solved.
@red
- Proxying file bytes through the API.
- Serving user uploads from the application's own origin.

### Design a search system for a product catalogue.
@short
Start with Postgres full-text search plus trigram matching for typo tolerance, moving to a dedicated search engine when relevance tuning, faceting or scale demand it. The design work is in the indexing pipeline, the ranking signals and keeping the index synchronised with the source of truth.
@deep
Requirements: catalogue size, how often it changes, whether faceted navigation is needed, personalisation, and how important relevance quality is commercially.

The synchronisation pipeline is the part that causes ongoing pain with a separate search engine — the index drifts from the database, and reindexing is a recurring operational task.
@arch Postgres first; a search engine when justified
  STAGE 1 — Postgres (up to a few million documents, good enough relevance)
    tsvector generated column with setweight(title A, brand B, description C)
    + pg_trgm for typo tolerance and prefix
    + websearch_to_tsquery for user input (handles quotes and negation safely)
    ✔ one datastore, transactional consistency, no sync pipeline

  STAGE 2 — dedicated engine (OpenSearch / Typesense) when you need:
    faceting, complex relevance tuning, synonyms, per-locale analysers, scale
    ┌─ Postgres (source of truth) ─┐
    │  CDC / outbox ──► indexer ──►│ search index
    └──────────────────────────────┘
    ⚠ the sync pipeline is the new operational surface: lag, drift, reindexing
    → full reindex must be a routine, tested operation with an alias swap

  RANKING SIGNALS (worth more than the engine choice)
    text relevance · availability · popularity/conversion · margin · recency
    → blended score, tuned against click and conversion data
@end
@code sql The Postgres implementation, done properly
ALTER TABLE products ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(name,'')),        'A') ||
    setweight(to_tsvector('english', coalesce(brand,'')),       'B') ||
    setweight(to_tsvector('english', coalesce(description,'')), 'C')
  ) STORED;
CREATE INDEX ON products USING gin (search);
CREATE INDEX ON products USING gin (name gin_trgm_ops);        -- typo tolerance

SELECT id, name,
       ts_rank_cd(search, q) * 1.0
     + (CASE WHEN in_stock THEN 0.3 ELSE 0 END)                 -- availability matters
     + log(1 + purchases_30d) * 0.1                             -- popularity
       AS score
  FROM products, websearch_to_tsquery('english', $1) q
 WHERE tenant_id = $2 AND search @@ q
 ORDER BY score DESC LIMIT 20;

-- Typo fallback when the exact search returns nothing
SELECT id, name, similarity(name, $1) s FROM products
 WHERE tenant_id = $2 AND name % $1 ORDER BY s DESC LIMIT 10;
@end
@senior
The ranking signals matter more than the engine: boosting in-stock items and popular products typically improves conversion more than any relevance-algorithm change, because a perfectly relevant out-of-stock result is worthless. I would tune those weights against click and conversion data rather than by intuition. On the engine choice, I would stay in Postgres well past the point where people assume a dedicated engine is necessary, because the synchronisation pipeline is a permanent operational cost — and when I do move, the full reindex with an alias swap must be a routine tested operation, since you will need it more often than you expect.
@followup
How do you measure whether search is working?
@answer
Behavioural metrics rather than relevance scores: the rate of searches with no results, the rate of searches followed by no click, click-through position (are users finding it in the top three or scrolling), search-to-purchase conversion, and query reformulation rate. Zero-result queries are the highest-value list because they name exactly what the catalogue or the synonym set is missing. Those metrics also let you A/B test ranking changes against revenue rather than against an offline relevance judgement.
@red
- Introducing a search engine before Postgres search was measurably insufficient.
- Ranking on text relevance alone, ignoring availability and popularity.

### Design a webhook delivery service.
@short
Accept events, persist them, deliver with signed requests and exponential backoff, record every attempt, expose a delivery log with manual redelivery, and disable endpoints that fail persistently. The design is about reliability and customer self-service rather than throughput.
@deep
Requirements: how many customers and endpoints, ordering guarantees (usually none, or per-entity), retention of the delivery log, and whether customers can filter which events they receive.

The customer experience is the differentiator: a delivery log they can inspect turns your most common support ticket into self-service.
@arch Event in, signed delivery out, with full observability
  producers → events table (append-only, per-tenant)
       │
       ▼
  fan-out to subscriptions (endpoint × event-type filter)
       │
       ▼  delivery queue, per-endpoint rate limited (a slow customer must not
       │  delay everyone else)
  DELIVER  POST endpoint.url
             X-Signature: t=<ts>,v1=<hmac(secret, ts + '.' + body)>   ← ts inside the sig
             X-Event-Id  (consumer dedupes on this)
             X-Delivery-Attempt
             timeout 5s
       │
       ├─ 2xx           → mark delivered
       ├─ 4xx (not 429) → permanent → do not retry; record and surface to the customer
       └─ 5xx / 429 / timeout → retry: 10s, 30s, 2m, 10m, 1h, 6h, 24h (with jitter)
                                after N failures → auto-disable + notify the customer

  CUSTOMER UI: delivery log (request, response, timing) + REDELIVER button
  → this removes the single most common support ticket
@end
@code ts Signing, delivery and endpoint health
export async function deliver(sub: Subscription, event: Event, attempt = 0) {
  const body = JSON.stringify({ id: event.id, type: event.type,
                                created: event.createdAt, data: event.payload });
  const ts = Math.floor(Date.now() / 1000);
  const sig = crypto.createHmac('sha256', sub.secret).update(`${ts}.${body}`).digest('hex');

  const started = Date.now();
  const res = await fetch(sub.url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json',
               'X-Acme-Signature': `t=${ts},v1=${sig}`,
               'X-Acme-Event-Id': event.id,
               'X-Acme-Delivery-Attempt': String(attempt + 1) },
    body, signal: AbortSignal.timeout(5_000),
  }).catch(() => null);

  await db.deliveries.record({ subscriptionId: sub.id, eventId: event.id, attempt,
    status: res?.status ?? 0, durationMs: Date.now() - started,
    responseBody: (await res?.text().catch(() => ''))?.slice(0, 2000) });   // for the customer UI

  if (res && res.status >= 200 && res.status < 300) return;
  if (res && res.status >= 400 && res.status < 500 && res.status !== 429) return;  // permanent
  if (attempt < 7) return schedule(sub, event, attempt + 1, backoff(attempt));
  await disableAndNotify(sub, 'persistent_failures');
}
@end
@senior
Including the timestamp inside the signed payload is what prevents replay — a captured body and signature can otherwise be resent indefinitely, and consumers should reject signatures older than a few minutes. The delivery log with a redeliver button is the feature that pays for itself: "we did not receive the webhook" is the most common integration support ticket, and giving customers the request, the response and a retry button converts it into self-service. And per-endpoint rate limiting is the isolation that stops one slow customer's endpoint from consuming your delivery capacity.
@followup
A customer needs events in order. Can you guarantee that?
@answer
Only per entity, and only by serialising delivery for that entity — hold subsequent events for an aggregate until the previous one is acknowledged. That reduces throughput and means one stuck event blocks the rest for that entity, so it is a deliberate trade. The better answer for most cases is to include a sequence number and a timestamp and let the consumer order or ignore stale events, which is more robust and does not couple your delivery throughput to their processing speed. I would document that ordering is not guaranteed by default.
@red
- Webhooks without signatures or with the timestamp outside the signature.
- No delivery log, so every failure becomes a support ticket.

### Design a subscription billing system.
@short
Let the payment provider own recurring schedules and dunning, mirror the subscription state locally from webhooks, derive entitlements from that local state so access checks are fast and offline-tolerant, and model proration, grace periods and plan changes as explicit policies.
@deep
Requirements: plan structure (seats, usage, tiers), billing frequency, proration policy, trials, taxes, and which regions — Indian recurring mandates behave quite differently from card subscriptions.

The design mistake is checking entitlement against the provider's API on every request, which is slow and couples availability.
@arch Provider owns money; you own entitlement
  provider (Stripe Billing / Razorpay subscriptions)
    schedules · retries · dunning · proration · invoices
        │  webhooks: subscription.created/updated/deleted,
        │            invoice.paid, invoice.payment_failed, trial_will_end
        ▼
  subscriptions table (mirror)
    plan · status(trialing|active|past_due|canceled|unpaid)
    current_period_end · cancel_at_period_end · grace_until
        │
        ▼
  ENTITLEMENT — derived locally, fast, no network call
    active|trialing  → until current_period_end
    past_due         → until grace_until (OUR policy, not the provider's)
    canceled         → until current_period_end if cancel_at_period_end

  USAGE-BASED: meter locally (idempotent, per period) → report to the provider
               at period close; reconcile reported vs metered
@end
@code ts Entitlement and the plan-change policy
export function hasAccess(sub: Subscription, feature: Feature, now = new Date()): boolean {
  if (!PLANS[sub.plan].features.includes(feature)) return false;
  if (sub.status === 'active' || sub.status === 'trialing') return sub.currentPeriodEnd > now;
  if (sub.status === 'past_due') return !!sub.graceUntil && sub.graceUntil > now;  // don't cut off instantly
  return false;
}

// Plan change: money to the provider, entitlement policy to us
async function changePlan(sub: Subscription, newPlan: string) {
  await provider.updateSubscription(sub.id, { plan: newPlan, proration_behavior: 'create_prorations' });
  // UPGRADE   → entitlement effective immediately
  // DOWNGRADE → effective at period end (they paid for what they have)
  const effective = PLANS[newPlan].rank > PLANS[sub.plan].rank ? 'now' : 'period_end';
  await db.subscriptions.scheduleChange(sub.id, newPlan, effective);
  await audit.record({ action: 'plan.change', from: sub.plan, to: newPlan, effective });
}

// Failed payment → grace, not immediate cutoff
case 'invoice.payment_failed':
  await db.subscriptions.update(sub.id, { status: 'past_due',
    graceUntil: addDays(new Date(), 7) });          // spans the provider's own retries
  await notify.paymentFailed(sub.tenantId, invoice.attemptCount);
@end
@senior
The grace period is a commercial decision with real revenue impact: cutting access off on the first failed renewal loses customers whose card simply expired, while a seven-day window spanning the provider's dunning retries recovers a large share of them. The other decision is deriving entitlement locally rather than querying the provider — it makes access checks fast and means a provider outage does not lock every customer out of your product. And upgrade-immediately, downgrade-at-period-end is the policy that matches customer expectations and avoids refund requests.
@followup
How do you handle usage-based billing accurately?
@answer
Meter idempotently on your side — every usage event has a unique id and is counted once per billing period — then report aggregates to the provider at period close, and reconcile what you reported against what you metered. The failure to avoid is double counting from retries, which is why the idempotency key on usage events matters as much as on payments. I would also expose usage to the customer in real time, because a bill that is larger than expected without visibility is the most common cause of a billing dispute.
@red
- Checking entitlement against the provider's API per request.
- Cutting off access on the first failed payment.

### Design a ticket booking system with limited inventory.
@short
The whole design is concurrency control: atomic conditional decrements, time-limited reservations so users can complete payment without losing their seat, a waiting room for demand spikes, and idempotent booking so a retry cannot double-book.
@deep
Requirements: total inventory, expected peak concurrency, whether specific seats or general admission, and how long a user gets to pay.

The reservation model is the part that determines the user experience: without it, users lose their seat during payment, which is both frustrating and a conversion killer.
@arch Reservation, payment, confirmation — with timeouts at each step
  1. BROWSE          availability from Redis (approximate, display only)
  2. RESERVE         atomic decrement in Postgres + reservation row with a 10-minute TTL
                     → the user now has a guaranteed seat and time to pay
  3. PAY             payment intent; webhook confirms
  4. CONFIRM         reservation → booking (guarded transition, idempotent)
  5. EXPIRE          a job releases reservations that were never paid (checking the
                     provider FIRST, so a paid-but-unconfirmed reservation is not released)

  HIGH DEMAND
   • virtual waiting room: admit at the rate the system can serve, with a position
   • sharded counters so one hot event is not a single serialisation point
   • CDN for the event page; the reserve endpoint is never load-shed
   • pre-scale; autoscaling cannot react to a 20:00 on-sale
@end
@code sql The concurrency-critical operations
-- RESERVE: atomic, conditional, no read-then-write anywhere
WITH taken AS (
  UPDATE events SET available = available - $2
   WHERE id = $1 AND available >= $2
  RETURNING id
)
INSERT INTO reservations (id, event_id, user_id, qty, expires_at, status)
SELECT gen_random_uuid(), $1, $3, $2, now() + interval '10 minutes', 'held'
  FROM taken
RETURNING id, expires_at;
-- 0 rows → sold out. No race is possible.

-- CONFIRM: guarded and idempotent
UPDATE reservations SET status='confirmed', confirmed_at=now()
 WHERE id=$1 AND status='held' AND expires_at > now()
RETURNING id;

-- EXPIRE: release, but CHECK THE PROVIDER FIRST
--   a reservation whose payment succeeded must be confirmed, not released
UPDATE events e SET available = available + r.qty
  FROM reservations r
 WHERE r.event_id = e.id AND r.status='held' AND r.expires_at < now()
RETURNING r.id;

-- SHARDED counters for a single very hot event
UPDATE inventory_shards SET available = available - 1
 WHERE event_id=$1 AND shard=$2 AND available >= 1;      -- shard = hash(userId) % 16
@end
@senior
Checking the payment provider before releasing an expired reservation is the detail that prevents the worst outcome — releasing a seat the customer has actually paid for, which means refunding them and disappointing them simultaneously. Counter sharding is the other one: for a single high-demand event, one inventory row is a serialisation point that no amount of application scaling fixes, and sixteen shard rows let sixteen transactions proceed in parallel at the cost of a slightly more complex "find a shard with capacity" path. The waiting room is what turns a total failure under extreme demand into an orderly queue.
@followup
Users complain that tickets appear available then fail at checkout.
@answer
That is the gap between the cached availability shown while browsing and the authoritative count at reservation, and it is unavoidable at high demand — the honest fix is to shorten the gap and communicate clearly. Reserve as early in the flow as possible so the guarantee happens before the user invests effort, show availability as approximate ("limited availability" rather than "3 left"), and make the failure message explain what happened with an immediate path to try again. Pretending the cached number is authoritative is what makes the experience feel broken.
@red
- Deciding availability from a cached count.
- Expiring reservations without checking whether payment succeeded.

### Design a social feed.
@short
Choose between fan-out on write (precomputed per-user timelines, fast reads, expensive for high-follower accounts) and fan-out on read (compute at request time, cheap writes, slower reads). Most systems use a hybrid: precompute for normal accounts, merge in celebrity posts at read time.
@deep
The estimates decide it: with a million users averaging two hundred follows and a few posts a day, fan-out on write is millions of timeline inserts per day but reads become a single range scan. A user with ten million followers makes a single post a ten-million-row write, which is why the hybrid exists.

Ranking adds another dimension — a chronological feed is a simple merge, while a ranked feed needs scoring at read time or a precomputed score.
@arch Hybrid fan-out
  POST created
    author follower_count < 10,000  → FAN OUT ON WRITE
        insert into each follower's timeline (Redis LIST/ZSET, capped at ~500)
        done asynchronously via a queue; failures retried
    author follower_count ≥ 10,000  → NO fan-out (celebrity)
        the post lives only in the author's own timeline

  READ /feed
    1. read the precomputed timeline from Redis (fast, capped)
    2. merge in recent posts from the CELEBRITY accounts this user follows
       (a small list; their posts are cached and shared across all followers)
    3. rank (chronological, or score = recency × affinity × engagement)
    4. paginate by cursor (post id + timestamp), never OFFSET

  Postgres holds the durable posts and follow graph; Redis holds timelines.
  Timeline rebuild (from Postgres) must be a routine operation — Redis is a cache.
@end
@code ts Fan-out and the read-time merge
// WRITE
async function publish(post: Post) {
  await db.posts.insert(post);                                   // durable first
  const followers = await graph.followerCount(post.authorId);

  if (followers < CELEBRITY_THRESHOLD) {
    await queue.add('fanout', { postId: post.id, authorId: post.authorId },
                    { jobId: `fanout:${post.id}` });             // idempotent
  }
  await redis.zadd(`timeline:author:${post.authorId}`, post.createdAt, post.id);
}

// FAN-OUT worker — batched, capped
for (const batch of chunk(await graph.followers(authorId), 1000)) {
  const pipe = redis.pipeline();
  for (const f of batch) {
    pipe.zadd(`timeline:${f}`, post.createdAt, post.id);
    pipe.zremrangebyrank(`timeline:${f}`, 0, -501);              // keep the newest 500
  }
  await pipe.exec();
}

// READ — precomputed + celebrity merge
const own = await redis.zrevrange(`timeline:${userId}`, 0, 49, 'WITHSCORES');
const celebs = await graph.celebrityFollows(userId);             // small list
const celebPosts = await Promise.all(celebs.map(c =>
  redis.zrevrange(`timeline:author:${c}`, 0, 9)));               // cached, SHARED
const merged = rank(dedupe([...own, ...celebPosts.flat()])).slice(0, 50);
@end
@senior
The hybrid exists because neither pure model works across the whole follower distribution, and being able to explain that trade-off with the arithmetic is what the question is testing. The other design point is that Redis timelines must be a cache, not the source of truth — a rebuild from Postgres has to be a routine, tested operation, because Redis will be lost at some point and a feed that cannot be reconstructed is a data-loss incident. Capping timelines at a few hundred entries is what keeps memory bounded; older content is served from the durable store on deep pagination.
@followup
How do you handle a user who follows 5,000 accounts?
@answer
Their precomputed timeline still works because fan-out cost is per follower, not per follow — the expense is on the publishing side. What does become expensive is the celebrity merge if many of those follows are large accounts, so I would cap the number of celebrity sources merged per request and rely on ranking to choose which. For extreme cases, precomputing a merged timeline for that user on a schedule is a reasonable escape hatch, treating them as their own small fan-out target.
@red
- Fan-out on write for accounts with millions of followers.
- Treating Redis timelines as the source of truth.

### Design an audit and compliance logging system.
@short
Append-only, tamper-evident storage in an account the application cannot administer, capturing who did what to which record, when, from where and why. Retention matched to the obligation, access to the logs itself audited, and query performance good enough that investigations are minutes rather than days.
@deep
Requirements: which regulations apply, retention periods, whether tamper evidence must be cryptographic, and who may read the logs.

The properties that matter are completeness (written at a layer nothing bypasses), immutability (the application cannot alter it), and usefulness (enough context to reconstruct events).
@arch Write path the application cannot bypass or alter
  application writes ─┐
  database triggers ──┼─► audit_log (Postgres, partitioned by month)
  admin tooling ──────┘     app role: INSERT + SELECT only. No UPDATE/DELETE/TRUNCATE.
                              │
                              ├─► streamed to S3 (Object Lock, WORM) in a SEPARATE

                              └─► hash chain: each record includes the hash of the
                                  previous → tamper-evident; periodic anchor published

  QUERY: partitioned + indexed on (actor, at), (resource, at), (tenant, at)
         older partitions → S3 + Athena for long-retention queries

  ACCESS TO THE AUDIT LOG IS ITSELF AUDITED. Reading it is a privileged action.
@end

@senior
Making the reason mandatory for privileged actions is what turns an audit log from a compliance artefact into an investigative tool — "support user X refunded order Y" answers what, and "because of ticket #4821" answers why, which is the question actually asked during a dispute or an investigation. The separate-account WORM copy is the other essential: an attacker with application access should not be able to erase the record of what they did, and that requires the destination to be outside the application's blast radius. And I would flag that audit logs contain personal data, so they inherit the same retention and erasure obligations as the source records.
@followup
How do you query two years of audit data quickly?
@answer
Partition by month with indexes on the dimensions investigations actually use — actor, resource and tenant, each with time — and keep recent partitions in Postgres while older ones are exported to S3 in a columnar format and queried with Athena. That gives interactive performance for the recent window, which covers most investigations, and acceptable performance for historical queries at a fraction of the storage cost. Retention becomes a partition drop plus an S3 lifecycle rule rather than a slow delete.
@red
- Audit logs the application role can update or delete.
- Logging the action without the actor or the reason.

### Design a rate limiting service.
@short
Atomic counting in a shared store with a token bucket or sliding window, a local pre-filter to avoid a round trip for obvious floods, cost-based consumption so expensive endpoints consume more budget, and an explicit failure policy per endpoint. Standard headers so clients can self-pace.
@deep
Requirements: how many distinct keys, acceptable accuracy, latency budget (this sits on every request), and whether limits are global or per region.

The design tension is between accuracy and latency: an exact global limit requires a shared store round trip, while a local approximation is faster and lets slightly more through.
@arch Two tiers: local approximation, shared authority
  request
    │
    ├─ LOCAL pre-filter (per instance, in-memory, ~0ms)
    │    obvious floods rejected without touching Redis
    │    approximate: each instance sees only its own share
    │
    ├─ SHARED authority (Redis + Lua, ~1ms)
    │    exact across instances; token bucket allows bursts
    │
    └─ EDGE (WAF/CDN) volumetric limits absorb attacks before they cost compute

  KEYS (layered, not one)
    per IP        coarse, catches floods, unfair to shared NATs
    per account   the meaningful limit for authenticated traffic
    per target    e.g. login attempts against ONE account, regardless of source
    per endpoint  cost-weighted: /ai/generate consumes 50, /orders consumes 1

  RESPONSE
    429 + Retry-After + RateLimit-Limit/Remaining/Reset on EVERY response
    → well-behaved clients pace themselves instead of hammering until blocked
@end
@code lua Atomic token bucket — one round trip, no race
-- KEYS[1] = bucket   ARGV: capacity, refillPerSec, nowMs, cost
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local cap, rate, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now
tokens = math.min(cap, tokens + ((now - ts) / 1000) * rate)
if tokens < cost then
  redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
  redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
  return { 0, math.ceil((cost - tokens) / rate), math.floor(tokens) }
end
redis.call('HMSET', KEYS[1], 'tokens', tokens - cost, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000))
return { 1, 0, math.floor(tokens - cost) }
@end
@senior
The failure policy per endpoint is the decision I would highlight: if the store is unavailable, a login endpoint should fail open because locking every user out is worse than the attack it prevents, while an expensive AI endpoint should fail closed because unbounded spend is worse than a brief outage. Those are opposite answers to the same technical failure, decided by business impact rather than by a general principle. The local pre-filter is the other practical detail — under an actual flood, it stops the rate limiter itself becoming the bottleneck, which is an ironic but real failure mode.
@followup
How do you handle limits that must be exact for billing?
@answer
Do not use the rate limiter for billing — meter separately, durably and idempotently, and reconcile. Rate limiting is a protection mechanism with approximate semantics under failure, while billing needs an auditable count. Conflating them means either your protection is too slow or your billing is wrong. I would meter usage events with unique ids into a durable store, aggregate per period, and reconcile against what was reported to the payment provider.
@red
- Read-then-write rate limiting from application code.
- One failure policy for every endpoint.

### Design a video upload and streaming platform.
@short
Direct multipart uploads to object storage, an asynchronous transcoding pipeline producing adaptive bitrate renditions, HLS or DASH delivery through a CDN, and signed URLs for access control. The API never touches video bytes.
@deep
Requirements: video length and volume, whether live streaming is in scope, DRM requirements, and how quickly a video must be watchable after upload.

Transcoding is the expensive part and it dominates both cost and latency, so the pipeline design — parallelism, rendition ladder, and whether to publish progressively — is the core of the answer.
@arch Upload, transcode, deliver
  UPLOAD    client → presigned multipart URLs → S3 (resumable, parallel parts)
            → POST /videos/complete → metadata row, status='uploaded'

  TRANSCODE S3 event → queue → MediaConvert / ffmpeg workers
            ladder: 240p 400k · 480p 1M · 720p 2.5M · 1080p 5M (+ AV1 where supported)
            → HLS segments + master playlist → S3 (immutable, content-hashed)
            → thumbnails, sprite sheet, duration, captions (ASR)
            → publish LOWEST rendition first → watchable in seconds, not minutes
            → status='ready' → notify

  DELIVER   CDN (CloudFront) with signed URLs/cookies for private content
            player requests the master playlist → adapts bitrate to bandwidth
            segments cached aggressively (immutable); playlists short TTL

  COST      transcoding dominates. Transcode ON DEMAND for the long tail
            (first request triggers it) rather than eagerly for everything.
@end
@code ts The pipeline, with the details that matter

@senior
Publishing the lowest rendition first is the design decision that most improves the experience: a video becomes watchable in seconds rather than after the full ladder completes, and quality improves as higher renditions land. On cost, transcoding the long tail on demand rather than eagerly is significant — most uploaded videos are watched rarely or never, and eagerly producing five renditions for all of them is a large, avoidable bill. The general principle, as with file storage, is that the API handles metadata and authorisation while specialised infrastructure handles the bytes.
@followup
How do you prevent people downloading and redistributing videos?
@answer
Honestly, you cannot fully — anything the player can decode can be captured. What you can do is raise the cost: signed URLs with short expiry so links cannot be shared, segment-level access control, and DRM (Widevine, FairPlay) where the content value justifies the complexity and licensing cost. I would set expectations explicitly rather than promising prevention, and focus on the controls that matter commercially: stopping casual link sharing and making bulk scraping expensive.
@red
- Uploading video through the application API.
- Eagerly transcoding every rendition for every upload.

### Design the backend for an offline-first mobile application.
@short
An API designed around idempotent batch writes and delta reads: client-generated ids, an idempotency key per batch, tombstones for deletions, a server-issued sync cursor, and an explicit conflict policy per entity. The client owns a local database and a durable outbox.
@deep
Requirements: which entities sync, expected offline duration, conflict semantics per entity, and data volume per device.

The two details that cause the most bugs are missing tombstones — so deletions never propagate — and using the device clock as the sync cursor, which silently skips records when clocks are wrong.
@arch The sync contract
  PUSH   POST /v1/sync/push          Idempotency-Key: <batch uuid>
         { mutations: [ { id: <client uuid>, entity, op, payload, baseVersion } ] }
         → per mutation: applied | conflict(current) | rejected(reason)
         → dedupe on the client uuid (unique index) → replay is a no-op

  PULL   GET /v1/sync/pull?since=<SERVER cursor>&limit=500
         → { changed: [...], deleted: [ {id, deletedAt} ], nextCursor, hasMore }
         ← tombstones are REQUIRED; absence ≠ unchanged
         ← the cursor is SERVER-issued; never the device clock

  CONFLICT POLICY, declared per entity:
    telemetry      append-only, dedupe on uuid       → no conflict possible
    user profile   last-write-wins on server time    → lossy, logged, acceptable
    shared notes   CRDT                              → merges
    order status   server authoritative              → client cannot write

  INDEXES: (tenant_id, updated_at) on every syncable table, and the same on tombstones
@end
@code ts The push handler, with per-mutation outcomes
app.post('/v1/sync/push', authenticate, async (req, res) => {
  const { mutations } = PushSchema.parse(req.body);
  const results: MutationResult[] = [];

  for (const m of mutations) {
    const outcome = await withTransaction(async (tx) => {
      const first = await tx.query(
        `INSERT INTO applied_mutations (id, user_id) VALUES ($1,$2)
         ON CONFLICT DO NOTHING RETURNING id`, [m.id, req.user.id]);
      if (!first.rowCount) return { id: m.id, status: 'duplicate' };      // idempotent replay

      const current = await repo.find(m.entity, m.payload.id, req.user.tenantId);
      if (current && current.version !== m.baseVersion)
        return { id: m.id, status: 'conflict', current };                 // client resolves

      await repo.apply(m, tx);
      return { id: m.id, status: 'applied', version: (current?.version ?? 0) + 1 };
    });
    results.push(outcome);
  }
  res.json({ results, serverTime: new Date().toISOString() });
});
@end
@senior
Returning a per-mutation outcome rather than failing the whole batch is what makes sync robust: one conflicted record should not block the other 199, and the client needs to know exactly which ones need resolution. The tombstone requirement is the other detail I would emphasise, because without it deleted records live forever on devices and users report "I deleted this and it came back" — which is a data-correctness bug that only manifests across devices. And the server-issued cursor removes an entire class of silent data loss caused by device clock skew, which is more common than people expect.
@followup
How do you handle a client that has been offline for months?
@answer
Bound the incremental sync: if the client's cursor is older than the tombstone retention window, return a "full resync required" signal and have the client wipe and re-download rather than applying an incomplete delta. Tombstones cannot be retained forever, so that boundary must be explicit rather than silently producing divergence. I would also enforce a minimum supported client version, because supporting arbitrarily old sync contracts indefinitely is not viable and a forced-update path is the honest solution.
@red
- No tombstones, so deletions never reach devices.
- Using the device clock as the sync cursor.

### Design an inventory management system across multiple warehouses.
@short
An append-only movement ledger as the source of truth with derived per-location balances, atomic reservations against specific locations, and an allocation strategy that chooses a warehouse per order. Balances are derived and verifiable rather than mutable fields that drift.
@deep
Requirements: number of locations, whether stock is reserved at order time or at fulfilment, whether transfers between warehouses are modelled, and how tolerant the business is of overselling.

The double-entry style ledger is what makes discrepancies detectable — a mutable quantity column drifts and nobody can reconstruct why.
@arch Ledger as truth, balances as a derived, verifiable projection
  stock_movements (append-only)
    id · sku · location · qty(+/-) · reason(receipt|sale|return|transfer|adjustment)
    reference(order_id / transfer_id) · actor · at
        │
        ▼  derived, maintained transactionally or by trigger
  stock_balances (sku, location, on_hand, reserved)
        │
        ▼  reconciliation job recomputes from the ledger and ALERTS on any mismatch

  RESERVATION at order time, against a SPECIFIC location:
    allocate(order) → choose location by: availability, distance to customer,
                      shipping cost, capacity → atomic conditional decrement there
    reservation has a TTL; expiry releases it

  TRANSFERS: two movements (−source, +destination) with an in-transit state,
             so stock is never invisible or double-counted
@end
@code sql The operations that must be exactly right
-- RESERVE at a specific location — atomic, conditional
UPDATE stock_balances
   SET reserved = reserved + $3
 WHERE sku = $1 AND location = $2 AND (on_hand - reserved) >= $3
RETURNING on_hand - reserved AS available_after;
-- 0 rows → not available there → try the next location in the allocation order

-- FULFIL: reservation becomes a real movement
WITH mv AS (
  INSERT INTO stock_movements (sku, location, qty, reason, reference, actor)
  VALUES ($1, $2, -$3, 'sale', $4, $5) RETURNING sku, location, qty
)
UPDATE stock_balances b SET on_hand = b.on_hand + mv.qty, reserved = b.reserved - $3
  FROM mv WHERE b.sku = mv.sku AND b.location = mv.location;

-- VERIFY continuously: derived balance must equal the ledger sum
SELECT b.sku, b.location, b.on_hand,
       (SELECT COALESCE(sum(qty),0) FROM stock_movements m
         WHERE m.sku=b.sku AND m.location=b.location) AS ledger_sum
  FROM stock_balances b
 WHERE b.on_hand <> (SELECT COALESCE(sum(qty),0) FROM stock_movements m
                      WHERE m.sku=b.sku AND m.location=b.location);
-- any row here is a SEV: the derived state has diverged from the truth
@end
@senior
The continuous verification query is the control that makes this trustworthy: balances are a performance optimisation over the ledger, and any divergence is a bug that must be detected rather than discovered during a stock count. Modelling transfers as two movements with an in-transit state is the other detail — a single "move" operation makes stock either invisible or double-counted during transit, which produces overselling. And the reason and reference on every movement is what makes an audit possible: "why is this SKU down by twelve" should be answerable by reading the ledger, not by guessing.
@followup
The physical stock count does not match the system. What do you do?
@answer
Record an explicit adjustment movement with a reason and an actor rather than editing the balance, so the discrepancy is part of the history and can be analysed — repeated adjustments at one location point at a process problem, theft, or a receiving error, and that pattern is only visible if adjustments are first-class records. I would also investigate before adjusting: a mismatch is often an unrecorded transfer or a fulfilment that never wrote its movement, and correcting the number without finding the cause guarantees it recurs.
@red
- A mutable quantity column as the source of truth.
- Adjusting balances directly without recording why.

### Design an API gateway.
@short
Terminate TLS, authenticate coarsely, apply volumetric rate limits and request-size caps, route by host and path, and add observability — while leaving business-aware authorisation and quotas to the services, which are the only components that know plans, tenants and record ownership.
@deep
Requirements: how many services, whether clients are internal or public, protocol translation needs, and whether you need per-consumer plans and analytics — the last of those pushes toward a managed gateway product.

The design risk is putting too much logic in the gateway, which creates a second source of truth for security decisions and a configuration surface outside code review.
@arch Responsibilities split so nothing is duplicated
  EDGE (CloudFront + WAF)      TLS · DDoS absorption · geo/IP rules · OWASP rules
        │                       volumetric rate limit · request size cap
        ▼
  GATEWAY (ALB / API Gateway / Kong)
        routing by host+path · canary weighting · request/response transformation
        coarse auth: is this token structurally valid and unexpired?
        per-consumer API key identification · circuit breaking · retries (idempotent only)
        observability: request id injection, access logs, metrics
        │
        ▼
  SERVICE
        token verification + revocation · per-user/plan/cost quotas
        authorisation scoped to the RECORD and TENANT · idempotency · validation
        ← the gateway REDUCES load; the service ENFORCES correctness

  RULE: a request that bypasses the gateway and reaches the service directly
        must still be rejected. Test that explicitly.
@end
@code yaml Gateway configuration, versioned with the application
routes:
  - host: api.acme.com
    paths:
      - path: /v1/orders/*
        service: orders-svc
        methods: [GET, POST, PATCH]
        timeout: 10s
        retries: { attempts: 2, on: [502, 503, 504], idempotent_only: true }
        rate_limit: { key: api_key, limit: 1000, window: 60s }
        request_max_body: 100kb
      - path: /v1/ai/*
        service: ai-svc
        timeout: 120s                    # streaming; different profile entirely
        buffering: false                 # ← must not buffer SSE
        rate_limit: { key: api_key, limit: 60, window: 60s }
      - path: /webhooks/*
        service: payments-svc
        request_raw_body: true           # ← signature verification needs exact bytes
        rate_limit: { key: ip, limit: 500, window: 60s }

# All of this lives in Terraform alongside the services, reviewed in the same PR.
@end
@senior
Keeping gateway configuration in version control rather than in a console is the operational discipline I would insist on, because a rate limit or a routing rule changed by hand during an incident is invisible, untested and eventually wrong. The `idempotent_only` retry flag is the other detail: a gateway that retries a POST on a 502 can duplicate a payment, so retries must be restricted to safe methods or to requests carrying an idempotency key. And I would test that a request reaching a service directly, bypassing the gateway, is still rejected — because in a VPC someone eventually will.
@followup
Should the gateway do authentication?
@answer
Coarse validation yes — reject structurally invalid or expired tokens early so bad traffic never reaches your compute — but not the authoritative decision, because the service is the only place that knows about revocation, per-record ownership and tenant scoping. Duplicating the full check creates two implementations that will diverge, and the gateway version will be the one nobody updates. The division I use is that the gateway filters obvious rubbish and the service makes the decision.
@red
- Full authorisation logic in the gateway.
- Gateway retries on non-idempotent methods.

### Design a recommendation service.
@short
Start with heuristics that require no machine learning — popular in category, frequently bought together, recently viewed — because they capture most of the value. Add collaborative filtering or embeddings when you have enough interaction data, always with an offline evaluation harness and an online A/B test.
@deep
Requirements: catalogue size, interaction volume, latency budget (this sits in a page render), and cold-start handling for new users and new items.

The architecture separates offline computation from online serving: models and candidate sets are computed in batch, and serving is a fast lookup plus lightweight ranking.
@arch Offline computation, online serving
  OFFLINE (batch, hourly/daily)
    interaction events → feature store
    → candidate generation: co-occurrence (bought together), popularity by segment,
                            embedding similarity (item2vec / matrix factorisation)
    → precomputed candidate lists per item and per user segment → Redis

  ONLINE (per request, <30ms)
    1. gather candidates: recent views + co-occurrence + popular in category
    2. filter: out of stock, already owned, disliked, not available in region
    3. rank: lightweight scoring (affinity × margin × recency × availability)
    4. diversify: avoid five near-identical items
    5. log the impression WITH the candidate source → this is your training data

  COLD START
    new user → popular in their segment / from their entry point
    new item → content-based similarity (category, attributes, embeddings) until
               it has interaction data
@end
@code ts Serving path, with the filters that matter commercially
export async function recommend(userId: string, context: Ctx): Promise<Rec[]> {
  const [recent, coBought, popular] = await Promise.all([
    redis.lrange(`views:${userId}`, 0, 9),
    redis.zrevrange(`cobought:${context.currentItemId}`, 0, 29, 'WITHSCORES'),
    redis.zrevrange(`popular:${context.category}:${context.region}`, 0, 29),
  ]);

  const candidates = dedupe([...coBought, ...popular]);
  const items = await catalog.mget(candidates);                 // one batched read

  const ranked = items
    .filter(i => i.inStock && i.availableIn(context.region))     // ← never recommend
    .filter(i => !recent.includes(i.id) && !owned.has(i.id))     //    what they cannot buy
    .map(i => ({ item: i, score: affinity(i, userId) * 0.5 + popularityScore(i) * 0.3
                                 + marginScore(i) * 0.2 }))
    .sort((a, b) => b.score - a.score);

  const diversified = mmr(ranked, { lambda: 0.7 }).slice(0, 10); // avoid near-duplicates
  await impressions.log(userId, diversified, context);           // → training data + A/B
  return diversified;
}
@end
@senior
Filtering out-of-stock and region-unavailable items is the unglamorous change that usually produces the largest measurable improvement, because a perfectly relevant recommendation the customer cannot buy is worse than a mediocre one they can. Logging impressions with the candidate source is the other essential — without it you cannot attribute conversions to strategies, cannot train a better model, and cannot run a meaningful A/B test. I would also be explicit that heuristics get you most of the way: "frequently bought together" is often within a few percent of a sophisticated model at a fraction of the complexity.
@followup
How do you know the recommendations are actually helping?
@answer
An A/B test measuring downstream business metrics — conversion, revenue per session, and importantly return rate, because recommendations that drive purchases people later return are not a win. Offline metrics like precision at k are useful for iterating quickly but do not reliably predict online performance, so they gate what gets tested rather than what ships. I would also watch for cannibalisation: recommendations that shift purchases users would have made anyway show as engagement but not as incremental revenue.
@red
- Building a machine-learning model before trying heuristics.
- Recommending items that are out of stock or unavailable in the region.

### Design a CI/CD system for a monorepo.
@short
Detect which projects are affected by a change, run only their tasks with aggressive caching, produce one immutable artefact per service, and promote that artefact through environments with automated verification and rollback. The goal is that a one-line change does not run the whole suite.
@deep
Requirements: number of services, build times, how independently services deploy, and whether the team wants a single release train or per-service deployment.

The two mechanisms that make monorepo CI viable are affected-project detection and remote task caching — without them, build times grow with the repository rather than with the change.
@arch Affected detection, caching, then promotion
  PR OPENED
    → determine affected projects from the dependency graph (Nx/Turborepo)
    → for each affected project, run: lint · typecheck · unit · integration
       ↳ REMOTE CACHE: identical inputs → cached result, seconds instead of minutes
    → shared checks always run: secret scan, dependency audit, license check
    → bundle-size and query-count budgets for affected apps
    → post a summary: what ran, what was cached, what changed in bundle size

  MERGE TO MAIN
    → build ONE image per affected service, tagged with the commit SHA
    → push to the registry (immutable; never `latest`)
    → deploy to staging → smoke tests → automated metric comparison
    → production: canary 10% → automated comparison → promote or auto-rollback
    → the SAME artefact throughout; no rebuilds per environment

  MIGRATIONS: separate step, before the app deploy, backwards-compatible only,
              with lock_timeout, rehearsed against a production-size snapshot
@end
@code yaml Affected detection and caching in practice
jobs:
  affected:
    outputs: { projects: ${{ steps.a.outputs.projects }} }
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }                       # need history for the diff base
      - id: a
        run: echo "projects=$(npx nx show projects --affected --base=origin/main --json)" >> $GITHUB_OUTPUT

  verify:
    needs: affected
    strategy: { matrix: { project: ${{ fromJson(needs.affected.outputs.projects) }} } }
    steps:
      - run: npx nx run-many -t lint,typecheck,test --projects=${{ matrix.project }}
        env: { NX_CLOUD_ACCESS_TOKEN: ${{ secrets.NX_CLOUD }} }   # remote cache

  build:
    needs: [affected, verify]
    steps:
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ env.ECR }}/${{ matrix.project }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
@end
@senior
Remote caching is what makes this work at scale: a project whose inputs have not changed returns a cached result in seconds, so CI time tracks the size of the change rather than the size of the repository. Without it, monorepo CI becomes the main argument against monorepos. The other discipline is building once and promoting the same artefact — rebuilding per environment means production runs something that was never tested, and it is a surprisingly common mistake because it feels harmless. I would also make the bundle-size and query-count budgets blocking, because those are the regressions that otherwise accumulate invisibly.
@followup
A shared library change triggers every project. Is that right?
@answer
It is correct — everything depending on it genuinely is affected — but it is also the signal that the library is too broad. Splitting it into narrower packages means a change to date formatting does not rebuild the payment service. In the meantime, caching limits the damage: projects whose behaviour is unchanged still get cache hits on unchanged inputs where the tooling can prove it. I would treat frequent full-graph rebuilds as a package-boundary problem rather than a CI problem.
@red
- Running the full test suite on every change.
- Rebuilding images per environment instead of promoting one artefact.

### Design a leaderboard and gamification system.
@short
Redis sorted sets for real-time ranking with O(log n) updates and range reads, Postgres as the durable record, periodic snapshots for historical leaderboards, and careful handling of ties, cheating and very large leaderboards where a user's exact rank is expensive.
@deep
Requirements: how many participants, how often scores change, whether ranks must be exact, and what time windows are needed — daily, weekly, all-time, or per segment.

Exact global rank for a user in a hundred-million-entry leaderboard is expensive; approximate rank or a bucketed position is usually acceptable and far cheaper.
@arch Redis for ranking, Postgres for truth
  score event → validate (anti-cheat) → Postgres (durable, auditable)
                                      → Redis ZINCRBY leaderboard:<scope>:<window>
  SCOPES/WINDOWS: global · country · friends × daily · weekly · all-time
    key per combination; daily/weekly keys expire naturally

  READS
   top N            ZREVRANGE key 0 N-1 WITHSCORES        O(log n + N)
   my rank          ZREVRANK key <user>                   O(log n)
   around me        ZREVRANGE key (rank-5) (rank+5)       O(log n + k)

  VERY LARGE LEADERBOARDS
   exact rank is fine in Redis, but showing "you are 4,821,003rd" is not useful
   → percentile or bucket ("top 5%") is cheaper to communicate and to compute

  HISTORICAL: snapshot the ZSET to Postgres at window close → final standings
              are immutable and auditable (prizes depend on them)
@end
@code ts Scoring, ties and anti-cheat
// Ties: encode a tiebreaker INTO the score so ordering is deterministic
// score * 10^10 + (10^10 - timestampSeconds)  → earlier achiever ranks higher
const composite = points * 1e10 + (1e10 - Math.floor(Date.now() / 1000));
await redis.zadd(`lb:global:weekly:${weekKey}`, composite, userId);

// Anti-cheat BEFORE it reaches the leaderboard
async function submitScore(userId: string, points: number, proof: Proof) {
  if (points > MAX_PLAUSIBLE_PER_EVENT) return flagForReview(userId, points, proof);
  const rate = await redis.incr(`scores:${userId}:${minuteKey()}`);
  if (rate > MAX_SUBMISSIONS_PER_MINUTE) return flagForReview(userId, points, proof);
  if (!verifyServerSide(proof)) return reject('INVALID_PROOF');   // recompute, don't trust
  // durable first, then the leaderboard
  await db.scores.insert({ userId, points, at: new Date(), proof });
  await redis.zincrby(`lb:global:weekly:${weekKey}`, points, userId);
}

// Window close: snapshot to Postgres — prizes depend on an immutable record
const final = await redis.zrevrange(key, 0, -1, 'WITHSCORES');
await db.leaderboardSnapshots.insert({ key, standings: final, closedAt: new Date() });
@end
@senior
Encoding the tiebreaker into the score is the trick that avoids unstable ordering — without it, users with equal scores swap positions on every read, which looks like a bug and generates complaints when prizes are involved. Server-side validation of every score is the other essential: any leaderboard with a reward attached will be attacked, and trusting a client-submitted score is the same mistake as trusting a client-submitted price. And snapshotting at window close matters because Redis is a cache — if prizes depend on final standings, those standings must exist in a durable, auditable store.
@followup
How do you show a user their rank among friends?
@answer
Maintain a separate sorted set per user's friend group, updated when their friends' scores change, or compute it on read by fetching the friends' scores and ranking them in memory — which is cheap for a few hundred friends and avoids maintaining many small sets. The read-time approach is simpler and scales fine until friend counts are large; the precomputed approach is better for very active leaderboards. I would start with read-time computation and measure before adding the maintenance burden.
@red
- Trusting client-submitted scores.
- Redis sorted sets as the durable record for prize-bearing standings.

### Design the observability stack for a platform you own.
@short
Metrics for alerting and dashboards, structured logs with a correlation id for investigation, and distributed traces for latency attribution — with business metrics alongside technical ones, alerts on user-visible symptoms, and every alert linked to a runbook.
@deep
Requirements: how many services, cardinality expectations, retention and budget — observability cost can rival compute cost if high-cardinality labels and unsampled logs are unmanaged.

The design decision that matters most is what you alert on: symptoms that users feel, not resource utilisation.
@arch The three pillars, plus the fourth nobody mentions
  METRICS   Prometheus/CloudWatch: RED per endpoint (rate, errors, duration)
            + USE per resource (utilisation, saturation, errors)
            + BUSINESS: orders/min, payment success rate, signup conversion
            ⚠ cardinality discipline: never user_id or request_id as a LABEL

  LOGS      structured JSON · request id on every line · redaction at the logger
            sampled on success (10%), 100% on error and on slow requests
            retention tiered: 7d hot / 30d warm / 1y archived

  TRACES    OpenTelemetry auto-instrumentation (http, pg, redis, queues)
            context propagated through HTTP headers AND queue payloads
            tail-based sampling: keep every error and every slow trace

  + THE FOURTH: SYNTHETIC checks from outside, exercising real user journeys
    → catches the case where every component is healthy and the whole is broken

  ALERTS: on SYMPTOMS (5xx rate, p99 latency, payment success rate, queue age),
          never on CPU alone. Every alert → runbook link + owner + user impact.
@end

@senior
The business metrics are the part that distinguishes a real observability practice: technical dashboards can be entirely green while payments fail for one provider because of a change on their side, and only the payment success rate reveals it. Cardinality discipline is the cost control — a user id as a metric label creates millions of series and can cost more than the servers being monitored. And synthetic checks from outside are the fourth pillar people omit, because component health checks verify the parts while only an end-to-end synthetic verifies the whole.
@followup
How do you keep observability costs under control?
@answer
Sample successful traces and logs aggressively while keeping every error and slow request, tier log retention so recent data is queryable and older data is archived cheaply, drop metric labels nobody queries, and review the highest-cardinality series regularly. I would also make the cost visible per service, because the team generating the logs is the team that can reduce them. The goal is not minimum spend but proportionality: paying more to observe a service than to run it is a signal that something is misconfigured rather than that observability is expensive.
