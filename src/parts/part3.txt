# SECTION Distributed Systems & Scalability | The round that decides whether you are hired as senior or as mid.

### Explain the CAP theorem and how it actually influences your design decisions.
@short
When a network partition occurs, a distributed system must choose between consistency and availability — you cannot have both. In practice partitions are rare but inevitable, so the real question is what your system does during one, and the answer differs per operation rather than per system.
@deep
CAP is often misquoted as "pick two of three". Partition tolerance is not optional in a distributed system, so the choice is between CP and AP *during a partition*. When there is no partition you can have both, which is why PACELC is the more useful framing: else (when there is no partition) you still trade Latency against Consistency.

The design consequence is per-operation. Reading a product description can be stale and available; decrementing inventory at checkout cannot. So the same system is CP for some operations and AP for others.
@arch The choice made per operation, not per system
  OPERATION                    PARTITION BEHAVIOUR            WHY
  ─────────────────────────────────────────────────────────────────────────────
  read product catalogue       AP — serve stale from cache    staleness is harmless
  read own order history       AP — stale by seconds is fine  read-your-writes only
  add to cart                  AP — local, reconcile later    conflict = merge items
  decrement inventory          CP — refuse rather than oversell  overselling costs money
  capture a payment            CP — single authority (provider) double-charge is fatal
  post a chat message          AP — CRDT/queue, converge      ordering per room only
  auth / permission check      CP — fail closed               a stale "allow" is a breach

  PACELC: with no partition, we still choose. Reads from a replica are lower
  latency and weaker consistency; reads from the primary are the reverse.
  Decide per query, and make read-after-write sticky to the primary.
@end
@senior
The senior version of this answer refuses the abstract framing and goes straight to operations. I would say: our system is AP for catalogue reads served from a CDN and Redis, CP for inventory and payment capture where we take a row lock and refuse rather than guess, and we implement read-your-writes by routing a user's reads to the primary for a short window after they write. That is a design you can defend, whereas "we chose AP" is a slogan. I would also point out that most single-region systems with one Postgres primary are effectively CP by construction, and the interesting CAP decisions appear when you add caches, replicas or a second region.
@followup
What is eventual consistency and how do you make it acceptable to users?
@answer
Eventual consistency means replicas converge given no new writes, but a read may be stale in the meantime. You make it acceptable by shaping the user experience: read-your-writes so a user always sees their own change immediately, optimistic UI so their action appears applied, and monotonic reads so they never see time go backwards. The failures users actually notice are seeing their own write disappear and seeing data move backwards — fix those two and eventual consistency is invisible for most workloads.
@red
- "Pick two of three."
- Choosing CAP at the system level rather than per operation.

### How do you design a system to handle 10× its current traffic?
@short
Find the current bottleneck by measurement, then work through the standard levers in order of cost: caching and reducing work, horizontal scaling of stateless tiers, read replicas, asynchronous processing of anything not needed synchronously, and only then partitioning or sharding the data tier. Each step is cheaper and less risky than the next.
@deep
The mistake is scaling everything uniformly. At 10× the constraint is almost always one thing — usually the database's write path or a single hot resource — and the rest of the system has headroom.

The other principle is removing work rather than adding capacity: a query fixed by an index, a payload trimmed, an N+1 batched, or a synchronous side effect moved to a queue often buys more than doubling instance count, and costs nothing to run.
@arch The order I would work through, cheapest first
  0. MEASURE      where does time and money go now? p95 per endpoint, DB CPU,
                  queue depth, cache hit rate. Do not guess.
  1. REMOVE WORK  fix N+1s, add the missing index, trim payloads, batch,
                  keep-alive agents, stop doing it at all if nobody uses it
  2. CACHE        CDN for public content · Redis for hot reads · stale-while-revalidate
                  → often the single biggest multiplier for read-heavy systems
  3. SCALE OUT    stateless app tier behind an LB; move ALL session/cache/lock
                  state to Redis first, or scaling out breaks correctness
  4. ASYNC        anything the user is not waiting for → queue: email, webhooks,
                  reports, media, analytics. Protects the sync path from spikes.
  5. READ SCALE   replicas for reporting/dashboards; read-your-writes to primary
  6. WRITE SCALE  batch writes, reduce indexes on hot tables, partition by time
  7. PARTITION    shard by tenant or entity — last, because it makes cross-shard
                  queries and transactions an application problem forever

  At each step, re-measure. The bottleneck MOVES; the plan must follow it.
@end
@senior
The point I would emphasise is that step 3 has a hidden prerequisite that breaks systems: the moment you go from one instance to many, everything in process memory becomes wrong — sessions, rate-limit counters, caches, WebSocket registries and cron schedulers. I would enumerate that list explicitly, because it is where teams get burned when they "just add instances". And I would resist step 7 hard: sharding is a permanent architectural tax, and partitioning plus archiving plus moving analytics off the primary handles far more than most teams expect.
@followup
How do you find the bottleneck?
@answer
Layer by layer with real measurements: application traces to see where request time goes, database statistics ranked by total time, event-loop lag to distinguish CPU-bound from I/O-bound, connection pool wait time, and queue depth and age. Then a load test that pushes past current traffic to see what bends first, because the bottleneck at 1× is often not the bottleneck at 5×. What I avoid is reasoning about it architecturally without data, because the answer is regularly something unglamorous like a missing index or a third-party call with no keep-alive.
@red
- Adding instances without moving state out of memory.
- Proposing sharding as an early step.

### How does database sharding work and what does it cost you?
@short
Sharding splits data across independent databases by a shard key, so each holds a subset. It scales writes and storage beyond one machine. The costs are permanent: cross-shard queries and transactions become application problems, the shard key becomes very hard to change, and rebalancing is a project.
@deep
Key choice determines everything. A tenant id shards cleanly for a B2B product because most queries are tenant-scoped, but creates hot shards when one customer is far larger. A user id distributes evenly but makes any cross-user query a scatter-gather. A hash distributes best but destroys range queries.

Routing lives either in the application, in a proxy (Vitess, Citus), or in a database that shards natively. Each moves the complexity rather than removing it.
@code text Shard key trade-offs, and what breaks
  BY TENANT     ✅ most queries are single-shard; clean isolation; easy per-tenant restore
                ❌ hot shard when one customer is 40% of volume → needs sub-sharding
                    or a dedicated instance for the whale

  BY USER HASH  ✅ even distribution
                ❌ "all orders for this tenant" becomes scatter-gather across N shards
                ❌ no range scans; ordering requires merging N sorted streams

  BY TIME       ✅ natural for events; old shards become read-only and archivable
                ❌ ALL writes hit the newest shard → the write hotspot you were fixing

  WHAT BREAKS EVERYWHERE
   • cross-shard transactions   → sagas with compensation, not 2PC
   • unique constraints         → only unique WITHIN a shard; global uniqueness needs
                                   a separate service or a composite key including the shard
   • auto-increment ids         → UUIDv7/ULID or a coordinated id service
   • joins across shards        → denormalise, or join in the application
   • rebalancing                → double-write + backfill + cutover, per key range
@end
@senior
The point I would make is that the shard key is effectively permanent — changing it means rewriting every row and every query, so it deserves far more analysis than it usually gets. Before sharding I would exhaust: partitioning within one database, moving analytical queries to a replica or a column store, archiving cold data, and reducing write amplification from excess indexes. Most systems that think they need sharding actually need one of those. And if I did shard, I would strongly prefer a managed solution like Citus over hand-rolled routing, because the operational surface of DIY sharding is enormous.
@followup
How do you handle a query that must span all shards?
@answer
Scatter-gather with bounded concurrency and a strict timeout, merging results in the application — and accept that it is the slowest possible query shape, bounded by the slowest shard. For anything frequent, the better answer is a denormalised read model: maintain a separate aggregated store (a search index, a materialised view, an analytics database) populated asynchronously from the shards. That converts an expensive cross-shard query into a cheap single-store read at the cost of some staleness.
@red
- Sharding before partitioning and archiving.
- A shard key chosen without analysing query patterns.

### What is a saga and when do you use one instead of a transaction?
@short
A saga is a sequence of local transactions across services, each with a compensating action to undo it if a later step fails. You use one when a business operation spans systems that cannot share a transaction — your database plus a payment provider plus a warehouse API.
@deep
Two coordination styles: orchestration, where a central coordinator drives the steps and knows the whole flow, and choreography, where each service reacts to events. Orchestration is easier to reason about and debug; choreography couples less but the flow exists only in everyone's heads.

Compensations are not rollbacks. You cannot un-send an email or un-charge without a refund — the compensation is a new business action with its own visible consequence, which is why the model must be designed with the business, not just the engineer.
@arch An order saga with explicit compensations
  ORCHESTRATOR (a state machine persisted in Postgres, one row per saga instance)

  STEP                        ON FAILURE → COMPENSATE (in reverse order)
  1. reserve inventory        → release reservation
  2. authorise payment        → void authorisation
  3. create shipment          → cancel shipment
  4. capture payment          → REFUND (not "void" — money has moved)
  5. send confirmation        → send cancellation notice (cannot unsend)

  Properties required at every step:
   • idempotent (each step may be retried)          key: sagaId + stepName
   • compensations idempotent too
   • the saga state is persisted BEFORE each external call, so a crash resumes
   • timeouts per step; a stuck step alerts rather than hanging forever
   • terminal failure → dead-letter + human review queue (money is involved)
@end
@code ts The orchestrator loop, resumable after a crash
export async function advance(sagaId: string) {
  const saga = await db.sagas.findForUpdate(sagaId);
  const step = STEPS[saga.currentStep];

  try {
    await db.sagas.mark(sagaId, 'in_progress');          // persisted BEFORE the call
    const result = await step.execute(saga.context, `${sagaId}:${step.name}`);  // idem key
    await db.sagas.completeStep(sagaId, step.name, result);
    if (saga.currentStep + 1 < STEPS.length) await queue.add('saga', { sagaId });
    else await db.sagas.mark(sagaId, 'completed');
  } catch (err) {
    if (isRetryable(err) && saga.attempts < 5) throw err;               // queue retries
    await db.sagas.mark(sagaId, 'compensating');
    for (const done of saga.completedSteps.reverse()) {
      await STEPS[done].compensate(saga.context, `${sagaId}:${done}:comp`);
    }
    await db.sagas.mark(sagaId, 'failed');
    await alert.notify('saga-failed', { sagaId, step: step.name, err });  // humans review
  }
}
@end
@senior
Persisting the saga state before each external call is what makes it crash-safe: if the process dies mid-call, the resumed saga knows it was in step 3 and retries idempotently rather than losing track. The other point I would make is that sagas expose intermediate states to users — an order can genuinely be "paid but not shipped" for a minute — so the UI and the support tooling must represent that honestly rather than pretending the operation is atomic. Designing the compensations with the business is essential too, because "refund and apologise" is a business policy, not an engineering default.
@followup
Why not two-phase commit?
@answer
Because it requires every participant to support it, it holds locks across the prepare phase which kills throughput, and it blocks indefinitely if the coordinator fails at the wrong moment. Third-party APIs like Stripe simply do not offer it. Sagas accept temporary inconsistency in exchange for availability and simplicity, and then converge — which matches how business processes actually work, since a real-world order fulfilment is also a sequence of steps with compensations, not an atomic transaction.
@red
- Assuming compensations are perfect rollbacks.
- No persisted state, so a crash loses the saga.

### How do you achieve exactly-once processing?
@short
You cannot get exactly-once *delivery* across a network — that is a theoretical impossibility. What you get is at-least-once delivery plus idempotent processing, which produces an exactly-once *effect*. The mechanism is a deduplication key enforced by a unique constraint, applied in the same transaction as the effect.
@deep
The reason delivery cannot be exactly-once is the two-generals problem: the sender cannot know whether a lost acknowledgement means the message was processed or not, so it must either risk losing it (at-most-once) or risk duplicating it (at-least-once).

The practical pattern is therefore: every message carries a stable id, the consumer records that id atomically with the effect, and a repeat sees the constraint violation and exits. The atomicity is the part people get wrong — recording the id in Redis after committing to Postgres leaves a window where a crash causes reprocessing.
@code sql The dedup record and the effect, in one transaction
BEGIN;
  INSERT INTO processed_messages (id, consumer, at)
  VALUES ($1, 'fulfilment', now())
  ON CONFLICT (id, consumer) DO NOTHING;
  -- 0 rows means we already handled it → ROLLBACK and ack the message

  UPDATE orders SET status = 'fulfilled' WHERE id = $2 AND status = 'paid';
  INSERT INTO shipments (order_id, ...) VALUES ($2, ...);
COMMIT;
@end
@code ts Consumer-side, with the acknowledgement ordering that matters
async function handle(msg: Message) {
  const applied = await withTransaction(async (tx) => {
    const first = await tx.query(
      `INSERT INTO processed_messages (id, consumer) VALUES ($1,$2)
       ON CONFLICT DO NOTHING RETURNING id`, [msg.id, CONSUMER]);
    if (!first.rowCount) return false;                    // duplicate → no-op
    await applyEffect(msg, tx);                           // SAME transaction
    return true;
  });

  await msg.ack();       // ack AFTER commit. Acking first risks losing the message.
  return applied;
}
// Retention: processed_messages needs a TTL/partition, or it grows forever.
@end
@senior
The acknowledgement ordering is the subtle part: acking before committing means a crash between them loses the message entirely (at-most-once), while acking after means a crash causes redelivery, which the dedup handles. So the correct order is commit, then ack — and that is exactly why the consumer must be idempotent rather than merely careful. I would also note that the dedup table needs a retention policy, partitioned by time and dropped, or it becomes the largest table in your database within a year.
@followup
What if the effect is not in a database — for example sending an email?
@answer
Then you cannot make it atomic, so you move it behind something you can: record the intent transactionally (the outbox), and let a worker perform the send with its own dedup key. The email provider itself usually supports an idempotency key or you dedupe on a message id you generate. You accept that in a narrow crash window an email might send twice, and you make that acceptable — receipts are idempotent-looking, and the alternative (possibly never sending) is worse. Naming which failure you prefer is the honest engineering answer.
@red
- Claiming a system achieves exactly-once delivery.
- Recording the dedup key outside the effect's transaction.

### How do you handle backpressure across a distributed system?
@short
Every stage needs a way to signal that it cannot keep up, and every upstream stage needs to respect it — bounded queues, rate limits, concurrency caps and load shedding. Without backpressure, an overloaded component silently buffers until it exhausts memory or until latency exceeds every client's timeout, at which point throughput collapses to zero.
@deep
The failure shape is important: an unbounded queue does not fail loudly, it degrades. Latency grows, clients time out and retry, which adds more load, and the system enters a state where it is doing maximum work and delivering nothing useful.

The fixes are bounded buffers with explicit rejection, concurrency limits per dependency (bulkheads), client-side rate limiting derived from server-provided limits, and load shedding that sheds the least valuable work first.
@arch Where backpressure must exist in a typical stack
  client ──► [rate limit + 429 + Retry-After]  ← reject early, cheaply, at the edge
      │
      ▼
  API ────► [bounded concurrency per dependency: pLimit / semaphore]
      │      [load shed: if queue depth > N or loop lag > X, return 503 fast]
      ▼
  queue ──► [BOUNDED length. Full → reject the enqueue, do not buffer forever]
      │      [monitor OLDEST JOB AGE, not just depth]
      ▼
  worker ─► [concurrency cap sized to the DB pool, not to CPU]
      │      [respect downstream 429s: pause consumption, do not spin]
      ▼
  database  [statement_timeout so no query can hold a connection forever]
            [connection pool = the real global concurrency limit]

  RULE: the slowest component must be able to say "stop", and every upstream
        component must be able to hear it. Otherwise the queue IS the failure.
@end
@code ts Load shedding based on event-loop lag
const loop = monitorEventLoopDelay({ resolution: 20 });
loop.enable();

app.use((req, res, next) => {
  const lagMs = loop.percentile(99) / 1e6;
  if (lagMs > 250 && !isCritical(req)) {                 // shed the cheap stuff first
    metrics.increment('load_shed', { route: req.path });
    return res.status(503).set('Retry-After', '2').json({ error: 'OVERLOADED' });
  }
  next();
});
// Critical paths (checkout, auth) are never shed; analytics and search are shed first.
@end
@senior
Prioritised shedding is the part that turns this from a blunt instrument into a design: under overload you want checkout to succeed and the recommendations widget to fail, not the reverse. Implementing that requires classifying endpoints by business value, which is a conversation with product rather than a purely technical decision. The other point is that retries are a load amplifier — a client that retries three times on failure triples your load exactly when you are already overloaded — which is why `Retry-After`, exponential backoff with jitter, and circuit breakers on the client side are part of the backpressure story, not separate from it.
@followup
What is the difference between a bulkhead and a circuit breaker?
@answer
A bulkhead limits how much of a shared resource one dependency can consume — a concurrency cap so that slow calls to the recommendations service cannot occupy every connection in your pool. A circuit breaker stops calling a failing dependency entirely for a period, so you fail fast instead of waiting for timeouts. They compose: the bulkhead contains the damage while the dependency is merely slow, and the breaker cuts it off once it is clearly broken. Using only one leaves a gap.
@red
- Unbounded queues described as "buffering".
- Retrying aggressively into an overloaded dependency.

### How would you design a globally distributed system?
@short
Partition users by home region so most requests are served locally with local data, replicate reference data everywhere, and route with latency-based DNS or anycast. Cross-region writes are the hard part, so I design to avoid them rather than to make them fast.
@deep
The physics are unavoidable: a round trip between continents is 150–250ms, so a synchronous cross-region write makes every such request slow. Systems that feel fast globally almost always partition ownership — your data lives in your region, and cross-region access is the exception.

Where global consistency is genuinely required, you either accept the latency (Spanner-style consensus) or restructure the problem so the global part is small — a globally unique username check, for instance, can be a separate small service.
@arch Region-partitioned architecture with global reference data
  DNS (latency-based) ─► nearest edge
        │
        ├── EU region                     ├── AP region                  ├── US region
        │   app + cache                   │   app + cache                │   app + cache
        │   Postgres (EU users OWN data)  │   Postgres (AP users)        │   Postgres (US)
        │        ▲                        │        ▲                     │        ▲
        └────────┴── async replication of REFERENCE data (catalogue, config, pricing)
                     via CDC/logical replication or a global KV store

  ROUTING   user → home region recorded at signup (residency + latency)
            a request arriving in the wrong region is PROXIED to the home region
            (correct but slower) rather than served from stale local data

  GLOBAL BITS (kept deliberately small)
   • globally unique handles → one small CP service
   • auth tokens            → asymmetric JWT: verify anywhere, issue in home region
   • billing/ledger         → single region of record; regions publish events to it
@end
@senior
The design instinct I would articulate is to make the globally consistent surface as small as possible, and to be explicit about what it is. Almost everything can be regional or eventually consistent; a handful of things — unique identifiers, the financial ledger, entitlement changes — genuinely need a single point of authority, and isolating those into small services keeps the rest fast. I would also insist that data residency requirements be considered at the same time, because "EU customer data stays in the EU" turns a performance optimisation into a legal constraint and changes what is negotiable.
@followup
How do you handle a user who travels between regions?
@answer
Their data stays in their home region and requests from elsewhere are proxied there — slower for them, but correct and consistent. Migrating a user's data between regions is possible but should be a deliberate, rare operation with a brief write freeze, not something triggered by travel. Serving them locally from a stale replica is the tempting option and it is usually wrong, because they will see their own writes disappear, which is the one inconsistency users always notice.
@red
- Synchronous cross-region writes on the hot path.
- Multi-master with no conflict resolution strategy.

### What is consensus, and where does it appear in systems you have built?
@short
Consensus is a set of nodes agreeing on a value despite failures — Raft and Paxos are the algorithms. I have not implemented it, but I depend on it constantly: leader election in Postgres failover, etcd behind Kubernetes, Kafka's controller, and distributed lock services all rely on it.
@deep
The core guarantee is that a majority quorum agrees, so the system tolerates a minority of failures while never producing two conflicting decisions. That is why quorum systems use odd numbers of nodes — three tolerates one failure, five tolerates two.

The practical relevance is understanding what it costs: consensus requires a round trip to a majority, so every write pays that latency, and it explains why strongly-consistent distributed databases are slower than eventually-consistent ones.
@code text Where consensus shows up under systems you actually operate
  Kubernetes         etcd (Raft) — every API object write goes through consensus
                     → why etcd latency degrades the whole control plane
  Postgres HA        Patroni uses etcd/Consul for leader election
                     → split-brain prevention requires a quorum witness
  Kafka              controller election; ISR replication is quorum-like
  Redis Sentinel     quorum of sentinels agrees a primary has failed
                     → why you need ≥3 sentinels, and why 2 is worse than 1
  Distributed locks  a correct lock service (etcd, ZooKeeper) uses consensus;
                     a Redis lock does NOT, which is why fencing tokens matter

  IMPLICATIONS I DESIGN AROUND
   • quorum writes cost a round trip to a majority → higher, more variable latency
   • an even number of nodes gains nothing (4 tolerates the same failures as 3)
   • a partition that leaves no majority = unavailable, by design, and that is correct
@end
@senior
The practical judgement I would express is that you should almost never implement consensus yourself — use etcd, ZooKeeper or a managed service. What you do need is to understand its failure semantics so you configure it correctly: three or five nodes rather than two or four, a witness node to avoid split-brain in two-datacentre setups, and the knowledge that losing quorum means unavailability by design rather than a bug. Misconfiguring a quorum system is one of the more common self-inflicted outages, and it comes from not understanding what majority actually requires.
@followup
Why is a Redis-based lock not equivalent to a real distributed lock?
@answer
Because Redis replication is asynchronous, so a lock acquired on the primary may not have reached the replica when a failover promotes it — two clients can then hold the same lock. Redlock attempts to address this across independent nodes but depends on bounded clock drift and bounded process pauses, which are not safe assumptions. The practical resolution is either to use the lock only where occasional double execution is merely inefficient, or to add fencing tokens so the downstream store rejects a stale holder's writes.
@red
- Claiming to have implemented Raft.
- Two-node or four-node quorum configurations.

### How do you design for failure — what fails and what do you do about each?
@short
Enumerate the dependencies and decide, for each, what happens when it is slow, when it is down, and when it returns wrong data. Then implement timeouts, retries with backoff, circuit breakers, fallbacks and degraded modes accordingly. The output is a written table, not a general intention to be resilient.
@deep
The distinction that matters is between "slow" and "down". A dependency that is down fails fast and is easy to handle; a dependency that is slow is far more dangerous because it consumes your resources while you wait, which is how one failing integration takes down an unrelated service.

Every fallback is a product decision: showing stale data, degrading a feature, or failing loudly are all valid, and which one is right depends on what is being served.
@code text The failure table I would actually write for a service
  DEPENDENCY      SLOW                      DOWN                      DEGRADED MODE
  ──────────────────────────────────────────────────────────────────────────────────
  Postgres        statement_timeout 10s     readiness fails,          none — this is the
                  pool wait timeout 5s      LB routes away            source of truth
  Redis (cache)   timeout 100ms, ignore     fall through to DB        slower, still correct
                  the cache on timeout      + alert                   ← MUST be survivable
  Redis (rate     —                         FAIL OPEN for /login      accept the risk
   limiter)                                 FAIL CLOSED for /ai       protect the spend
  Payment         timeout 8s + idempotency  breaker opens, offer      "try another method"
   provider       key so retry is safe      the alternate provider
  Email provider  queue it — user is not    retries with backoff,     silent to the user
                  waiting                   DLQ after 8 attempts
  Search (OS)     timeout 500ms             fall back to Postgres     worse results, works
                                            ILIKE/FTS
  LLM provider    stream timeout 30s        breaker + fallback model  "unavailable, retry"
  S3              retry 3× (SDK default)    uploads fail loudly       queue for retry
  Auth service    timeout 2s                FAIL CLOSED               no degraded mode
@end
@senior
Writing this table is the exercise, and the valuable part is that it forces a decision on the rate limiter row: fail open on login because locking every user out is worse than the attack you are preventing, but fail closed on an expensive AI endpoint because unbounded spend is worse than a brief outage. Those are opposite answers to the same technical failure, decided by business impact — and having made that decision in advance means the behaviour is designed rather than accidental. I would also insist that the cache row is genuinely survivable, and test it, because a "cache" the system cannot run without is a database with no durability.
@followup
How do you test that these behaviours actually work?
@answer
Fault injection in a non-production environment: block the dependency at the network level, add latency with a proxy like toxiproxy, and verify the observed behaviour matches the table — the breaker opens, the fallback serves, the alert fires. Most of these paths are never exercised in normal operation, so they rot silently; a scheduled game day where you take a dependency down deliberately is the only way to know they still work. Discovering that your fallback throws during a real incident is a particularly bad moment.
@red
- "We use retries" as a complete failure strategy.
- Fallback paths that have never been executed.

### How do you migrate a live system with zero downtime?
@short
Expand and contract at every layer: add the new path alongside the old, dual-write, backfill, verify by comparison, switch reads, verify again, then remove the old path. Each step is separately deployable and reversible, and traffic moves gradually with a kill switch at every stage.
@deep
The requirement that shapes everything is that old and new code run simultaneously during any rolling deploy, so every intermediate state must be valid for both. That rules out any change that flips a representation atomically.

Verification is the step people skip. Dual-writing and then switching without comparing the two paths on real traffic means you discover the discrepancy from customers.
@arch Migrating a datastore with no downtime
  PHASE 1  DUAL WRITE      writes go to OLD (authoritative) and NEW (shadow)
                           failures on NEW are logged, never surfaced
  PHASE 2  BACKFILL        historical data copied in batches, throttled,
                           resumable, with a checksum per batch
  PHASE 3  SHADOW READ     read from OLD (served) and NEW (compared, discarded)
                           → mismatch rate must reach ~0 before proceeding
                           → this is where you find the bugs, safely
  PHASE 4  FLIP READS      feature flag, per-tenant or per-percentage ramp
                           1% → 10% → 50% → 100%, watching error and latency
                           kill switch at every step
  PHASE 5  STOP DUAL WRITE new is authoritative; old kept read-only for a period
  PHASE 6  DECOMMISSION    after a full business cycle with no need to fall back

  ROLLBACK is available at every phase up to 5. That is the point of the sequence.
@end
@code ts Dual write and shadow compare, safely
export async function saveOrder(o: Order) {
  await oldStore.save(o);                                 // authoritative
  queueMicrotask(async () => {                            // never block or fail the request
    try { await newStore.save(o); }
    catch (e) { metrics.increment('dualwrite.new.error'); logger.warn({ e }, 'shadow write failed'); }
  });
}

export async function getOrder(id: string) {
  const legacy = await oldStore.get(id);
  if (await flag('migration.shadowRead')) {
    void (async () => {
      const next = await newStore.get(id).catch(() => null);
      if (!deepEqual(normalise(legacy), normalise(next))) {
        metrics.increment('migration.mismatch');
        logger.warn({ id, legacy, next }, 'shadow read mismatch');   // ← find bugs safely
      }
    })();
  }
  return legacy;
}
@end
@senior
The shadow-read phase is where the value is: it validates the new implementation against every real edge case in production data without any user-visible risk, and the mismatch rate is an objective readiness signal rather than a judgement call. I would hold the bar at zero mismatches across a full business cycle, because the residual differences are always the interesting ones — nulls, timezones, rounding, legacy records written by a version of the code nobody remembers. And the per-tenant ramp matters more than a percentage ramp for B2B, because it lets you start with tolerant customers and keep the largest ones last.
@followup
What if the data volume makes backfill take weeks?
@answer
Then the backfill runs continuously in the background while dual-writing keeps new data current, and you migrate read traffic per entity as its backfill completes rather than waiting for the whole set — a per-record "migrated" flag makes that possible. The backfill must be throttled and monitored against replication lag, resumable from a checkpoint, and it should be able to run at reduced rate during peak hours. Weeks is fine as long as the system remains correct and rollback-able throughout, which the sequence guarantees.
@red
- A cutover with a maintenance window as the only plan.
- Switching reads without shadow comparison.

### How do you design an idempotent, ordered event pipeline?
@short
Partition by the entity whose ordering matters, so events for one aggregate go to one partition and are processed in order by one consumer. Give every event a stable id for deduplication and a monotonic sequence per aggregate so consumers can detect gaps and reordering. Global ordering is neither achievable nor usually needed.
@deep
Ordering guarantees in message systems are per-partition, not global — Kafka guarantees order within a partition, SQS FIFO within a message group. So the partition key is the design decision: order by `orderId` and every event for that order is sequential, while different orders proceed in parallel.

Consumers still need to handle reordering across partitions and duplicates within one, because a rebalance or a retry can deliver out of order relative to what the producer sent.
@code ts Partitioning, sequencing and gap-tolerant consumption
// Producer: partition by the aggregate whose order matters
await producer.send({
  topic: 'order-events',
  messages: [{
    key: orderId,                          // ← partition key: per-order ordering
    value: JSON.stringify({ eventId, orderId, seq, type, payload }),
    headers: { traceparent },
  }],
});

// Consumer: idempotent + order-aware, tolerant of gaps
async function handle(e: OrderEvent) {
  await withTransaction(async (tx) => {
    const claimed = await tx.query(
      `INSERT INTO processed_events (id, consumer) VALUES ($1,$2)
       ON CONFLICT DO NOTHING RETURNING id`, [e.eventId, CONSUMER]);
    if (!claimed.rowCount) return;                                   // duplicate

    const state = await tx.query(
      `SELECT last_seq FROM projections WHERE order_id=$1 FOR UPDATE`, [e.orderId]);
    const last = state.rows[0]?.last_seq ?? 0;

    if (e.seq <= last) return;                                       // stale/reordered → ignore
    if (e.seq > last + 1) {                                          // GAP → we missed one
      await tx.query(`INSERT INTO pending_events VALUES ($1,$2,$3)`, [e.orderId, e.seq, e]);
      metrics.increment('pipeline.gap');
      return;                                                        // apply later, in order
    }
    await applyProjection(e, tx);
    await tx.query(`UPDATE projections SET last_seq=$2 WHERE order_id=$1`, [e.orderId, e.seq]);
    await drainPending(e.orderId, tx);                               // apply buffered successors
  });
}
@end
@senior
Buffering out-of-order events rather than dropping or blindly applying them is the detail that makes a projection trustworthy. Dropping loses data silently; applying out of order corrupts the state; buffering and draining is correct and self-healing. The other design point is that the partition key determines your parallelism ceiling — keying by `orderId` gives you high parallelism, keying by `tenantId` gives you per-tenant ordering but makes a large tenant a hot partition. That trade-off is worth stating explicitly because it is where these pipelines actually break under load.
@followup
How do you reprocess a stream after fixing a projection bug?
@answer
Rebuild the projection from the event log: create a new projection table, replay from the beginning (or from a snapshot) into it with the fixed logic, verify against the old one, then switch reads. That requires the events to be retained and the projection to be a pure function of the event history — which is the main practical benefit of event sourcing. If the consumer has external side effects, replay must be able to suppress them, which is why side effects belong in a separate consumer from projections.
@red
- Assuming global ordering across partitions.
- Applying out-of-order events without detection.

### How do you design a multi-tenant system that stays fair under load?
@short
Isolate tenants at every shared resource: per-tenant rate limits and quotas, bounded concurrency per tenant against the database and queues, separate queues or priority lanes for large customers, and per-tenant observability so a noisy neighbour is identifiable in seconds rather than hours.
@deep
The problem is that shared resources are consumed first-come-first-served by default, so one tenant running an expensive export can starve everyone. Rate limiting requests is not sufficient, because one request can be a thousand times more expensive than another.

The controls that actually work are concurrency caps (a tenant may hold at most N database connections or N worker slots) and cost-based quotas, plus statement timeouts so no single query can monopolise the database.
@code ts Per-tenant fairness at the resource level, not just the request level
// Concurrency cap per tenant — the real protection against expensive requests
const tenantLimiters = new LRUCache<string, Limiter>({ max: 10_000 });
function limiterFor(tenantId: string, plan: Plan) {
  return tenantLimiters.get(tenantId) ??
    tenantLimiters.set(tenantId, pLimit(plan === 'enterprise' ? 20 : 5)).get(tenantId)!;
}

app.use(async (req, res, next) => {
  const limit = limiterFor(req.user.tenantId, req.user.plan);
  if (limit.pendingCount > 50)                                  // queue too deep for this tenant
    return res.status(429).set('Retry-After', '5').json({ error: 'TENANT_CONCURRENCY' });
  limit(() => new Promise<void>(resolve => { res.on('finish', resolve); next(); }));
});

// Worker fairness: round-robin across tenant queues rather than FIFO across all work
const queues = tenants.map(t => new Queue(`jobs:${t}`));
// ...consume one job from each tenant in rotation, so a 10,000-job import
//    from one tenant cannot delay everyone else's single job.

-- Database: no query may monopolise a connection
ALTER ROLE app_runtime SET statement_timeout = '15s';
@end
@senior
Round-robin consumption across per-tenant queues is the detail that matters most in practice: with a single shared queue, one customer enqueuing ten thousand jobs delays every other customer's job behind them, and no amount of request rate limiting prevents it because the requests were legitimate. Per-tenant queues with fair scheduling fix it structurally. I would also emphasise per-tenant metrics — request rate, latency, database time and queue depth labelled by tenant — because during an incident the first question is "is this everyone or one customer", and without that dimension you cannot answer it quickly.
@followup
When do you move a tenant to dedicated infrastructure?
@answer
When their load or their requirements make them a risk to everyone else, or when they pay for isolation — a customer who is 40% of your volume, or one with data residency or compliance requirements that shared infrastructure cannot satisfy. The important thing is that the migration path exists before you need it: a tenant-scoped schema and tenant-aware routing mean moving one customer is an operational task, whereas a system with no tenant isolation requires an architecture change under pressure.
@red
- Rate limiting requests but not resource consumption.
- A single shared queue for all tenants.

# SECTION Node.js & Backend Internals | The questions that separate "I use Node" from "I have debugged Node in production".

### Walk through the libuv event loop phases in detail.
@short
Each iteration runs: timers (expired `setTimeout`/`setInterval`), pending callbacks (deferred system errors), idle/prepare (internal), poll (wait for and process I/O), check (`setImmediate`), and close callbacks. Between every phase, and between every callback, `process.nextTick` drains and then the microtask queue drains.
@deep
The poll phase is where the loop actually waits. If there are no pending timers and nothing in the check queue, it blocks on epoll for incoming I/O — which is why an idle Node process consumes no CPU. If a timer is due soon, the poll timeout is bounded by that.

The subtlety that catches people: `setTimeout(fn, 0)` is clamped to 1ms, and whether it fires before a `setImmediate` at the top level depends on how long the process took to start — genuinely non-deterministic. Inside an I/O callback the answer is deterministic, because you are already past poll.
@arch One iteration, with the drain points marked
   ┌─────────────────────────────────────────────────────────────┐
   │  timers        expired setTimeout / setInterval callbacks    │
   │      ↓  ← nextTick queue drained, then microtasks drained    │
   │  pending       deferred TCP errors etc.                      │
   │      ↓  ← drain                                              │
   │  idle/prepare  internal                                      │
   │      ↓                                                       │
   │  poll          ▸ compute timeout (0 if check queue non-empty,│
   │                  else time to next timer, else block)        │
   │                ▸ epoll_wait → run I/O callbacks              │
   │      ↓  ← drain                                              │
   │  check         setImmediate callbacks                        │
   │      ↓  ← drain                                              │
   │  close         'close' events (socket.on('close'))           │
   └───────────────────────────┬─────────────────────────────────┘
                               └──► next iteration

   THREAD POOL (default 4, UV_THREADPOOL_SIZE): fs, dns.lookup, zlib,
   crypto.pbkdf2/scrypt/randomBytes. Completions are delivered in the poll phase.
   NETWORK I/O does NOT use the pool — it uses epoll/kqueue directly.
@end
@code js Demonstrating pool saturation versus loop blocking — two different problems
// A. Thread-pool saturation: CPU is idle, latency rises, loop lag is LOW
for (let i = 0; i < 8; i++) crypto.pbkdf2('p','s',200_000,64,'sha512', () => {});
// → the 5th–8th wait for a free pool thread. Fix: UV_THREADPOOL_SIZE, or move it out.

// B. Event-loop blocking: CPU is pinned, loop lag is HIGH, everything stalls
JSON.parse(hugeString);                 // synchronous, 800ms, nothing else runs
// → Fix: stream it, or worker_threads, or do not do it in the request path.

// Distinguishing them in production:
//   loop lag high + CPU high   → blocking JS (profile it)
//   loop lag low  + latency high → pool saturation OR a slow dependency (trace it)
@end
@senior
Being able to distinguish thread-pool saturation from event-loop blocking is the practically useful part of knowing the phases, because they present identically to users and need opposite fixes. The signature is that pool saturation shows normal loop lag and normal CPU with rising latency — which looks like "the database is slow" until you notice the database is fine. I have seen that caused by `bcrypt` on a login endpoint under a traffic spike, and the fix was moving hashing off the request path rather than scaling instances.
@followup
Why does `dns.lookup` use the thread pool but `dns.resolve` not?
@answer
`dns.lookup` calls the operating system's `getaddrinfo`, which is a blocking synchronous C call, so libuv runs it on the thread pool — meaning a burst of outbound connections to new hostnames can saturate four threads and stall unrelated file I/O. `dns.resolve` talks to a DNS server directly over the network using c-ares, so it uses the event loop like any other socket. In practice the fix for a service making many outbound calls is a DNS cache plus keep-alive agents, which removes most lookups entirely.
@red
- Describing the loop as a single queue.
- Not knowing which operations use the thread pool.

### How does V8 optimise and deoptimise, and when does that matter?
@short
V8 interprets bytecode in Ignition while collecting type feedback, then TurboFan compiles hot functions to machine code using speculative assumptions about the shapes and types it observed. If those assumptions are violated the code is deoptimised back to the interpreter, which can be a significant cliff in a hot loop.
@deep
Hidden classes and inline caches are the mechanism. Objects created with the same properties in the same order share a hidden class, so a property access site that always sees one shape compiles to a fixed offset load — monomorphic. Two to four shapes is polymorphic and slower; more is megamorphic and falls back to a dictionary lookup.

Deoptimisation triggers include a new object shape at a hot site, a value that overflows the assumed representation (a small integer becoming a double), and `try/catch` patterns in older versions.
@code js Where this genuinely matters — and where it does not
// MATTERS: a hot loop over millions of records with inconsistent shapes
// ❌ two hidden classes → polymorphic access, slower per iteration
const rows = raw.map(r => r.email ? { id: r.id, email: r.email } : { id: r.id });

// ✅ one shape always
const rows = raw.map(r => ({ id: r.id, email: r.email ?? null }));

// MATTERS: number representation. Staying in Smi range is measurably faster.
let total = 0;                    // Smi
total += row.amountMinor;         // stays integer — good
// total += row.amount * 1.18;    // becomes double → different representation

// DOES NOT MATTER: a request handler that does 3 database calls.
// The 200ms of I/O dwarfs every V8 consideration. Optimise the I/O.

// Diagnose before believing any of this:
//   node --trace-deopt --trace-opt app.js     (noisy but definitive)
//   or just take a CPU profile and look at the widest frame
@end
@senior
The honest framing is that this matters in perhaps one percent of application code — a parser, a transform over a very large dataset, a hot serialisation path — and is irrelevant everywhere else, where the cost is I/O. I would resist a candidate-style answer that treats V8 micro-optimisation as a general performance strategy. What I do apply universally is consistent object shapes, because it costs nothing, improves readability and makes TypeScript happier. Everything beyond that requires a profile showing the function is actually hot.
@followup
Why is `delete obj.x` discouraged?
@answer
Deleting a property transitions the object out of its hidden class into dictionary mode, where property access is a hash lookup rather than a fixed offset — and it generally stays that way for the object's lifetime. In a hot path that is a substantial slowdown, and it also invalidates inline caches at every site that touches similar objects. Setting the property to `null` or `undefined`, or constructing a new object without it, avoids the transition. In cold code it genuinely does not matter.
@red
- Presenting V8 micro-optimisation as a general strategy.
- Claiming to optimise for V8 without ever profiling.

### How do worker threads work and when do you use them?
@short
`worker_threads` runs JavaScript on a separate thread with its own event loop and V8 isolate, communicating by message passing or shared memory via `SharedArrayBuffer`. I use them for CPU-bound work that must stay in-process — parsing, hashing, image transforms — behind a bounded pool, because worker startup costs tens of milliseconds.
@deep
Each worker has its own heap, so passing objects copies them via structured clone, which is itself expensive for large payloads. `ArrayBuffer` can be *transferred* rather than copied, moving ownership at near-zero cost, and `SharedArrayBuffer` allows genuine shared memory with `Atomics` for coordination.

The memory model matters operationally: workers share the process's memory limit, so ten workers each holding a large buffer will OOM the container.
@code ts A bounded worker pool with transfer rather than copy
import Piscina from 'piscina';

const pool = new Piscina({
  filename: new URL('./workers/transform.js', import.meta.url).href,
  minThreads: 2,
  maxThreads: Math.max(2, cpus().length - 1),      // leave a core for the main loop
  idleTimeout: 30_000,
  maxQueue: 200,                                   // ← backpressure: reject rather than buffer
  resourceLimits: { maxOldGenerationSizeMb: 256 }, // one worker cannot eat the whole container
});

// Transfer the buffer — ownership moves, no copy. Critical for large payloads.
const result = await pool.run({ buffer }, { transferList: [buffer] });

// worker: transform.js
export default function ({ buffer }) {
  return heavyPureComputation(new Uint8Array(buffer));   // no I/O, no shared state
}
@end
@senior
`maxQueue` is the line that turns a worker pool from a performance feature into a resilient one: without it, a burst of CPU work queues unboundedly, memory grows, and requests time out while still consuming a slot. Rejecting with a 503 when the pool queue is full is the correct behaviour. The other point is the decision boundary — workers are right for CPU work measured in tens or hundreds of milliseconds that must return within the request; anything longer belongs in a queue and a separate service, because it needs independent scaling and must survive a deploy.
@followup
When is a worker slower than doing the work inline?
@answer
When the work is short relative to the overhead: worker startup is tens of milliseconds, and structured-clone serialisation of a large object can cost more than the computation itself. A pool amortises startup, but the transfer cost remains. So for anything under a few milliseconds, or where the payload is large and cannot be transferred as a buffer, inline is faster. I measure rather than assume, because the crossover point depends heavily on payload shape.
@red
- Creating a worker per request.
- Passing large objects by copy instead of transferring buffers.

### How do you diagnose and fix a production memory leak, end to end?
@short
Confirm the trend with RSS and post-GC heap floor over hours, take heap snapshots under load at intervals, diff them to find the growing object types, and follow the retainer path to the holder. In Node the cause is almost always an unbounded cache, uncleaned listeners, a timer holding a closure, or streams not destroyed.
@deep
The distinction between heap and RSS growth directs the investigation. Growing heap with growing object counts is a JavaScript retention problem. Growing RSS with flat heap points at `Buffer` allocations, native module memory, or many open handles — which a heap snapshot will not show clearly.

Snapshot diffing is the decisive tool: the comparison view shows which constructors grew between snapshots, and selecting an instance shows the chain of references keeping it alive.
@code js The investigation, with the instrumentation that makes it possible
// 1. Confirm: is the POST-GC floor rising, or is this normal sawtooth?
setInterval(() => {
  const m = process.memoryUsage();
  logger.info({ rssMb: m.rss/1e6, heapUsedMb: m.heapUsed/1e6,
                externalMb: m.external/1e6,               // Buffers live here
                arrayBuffersMb: m.arrayBuffers/1e6,
                handles: process._getActiveHandles().length,   // sockets/timers not cleaned
                requests: process._getActiveRequests().length }, 'mem');
}, 30_000).unref();

// 2. Capture on demand during the incident (SIGUSR2 → not caught by anything else)
process.on('SIGUSR2', () => v8.writeHeapSnapshot(`/tmp/heap-${Date.now()}.heapsnapshot`));

// 3. Diff in Chrome DevTools → Comparison view → sort by "# Delta"
//    Typical findings and their causes:
//      Closure ×420,000 retained by Timeout      → setInterval capturing per-request state
//      Array ×1 with 2.1M elements               → module-level cache never evicted
//      Socket ×18,400                            → streams not destroyed on error
//      String ×900,000 retained by Map           → unbounded memo keyed by request body
@end
@senior
Tracking `_getActiveHandles().length` alongside memory is the cheapest early-warning signal I know: a steadily rising handle count means sockets, timers or streams are leaking, and it moves before memory becomes critical, so you can act during business hours rather than at 3am. The other operational point is `--max-old-space-size` relative to the container limit — setting the heap limit below the container's memory means you get a catchable JavaScript out-of-memory error with a stack trace instead of a silent SIGKILL from the kernel OOM killer, which is the difference between a diagnosable incident and a mysterious restart.
@followup
What if the leak is in a dependency?
@answer
Confirm it with a minimal reproduction, check the issue tracker for a known fix, and in the meantime contain it: bound the usage, restart on a schedule as a temporary mitigation, or isolate the dependency into a separate process that can be recycled without affecting the main service. I would also weigh replacing it — a leaking dependency in a long-running process is a recurring operational cost, and the effort of switching is often less than living with scheduled restarts indefinitely.
@red
- Concluding "memory leak" from RSS growth alone without checking the GC floor.
- Restarting on a schedule and stopping there.

### How do you handle CPU-bound work in a Node service architecturally?
@short
Classify by duration and user expectation: microseconds stays inline, tens to hundreds of milliseconds goes to a worker pool, anything longer goes to a queue and a separate worker service. The queue option also gives you retries, backpressure, independent scaling and survival across deploys.
@deep
The architectural reason to prefer the queue for longer work is isolation: CPU-heavy processing in the same service as the API means a burst of processing degrades every API request, and autoscaling on CPU cannot distinguish the two workloads.

Separating them lets you scale the API on request rate and the workers on queue depth, and lets the workers run on cheaper compute optimised for CPU.
@arch The decision tree, with the metric that drives each
  < 1ms          inline. Do not think about it.
  1–50ms         inline, but measure event-loop lag under load. Consider batching.
  50–500ms       worker_threads pool, bounded queue, reject when full (503).
                 → keeps the API responsive; result still returned in the request
  > 500ms        QUEUE + separate worker service. Return 202 + job id.
                 → user polls, or receives a webhook/websocket/push on completion
  > 30s          definitely queue. Also: progress reporting, cancellation, resumability.

  WHY the split at ~500ms: beyond that you are fighting client timeouts, load-balancer
  idle timeouts, and mobile radio behaviour. 202 + polling is more reliable AND
  scales better than holding a connection open.

  SCALING SIGNALS
   API service     → requests/sec, p95 latency, event-loop lag
   Worker service  → queue depth AND oldest-job age (age is the user-facing one)
@end
@code ts The 202 pattern, with progress and cancellation
app.post('/reports', authenticate, async (req, res) => {
  const job = await reports.enqueue({ tenantId: req.user.tenantId, spec: req.body });
  res.status(202).location(`/reports/${job.id}`).json({ id: job.id, status: 'queued' });
});

app.get('/reports/:id', authenticate, async (req, res) => {
  const job = await reports.get(req.params.id, req.user.tenantId);   // tenant-scoped
  res.json({ status: job.status, progress: job.progress,             // 0..1
             downloadUrl: job.status === 'done' ? await signedUrl(job.key) : null,
             error: job.error });
});

app.delete('/reports/:id', authenticate, async (req, res) => {
  await reports.cancel(req.params.id, req.user.tenantId);            // sets a flag the worker checks
  res.status(204).end();
});
@end
@senior
Returning 202 with a job resource rather than holding a connection is the architectural point, and it has consequences people underestimate: it survives deploys, it works on mobile networks where a 40-second connection will not, it gives you progress and cancellation for free, and it makes the work retryable. The alternative — a synchronous endpoint that "usually" completes in 20 seconds — fails at the load balancer's idle timeout, fails on a rolling deploy, and gives the user nothing when it does. I would also monitor oldest-job age rather than queue depth, because that is what the user experiences.
@followup
How do you cancel work that is already running?
@answer
Cooperatively: the worker checks a cancellation flag between units of work, or an `AbortSignal` propagated into the operations that support it, and stops cleanly. You cannot forcibly kill a thread or a promise in Node, so the work must be structured in chunks that yield. For a subprocess you can send a signal, and for an external API call the `AbortController` aborts the HTTP request — which for something like an LLM call also stops you paying for tokens.
@red
- Holding an HTTP connection open for a 60-second job.
- Autoscaling API and CPU work together on one metric.

### How do you design a Node service for high throughput specifically?
@short
Keep the event loop free, reuse connections, avoid per-request allocation in hot paths, batch database access, stream large payloads, and choose a fast serialisation path. Then scale horizontally with one process per container so the orchestrator's metrics are meaningful.
@deep
The biggest single-process wins in my experience are connection reuse for outbound HTTP (a keep-alive agent removes a TLS handshake per call), schema-compiled JSON serialisation, and eliminating synchronous work from the request path.

Framework choice matters less than people think — Fastify is genuinely faster than Express, mainly due to schema-based serialisation and a faster router, but the difference is typically dwarfed by database time in a real application.
@code ts The changes that actually move throughput
// 1. Outbound connection reuse — often the single biggest win
const agent = new https.Agent({ keepAlive: true, maxSockets: 128, keepAliveMsecs: 30_000,
                                scheduling: 'lifo' });

// 2. Schema-compiled serialisation (what makes Fastify fast) — 2–4× vs JSON.stringify
const stringify = fastJson({
  type: 'object',
  properties: { id: { type: 'string' }, totalMinor: { type: 'integer' },
                status: { type: 'string' } },
});
res.setHeader('content-type', 'application/json').end(stringify(order));

// 3. Batch instead of per-item round trips
const users = await db.query('SELECT * FROM users WHERE id = ANY($1)', [ids]);

// 4. Stream large responses; never buffer
await pipeline(cursorStream, toNdjson, res);

// 5. Compression: worth it for text, costs CPU. Threshold it, and prefer the
//    load balancer/CDN doing it over the Node process.
app.use(compression({ threshold: 1024 }));

// 6. One process per container; let the orchestrator scale on requests + loop lag
@end
@senior
The keep-alive agent is the change I would highlight because it is one line and frequently worth tens of milliseconds per outbound call — without it Node opens a new TCP and TLS connection for every request to a third party, which under load also exhausts ephemeral ports. The serialisation point is the second: `JSON.stringify` is generic and has to inspect the object, while a compiled serialiser generated from a schema knows the shape in advance. That said, I would always be clear that these matter after the database work is right; a 2× serialisation improvement on an endpoint spending 300ms in Postgres is noise.
@followup
Would you switch from Express to Fastify for performance?
@answer
Not for performance alone in a database-bound service, because the framework is rarely the bottleneck — I would need a profile showing routing and serialisation as a meaningful share of request time. I would consider Fastify for a new service on its own merits: schema-first validation and serialisation, better TypeScript integration, and a plugin model with proper encapsulation. Migrating a large working Express codebase for a few percent throughput is usually a poor trade against the risk and the effort.
@red
- Chasing framework benchmarks while the database is the bottleneck.
- No keep-alive on outbound HTTP.

### How do you build a rate limiter that is correct under concurrency and failure?
@short
Atomic increment-and-check in a single Redis operation, usually a Lua script implementing a token bucket or sliding window, keyed by the dimension you want to protect, with the failure policy chosen per endpoint. Anything that reads then writes from application code is racy and will let bursts through.
@deep
The algorithms differ in accuracy and cost. Fixed window is cheapest but allows double the limit across a boundary. Sliding window log is exact but stores a timestamp per request. Sliding window counter approximates well with two counters. Token bucket allows bursts up to capacity while enforcing a sustained rate, which is usually the best user experience.

Distribution matters too: with many application instances, only a shared store gives a correct global limit, and the network round trip becomes part of your latency budget.
@code lua Sliding-window counter — accurate, two keys, one round trip
-- KEYS[1] = current window key, KEYS[2] = previous window key
-- ARGV: limit, windowMs, nowMs, cost
local limit, window, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local elapsed = now % window
local weight  = (window - elapsed) / window          -- how much of the previous window still counts

local prev = tonumber(redis.call('GET', KEYS[2]) or '0')
local cur  = tonumber(redis.call('GET', KEYS[1]) or '0')
local estimated = prev * weight + cur

if estimated + cost > limit then
  return { 0, math.ceil((window - elapsed) / 1000), limit - math.floor(estimated) }
end
redis.call('INCRBY', KEYS[1], cost)
redis.call('PEXPIRE', KEYS[1], window * 2)
return { 1, 0, limit - math.floor(estimated + cost) }
@end
@code ts Applying it, with a local pre-filter to save round trips
// Local token bucket as a cheap pre-filter: obvious floods are rejected without
// touching Redis at all. Redis remains the authority for anything that passes.
const localBucket = new LRUCache<string, number>({ max: 50_000, ttl: 1000 });

export async function allow(key: string, cost: number, limit: number) {
  const localCount = (localBucket.get(key) ?? 0) + cost;
  localBucket.set(key, localCount);
  if (localCount > limit) return { allowed: false, retryAfter: 1 };   // no Redis call needed

  try {
    const [ok, retryAfter, remaining] = await redis.eval(SCRIPT, 2, cur(key), prev(key),
                                                         limit, WINDOW_MS, Date.now(), cost);
    return { allowed: ok === 1, retryAfter, remaining };
  } catch {
    return { allowed: FAIL_OPEN_ROUTES.has(key), retryAfter: 1 };     // policy, per route
  }
}
@end
@senior
The local pre-filter is a genuinely useful optimisation under attack conditions: during a flood, most requests can be rejected without a Redis round trip, which stops the rate limiter itself becoming the bottleneck — an ironic but real failure mode. It is approximate, since each instance has its own view, but it only ever rejects traffic that would exceed the limit even on one instance. The other point is that the failure policy belongs per route, not globally: failing open on login and closed on an expensive AI endpoint are both correct, for opposite reasons.
@followup
How do you rate limit fairly when clients share an IP?
@answer
Prefer authenticated identity over IP wherever it exists, and when you must use IP, layer it: a generous IP limit to catch obvious floods, plus a tighter per-account limit for the sensitive operations. For login specifically I key on the target account as well as the source, so credential stuffing against one account is throttled regardless of how many IPs the attacker uses. Pure IP limiting punishes corporate NATs and mobile carriers while barely inconveniencing a botnet, which is the worst of both.
@red
- Read-then-write rate limiting from application code.
- One global failure policy for every endpoint.

### How does garbage collection work in V8 and how does it affect latency?
@short
V8 uses a generational collector: a small young generation collected frequently by a fast copying scavenger, and an old generation collected by mark-sweep-compact, which runs incrementally and concurrently to limit pause times. Most objects die young, so scavenges are cheap; old-generation collections are the ones that show up in tail latency.
@deep
Modern V8 does most old-space marking concurrently on background threads and only pauses briefly for atomic phases, so typical pauses are single-digit milliseconds rather than the hundreds you might expect. But a large live heap increases both marking work and compaction cost, so tail latency degrades as heap size grows.

The lever you actually control is allocation rate and retention. Fewer allocations mean fewer scavenges; less retention means a smaller old generation.
@code js Observing GC and reducing pressure
import { PerformanceObserver } from 'node:perf_hooks';

new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    gcHistogram.observe({ kind: e.detail.kind }, e.duration);
    if (e.duration > 50) logger.warn({ ms: e.duration, kind: e.detail.kind }, 'long GC pause');
  }
}).observe({ entryTypes: ['gc'] });

// Reducing allocation pressure in a hot path
// ❌ allocates a new object and a new array per row, 200k times
rows.map(r => ({ ...r, total: r.qty * r.price }));

// ✅ reuse a buffer / write directly into the output; avoid intermediate arrays
const out = new Array(rows.length);
for (let i = 0; i < rows.length; i++) out[i] = rows[i].qty * rows[i].price;

// Container tuning that matters more than GC flags:
//   --max-old-space-size below the container memory limit
//   → catchable JS OOM error instead of a silent SIGKILL
@end
@senior
The practically important point is that GC tuning is almost never the right lever in application code — the effective fix for GC-related latency is to allocate less and retain less, which is the same work as fixing a memory leak. Where GC does matter operationally is heap sizing relative to the container: too small and you collect constantly, too large and pauses lengthen and the kernel may kill you. Setting `--max-old-space-size` deliberately, below the container limit, is the one configuration change I would always make.
@followup
Does Node have stop-the-world pauses that affect p99?
@answer
Yes, but much smaller than people expect on modern V8 — concurrent marking and incremental compaction keep typical pauses in the low single-digit milliseconds, so they are visible in p999 rather than p99 for most services. They become significant with a large live heap, which is why an in-process cache holding hundreds of megabytes is a latency decision as well as a memory one. If GC pauses genuinely dominate your tail latency, moving that cache to Redis usually fixes it more effectively than any flag.
@red
- Recommending `global.gc()` or manual collection.
- Blaming GC for latency without a GC trace.

### How do you handle streams, backpressure and error propagation correctly?
@short
Use `stream.pipeline` rather than `.pipe()`, because pipeline propagates errors and destroys every stream in the chain on failure, whereas `.pipe()` leaks file descriptors and sockets. Respect `highWaterMark` by letting pipeline handle flow control, and never mix async iteration with piping on the same stream.
@deep
The classic leak is `a.pipe(b)` where `b` errors: `a` keeps reading, its handle is never released, and under load you exhaust file descriptors. `pipeline` was added specifically to fix this and is the only form I use.

Async generators compose nicely with pipeline, which lets you write the transformation as readable business logic while pipeline handles buffering, backpressure and teardown.
@code ts A streaming export with correct teardown and error handling
import { pipeline } from 'node:stream/promises';

app.get('/exports/transactions.ndjson', authenticate, async (req, res) => {
  const cursor = db.queryStream(
    'SELECT id, amount_minor, created_at FROM transactions WHERE tenant_id = $1',
    [req.user.tenantId]);

  res.setHeader('Content-Type', 'application/x-ndjson');
  res.setHeader('Cache-Control', 'no-store');

  // async generator: readable logic, pipeline handles backpressure + destroy-on-error
  async function* toNdjson(source: AsyncIterable<Row>) {
    let n = 0;
    for await (const row of source) {
      yield JSON.stringify(row) + '\n';
      if (++n % 10_000 === 0) metrics.gauge('export.rows', n);
    }
  }

  try {
    await pipeline(cursor, toNdjson, res, { signal: AbortSignal.timeout(300_000) });
  } catch (err) {
    if (res.headersSent) res.destroy(err as Error);        // cannot change status now
    else res.status(500).json({ error: 'EXPORT_FAILED' });
    logger.error({ err, tenantId: req.user.tenantId }, 'export failed');
  }
});

// Client disconnects mid-export → pipeline destroys the DB cursor. Without it,
// the query keeps running and holds a connection.
@end
@senior
The client-disconnect case is the one that bites in production: a user closes the tab during a large export, and without proper teardown the database cursor keeps streaming and holds a pooled connection until the query finishes — which under repeated use exhausts the pool. `pipeline` propagates the destroy in both directions, which is the whole reason to use it. I would also note the headers-sent constraint: once you have started streaming a 200, you cannot switch to a 500, so all validation and authorisation must complete before the first byte.
@followup
When would you not use streams?
@answer
When the data is small enough that the complexity is not worth it — under a few megabytes, buffering is simpler and the memory cost is irrelevant. Streams also make error handling and testing harder, and they interact awkwardly with anything that needs the whole payload, such as computing a signature over a body. The rule I use is that streaming is for unbounded or user-controlled sizes; for known-small responses, simplicity wins.
@red
- `.pipe()` in production code.
- Not destroying upstream resources when the client disconnects.

# SECTION Database Internals & Advanced PostgreSQL | Where senior backend interviews get genuinely hard. Your production engine is MySQL and InnoDB — answer in Postgres terms only where the question is Postgres, and say which engine you are describing.

### Explain MVCC and its consequences.
@short
Every row update writes a new version rather than overwriting, tagged with the transaction id that created it and the one that deleted it. Each transaction sees a snapshot consistent with its start, so readers never block writers and writers never block readers. The costs are dead tuples requiring vacuum, table bloat, and transaction id wraparound.
@deep
Visibility is decided per tuple by comparing `xmin` and `xmax` against the transaction's snapshot. Under Read Committed a new snapshot is taken per statement; under Repeatable Read one snapshot covers the whole transaction.

The operational consequences follow directly. Updates are effectively insert-plus-mark-dead, so an update-heavy table grows and needs vacuum. A long-running transaction holds an old snapshot, which prevents vacuum from removing anything newer — so one forgotten transaction bloats the entire database.
@code sql Seeing MVCC directly, and its costs
-- Every row carries its version metadata
SELECT xmin, xmax, ctid, * FROM orders WHERE id = $1;

-- An UPDATE creates a new tuple; the old one becomes dead until vacuumed
UPDATE orders SET status = 'paid' WHERE id = $1;
-- ctid changes → the physical location moved → every index entry must be updated too,
-- UNLESS it is a HOT update (no indexed column changed AND there is room in the page)

-- Why a long transaction is destructive
SELECT pid, now() - xact_start AS age, state, left(query, 60)
  FROM pg_stat_activity
 WHERE xact_start IS NOT NULL AND now() - xact_start > interval '5 min'
 ORDER BY age DESC;
-- Any tuple newer than the OLDEST such snapshot cannot be vacuumed, database-wide.

-- Bloat symptom: size grows while row count is flat
SELECT relname, n_live_tup, n_dead_tup,
       pg_size_pretty(pg_total_relation_size(relid)) AS total
  FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
@end
@senior
HOT updates are the detail worth knowing because they are the difference between an update costing one page write and costing one page write plus an index write per index. If no indexed column changed and the page has free space, Postgres links the new tuple within the page and skips index maintenance entirely. That is why `fillfactor` below 100 on an update-heavy table can measurably improve write throughput, and why adding an index on a frequently updated column has a hidden cost beyond the index itself — it disables HOT for those updates.
@followup
What is transaction id wraparound and how do you avoid it?
@answer
Transaction ids are 32-bit and wrap; vacuum freezes old tuples so ancient transactions do not appear to be in the future. If autovacuum cannot keep up — usually because of a long-running transaction, an abandoned replication slot, or a prepared transaction left behind — the database eventually refuses writes to protect itself. I monitor `age(datfrozenxid)` with an alert well before the threshold, and I treat abandoned replication slots as a first-class alert because they are the most common real-world cause and they also grow WAL until the disk fills.
@red
- Not connecting long transactions to bloat.
- Thinking an UPDATE modifies a row in place.

### How does the query planner choose a plan, and how do you influence it?
@short
It enumerates plans, estimates each one's cost from table statistics and cost constants, and picks the cheapest. You influence it by giving it better information — accurate statistics, extended statistics for correlated columns, appropriate indexes — and by tuning cost constants to match your hardware, not by forcing plans.
@deep
Estimates come from `pg_statistic`: row counts, most common values, histograms and correlation. The planner assumes independence between columns, which is where it goes badly wrong on correlated predicates — the selectivities multiply and the estimate can be off by orders of magnitude.

Cost constants matter too. `random_page_cost` defaults to 4.0, which assumes spinning disks; on SSD it should be near 1.1, and leaving it at the default systematically biases the planner against index scans.
@code sql Fixing a bad plan by fixing the information, not by forcing
-- Symptom: estimate 421 rows, actual 184,213 → nested loop chosen catastrophically
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'paid' AND created_at > now() - interval '7 days';

-- Cause: status and created_at are correlated (recent orders are mostly 'paid'),
-- but the planner multiplies independent selectivities.
CREATE STATISTICS orders_status_created (dependencies, ndistinct, mcv)
  ON status, created_at FROM orders;
ANALYZE orders;

-- Raise the sample size for a skewed column
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;

-- Hardware-appropriate cost constants (SSD)
ALTER SYSTEM SET random_page_cost = 1.1;
ALTER SYSTEM SET effective_cache_size = '12GB';    -- what the planner believes is cached

-- Diagnostic ONLY, never a production fix:
SET enable_seqscan = off;    -- proves the index plan is better; then fix the cause
@end
@senior
Extended statistics are the tool most people have never used, and correlated columns are the single most common source of catastrophic misestimation in real schemas — status and date, tenant and region, category and price band. Creating a statistics object often fixes a plan with no index change at all. The other point I would make is that forcing plans with `enable_*` flags is a diagnostic, not a fix: the data distribution changes, and a forced plan that is right today is wrong in three months, whereas correct statistics adapt.
@followup
Why does the same query have different plans in staging and production?
@answer
Different statistics, different data volumes and different configuration. A query over 5,000 rows in staging will legitimately choose a sequential scan; over 50 million it must not. Differences in `work_mem` change whether a hash join fits in memory, and differences in `effective_cache_size` change the planner's view of what is cached. That is why performance testing needs production-scale data, and why `auto_explain` in production is valuable — it captures the plan that actually ran under real conditions rather than the one you can reproduce locally.
@red
- Forcing plans as a permanent fix.
- Default `random_page_cost` on SSD storage.

### Explain isolation levels and the anomalies each prevents.
@short
Read Committed prevents dirty reads and is Postgres's default; each statement sees a fresh snapshot, so non-repeatable reads and phantoms are possible. Repeatable Read gives one snapshot for the whole transaction, preventing both, but can fail with a serialization error. Serializable additionally detects write skew, aborting transactions that would produce a non-serializable outcome.
@deep
The anomaly most people have never heard of is write skew, and it is the one that causes real bugs: two transactions each read a set, each decide their write is fine based on what they read, and both commit — producing a state neither would have allowed alone. Classic examples are two doctors both going off-call, or two concurrent bookings each checking that a room is free.

Postgres's Serializable uses Serializable Snapshot Isolation, which detects dangerous dependency structures and aborts one transaction rather than locking, so the application must be prepared to retry.
@code sql Write skew, and the three ways to prevent it
-- Two concurrent transactions, each checking "at least one doctor remains on call"
-- T1: SELECT count(*) FROM oncall WHERE shift=1 AND on_call;  -- 2 → OK to go off
-- T2: SELECT count(*) FROM oncall WHERE shift=1 AND on_call;  -- 2 → OK to go off
-- both UPDATE ... SET on_call=false. Result: ZERO doctors on call.
-- Read Committed AND Repeatable Read both allow this. It is WRITE SKEW.

-- FIX 1: Serializable — the database detects it and aborts one
BEGIN ISOLATION LEVEL SERIALIZABLE;
  ...
COMMIT;   -- may raise 40001 → the APPLICATION MUST RETRY

-- FIX 2: materialise the conflict with an explicit lock
SELECT * FROM oncall WHERE shift = 1 FOR UPDATE;   -- serialises the readers

-- FIX 3: express the invariant as a constraint the database enforces
ALTER TABLE oncall ADD CONSTRAINT at_least_one
  CHECK (...);   -- or an exclusion constraint / a counter row with a check
@end
@code ts Retrying serialization failures — mandatory with Serializable
async function withSerializable<T>(fn: (tx: Tx) => Promise<T>, attempts = 5): Promise<T> {
  for (let i = 0; i < attempts; i++) {
    try {
      return await withTransaction(async (tx) => {
        await tx.query('SET TRANSACTION ISOLATION LEVEL SERIALIZABLE');
        return fn(tx);
      });
    } catch (e: any) {
      if (e.code !== '40001' && e.code !== '40P01') throw e;   // serialization / deadlock
      await sleep(2 ** i * 10 + Math.random() * 20);           // backoff + jitter
    }
  }
  throw new Error('SERIALIZATION_RETRIES_EXHAUSTED');
}
@end
@senior
The point I would make is that Serializable is not free and not automatic: it moves the burden to the application, which must retry on 40001, and under high contention the abort rate can be severe. So my default is Read Committed with explicit locking or atomic updates where an invariant matters, and Serializable reserved for genuinely complex invariants that are hard to express otherwise — a booking system with overlapping constraints being the canonical case. Choosing it and then not retrying is worse than not choosing it at all, because the failures are intermittent and look like random errors.
@followup
Does an ORM's default isolation level matter?
@answer
Yes, and most default to the database's default — Read Committed in Postgres, Repeatable Read in MySQL InnoDB — which means the same application code behaves differently on the two databases. That is a genuine portability trap: a read-modify-write that is safe under MySQL's Repeatable Read with gap locks can be racy under Postgres's Read Committed. I set the isolation level explicitly for any transaction where it matters, rather than relying on a default that varies by engine and by configuration.
@red
- Not knowing what write skew is.
- Using Serializable without retry logic.

### How do locks work in Postgres, and how do you debug lock contention?
@short
Postgres takes row-level locks for writes and table-level locks for DDL, with a conflict matrix defining what blocks what. Contention shows up as queries waiting; you find it by joining `pg_stat_activity` with `pg_locks` to see who blocks whom, and you prevent most of it with short transactions and consistent lock ordering.
@deep
The table-level modes are the ones that cause outages: `ACCESS EXCLUSIVE`, taken by most `ALTER TABLE` forms and by `VACUUM FULL`, conflicts with everything including reads. Worse, a pending exclusive lock queues behind existing readers and blocks all subsequent queries — so a migration waiting for a lock takes down the table even before it runs.

Row-level deadlocks come from inconsistent ordering: two transactions locking the same rows in different sequences. Postgres detects the cycle and kills one after `deadlock_timeout`.
@code sql Finding the blocker, and preventing the class of problem
-- Who is blocking whom, right now
SELECT blocked.pid AS blocked_pid, blocked.query AS blocked_query,
       blocking.pid AS blocking_pid, blocking.query AS blocking_query,
       now() - blocking.xact_start AS blocking_age
  FROM pg_stat_activity blocked
  JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
 WHERE blocked.wait_event_type = 'Lock';

-- Emergency: cancel (gentle) or terminate (hard) the blocker
SELECT pg_cancel_backend(12345);
SELECT pg_terminate_backend(12345);

-- PREVENTION 1: never let a migration queue the world behind it
SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN region text;    -- fails fast instead of blocking everything

-- PREVENTION 2: consistent lock ordering avoids deadlocks
SELECT * FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE;   -- ← always by id

-- PREVENTION 3: queue consumers that never contend
SELECT * FROM jobs WHERE status='pending'
 ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 10;
@end
@senior
`FOR UPDATE SKIP LOCKED` is the pattern I would highlight for anything queue-like in the database: multiple workers can claim disjoint batches with no contention and no coordination, and a crashed worker's rows are simply reclaimed. It turns "we need a message broker" into "we can use Postgres" for a lot of workloads. And `SET lock_timeout` before DDL is the single most valuable operational habit in this area — I have seen a migration that should have been instant take an application down for six minutes purely because it queued behind a long-running report.
@followup
Why did adding a column take down the site?
@answer
Because `ALTER TABLE` needs an `ACCESS EXCLUSIVE` lock, and it could not get it — a long-running query held a conflicting lock. The pending exclusive request then queues, and every new query on that table queues behind it, so within seconds the entire table is unavailable even though the migration itself would have taken milliseconds. The fix is `lock_timeout` so the migration fails fast and retries, plus killing long-running queries before running DDL, plus using the non-blocking variants (`ADD COLUMN` nullable, `NOT VALID` constraints, `CREATE INDEX CONCURRENTLY`).
@red
- Running DDL without a lock timeout.
- Locking rows in different orders in different code paths.

### How do WAL, checkpoints and replication actually work?
@short
Every change is written to the write-ahead log before the data pages, so a crash can be recovered by replaying WAL. Checkpoints periodically flush dirty pages so recovery has a bounded starting point. Streaming replication ships WAL to replicas, which replay it — asynchronously by default, so a failover can lose the most recent transactions.
@deep
Checkpoint behaviour is a real tuning axis: infrequent checkpoints mean less repeated I/O but longer recovery and larger WAL; `checkpoint_completion_target` spreads the flushing so you get a gentle I/O curve rather than a spike that shows up as periodic latency.

Logical replication decodes WAL into row-level changes, which is what powers change-data-capture, selective replication and zero-downtime major-version upgrades.
@code sql Configuration, monitoring and the failure mode that fills your disk
-- Checkpoint tuning: fewer, spread-out checkpoints
max_wal_size = '8GB'
min_wal_size = '2GB'
checkpoint_completion_target = 0.9     -- spread I/O over 90% of the interval
wal_compression = on

-- Monitor replication lag in BYTES (time-based lag hides a stalled replica)
SELECT client_addr, state, sync_state,
       pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn)   AS sent_lag,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS replay_lag
  FROM pg_stat_replication;

-- ⚠️ THE CLASSIC OUTAGE: an inactive replication slot retains WAL forever
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
  FROM pg_replication_slots
 ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;
-- Inactive slot + high retained = your disk is filling. Drop it or fix the consumer.
ALTER SYSTEM SET max_slot_wal_keep_size = '64GB';   -- bound it defensively
@end
@senior
The abandoned replication slot is the specific failure I would name, because it is quietly catastrophic: a CDC consumer or a replica that goes away leaves its slot active, Postgres retains every WAL segment since that slot's position, and the disk fills — at which point the primary stops accepting writes entirely. `max_slot_wal_keep_size` bounds it at the cost of breaking that consumer, which is the right trade. I alert on both inactive slots and WAL directory size, because this is one of the few database failures that takes you from healthy to completely down with little warning.
@followup
How do you upgrade Postgres major versions with minimal downtime?
@answer
Logical replication: stand up the new version, replicate into it, let it catch up, then perform a brief cutover — stop writes, wait for the final lag to drain, repoint the application, and resume. Downtime is seconds to a minute rather than the hours a dump-and-restore would take on a large database. `pg_upgrade` with hard links is faster than dump-and-restore but still requires downtime proportional to catalogue size. Either way, the rehearsal on a restored snapshot is what makes the real one uneventful.
@red
- Not monitoring replication slots.
- Assuming asynchronous replication loses nothing on failover.

### How do you design indexes for a mixed read/write workload?
@short
Index for the queries that matter, then audit ruthlessly, because every index taxes every write. Prefer composite indexes that serve several queries over many single-column indexes, use partial indexes when queries always filter a subset, and use covering indexes to achieve index-only scans on hot read paths.
@deep
The write cost is concrete: each index must be updated on insert and delete, and on update unless the change qualifies as HOT. On a table with eight indexes, an insert is roughly eight additional random writes plus WAL.

The read benefit is only realised if the index matches the query's predicate and sort order. An index that is close but not quite right is pure cost.
@code sql Consolidating indexes, and measuring the write cost
-- ❌ four single-column indexes: four write costs, and none serves the real query well
CREATE INDEX ON orders (user_id);
CREATE INDEX ON orders (status);
CREATE INDEX ON orders (created_at);
CREATE INDEX ON orders (tenant_id);

-- ✅ one composite serves: (tenant), (tenant,user), (tenant,user,status),
--    and the sort — one write cost instead of four
CREATE INDEX CONCURRENTLY ON orders (tenant_id, user_id, status, created_at DESC)
  INCLUDE (total_minor);

-- ✅ partial index for a hot, tiny subset of a huge table
CREATE INDEX CONCURRENTLY ON orders (created_at)
 WHERE status = 'pending';        -- 0.4% of rows → tiny, stays in cache

-- AUDIT: which indexes are never used?
SELECT s.relname, s.indexrelname, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
  FROM pg_stat_user_indexes s
  JOIN pg_index i ON i.indexrelid = s.indexrelid
 WHERE s.idx_scan < 50 AND NOT i.indisunique
 ORDER BY pg_relation_size(s.indexrelid) DESC;

-- Reduce update cost on a hot table: leave room for HOT updates
ALTER TABLE orders SET (fillfactor = 85);
@end
@senior
The consolidation argument is the one I would lead with: a single well-ordered composite index frequently replaces three or four single-column ones, serving more queries at a quarter of the write cost. Postgres can combine separate indexes with bitmap scans, but that is usually slower than one correctly ordered composite. The `fillfactor` adjustment is the other lever specific to write-heavy tables — leaving free space in each page allows HOT updates, which skip index maintenance entirely, and that can meaningfully improve update throughput on a table with several indexes.
@followup
When is a BRIN index the right choice?
@answer
When the table is large, append-only, and the indexed column correlates with physical row order — time-series and event logs are the canonical case. BRIN stores only a min/max summary per block range, so it is orders of magnitude smaller than a B-tree: a few hundred kilobytes where a B-tree would be gigabytes, with negligible write cost. The trade is coarse granularity, so it is excellent for range scans over time and useless for point lookups. If the physical correlation breaks — because of updates or non-sequential inserts — it degrades badly.
@red
- One index per column by default.
- Never auditing which indexes are actually used.

### How do you handle very large tables — partitioning, archiving, or something else?
@short
Partition by the dimension queries filter on, usually time, so pruning limits each query to relevant partitions and retention becomes an instant `DROP TABLE`. Archive cold partitions to cheaper storage. Sharding is a later and much more expensive step, and most tables never need it.
@deep
The benefits of partitioning are query pruning, smaller per-partition indexes that stay in cache, instant retention, and cheaper maintenance because vacuum and reindex operate per partition.

The constraints are real: unique constraints must include the partition key, the planner cost grows with partition count, and a query without the partition key scans everything — which is worse than not partitioning at all.
@code sql A partitioned table with automated lifecycle and tiered storage
CREATE TABLE events (
  id bigserial, tenant_id uuid NOT NULL, type text NOT NULL,
  payload jsonb NOT NULL, created_at timestamptz NOT NULL,
  PRIMARY KEY (id, created_at)
) PARTITION BY RANGE (created_at);

-- Hot partitions: full indexes, on fast storage
CREATE TABLE events_2026_08 PARTITION OF events FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
CREATE INDEX ON events_2026_08 (tenant_id, created_at DESC);
CREATE INDEX ON events_2026_08 USING gin (payload jsonb_path_ops);

-- Warm partitions: drop the expensive GIN index, keep the btree
DROP INDEX events_2026_05_payload_idx;

-- Cold: detach and export, then drop. Instant, no bloat, no WAL storm.
ALTER TABLE events DETACH TABLE events_2025_08;
-- COPY events_2025_08 TO PROGRAM 'aws s3 cp - s3://archive/events_2025_08.csv.gz' (FORMAT csv);
DROP TABLE events_2025_08;

-- Verify pruning actually happens for your real queries
EXPLAIN SELECT * FROM events
 WHERE tenant_id = $1 AND created_at >= now() - interval '2 days';
-- must show only the 1–2 relevant partitions in the Append node
@end
@senior
Dropping the expensive indexes from older partitions is a technique worth knowing: recent data is queried by many dimensions and old data is usually queried only by time, so keeping a GIN index on two years of history is paying continuously for a capability nobody uses. Per-partition index policy is only possible because partitions are real tables. The other thing I would verify explicitly is pruning — I check `EXPLAIN` on the actual production queries after partitioning, because a query that omits the partition key silently scans everything and people assume partitioning made things faster when it made them slower.
@followup
How many partitions is too many?
@answer
Planning time grows with partition count, and although modern Postgres prunes efficiently, thousands of partitions add measurable overhead — especially for queries that cannot prune. Monthly partitions for multi-year retention keeps you in the tens; daily partitioning for three years is over a thousand and starts to hurt. I choose the granularity from the retention requirement and the query pattern: fine enough that dropping is useful, coarse enough that the count stays manageable, and I would use sub-partitioning rather than very fine ranges if both dimensions matter.
@red
- Partitioning on a column queries do not filter by.
- Daily partitions retained for years.

### How do you optimise a query that is slow despite a good plan?
@short
Reduce the work it must do rather than the way it does it: return fewer columns and rows, precompute with a materialised view or a rollup table, cache the result, restructure the access pattern, or move the workload off the primary. A good plan over too much data is a data-model problem, not a query problem.
@deep
The pattern that recurs is a dashboard query aggregating millions of rows on every page load. No index makes that fast, because the work is inherent. Precomputing into a rollup that is updated incrementally converts an O(n) scan into an O(1) lookup.

The other frequent case is `SELECT *` on a table with large text or JSONB columns, where the query plan is perfect but the I/O and network cost is dominated by columns nobody uses.
@code sql Precompute rather than optimise
-- Slow but well-planned: 40M rows scanned per dashboard load
SELECT date_trunc('day', created_at) d, tenant_id, count(*), sum(total_minor)
  FROM orders WHERE created_at >= now() - interval '90 days'
 GROUP BY 1, 2;

-- Option A: materialised view, refreshed on a schedule
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', created_at) AS d, tenant_id, count(*) AS orders,
       sum(total_minor) AS revenue
  FROM orders WHERE status = 'paid' GROUP BY 1, 2;
CREATE UNIQUE INDEX ON daily_revenue (d, tenant_id);   -- enables CONCURRENTLY
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;  -- no read lock

-- Option B: incremental rollup — cheaper, fresher, more code
INSERT INTO daily_revenue (d, tenant_id, orders, revenue)
SELECT date_trunc('day', created_at), tenant_id, count(*), sum(total_minor)
  FROM orders WHERE created_at >= $1 AND created_at < $2 AND status='paid'
 GROUP BY 1, 2
ON CONFLICT (d, tenant_id) DO UPDATE
   SET orders = EXCLUDED.orders, revenue = EXCLUDED.revenue;

-- Option C: it is an analytical workload → it does not belong on the OLTP primary
--   → read replica, or a column store (ClickHouse/Timescale) fed by CDC
@end
@senior
The framing I would give is that there are three ways to make a query faster — do it better, do it less often, or do it somewhere else — and once the plan is good you are choosing between the last two. Materialised views are the cheapest step; incremental rollups are fresher and more code; moving analytics off the primary entirely is the right answer once dashboards start affecting transactional latency. I would also mention `REFRESH ... CONCURRENTLY`, since a plain refresh takes an exclusive lock and makes the dashboard unavailable while it runs, which people discover in production.
@followup
When would you introduce a separate analytics database?
@answer
When analytical queries start affecting transactional performance, when the questions require scanning far more history than the OLTP store should retain, or when the access pattern is genuinely columnar — aggregations over a few columns across billions of rows. Then a column store fed by change data capture is the right shape, and it also lets you keep the OLTP database small by archiving aggressively. Before that, a read replica plus materialised views handles a great deal, and it avoids a second system to operate.
@red
- Adding indexes to a query whose problem is the volume of data.
- `REFRESH MATERIALIZED VIEW` without `CONCURRENTLY` on a live dashboard.

### How do you approach connection pooling at scale?
@short
Pool per instance sized so total connections stay well under the database's limit, plus an external pooler like PgBouncer in transaction mode when instance count or serverless concurrency makes that arithmetic impossible. Fail fast on pool acquisition rather than queueing, and set statement timeouts so no query can hold a connection indefinitely.
@deep
Postgres allocates a backend process per connection, so hundreds of connections cost memory and context switching. Throughput typically peaks at a modest number of active connections — often somewhere near a small multiple of the core count — and degrades beyond it.

PgBouncer in transaction mode multiplexes many client connections onto few server connections, which is what makes serverless and high-instance-count architectures viable. The cost is losing session-level features.
@arch The pooling arithmetic, and where PgBouncer fits
  WITHOUT POOLER
    12 app instances × 20 pool = 240   + 10 workers + 2 migrations + 5 human
    = 257  >  max_connections 200  ❌  → "sorry, too many clients already"

  WITH PGBOUNCER (transaction mode)
    app instances ──► PgBouncer (default_pool_size 25, max_client_conn 2000) ──► Postgres
    240 client connections multiplexed onto ~25 server connections ✅

  WHAT TRANSACTION MODE BREAKS
    • prepared statements (unless the driver uses protocol-level support carefully)
    • SET / session GUCs → must use SET LOCAL inside a transaction
    • advisory locks held across statements
    • LISTEN/NOTIFY
    • temporary tables

  TIMEOUTS THAT MATTER MORE THAN POOL SIZE
    connectionTimeoutMillis 5s   → fail fast, do not queue behind an exhausted pool
    statement_timeout 10s        → no query holds a connection forever
    idle_in_transaction_session_timeout 60s → no forgotten transaction blocks vacuum
@end
@senior
The `SET LOCAL` requirement is the trap that bites when you adopt PgBouncer with row-level security: a plain `SET app.tenant_id` persists on the pooled server connection and can leak the previous request's tenant into the next one, which is a cross-tenant data exposure caused purely by a pooling change. `SET LOCAL` scopes it to the transaction and is correct. More broadly, I would say the timeouts matter more than the pool size — a pool that is slightly too small degrades gracefully, whereas a pool with no acquisition timeout turns one slow query into a total outage as every request queues.
@followup
Why is pool exhaustion so catastrophic?
@answer
Because it converts a localised problem into a total one. One slow query or one leaked client means requests queue for connections, latency rises, health checks time out, the orchestrator restarts instances, and the restarts reconnect en masse — which adds load to a database that is already the bottleneck. The defences are an acquisition timeout so requests fail fast rather than queueing, a statement timeout so nothing holds a connection indefinitely, releasing clients in `finally`, and monitoring `idle in transaction` sessions, which are the usual culprit.
@red
- Pool size chosen without the total-connection arithmetic.
- `SET` instead of `SET LOCAL` behind a transaction-mode pooler.

### How do you implement change data capture and why?
@short
Read the WAL through logical replication or Debezium to emit row-level change events, rather than polling or writing dual-write code. It gives you an accurate, ordered, complete stream of changes with no application changes and no missed updates from paths that bypass your ORM.
@deep
The alternatives are worse. Polling `updated_at` misses deletes and hard-deletes, and misses updates that happen between polls with the same timestamp. Application-level dual writes miss anything written by a migration, a backfill script or a manual fix, and they reintroduce the dual-write consistency problem.

CDC is the standard way to feed search indexes, analytics warehouses, caches and downstream services from a system of record without coupling them to the application.
@arch CDC feeding derived systems, with the outbox variant
  Postgres (system of record)
      │  logical replication slot (wal2json / pgoutput)
      ▼
  Debezium / custom consumer ──► Kafka topics (one per table, keyed by PK)
      │                              │            │              │
      ▼                              ▼            ▼              ▼
   search index               analytics WH   cache invalidation  downstream svc

  RAW CDC              streams table rows → consumers must understand YOUR schema
                       → schema changes break consumers (tight coupling)
  OUTBOX + CDC         application writes DOMAIN EVENTS to an outbox table in the
                       same transaction; CDC streams THAT table
                       → consumers get a stable contract, not your schema  ← preferred

  CAUTIONS
   • an inactive slot retains WAL forever → disk fills → primary stops accepting writes
   • initial snapshot of a large table must be throttled
   • ordering is guaranteed per key/partition, not globally
@end
@senior
The outbox-plus-CDC combination is the design I would advocate: streaming raw table changes couples every consumer to your internal schema, so a column rename breaks three downstream systems. Writing explicit domain events to an outbox table and streaming that gives consumers a versioned contract while still getting transactional guarantees and no dual write. And I would repeat the replication-slot warning, because it is the operational failure that turns a nice architecture into a production outage: a consumer that stops consuming will fill your primary's disk, so slot monitoring and `max_slot_wal_keep_size` are mandatory rather than optional.
@followup
How do you handle schema changes with CDC consumers?
@answer
Version the event contract and evolve it additively — new optional fields are safe, removing or repurposing a field is not. With an outbox that is straightforward because you control the event shape independently of the table. With raw CDC you need a schema registry and compatibility rules, and you must coordinate deployments across teams, which is exactly the coupling the outbox avoids. Either way, consumers should ignore unknown fields, which makes additive evolution non-breaking by default.
@red
- Polling `updated_at` as a substitute for CDC.
- Streaming raw table schemas to external consumers.

### How do you decide between Postgres and a specialised datastore?
@short
Start with Postgres and move a workload out when there is a measured reason: an access pattern it handles poorly at your scale, an operational limit you have hit, or a feature that would be a large project to replicate. Every additional datastore is permanent operational cost, so the bar should be evidence rather than anticipation.
@deep
Postgres now covers a surprising amount: JSONB for document workloads, full-text search, PostGIS for geospatial, pgvector for embeddings, LISTEN/NOTIFY for lightweight pub/sub, and partitioning for time series. That consolidation is worth a lot — one backup story, one security model, one set of monitoring, and cross-domain queries in a single statement.

Where specialised stores genuinely win: Redis for sub-millisecond ephemeral state, ClickHouse for analytical scans, Elasticsearch for advanced search relevance and faceting, Kafka for high-throughput event streaming with replay.
@code text A decision table with the crossing point for each
  WORKLOAD           STAY IN POSTGRES UNTIL…                 THEN MOVE TO
  ────────────────────────────────────────────────────────────────────────────
  caching            never — Postgres is not a cache          Redis (from day 1)
  full-text search   relevance tuning/faceting is inadequate  OpenSearch/Typesense
                     (often ~1–10M docs, workload dependent)
  vector search      HNSW build time/memory becomes a limit   Pinecone/Qdrant/Milvus
                     (often tens of millions of vectors)
  time series        partitioning + rollups stop keeping up   TimescaleDB → ClickHouse
  analytics          scans affect OLTP latency                column store via CDC
  queues             throughput/latency needs exceed          Redis/BullMQ → SQS → Kafka
                     SELECT … FOR UPDATE SKIP LOCKED
  document store     genuinely variable schema AND you never  keep JSONB, or MongoDB
                     need joins/constraints on it

  COST OF EACH ADDITION: backups, monitoring, patching, access control, on-call
  knowledge, cross-store consistency, and one more thing to reason about at 3am.
@end
@senior
The argument I would make is that the cost of an extra datastore is paid every day forever, while the benefit is usually specific to one workload — so the decision should be evidence-driven and reversible where possible. I have kept full-text search and vector search in Postgres well past the point where people assumed a specialised store was necessary, and the operational simplicity was worth more than the marginal capability. What I would not do is use Postgres as a cache or as a high-throughput queue at scale, because those are workloads it is genuinely poor at and Redis solves properly.
@followup
What would make you add Kafka?
@answer
Multiple independent consumers needing to replay the same event stream, retention measured in weeks rather than hours, and throughput beyond what Redis Streams or a database-backed queue handles comfortably. Event sourcing and analytics pipelines are the natural fits. What would not justify it is a job queue — SQS or BullMQ is simpler and sufficient — and I would be explicit that Kafka is a significant operational commitment even when managed, so it should follow a requirement rather than an aspiration.
@red
- Adding a datastore per workload by default.
- Using Postgres as a high-throughput queue at scale.

# SECTION AI Engineering Deep Dive | RAG, embeddings, tool calling and evaluation — the fastest-growing section of senior interviews, and the pgvector, Gemini and ingestion work from your projects. State the provenance once, then answer at full depth.

### How do embeddings work and how do you choose a model and dimensionality?
@short
An embedding maps text to a dense vector so that semantically similar text is close in that space, usually by cosine distance. You choose the model by evaluating retrieval quality on your own data, and dimensionality trades accuracy against storage, index size and query latency.
@deep
The vectors come from a transformer trained so that related passages land near each other. Different models produce incompatible spaces, so changing models means re-embedding everything — the migration cost is why the choice matters.

Dimensionality is a real cost axis: at 1536 dimensions, a million chunks is roughly 6GB of raw float32 vectors before index overhead. Matryoshka-style models allow truncating dimensions with graceful degradation, and quantisation reduces storage further at a small recall cost.
@code sql Dimensionality and quantisation trade-offs, measured
-- Storage: 1M chunks
--   float32 × 1536 dims = 6.1 GB   + HNSW index ≈ +30–50%
--   float32 × 768  dims = 3.1 GB   ← Matryoshka truncation, often ~1–2% recall loss
--   halfvec × 1536      = 3.1 GB   ← pgvector half precision, minimal recall loss
--   binary quantised    = 0.2 GB   ← rerank-required; big recall loss alone

ALTER TABLE chunks ALTER COLUMN embedding TYPE halfvec(1536);
CREATE INDEX ON chunks USING hnsw (embedding halfvec_cosine_ops) WITH (m=16, ef_construction=64);

-- Two-stage: cheap binary scan → exact rerank on the survivors
-- (the pattern that makes very large corpora affordable)
WITH candidates AS (
  SELECT id FROM chunks
   WHERE tenant_id = $2
   ORDER BY binary_embedding <~> $1::bit(1536)      -- Hamming distance, very fast
   LIMIT 500
)
SELECT c.id, c.content, c.embedding <=> $3 AS distance
  FROM chunks c JOIN candidates USING (id)
 ORDER BY distance LIMIT 20;                        -- exact cosine on 500, not 1M
@end
@senior
The point I would make is that model choice must be evaluated on your own corpus, because published benchmarks are averaged over domains that may look nothing like yours — a model that is excellent on general web text can be mediocre on legal contracts or on log messages full of identifiers. I build a golden set of query-to-expected-chunk pairs and measure recall at k for each candidate model, which usually takes a day and prevents a much more expensive mistake. And I would note that re-embedding is a migration: it needs a version column on the chunks so old and new embeddings can coexist during the switch.
@followup
Cosine, dot product or Euclidean distance?
@answer
Whatever the model was trained with — using the wrong metric silently degrades results. Most modern embedding models are trained for cosine similarity and produce normalised vectors, in which case cosine and dot product rank identically and dot product is marginally cheaper. Euclidean distance on normalised vectors is also monotonically related to cosine, so it gives the same ordering. The failure case is using dot product with unnormalised vectors, where magnitude leaks into the ranking and longer documents win regardless of relevance.
@red
- Choosing an embedding model from a leaderboard without testing on your data.
- Mismatching the distance metric to the model.

### How do you design a chunking strategy?
@short
Split on structure first — headings, sections, paragraphs, table boundaries — with a target size that fits the retrieval budget and modest overlap so a concept split across a boundary is still retrievable. Then enrich each chunk with context: the document title and section path, so the embedding reflects where it came from.
@deep
Fixed-size character chunking is the default in tutorials and it is consistently the worst option, because it splits sentences and tables and destroys the semantic unit the embedding is supposed to capture.

The two enhancements that measurably help are contextual headers on each chunk, and small-to-big retrieval: embed small precise chunks for matching, but return the larger surrounding section to the model so it has enough context to answer.
@code ts Structure-aware chunking with context enrichment
export function chunkDocument(doc: ParsedDoc): Chunk[] {
  const chunks: Chunk[] = [];

  for (const section of doc.sections) {                    // split on real structure
    const path = section.headingPath.join(' > ');          // "Billing > Refunds > Timing"

    // tables and code blocks are atomic — splitting them destroys meaning
    for (const block of section.blocks) {
      if (block.type === 'table' || block.type === 'code') {
        chunks.push(make(block.text, path, doc, { atomic: true }));
        continue;
      }
      for (const part of splitBySentence(block.text, { target: 700, overlap: 100 })) {
        chunks.push(make(part, path, doc, {}));
      }
    }
  }
  return chunks;
}

function make(text: string, path: string, doc: ParsedDoc, meta: object): Chunk {
  return {
    // ✅ the EMBEDDED text carries context; the DISPLAYED text does not
    embedText: `Document: ${doc.title}\nSection: ${path}\n\n${text}`,
    content: text,
    docId: doc.id, section: path, tokens: countTokens(text), ...meta,
  };
}

// Small-to-big: match on the precise chunk, return the surrounding section
const matched = await retrieve(question);
const expanded = await db.sections.byIds(matched.map(m => m.sectionId));   // more context
@end
@senior
Embedding a contextual header while displaying only the raw content is the trick worth knowing: a chunk that says "refunds are processed within 5 working days" is ambiguous in isolation, but embedded as part of "Document: Merchant Agreement, Section: Billing > Refunds" it matches the right questions. Small-to-big is the complementary idea — precision in matching, generosity in context. Both are cheap to implement and both moved my retrieval metrics more than any prompt change, which is why I would frame chunking as the highest-leverage stage rather than a preprocessing detail.
@followup
How do you handle documents that update frequently?
@answer
Chunk-level change detection: hash each chunk's content and only re-embed the ones that changed, rather than re-embedding the whole document. That keeps cost proportional to the edit rather than to the document size. Deletions need tombstones so removed chunks leave the index, and the whole operation should be transactional with the document update so retrieval never sees a half-updated document. For very frequently changing documents I would also consider whether retrieval is the right pattern at all, or whether a live query against the source is better.
@red
- Fixed-character chunking with no structure awareness.
- Re-embedding entire documents on every small edit.

### How do you evaluate a RAG system rigorously?
@short
Separate retrieval evaluation from generation evaluation. For retrieval, a golden set of questions with known relevant chunks measured by recall at k and MRR. For generation, faithfulness to the retrieved context, answer relevance, and the rate of confident wrong answers — measured by an LLM judge calibrated against human ratings.
@deep
Measuring only end-to-end quality makes regressions undiagnosable, because you cannot tell whether retrieval failed or generation did. Splitting them means a change to chunking is evaluated on retrieval metrics alone, which is fast and cheap.

The judge must be calibrated: sample fifty items, have humans rate them, and check the judge agrees. An uncalibrated LLM judge is a number that feels rigorous and may be meaningless.
@code ts An evaluation harness that runs in CI
const GOLDEN: EvalCase[] = [
  { q: 'How long do refunds take?', relevantChunkIds: ['c_412','c_413'],
    expectedFacts: ['5 working days'], mustNotSay: ['instant', 'immediately'] },
  // ~100–200 cases covering: common questions, edge cases, out-of-scope questions,
  // questions answerable only by combining two documents, and adversarial ones
];

export async function evaluate() {
  const results = await Promise.all(GOLDEN.map(async (c) => {
    const retrieved = await retrieve(c.q, TENANT, 5);
    const ids = retrieved.map(r => r.id);

    const recall = c.relevantChunkIds.filter(id => ids.includes(id)).length
                 / c.relevantChunkIds.length;
    const mrr = 1 / (ids.findIndex(id => c.relevantChunkIds.includes(id)) + 1 || Infinity);

    const answer = await generate(c.q, retrieved);
    const faithful = await judge('Is every claim supported by the context?', { retrieved, answer });
    const hasFacts = c.expectedFacts.every(f => answer.toLowerCase().includes(f.toLowerCase()));
    const violated = c.mustNotSay.some(f => answer.toLowerCase().includes(f.toLowerCase()));

    return { recall, mrr, faithful: faithful.score, hasFacts, violated };
  }));

  const summary = aggregate(results);
  // CI gate: fail the build on a regression, not on an absolute threshold
  if (summary.recallAt5 < BASELINE.recallAt5 - 0.03) throw new Error('RETRIEVAL REGRESSION');
  if (summary.violationRate > BASELINE.violationRate) throw new Error('SAFETY REGRESSION');
  return summary;
}
@end
@senior
Gating CI on regression against a baseline rather than on an absolute threshold is the practical detail: absolute targets are arbitrary and get lowered when they fail, whereas "this change made retrieval worse" is an objective statement about the change. The `mustNotSay` assertions are the other underrated piece — they encode the specific wrong answers you have already seen in production, so a regression that reintroduces a known failure is caught automatically. And I would insist on including out-of-scope questions in the golden set, because a system that answers questions it should refuse is the failure users complain about most.
@followup
How do you build the golden set without a huge annotation effort?
@answer
Bootstrap from real usage: take actual user questions from logs, cluster them, and annotate a representative sample — which is far more valuable than invented questions because it reflects the real distribution. For the relevant-chunk labels, a first pass by a strong model followed by human verification is much faster than labelling from scratch. A hundred well-chosen cases covering the main intents plus known failure modes is enough to detect regressions; perfection is not required for the metric to be useful.
@red
- Evaluating end-to-end only.
- An LLM judge with no human calibration.

### How do you design an agent that uses tools safely?
@short
Constrain what the agent can do rather than what it is told: tools with narrow, validated inputs, execution under the calling user's permissions, hard limits on iterations and cost, human approval for consequential actions, and a full audit trail. The model chooses which tool to call; the system decides whether it is allowed.
@deep
The core insight is that an agent loop amplifies both capability and risk. A model that can call five tools in sequence can accomplish more and can also cause more damage from a single injected instruction or a reasoning error.

Bounding the loop matters operationally too: without an iteration cap and a cost budget, a confused agent can loop indefinitely, calling tools and burning money.
@code ts A bounded, audited agent loop
export async function runAgent(task: string, ctx: UserContext) {
  const budget = { iterations: 8, tokens: 40_000, currency: 0.50 };
  const trace: Step[] = [];
  let messages: Msg[] = [{ role: 'user', content: task }];

  for (let i = 0; i < budget.iterations; i++) {
    if (spent.tokens > budget.tokens || spent.currency > budget.currency)
      return { status: 'budget_exceeded', trace };

    const res = await llm.chat({ messages, tools: toolsFor(ctx), max_tokens: 1024 });
    spent.add(res.usage);

    if (!res.toolCalls?.length) return { status: 'done', answer: res.text, trace };

    for (const call of res.toolCalls) {
      const tool = TOOLS[call.name];
      if (!tool) { messages.push(toolError(call, 'UNKNOWN_TOOL')); continue; }

      const input = tool.schema.safeParse(call.input);                 // 1. validate
      if (!input.success) { messages.push(toolError(call, 'INVALID_INPUT')); continue; }

      if (tool.requiresApproval(input.data)) {                          // 2. human gate
        await approvals.create({ task, call, ctx, trace });
        return { status: 'awaiting_approval', trace };
      }

      const result = await tool.execute(input.data, ctx);               // 3. runs AS THE USER
      await audit.record({ action: `agent.${call.name}`, actor: ctx.userId,
                           via: 'agent', input: input.data, task });    // 4. audit
      trace.push({ tool: call.name, input: input.data, result });
      messages.push(toolResult(call, result));
    }
  }
  return { status: 'iteration_limit', trace };
}
@end
@senior
The approval gate keyed on the tool's own assessment of the input is the design detail I would emphasise: a refund of ten rupees can proceed autonomously while a refund of fifty thousand requires a human, and that threshold lives in the tool rather than in the prompt where an injection could influence it. The budget guard is the second — agents fail by looping, and an unbounded loop against a paid API is a financial incident. And the trace is not just for debugging: when an agent does something wrong, you need to be able to show exactly what it did and why, which is a product and compliance requirement as much as an engineering one.
@followup
How do you make agent behaviour reproducible enough to debug?
@answer
Persist the full trace — every message, tool call, input, result and token count — keyed by a run id, and make it replayable against recorded tool outputs. Temperature zero helps but does not guarantee determinism across model versions, so the trace is the source of truth rather than the ability to re-run. I also pin the model version explicitly, because a silent model upgrade changing agent behaviour is otherwise indistinguishable from a code regression.
@red
- Tools that execute with service-level rather than user-level permissions.
- Agent loops with no iteration or cost bound.

### How do you stream LLM responses reliably to a browser and a mobile app?
@short
Server-Sent Events for the browser, because it is plain HTTP with automatic reconnection and resumption via `Last-Event-ID`. Disable proxy buffering, send heartbeats to keep intermediaries from closing the connection, abort the upstream call when the client disconnects, and persist the partial answer so a reconnect can resume rather than restart.
@deep
The infrastructure details are where streaming breaks in production: Nginx and CDNs buffer by default, so the user sees nothing for thirty seconds and then everything at once; load balancer idle timeouts close a connection during a long thinking pause; and mobile networks drop connections routinely.

Resumability is what makes it feel reliable: storing the generated tokens as they are produced means a reconnect can replay from the last received index instead of regenerating.
@code ts SSE with heartbeats, resumption and upstream cancellation
app.get('/api/chat/:id/stream', authenticate, async (req, res) => {
  const lastEventId = Number(req.get('Last-Event-ID') ?? req.query.from ?? 0);

  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache, no-transform',    // no-transform: proxies must not buffer
    'Connection': 'keep-alive',
    'X-Accel-Buffering': 'no',                    // Nginx-specific
  });

  // Resume: replay what was already generated before continuing
  const existing = await store.tokensSince(req.params.id, lastEventId);
  for (const t of existing) res.write(`id: ${t.i}\ndata: ${JSON.stringify(t)}\n\n`);
  if (await store.isComplete(req.params.id)) { res.write('event: done\ndata: {}\n\n'); return res.end(); }

  const heartbeat = setInterval(() => res.write(': ping\n\n'), 15_000);   // keep LB/proxy happy
  const abort = new AbortController();
  req.on('close', () => { clearInterval(heartbeat); abort.abort(); });    // stop paying immediately

  let i = existing.length;
  try {
    for await (const token of llm.stream(prompt, { signal: abort.signal })) {
      await store.appendToken(req.params.id, i, token);   // persist → resumable
      res.write(`id: ${i}\ndata: ${JSON.stringify({ t: token })}\n\n`);
      i++;
    }
    await store.markComplete(req.params.id);
    res.write('event: done\ndata: {}\n\n');
  } catch (e) {
    if (!abort.signal.aborted) res.write(`event: error\ndata: ${JSON.stringify({ code: 'GEN_FAILED' })}\n\n`);
  } finally { clearInterval(heartbeat); res.end(); }
});
@end
@senior
Persisting tokens as they are generated is what turns streaming from a demo into a product: on a mobile network the connection will drop, and the difference between resuming from token 340 and regenerating the whole answer is both cost and user trust. Aborting the upstream call on disconnect is the other operational essential — without it you continue generating and paying for an answer nobody will read, and at scale that is a measurable share of the bill. For a mobile app specifically I would additionally consider a background-safe channel, because the OS will suspend the app and kill the connection when it backgrounds.
@followup
Why not WebSockets for LLM streaming?
@answer
Because the traffic is one-directional and SSE gives you automatic reconnection, resumption via `Last-Event-ID`, standard HTTP authentication and compression, and no protocol upgrade to negotiate through proxies. WebSockets are the right choice if the same connection carries other bidirectional traffic — a collaborative editor that also streams AI suggestions, for example — but for a chat completion the upstream channel is a single request, which HTTP already handles. Choosing SSE removes a whole category of operational complexity for no functional loss.
@red
- Streaming through a proxy without disabling buffering.
- Not aborting the upstream generation when the client disconnects.

### How do you control and attribute LLM cost at scale?
@short
Measure per request with model, tenant and feature labels; cap output tokens; cache aggressively including semantically; route by task difficulty; and enforce per-tenant budgets that fail closed. Cost is the one metric that can grow ten times overnight from a single code path, so it needs alerting like an error rate.
@deep
The largest wastes in practice are: sending more context than needed, re-sending an unchanged system prompt every turn instead of using prompt caching, no output cap so a runaway generation costs unboundedly, and continuing generation after the user has left.

Attribution matters as much as reduction. Without per-tenant and per-feature labels you cannot tell whether the bill is a feature working as intended or a bug.
@code ts Cost accounting as a first-class metric
const cost = new client.Counter({
  name: 'llm_cost_microcents_total',
  labelNames: ['model', 'tenant', 'feature', 'cached'],
});

export async function complete(req: LlmRequest, ctx: Ctx) {
  const budget = await budgets.remaining(ctx.tenantId);
  if (budget <= 0) throw new PaymentRequired('AI_BUDGET_EXHAUSTED');   // fail CLOSED

  const cached = await semanticCache.get(req.promptEmbedding, ctx.tenantId, 0.97);
  if (cached) { cost.inc({ ...labels, cached: 'true' }, 0); return cached; }

  const res = await llm.chat({
    ...req,
    max_tokens: Math.min(req.maxTokens ?? 1024, 2048),        // hard cap
    system: [{ type: 'text', text: SYSTEM, cache_control: { type: 'ephemeral' } }],  // prompt cache
  });

  const micro = priceOf(res.model, res.usage);                 // includes cache read/write rates
  cost.inc({ model: res.model, tenant: ctx.tenantId, feature: ctx.feature, cached: 'false' }, micro);
  await budgets.consume(ctx.tenantId, micro);
  await semanticCache.set(req.promptEmbedding, res, ctx.tenantId);
  return res;
}

// Alerts: tenant spend rate > 3× its 7-day baseline · daily total > budget ×0.8
//         cache hit rate drop > 20pp (a prompt change probably broke caching)
@end
@senior
Alerting on a drop in cache hit rate is the non-obvious one and it is genuinely useful: a small change to the system prompt invalidates the prompt cache for every request, and the only symptom is the bill — latency and errors look fine. Similarly, a tenant whose spend rate triples is either a new use case worth understanding or a bug worth stopping. I would also emphasise failing closed on budget exhaustion, unlike most availability decisions: an AI feature that stops working is recoverable, whereas an unbounded spend is not.
@followup
How do you decide the semantic cache similarity threshold?
@answer
Empirically, by measuring false hits on real traffic: set it high — around 0.97 for a normalised embedding space — sample the hits, and check that the cached answer genuinely answers the new question. Too low and you serve subtly wrong answers, which is far worse than a cache miss. I also scope the cache per tenant so one customer's answer cannot be served to another, and I exclude anything personalised or time-sensitive, because a cached answer about "your current balance" is a correctness bug rather than an optimisation.
@red
- No output token cap.
- Cost tracked in aggregate with no tenant or feature attribution.

### How do you handle model versioning, upgrades and drift?
@short
Pin the model version explicitly, evaluate any new version against your golden set before switching, roll out behind a flag with a shadow comparison, and monitor quality metrics continuously so a provider-side change is detected. Treat a model upgrade like a dependency upgrade with behavioural risk.
@deep
Model providers deprecate versions and behaviour changes between them — prompts tuned for one version can degrade on the next in ways that are invisible without evaluation. Aliases that float to the latest version are convenient and dangerous in production.

Drift also happens without an upgrade: if your data distribution changes, retrieval and answer quality change even though nothing in your system did.
@code ts Shadow evaluation of a new model version
const ROUTES = {
  primary: 'claude-sonnet-4-5-20250929',       // pinned, explicit
  candidate: process.env.CANDIDATE_MODEL,      // evaluated in shadow
};

export async function answer(q: Question, ctx: Ctx) {
  const primary = await generate(ROUTES.primary, q, ctx);

  if (ROUTES.candidate && sample(0.05)) {                      // 5% shadow traffic
    void (async () => {
      const candidate = await generate(ROUTES.candidate, q, ctx);
      const verdict = await judge('Which answer is better and why?',
                                  { question: q, a: primary, b: candidate });
      await evalStore.record({ q, primary, candidate, verdict, at: now() });
      metrics.increment('model.shadow.compare', { winner: verdict.winner });
    })();
  }
  return primary;                                              // users always get the pinned model
}

// Promote only when: golden-set metrics ≥ baseline AND shadow win rate ≥ 50%
// AND cost/latency acceptable. Then flip the flag with a percentage ramp.
@end
@senior
Shadow comparison on live traffic is the technique I would advocate, because a golden set covers the questions you thought of and production covers the ones you did not. Running the candidate on a small sample, judging pairwise, and only promoting on a favourable win rate turns a model upgrade from a leap of faith into a measured change. I would also mention the operational reason to pin: a floating alias means the provider can change your product's behaviour without a deploy, which makes any incident impossible to correlate with a change on your side.
@followup
How do you detect quality degradation in production?
@answer
Proxy metrics that do not need labels: the rate of refusals, the rate of answers with no citations, average answer length, user feedback signals like thumbs-down or a follow-up rephrasing of the same question, and escalation-to-human rate for a support assistant. Those move before anyone files a complaint. I sample a small number of conversations for periodic human review as well, because automated metrics catch drift in known dimensions and humans catch the unknown ones.
@red
- Using a floating model alias in production.
- Upgrading models without an evaluation set.

### How do you handle very long documents and large context requirements?
@short
Retrieval before stuffing: pull only the relevant sections rather than sending the whole document. Where the whole document genuinely matters, use hierarchical summarisation — summarise sections, then summarise the summaries — or map-reduce over chunks with a final synthesis step. Long-context models help but are slower and more expensive, and attention quality degrades in the middle.
@deep
The "lost in the middle" effect is well documented: models attend most reliably to the beginning and end of a long context, so burying the critical passage in the middle of a hundred thousand tokens reduces the chance it is used. That argues for retrieval and ordering rather than brute-force stuffing even when the context window allows it.

Map-reduce is the pattern for tasks that genuinely need everything — extracting every obligation from a contract, for instance — and it parallelises well.
@code ts Map-reduce over a long document, with ordering that respects attention
export async function extractObligations(doc: Document) {
  const sections = splitByStructure(doc);

  // MAP: independent, parallel, bounded concurrency
  const limit = pLimit(8);
  const partial = await Promise.all(sections.map(s => limit(async () =>
    generate(EXTRACT_PROMPT, { section: s.text, path: s.path }, { max_tokens: 800 })
  )));

  // REDUCE: synthesise, deduplicate, resolve cross-references
  const merged = await generate(MERGE_PROMPT, {
    partials: partial,
    instruction: 'Deduplicate, resolve cross-references, keep section citations.',
  });
  return merged;
}

// When stuffing IS appropriate, order for attention: most relevant first AND last
function orderForAttention(chunks: Chunk[]) {
  const sorted = [...chunks].sort((a, b) => b.score - a.score);
  const out: Chunk[] = [];
  sorted.forEach((c, i) => (i % 2 === 0 ? out.unshift(c) : out.push(c)));
  return out;      // highest-scoring at both ends, weakest buried in the middle
}
@end
@senior
The attention-ordering trick is a small, cheap and genuinely effective optimisation: placing the highest-scoring passages at the start and end of the context, and the weakest in the middle, measurably improves how often the model uses the right evidence. The broader judgement is that a large context window is not a substitute for retrieval — it is slower, more expensive and less accurate than sending five well-chosen passages, and the temptation to stuff everything because you can is one of the more common ways teams end up with an expensive system that answers worse than a cheaper one.
@followup
When is fine-tuning better than retrieval?
@answer
Fine-tuning is for teaching form — a house style, a strict output format, a domain vocabulary, a classification task with many examples. Retrieval is for supplying facts, especially facts that change. They are complementary, and the common mistake is fine-tuning to inject knowledge, which is expensive, hard to update and does not produce citations. If the requirement is "answer from our documentation", that is retrieval. If it is "always respond in this exact structure with this tone", fine-tuning or a well-constrained prompt is right.
@red
- Stuffing whole documents because the context window allows it.
- Fine-tuning to add facts that change.

### How do you make LLM outputs structured and reliable enough to act on?
@short
Constrained generation — a JSON schema or tool-call interface enforced by the provider — plus validation with Zod on the way out, plus a repair loop for the rare failure. Never parse free text with a regex when the provider supports structured output, and never trust the structure without validating it.
@deep
Even with schema-constrained output, semantic validity is your problem: the model can return a well-formed object with a nonsensical value, an id that does not exist, or a date in the past. So validation is two layers — structural (schema) and semantic (does this id exist, is this amount within range).

The repair loop matters for the tail: feeding the validation error back to the model usually produces a correct result on the second attempt, which is cheaper than failing the request.
@code ts Structured output with validation and a bounded repair loop
const Extraction = z.object({
  invoiceNumber: z.string().regex(/^INV-\d{6}$/),
  totalMinor: z.number().int().positive(),
  currency: z.enum(['INR', 'USD', 'EUR']),
  lineItems: z.array(z.object({
    description: z.string().min(1), qty: z.number().int().positive(), unitMinor: z.number().int(),
  })).min(1),
  issuedAt: z.string().datetime(),
});

export async function extract(text: string, attempts = 2) {
  let lastError: string | undefined;

  for (let i = 0; i <= attempts; i++) {
    const res = await llm.chat({
      messages: [{ role: 'user', content: lastError
        ? `${text}\n\nYour previous output failed validation: ${lastError}. Return valid JSON only.`
        : text }],
      tools: [{ name: 'record_invoice', input_schema: zodToJsonSchema(Extraction) }],
      tool_choice: { type: 'tool', name: 'record_invoice' },      // FORCE the structured call
    });

    const parsed = Extraction.safeParse(res.toolCalls[0]?.input);
    if (!parsed.success) { lastError = JSON.stringify(parsed.error.flatten()); continue; }

    // Semantic validation — the schema cannot check these
    const sum = parsed.data.lineItems.reduce((t, l) => t + l.qty * l.unitMinor, 0);
    if (Math.abs(sum - parsed.data.totalMinor) > 100) {           // 1 unit tolerance
      lastError = `Line items sum to ${sum} but total is ${parsed.data.totalMinor}`;
      continue;
    }
    return parsed.data;
  }
  throw new ExtractionFailed(lastError);      // → human review queue, not a silent guess
}
@end
@senior
The arithmetic cross-check is the kind of semantic validation that catches real extraction errors a schema never will — the model returns a perfectly valid object where the line items do not sum to the stated total, which means it misread something. Feeding that specific error back is far more effective than a generic retry. And the failure path matters: an extraction that cannot be validated goes to a human review queue rather than being written to the database with a shrug, because a confidently wrong invoice total is worse than an unprocessed one.
@followup
Does structured output reduce quality?
@answer
It can slightly, for open-ended reasoning tasks, because constraining the output format constrains the generation. The mitigation is to let the model reason in free text first — a `reasoning` field before the structured fields, or a separate thinking step — and then produce the structure. That preserves the reasoning benefit while keeping the machine-readable result. For pure extraction and classification the effect is negligible and the reliability gain is large.
@red
- Parsing free-text output with regular expressions.
- Trusting schema-valid output without semantic checks.

### How do you build guardrails and safety into an AI product?
@short
Layered: input filtering for obvious abuse, retrieval scoped to what the user may see, system prompts that define scope, output validation for policy violations and PII leakage, and human review for consequential actions. Each layer is imperfect, which is why there are several and why the last one is architectural rather than textual.
@deep
The most important guardrail is not a filter but a permission boundary: an assistant that can only retrieve documents the user could already read cannot leak data regardless of what it is asked. That is enforced in the query, not in the prompt.

Output-side checks catch what gets through: PII in a response that should not contain it, advice outside the product's scope, or a claim with no supporting citation.
@code ts Layered checks, with the architectural one doing the real work
export async function ask(question: string, ctx: UserCtx) {
  // 1. INPUT — cheap, catches obvious abuse and off-topic use
  if (question.length > 4000) throw new BadRequest('TOO_LONG');
  const intent = await classify(question);                    // small, cheap model
  if (intent === 'abuse' || intent === 'out_of_scope')
    return { answer: OUT_OF_SCOPE_MESSAGE, refused: true };

  // 2. RETRIEVAL SCOPE — the guardrail that actually holds
  const chunks = await retrieve(question, {
    tenantId: ctx.tenantId,
    docIds: await acl.visibleDocuments(ctx.userId),           // ← enforced in SQL
  });

  // 3. GENERATION — scope and citation requirements in the system prompt
  const answer = await generate(SYSTEM_WITH_SCOPE, chunks, question);

  // 4. OUTPUT — validate before it reaches the user
  if (containsPii(answer) && !ctx.maySeePii) return { answer: REDACTED, refused: true };
  if (citationsInvalid(answer, chunks)) { metrics.increment('llm.bad_citation'); return FALLBACK; }

  // 5. ACTION — anything consequential is proposed, not executed
  return { answer, citations: extractCitations(answer, chunks), refused: false };
}
@end
@senior
Layer 2 is the one that matters, and I would say so explicitly: prompt-level scoping is advisory and can be talked around, whereas retrieval restricted by an access-control list in the SQL query cannot leak documents the user was never allowed to see. Every other layer reduces the probability of a bad outcome; that one changes what is possible. I would also emphasise that a refusal path must exist and be measured — a system with a zero refusal rate is not safe, it is over-confident, and the refusal rate is one of the better proxy metrics for quality drift.
@followup
How do you handle a user reporting a harmful or wrong answer?
@answer
Capture the full trace — question, retrieved chunks, model version, prompt, answer — from the conversation id, so the failure can be reproduced and classified: was it retrieval, generation, or missing content. Add it to the evaluation set as a regression case, which is the mechanism that stops it recurring. Then decide whether it is a content gap (fix the documents), a retrieval gap (fix chunking or ranking), or a generation gap (fix the prompt or add a guardrail). Without the trace none of that is possible, which is why full logging of AI interactions is a design requirement.
@red
- Prompt-based access control instead of query-level scoping.
- No refusal path, so the system always answers.

### How do you design a hybrid search system that beats either method alone?
@short
Run vector and keyword retrieval independently, fuse the ranked lists with reciprocal rank fusion, then rerank the fused candidates with a cross-encoder. Vector search supplies semantic recall, keyword search supplies exact-match precision for identifiers, and the reranker supplies final ordering.
@deep
The two methods fail in complementary ways. Embeddings are poor at exact tokens — product codes, error codes, names, version numbers — because those carry little semantic signal. Keyword search is poor at paraphrase and synonymy. Fusing them covers both.

Reciprocal rank fusion is preferred over score-weighted blending because the two scores are on incomparable scales and their distributions shift with the query; RRF uses only ranks, so it needs no tuning and is robust.
@code sql Hybrid retrieval with RRF, then rerank
WITH vec AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> $1) AS rank
    FROM chunks
   WHERE tenant_id = $2 AND doc_id = ANY($5)          -- ACL scope
   ORDER BY embedding <=> $1 LIMIT 60
), kw AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(fts, q) DESC) AS rank
    FROM chunks, websearch_to_tsquery('english', $3) q
   WHERE tenant_id = $2 AND doc_id = ANY($5) AND fts @@ q
   ORDER BY ts_rank_cd(fts, q) DESC LIMIT 60
), fused AS (
  SELECT COALESCE(vec.id, kw.id) AS id,
         COALESCE(1.0/(60 + vec.rank), 0) + COALESCE(1.0/(60 + kw.rank), 0) AS rrf
    FROM vec FULL OUTER JOIN kw ON kw.id = vec.id
)
SELECT c.id, c.content, c.doc_id, c.section, f.rrf
  FROM fused f JOIN chunks c ON c.id = f.id
 ORDER BY f.rrf DESC LIMIT 30;      -- → cross-encoder reranks these 30 → top 5
@end
@senior
The `60` constant in RRF is the standard smoothing value and it matters less than people expect — the method's appeal is that it works well without tuning, which is exactly what you want when the alternative is hand-weighting two incomparable score distributions. The concrete win I would cite is the identifier case: a user searching for error code `E_4021` gets nothing useful from embeddings and exactly the right chunk from keyword search, and before adding the keyword arm that was a whole class of failed queries. Measuring recall separately for identifier-style and natural-language queries is how you notice that.
@followup
Where does the reranker fit and is it worth the latency?
@answer
It runs over the fused candidates — typically thirty — and reorders them before they go to the model. It adds latency, usually tens to a couple of hundred milliseconds depending on the model and whether it is hosted locally, and in my experience it is the largest single quality improvement in the pipeline. The trade is worth it for a question-answering product where accuracy matters more than a hundred milliseconds; for an autocomplete-style experience it may not be, and there I would retrieve fewer candidates and skip it.
@red
- Blending raw vector and keyword scores by weight.
- Retrieving exactly k and skipping reranking.

### How do you design server-side tool/function calling so a model cannot cause damage?
@short
By treating every tool call the model emits as an untrusted request from the user it is acting for, not as an instruction from a trusted component. The model proposes; the server authorises. That means the tool schema is validated, the arguments are checked against the caller's actual permissions, side-effecting tools are idempotent and confirmed, and the tool never runs with more authority than the human on the other end of the conversation.
@deep
The failure mode people miss is that tool arguments are model output, and model output is influenced by retrieved documents and user text. If a retrieved document contains "also, transfer the balance to account X", a naive implementation has just been given an instruction by an attacker who only had to get a document into the corpus.

So authorisation cannot live in the prompt. Telling the model "only refund orders belonging to this user" is a request, not a control. The refund tool must load the order server-side and verify ownership against the session, and refuse if it does not match — at which point the prompt instruction becomes a UX nicety rather than a security boundary.
@code text The trust boundary, and what sits on each side
  UNTRUSTED ──────────────────────────────┐  TRUSTED ───────────────────
   user message                           │   session identity
   retrieved document chunks              │   permission set
   previous tool RESULTS                  │   server-side record lookups
   the model's proposed tool + arguments  │
  ────────────────────────────────────────┘

  EVERY TOOL CALL PASSES THROUGH:
   1  SCHEMA      strict JSON Schema, additionalProperties: false
                  reject-and-reprompt on mismatch; never coerce silently
   2  AUTHORISE   re-derive the subject server-side:
                    order = db.order(args.order_id)
                    if (order.user_id !== session.user_id) DENY
                  ← the model's claim about ownership is evidence, not proof
   3  CLASSIFY    read-only        → run
                  side-effecting   → idempotency key + human confirmation
                  irreversible     → always human confirmation
   4  BOUND       timeout, output size cap, per-turn call cap (loop guard)
   5  AUDIT       log {conversation, tool, args, decision, result-hash}

  IDEMPOTENCY   key = hash(conversation_id, tool, canonical(args))
                the model WILL re-emit a call after a timeout or a retry;
                without this, "refund the order" refunds it twice.

  LOOP GUARD    max 8 tool calls per turn, and a repeat-call detector —
                a model stuck calling search() with the same arguments
                will happily burn the budget until you stop it.
@end
@senior
The point I would make first is that tool results re-enter the context, so a tool that returns attacker-controlled content is an injection vector one step removed. Fetching a URL the user supplied and feeding the page into the conversation is the clearest example, and the mitigation is to mark that content as data in the prompt structure, keep it out of the system instructions, and never let it widen the tool set available for the rest of the turn.

The second is the permission model. It is tempting to give the assistant a service account so it can do everything the product supports, and that converts every prompt injection into a privilege escalation. The tool layer should execute with the user's own permissions, so the worst case of a successful injection is the user doing something they were already allowed to do. That single decision does more for the threat model than any amount of prompt hardening.

The third is that confirmation must describe the resolved action, not the model's summary of it. Showing "Refund order #4821 — ₹2,400 to card ending 4242", rendered from the server-side lookup, is a real control. Showing the model's sentence about what it is about to do is theatre, because that sentence is generated by the same untrusted process.
@followup
The model keeps calling a tool with slightly wrong arguments. Do you fix the prompt or the schema?
@answer
The schema first, because it is deterministic and the prompt is not. Tightening types, using enums instead of free strings, making required fields explicit and giving each field a description in the schema fixes most argument errors without touching the prompt at all — the schema is part of the model's input, and a well-described parameter is a better instruction than a paragraph of prose. I also return a structured validation error and let the model retry once, since models correct reliably from a specific error message. Only if it persists do I look at the prompt, and if it still persists, I treat it as a sign the tool is badly factored — a tool that takes eight optional parameters and behaves differently depending on the combination is hard for a model for the same reason it is hard for a person, and splitting it into two clear tools usually solves it.
@red
- Enforcing authorisation in the system prompt instead of in the tool.
- Running tools with a service account rather than the user's permissions.
- No idempotency key on side-effecting tools.
- Confirmation dialogs built from the model's text rather than a server lookup.
- No cap on tool calls per turn.

### You have used Gemini, Groq and Ollama. How do you design for provider choice without ending up with a lowest-common-denominator abstraction?
@short
With a thin internal interface over the two things that are genuinely universal — streaming chat completion and tool calling — and explicit escape hatches for everything else. I do not try to abstract away model behaviour, because that is the part that actually differs. The interface normalises transport, retries, token accounting and streaming shape; prompts and evaluation stay per-model, because a prompt tuned for one model is not portable and pretending otherwise is how quality silently regresses.
@deep
The reason to have the seam at all is not vendor independence as a principle — it is that the three have genuinely different roles. Ollama runs locally, which makes development free and offline and keeps sensitive documents on the machine during testing. Groq is chosen for latency when the answer is short and interactive. A hosted frontier model is for the turns where quality actually matters.

That makes routing, not portability, the real design goal: choosing per turn rather than per application, based on what the turn needs.
@code text A seam narrow enough to be honest
  interface LLM {
    stream(req: {
      messages: Message[]
      tools?: ToolSchema[]
      maxOutputTokens: number
      signal: AbortSignal        // non-negotiable — see below
    }): AsyncIterable<Delta>     // {type:'text'|'tool_call'|'usage'}
  }

  NORMALISED (safe to hide)        NOT NORMALISED (deliberately exposed)
   ✔ SSE / chunk framing            ✘ prompt wording and system-prompt style
   ✔ retry + backoff on 429/5xx     ✘ which model handles which turn
   ✔ token usage accounting         ✘ sampling params that differ in meaning
   ✔ tool-call delta assembly       ✘ provider-specific modes (JSON mode,
   ✔ timeout + abort propagation       caching, structured output, thinking)
   ✔ error taxonomy                 ✘ context window and truncation policy

  ROUTING — per turn, not per app
    short conversational reply   → fast/cheap  (latency is the product)
    tool-calling turn            → the model that is reliably good at it
    long synthesis over context  → frontier model
    local dev / sensitive corpus → Ollama, no data leaves the machine
    FALLBACK on provider outage  → next tier, and record the substitution,
                                   because quality metrics are not comparable
                                   across models and a silent swap corrupts
                                   your evaluation history

  EVALUATION   the golden set runs per model. A prompt change that improves
               one model can regress another — so "which model" is a result,
               not a configuration guess.
@end
@senior
On frameworks: I use LangChain for what it is genuinely good at — the ecosystem of loaders, splitters and integrations while prototyping — and I do not put its abstractions on the critical path in production. The reason is debuggability. When retrieval quality drops, I need to see the exact prompt, the exact context and the exact token counts, and layers that construct prompts on my behalf make that harder precisely when it matters most. So I prototype with the framework and keep the production path as explicit calls behind my own interface. That is a considered position rather than a dismissal, and I would give the same answer about any framework whose main value is convenience during exploration.

The detail I would defend hardest in the interface above is that `AbortSignal` is mandatory rather than optional. Streaming plus no cancellation means every abandoned request bills to completion, and in a voice or chat product abandonment is normal, not exceptional. An abstraction that cannot cancel is not a usable abstraction regardless of how clean it looks.
@followup
Does an abstraction like that not just become a burden as providers add features?
@answer
It does if you let it grow to cover everything, which is why the interface is deliberately small and the escape hatch is explicit — a provider-specific options object that is passed through untouched and typed per provider. Code that uses it is knowingly provider-specific, which is honest, rather than a leaky abstraction that pretends otherwise. The test I apply is whether adding a provider requires changing anything outside its own adapter; if it does, the seam is in the wrong place. And if only one provider is ever realistically going to be used, I would not build the seam at all — I would call the SDK directly and add the interface at the point a second provider becomes real, because an abstraction over one implementation is speculative design.
@red
- Abstracting prompts as if they were portable between models.
- Silent provider fallback that corrupts evaluation history.
- No cancellation in a streaming interface.
- Framework abstractions on the production path where you need to see the exact prompt.

### How do you choose and tune a `pgvector` index — HNSW or IVFFlat?
@short
HNSW almost always, because it gives better recall at the same latency and does not need the data to exist before you build it. IVFFlat is worth considering only when index build time or memory is the binding constraint. The knobs that matter are `m` and `ef_construction` at build time, and `ef_search` at query time — and `ef_search` is the one you actually tune, because it is the live dial between recall and latency.
@deep
HNSW is a navigable small-world graph: each vector is a node with `m` neighbours per layer, and a search walks the graph greedily from an entry point, keeping a candidate list of size `ef_search`. Bigger `ef_search` means a wider walk, which means better recall and more time. IVFFlat instead partitions the space into `lists` centroids and scans `probes` of them, so it is cheap to build and degrades badly when the data distribution shifts after the build.

The critical operational fact about IVFFlat is that it must be built on representative data — building it on an empty or tiny table produces useless centroids, and it does not rebalance as you insert. HNSW has no such trap, which is most of why it is the default answer.

Both are approximate. Neither guarantees the true top-k, and that is the thing to say out loud: you are trading exactness for latency, and the size of that trade is measurable on your own golden set rather than assumable.
@code sql The knobs, what each costs, and how to tune them honestly
-- BUILD TIME ------------------------------------------------------------
--   m               graph degree. 16 default. ↑ = better recall, more memory,
--                   slower build. 32–64 only for high-dimensional, high-recall needs.
--   ef_construction candidate list while building. 64 default. ↑ = better graph
--                   quality, much slower build. 128–200 is a common upgrade.
CREATE INDEX CONCURRENTLY idx_chunks_hnsw
  ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 128);

-- Build is the expensive part. Buy it back with memory and parallelism:
SET maintenance_work_mem = '4GB';          -- graph built in memory or it spills to disk
SET max_parallel_maintenance_workers = 7;  -- pgvector 0.6+ builds in parallel

-- QUERY TIME ------------------------------------------------------------
--   ef_search  candidate list while searching. 40 default. MUST be >= LIMIT.
SET LOCAL hnsw.ef_search = 100;            -- per-transaction, not global
SELECT id, content, embedding <=> $1 AS distance
  FROM chunks WHERE tenant_id = $2
 ORDER BY distance LIMIT 20;

-- IVFFlat, for the case where build cost dominates:
--   lists  ≈ rows/1000 up to 1M rows, then sqrt(rows). probes ≈ sqrt(lists).
CREATE INDEX ON chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 1000);
SET LOCAL ivfflat.probes = 32;

@senior
The point I would make in an interview is that `ef_search` is a per-query dial, not a global setting, so it can be raised for the operations that deserve it and left low for the ones that do not — a background reindexing job or a high-value support query can afford 200 where a type-ahead cannot. I set it with `SET LOCAL` inside the transaction so it cannot leak into the connection pool, which is a real bug: a pooled connection left at `ef_search = 400` makes unrelated queries mysteriously slow for whoever gets that connection next.

The second point is that recall is not observable in production — a missing chunk produces a plausible answer, not an error — so the golden set is not a nicety, it is the only instrument you have. I measure recall against an exact scan on a sample, not against the ANN index itself, because comparing an approximation to itself always looks perfect.
@followup
Your HNSW index no longer fits in memory. What are the options, in order?
@answer
In cost order: reduce the vector, then reduce the index, then reduce the scope, then move the data. `halfvec` halves storage for a recall loss usually under a percent and is a one-line migration. Matryoshka truncation to 768 dimensions halves it again if the model supports it. Lowering `m` shrinks the graph but degrades recall more sharply, so I would do it after the first two. Partial indexes per tenant or per document class keep each index small and are very effective when queries are always scoped anyway. Binary quantisation with an exact rerank over the survivors is the pattern for genuinely large corpora — a cheap Hamming scan for 500 candidates, exact cosine on those. Only after all of that would I add a dedicated vector store, because that is a new datastore to operate, not a tuning change.
@red
- Building IVFFlat on an empty table and never rebuilding it.
- Setting `hnsw.ef_search` globally, or leaving it elevated on a pooled connection.
- Quoting recall numbers with no exact-scan baseline to compare against.

### How do you combine metadata filters with vector search without destroying recall?
@short
The naive version — filter in a `WHERE` clause alongside an ANN `ORDER BY` — quietly returns fewer results than you asked for, because the index walks the graph first and the filter then removes survivors. The fixes are partial indexes when the filter is a small, fixed set of values, `iterative_scan` on modern pgvector, and pre-filtering to an exact scan when the filter is selective enough that the candidate set is small.
@deep
This is the failure mode most teams hit second, after chunking. HNSW searches the graph for the nearest `ef_search` vectors globally, and Postgres applies your `WHERE tenant_id = 42` to whatever came back. If tenant 42 is 0.1% of the corpus, a walk that returns 100 candidates may contain zero of their chunks — so the query returns nothing, or three rows, and it looks like a retrieval bug rather than an index behaviour.

There are three regimes, and the right answer is to identify which one you are in rather than to pick a favourite technique. When the filter matches most of the corpus, post-filtering is fine. When it matches a small fraction — a single tenant, one document — an exact scan over that subset is both correct and fast, because the subset is small. The awkward middle is where `iterative_scan` earns its place: pgvector 0.8 will keep walking the graph until it has enough rows that pass the filter, instead of giving up after the first batch.
@code sql The three regimes, and how to make Postgres pick the right one
-- ❌ THE TRAP: silently under-returns when tenant_id is selective
SELECT id, content FROM chunks
 WHERE tenant_id = 42                      -- applied AFTER the ANN walk
 ORDER BY embedding <=> $1 LIMIT 20;       -- may return 0–5 rows, not 20

-- ✅ 1. SELECTIVE FILTER (< ~1% of rows): force the exact path. It is fast
--       because the subset is small, and it is exact, not approximate.
SELECT id, content FROM chunks
 WHERE tenant_id = 42

-- with a btree on (tenant_id) and the planner choosing it — verify with EXPLAIN.
-- If the planner insists on the HNSW index, this forces the issue:
--   BEGIN; SET LOCAL enable_indexscan = off;  -- blunt, but explicit

-- ✅ 2. FIXED, LOW-CARDINALITY FILTER: a partial index per value.
--       Each index is small, in-memory, and exact for its slice.
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WHERE doc_type = 'contract';
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WHERE doc_type = 'policy';

-- ✅ 3. THE MIDDLE (pgvector 0.8+): keep walking until the filter is satisfied.

  SET LOCAL hnsw.iterative_scan = relaxed_order;   -- or strict_order
  SET LOCAL hnsw.max_scan_tuples = 20000;          -- bound the worst case
  SELECT id, content FROM chunks
   WHERE tenant_id = 42 AND created_at > now() - interval '90 days'
   ORDER BY embedding <=> $1 LIMIT 20;
COMMIT;

-- ✅ 4. MULTI-TENANCY AT SCALE: partition, so the filter becomes partition pruning
--       and each partition carries its own small HNSW index.
CREATE TABLE chunks (tenant_id int, embedding vector(1536), ...)
  PARTITION BY HASH (tenant_id);

@senior
The senior framing is that this is a correctness bug that presents as a quality complaint. Nobody files "the ANN index post-filtered my results"; they file "the assistant says it cannot find our refund policy", and the policy is right there in the corpus. So the thing I would instrument is the gap between requested `LIMIT` and rows actually returned — if a query asked for 20 and got 6, that is a filtered-recall event and it should be a metric, not a silent shrug.

On multi-tenancy specifically, I would argue the filter should not be a filter at all where it can be avoided. Partitioning by tenant, or a partial index per large tenant, turns "search everything then discard" into "search only what is relevant", which is faster and exact and removes the cross-tenant leak risk structurally rather than by remembering to write the `WHERE` clause. A tenant filter you can forget to write is a data-leak waiting for one careless query; a partition boundary is not.
@followup
How do you prove no cross-tenant leakage is possible?
@answer
By making it structural rather than disciplinary. Row-level security on the chunks table with the tenant set from the session, so a missing `WHERE` clause returns nothing instead of everything, is the strongest single control — the database enforces it, not the developer. Above that, the retrieval layer takes the tenant from the authenticated session and never from a request parameter, so it cannot be supplied by the caller. And I would add a test that runs the full retrieval path as tenant A against a corpus seeded with a distinctive tenant B document and asserts it is never returned, plus the same assertion on the semantic cache key, because a cache keyed only on the question text is the second leak path and it is easy to miss.
@red
- Filtering in the `WHERE` clause and assuming the `LIMIT` was satisfied.
- Relying on the application always remembering the tenant predicate.
- Testing filtered retrieval only with a corpus small enough that everything is returned anyway.

### How do you handle the gap between what the user typed and what you should search for?
@short
The raw question is often a bad query — it is a follow-up with a pronoun in it, or it is phrased in words the corpus never uses. So I rewrite it before retrieving: resolve conversational references against the history, and where the vocabulary gap is real, expand into several queries and fuse the results. The rule I hold to is that the rewrite is for retrieval only — the model still answers from the user's actual words.
@deep
Three distinct problems get bundled under "query transformation" and they need separating, because they have different costs.

The first is conversational reference. "What about for enterprise?" is meaningless as an embedding — it retrieves nothing useful because it is about nothing on its own. It has to be rewritten against the conversation into "What is the refund window for enterprise customers?" before it touches the index. This one is close to mandatory in any chat interface, and it is a cheap, small-model call.

The second is vocabulary mismatch: the user says "can I get my money back" and the corpus says "reimbursement eligibility". Multi-query expansion generates several phrasings, retrieves for each, and fuses with reciprocal rank fusion. It costs one extra generation and N retrievals, and it measurably helps on corpora with domain jargon.

The third is HyDE — generate a hypothetical answer and embed that, on the theory that a fake answer sits closer in the embedding space to the real answer than the question does. It is genuinely clever and I would use it selectively, because it adds a full generation to the latency budget and it can confidently hallucinate its way toward the wrong region of the space.
@code ts Rewrite for retrieval, answer from the original
const REWRITE = `Rewrite the final user message as a standalone search query.
Resolve every pronoun and reference using the conversation. Output the query only.
If it is already standalone, output it unchanged.`;

async function retrieveForTurn(history: Turn[], question: string) {
  // 1. CONVERSATIONAL REWRITE — cheap model, low latency, high value
  const standalone = await generate(REWRITE, { history: last(history, 6), question },
                                    { model: FAST_MODEL, max_tokens: 80 });

  // 2. MULTI-QUERY — only when the rewrite looks jargon-poor or recall was thin
  const queries = needsExpansion(standalone)
    ? [standalone, ...await generate(EXPAND, { standalone }, { max_tokens: 120 })]
    : [standalone];

  // 3. RETRIEVE IN PARALLEL, FUSE BY RANK (not by score — scores are not comparable)
  const runs = await Promise.all(queries.map(q => hybridSearch(q, { k: 20 })));
  return reciprocalRankFusion(runs, { k: 60 }).slice(0, 20);
}

function reciprocalRankFusion(runs: Hit[][], { k }: { k: number }) {
  const scores = new Map<string, number>();
  for (const run of runs)
    run.forEach((hit, rank) =>
      scores.set(hit.id, (scores.get(hit.id) ?? 0) + 1 / (k + rank + 1)));
  return [...scores.entries()].sort((a, b) => b[1] - a[1]).map(([id]) => byId(id));
}

// ✅ The generation prompt gets the ORIGINAL question, never the rewrite —
//    otherwise the model answers a question the user did not ask.
const answer = await generate(ANSWER, { question, chunks: fused });
@end
@senior
The trade-off worth naming is latency. Every transformation is a serial LLM call in front of retrieval, so a naive pipeline that rewrites, expands, retrieves, reranks and then generates has four round trips before a single token reaches the user. I keep the rewrite because it fixes a correctness problem, run it on the fastest model available, and make expansion conditional rather than unconditional — triggered when the first retrieval comes back with weak scores, so the common case stays fast and only the hard queries pay.

The failure mode I have actually hit is the rewrite changing the question's meaning — a rewrite that "helpfully" narrows "what are the fees" into "what is the late payment fee" produces a confident answer to the wrong question, and it is nearly invisible in logs unless you record both strings. So I log the original and the rewrite together on every turn, and the rewrite is never what the answering model sees.
@followup
When is query transformation the wrong fix?
@answer
When the real problem is chunking or the corpus, which it usually is. If the document simply does not contain the answer, no amount of query rewriting will retrieve it, and adding transformation layers just makes a failing pipeline slower and harder to debug. My order of investigation is: is the answer in the corpus at all, is it in a chunk that makes sense on its own, does hybrid search find it when I search manually, and only then is the query the problem. Transformation is also wrong for the first turn of a conversation with a well-phrased question — there is nothing to resolve, so the call is pure latency, which is why I gate it on whether the question actually contains an unresolved reference.
@red
- Feeding the rewritten query to the answering model instead of the user's real question.
- Running HyDE and multi-query unconditionally and eating 800ms on every turn.
- Fusing by raw score across retrievers whose scores are on different scales.

### When is a reranker worth its latency, and how do you deploy one?
@short
A reranker is a cross-encoder that scores each candidate against the query jointly, rather than comparing two independently produced vectors, so it is far more accurate and far more expensive. The pattern is retrieve wide and cheap — 50 to 100 candidates by hybrid search — then rerank down to the 5 you actually send to the model. It is worth it when the answer is usually in the top 50 but not in the top 5, which is exactly what a recall curve tells you.
@deep
The reason a bi-encoder and a cross-encoder differ so much is structural. An embedding is computed for the chunk before it ever sees your query, so it has to be a general-purpose summary of that chunk. A cross-encoder reads the query and the chunk together and can attend across both, so it can tell that a passage mentioning "refund" is about refund *timing* rather than refund *eligibility*. That is why it wins on precision, and also why it cannot be precomputed or indexed — it is O(candidates) model calls per query.

The decision is a measurement, not a preference. If recall@50 is 0.95 and recall@5 is 0.70, there is 25 points of accuracy sitting in the gap and a reranker recovers most of it. If recall@50 and recall@5 are both 0.72, the answer is not in the candidate set and the reranker has nothing to work with — the problem is chunking or hybrid search, and adding a reranker buys latency and nothing else.
@code ts Retrieve wide, rerank narrow, with a latency budget that degrades safely
async function retrieveAndRank(query: string, k = 5): Promise<Chunk[]> {
  // STAGE 1 — cheap and wide. Hybrid, because vector alone misses exact terms.
  const candidates = await hybridSearch(query, { k: 60 });     // ~30ms

  // STAGE 2 — expensive and narrow, with a hard deadline.
  try {
    const scored = await withTimeout(
      rerank(query, candidates.map(c => c.content)),            // ~120ms, one batch
      { ms: 250 },
    );
    return scored
      .filter(s => s.score > RELEVANCE_FLOOR)   // ← the underrated part: drop the junk
      .slice(0, k)
      .map(s => candidates[s.index]);
  } catch (e) {
    // ✅ Degrade to stage 1 order rather than failing the request.
    metrics.increment('rerank.fallback', { reason: e.name });
    return candidates.slice(0, k);
  }
}

// Batch the whole candidate set in ONE call. N sequential calls is the mistake
// that turns a 120ms stage into a 6-second one.
@end
@senior
The part people skip is the relevance floor. A reranker does not only reorder — it gives you a calibrated score you can threshold on, which means you can return four chunks instead of five, or zero chunks and an honest "I do not have that information". That is a real quality gain, because the largest single source of confident wrong answers is padding the context with the least-bad remaining chunks until you have filled k slots. Retrieval scores from a bi-encoder are not calibrated well enough to threshold on; cross-encoder scores are.

On deployment, I would state the cost plainly: a hosted reranker is a network call and a per-query price, a self-hosted one is a GPU you now operate. For a corpus and traffic level like mine, hosted with a strict timeout and a graceful fallback is obviously right, and I would only consider self-hosting when either data residency forbids the call or volume makes the per-query price larger than an instance.
@followup
Does a reranker let you skip hybrid search?
@answer
No, and this is the ordering people get backwards. A reranker can only reorder what retrieval handed it, so if the vector search never surfaced the chunk containing the exact error code the user pasted, reranking a list that does not contain it changes nothing. Hybrid search fixes recall; reranking fixes precision. They solve different halves of the problem and the recall half has to be solved first — which is also why I measure recall@50 before I consider a reranker at all, because that number tells me whether there is anything for it to find.
@red
- Adding a reranker when recall@50 and recall@5 are the same — spending latency for nothing.
- Reranking one chunk per call instead of batching.
- Ignoring the score and always returning exactly k chunks.

### RAG, fine-tuning, long context or tools — how do you choose?
@short
They solve different problems and the mistake is treating them as competing options. RAG injects knowledge the model does not have. Fine-tuning changes behaviour, format and style, not facts. Long context is a delivery mechanism for a small, bounded set of documents. Tools are for anything that is live, transactional, or computed. I start with RAG plus tools because they are cheapest to change, and I reach for fine-tuning only when the requirement is a consistent behaviour I cannot get from prompting.
@deep
The distinction that matters is knowledge versus behaviour. Fine-tuning is very good at teaching a model to always answer in your output schema, adopt a house tone, or handle a classification task with a small model that would otherwise need a large one. It is bad at teaching facts: the facts get blended into weights, they cannot be cited, they cannot be updated without retraining, and the model becomes more confidently wrong when they change. Any requirement containing the phrase "and it must be up to date" rules fine-tuning out.

Long context is the option that looks like it deletes the problem and does not. It works honestly well when the corpus is genuinely small and bounded — one contract, one codebase module, a single policy handbook. Past that it fails on three axes at once: cost scales linearly with every token on every request, latency scales with it, and attention quality degrades in the middle of very long inputs, so the model can miss a fact that is demonstrably present.

Tools are the one people under-use. "What is my current balance" is not a retrieval question and no amount of embedding will make it one — it is an API call. A large fraction of what gets built as RAG should have been function calling against the system of record.

@senior
The nuance I would offer is that these compose, and the strongest systems use three of them at once — retrieval for knowledge, tools for live state, and constrained decoding for shape — while using no fine-tuning at all. So when someone frames it as "should we fine-tune or do RAG", I would push back on the premise and ask what the actual failure is. If the complaint is "it gets facts wrong", fine-tuning makes that worse, not better.

I would also be honest about the economics from the other direction: fine-tuning a small model to replace a large one on a narrow, high-volume task is one of the few reliable order-of-magnitude cost wins available, and it is underused because it feels like more work than changing a prompt. It is more work — it needs a dataset, an eval and a retraining path — and on a task running millions of times a month it pays for itself quickly.
@followup
What would make you fine-tune an embedding model?
@answer
A recall problem that survives good chunking and hybrid search, on a corpus whose vocabulary is genuinely unlike anything in the model's training data — internal part numbers, clinical shorthand, a jargon-dense domain where the general model puts unrelated terms close together. The signal is that my golden set shows the right chunk sitting at rank 40 rather than absent, meaning the space is nearly right but not discriminating. It needs training pairs, which in practice come from real query logs plus the chunk that turned out to be correct, so it is only available once the system has been running. Before that I would try a domain-appropriate off-the-shelf model and hybrid search, because both are a day's work rather than a project.
@red
- Proposing fine-tuning as the fix for factual errors or stale data.
- Treating long context as a free replacement for retrieval at any corpus size.
- Building retrieval over data that should have been a function call.

### How do you design a voice pipeline — speech in, speech out — so it feels instant?
@short
By streaming every stage and overlapping them, so the user hears the first syllable while the rest is still being generated. The budget I hold to is under a second from the user finishing speaking to audio starting: partial transcripts stream during speech, generation starts on the finalised transcript, and text-to-speech runs sentence by sentence rather than waiting for the whole answer. Barge-in — cancelling everything the instant the user speaks — matters as much as raw latency, because being talked over is what makes an assistant feel broken.
@deep
The naive pipeline is four blocking stages: record fully, transcribe fully, generate fully, synthesise fully, then play. Each stage waits for the previous one to complete, so the latencies add up and the user sits in silence for four or five seconds. Every fix is the same idea applied at a different boundary — start the next stage on the first useful output of the previous one rather than on its last.

The pieces that buy the most are streaming transcription with endpointing, so the transcript is essentially finished the moment the user stops talking rather than starting then; retrieval issued speculatively on the partial transcript, because a stable partial is usually enough to pick the right chunks; and sentence-boundary chunking into TTS, because a single sentence takes a few hundred milliseconds to synthesise while a full paragraph takes seconds.

Endpointing is the underrated component. Deciding when the user has actually finished — as opposed to pausing mid-thought — is the difference between an assistant that interrupts people and one that feels slow. A fixed silence threshold is wrong in both directions, and this is where most of the perceived quality lives.
@arch Where the second goes, and how overlapping it recovers most of it
  SERIAL (the naive build)                   ~4.4s of silence
  ┌────────────┬──────────┬──────────────┬───────────┐
  │ record     │ STT 600  │ LLM 2200     │ TTS 1100  │ ▶ audio
  └────────────┴──────────┴──────────────┴───────────┘

  OVERLAPPED (what I would build)            ~0.9s to first audio
  record ──┬── STT streams partials ──┐
           │                          ├─ endpoint detected

                                            first sentence ────┴─ TTS sentence 1 ▶
                                            sentence 2 ─────────── TTS sentence 2 ▶
                                                                  (queued, gapless)

  BARGE-IN: user speaks at any point
    → stop audio playback immediately (do not finish the sentence)
    → AbortController on the LLM stream (stops token spend too)
    → drop the TTS queue

      because the model must know what the user actually heard
@end
@senior
The engineering point I would make is that this is a cancellation problem more than a speed problem. Three concurrent streams — audio out, tokens in, transcription — all have to die instantly and in the right order when the user starts speaking, and the state has to remain coherent afterwards. If the interrupted response is written to conversation history as though it completed, the model will reference things the user never heard, and the conversation quietly goes wrong. So I record what was actually spoken aloud, not what was generated.

I would also flag the thing that surprised me: the perceptual budget is not uniform. Users tolerate a two-second pause before a long, considered answer far better than half a second of dead air before "yes" — silence with no signal is what reads as broken. A short acknowledgement token, or even the audio channel opening, resets the clock. That is a product observation with a direct engineering consequence, which is that I optimise time-to-first-audio rather than total response time, and they are very different targets.
@followup
The transcription is wrong for domain-specific words. What do you do?
@answer
Start with the cheap controls before touching models. Most speech-to-text APIs accept a vocabulary or phrase hint list, and seeding it with the product names, customer names and jargon relevant to that user fixes the majority of it for the cost of a request parameter — and it can be personalised per tenant, which is where the wins are. Beyond that, retrieval can absorb a surprising amount of transcription noise: hybrid search with fuzzy matching still finds the right chunk when a product name is misheard by a character or two, so the pipeline is more robust than the transcript. What I would not do is have the LLM "correct" the transcript freely, because it will silently rewrite what the user said into something more plausible, and a misheard word that produces a confident answer to a different question is worse than an obvious mistranscription the user can see and repeat.
@red
- Waiting for the full generation before starting text-to-speech.
- No barge-in, so the assistant talks over the user.
- Recording the generated response in history when playback was cut off.

### How do you manage conversation memory without the context window growing forever?
@short
A rolling window of recent turns kept verbatim, an older summary that is updated incrementally, and durable facts extracted into structured storage rather than left in prose. The reason not to simply send everything is not only cost — it is that a long, diluted context measurably degrades answer quality, and it makes every turn slower and more expensive than the last.
@deep
Naive accumulation has a compounding problem: turn 50 pays for turns 1 through 49 on every request, so cost and latency grow linearly within a conversation while quality drifts downward as the genuinely relevant recent turns get diluted by stale ones.

The three tiers each hold a different kind of thing. Recent turns need to be verbatim, because pronouns and corrections resolve against exact wording. Older context can be a summary, updated incrementally when the window overflows rather than regenerated from scratch each time — regenerating is both expensive and lossy, since summarising a summary compounds distortion. And durable facts — the user's name, their plan, a preference they stated once in turn 3 — belong in a structured store, retrieved by relevance, not carried along in a prose blob where they will eventually be summarised away.

That third tier is the one that separates a system that works at turn 60 from one that does not. "I'm allergic to shellfish", said once, must survive indefinitely, and no summarisation strategy reliably preserves it.
@code ts Three tiers: verbatim recent, incremental summary, structured facts
async function buildContext(sessionId: string, question: string) {
  const s = await sessions.get(sessionId);

  // TIER 1 — verbatim recent turns. Budget in TOKENS, not in turn count:
  // one turn containing a pasted stack trace is not one turn's worth of context.
  const recent = takeWithinBudget(s.turns, { tokens: 2000 });

  // TIER 3 — durable facts, retrieved by relevance to THIS question.
  const facts = await memory.search(s.userId, question, { k: 5 });

  return { summary: s.summary, facts, recent, question };
}

// Compaction runs when the window overflows — incremental, never from scratch.
async function compact(sessionId: string) {
  const s = await sessions.get(sessionId);
  if (tokensOf(s.turns) < COMPACT_AT) return;

  const [older, keep] = splitAt(s.turns, -RECENT_TURNS);

  const summary = await generate(SUMMARISE, { previous: s.summary, older },
    { max_tokens: 400 });                       // ✅ folds INTO the old summary

  // Extraction is a separate call with a schema — facts must not be prose.
  const extracted = await generate(EXTRACT_FACTS, { older }, {
    schema: z.array(z.object({
      kind: z.enum(['preference', 'constraint', 'identity', 'commitment']),
      fact: z.string(), confidence: z.number(),
    })),
  });
  await memory.upsert(s.userId, extracted.filter(f => f.confidence > 0.8));

  await sessions.update(sessionId, { summary, turns: keep });
}
@end
@senior
The failure I would highlight is contradiction. A user says "actually, make it the 15th" at turn 20, and if the extraction layer appends rather than supersedes, the store now holds two conflicting commitments and the model picks one arbitrarily. So facts need identity and recency — an upsert keyed on what the fact is about, not an append — and the retrieval has to prefer the latest. That is a boring database concern rather than an AI one, which is exactly why it gets missed in AI codebases.

The second thing is that memory is a privacy surface. Anything extracted and stored durably is personal data with a retention obligation and a deletion path, and it needs the same tenant isolation as the document corpus. "Delete my account" has to clear the extracted memory too, and if that memory has been embedded for retrieval, it has to clear the vectors — which is the same index-versus-source-of-truth sync problem as the document pipeline, and worth saying out loud because it is the one people forget.
@followup
How do you keep quality from degrading right after a compaction?
@answer
By measuring it explicitly, because it is the moment where things break and it is invisible otherwise. I keep a set of multi-turn evaluation conversations that deliberately reference something from early on after a compaction has happened, and I assert the answer still holds — that is the regression test for the summariser, and it is the only way to know the prompt change you just made did not quietly start dropping constraints. In the design itself, the protection is that anything load-bearing should not be relying on the summary at all: constraints, commitments and identity go to the structured store where they are retrieved exactly, and the summary carries narrative context whose loss is survivable. If losing a detail would produce a wrong answer rather than a vaguer one, it does not belong in prose.
@red
- Sending the entire conversation history on every turn.
- Re-summarising the whole conversation from scratch at each compaction.
- Appending contradictory extracted facts instead of superseding them.

# SECTION Concurrency, Consistency & Coordination | The bugs that only appear under load, and how to make them impossible.

### How do you prevent overselling the last item in stock?
@short
Make the decrement atomic and conditional in the database — `UPDATE ... SET stock = stock - 1 WHERE id = $1 AND stock >= 1` — and treat zero affected rows as "out of stock". No application-level read-then-write, no distributed lock, no cache as the source of truth for the decision.
@deep
The naive read-then-write is a lost update: two requests both read one, both decide it is available, both write zero. Neither the ORM nor the single-threaded event loop protects you, because the await between the read and the write is a yield point.

Three correct approaches exist and the right choice depends on whether you need to reason about the value before writing: an atomic conditional update, a pessimistic row lock, or optimistic concurrency with a version and a retry.
@code sql The three correct solutions, and when each fits
-- 1. ATOMIC CONDITIONAL UPDATE — best when the logic fits in SQL
UPDATE products SET stock = stock - $2
 WHERE id = $1 AND stock >= $2
RETURNING stock;
-- 0 rows → insufficient stock. No race is possible. No lock held across think time.

-- 2. PESSIMISTIC LOCK — when you must read, decide with complex logic, then write
BEGIN;
  SELECT stock, reserved FROM products WHERE id = $1 FOR UPDATE;   -- serialises writers
  -- ... business rules that cannot be expressed in one UPDATE ...
  UPDATE products SET stock = stock - $2 WHERE id = $1;
COMMIT;
-- Cost: the hot row becomes a serialisation point. Fine for normal traffic,
-- a bottleneck during a flash sale on one SKU.

-- 3. OPTIMISTIC — low contention, no lock held, retry on conflict
UPDATE products SET stock = $3, version = version + 1
 WHERE id = $1 AND version = $2;
-- 0 rows → someone else changed it → re-read and retry (bounded attempts)

-- FLASH SALE variant: shard the counter to remove the hot row entirely
UPDATE stock_shards SET qty = qty - 1
 WHERE product_id = $1 AND shard = $2 AND qty >= 1;   -- shard = hash(userId) % 16
@end
@senior
Counter sharding is the answer for genuine flash-sale contention: a single row that every request must lock is a serialisation point no hardware fixes, and splitting the stock across sixteen shard rows lets sixteen transactions proceed in parallel. The cost is that the total requires a sum and a shard can be empty while others are not, so you need a fallback that tries another shard. I would also point out that a reservation model — decrement into a `reserved` column with a TTL, confirm on payment, release on expiry — is usually the right business model, because holding stock during checkout is what customers expect and it avoids the "payment succeeded but stock is gone" failure.
@followup
Why is a Redis lock not the right answer here?
@answer
Because the data lives in Postgres, so the correct place to enforce the invariant is Postgres — a Redis lock adds a second system that can fail independently, and its failure modes (asynchronous replication, expiry during a pause) mean it does not actually guarantee mutual exclusion. Using the database's own atomicity is simpler, faster and genuinely correct. I would use a Redis lock for coordinating something outside the database, such as ensuring one instance runs a scheduled job.
@red
- Read-then-write in application code.
- A distributed lock to protect a single database row.

### How do you implement optimistic concurrency in an API?
@short
Version each resource, require the client to send the version it based its edit on, and reject with 409 if it no longer matches. Over HTTP that is `ETag` on the response and `If-Match` on the update, which gives you a standard, cache-friendly mechanism instead of a bespoke field.
@deep
The purpose is to prevent silent lost updates in the classic edit-form scenario: two users load the same record, both edit, and the second save overwrites the first with no indication anything was lost.

The `409` response should be actionable — return the current state so the client can show a diff and let the user merge, rather than just refusing.
@code ts ETag / If-Match, with a useful conflict response
app.get('/api/v1/documents/:id', authenticate, async (req, res) => {
  const doc = await repo.find(req.params.id, req.user.tenantId);
  if (!doc) return res.status(404).json({ error: 'NOT_FOUND' });

  const etag = `"${doc.version}"`;
  if (req.get('If-None-Match') === etag) return res.status(304).end();
  res.set('ETag', etag).json(toResponse(doc));
});

app.put('/api/v1/documents/:id', authenticate, async (req, res) => {
  const ifMatch = req.get('If-Match');
  if (!ifMatch) return res.status(428).json({ error: 'IF_MATCH_REQUIRED' });   // 428 Precondition Required

  const { rowCount, rows } = await db.query(
    `UPDATE documents SET body = $3, version = version + 1, updated_at = now()
      WHERE id = $1 AND tenant_id = $4 AND version = $2
      RETURNING *`,
    [req.params.id, Number(ifMatch.replaceAll('"','')), req.body.body, req.user.tenantId]);

  if (!rowCount) {
    const current = await repo.find(req.params.id, req.user.tenantId);
    if (!current) return res.status(404).json({ error: 'NOT_FOUND' });
    return res.status(409).json({                        // ← give the client what it needs to merge
      error: 'VERSION_CONFLICT',
      currentVersion: current.version,
      current: toResponse(current),
      yours: req.body,
    });
  }
  res.set('ETag', `"${rows[0].version}"`).json(toResponse(rows[0]));
});
@end
@senior
Returning the current state alongside the 409 is what makes this usable rather than merely correct — the client can present a three-way merge or at minimum show what changed, instead of telling the user their work conflicted and offering nothing. Requiring `If-Match` with a 428 when it is absent is the other detail: making the precondition mandatory means a client cannot accidentally perform a blind overwrite. For collaborative text specifically, this is where a CRDT is a better answer, because per-document versioning forces a conflict on every concurrent edit, whereas a CRDT merges them.
@followup
When is last-write-wins acceptable?
@answer
When the field is genuinely independent and the loss is trivial — a user's theme preference, a last-viewed timestamp, a cached derived value. It is unacceptable whenever a user has invested effort in the content or where the value has financial meaning. The honest position is that last-write-wins is a decision to lose data silently, so it should be a deliberate choice for specific fields rather than a default for the whole record.
@red
- Blind overwrites with no version check.
- A 409 with no information about the current state.

### How do you build a reliable distributed scheduler?
@short
Store schedules in the database, have workers claim due jobs with `SELECT ... FOR UPDATE SKIP LOCKED`, and make execution idempotent keyed on the scheduled occurrence rather than the run attempt. That gives you multi-instance safety, crash recovery and an audit trail without a separate scheduling system.
@deep
Cron in every replica runs the job N times; cron in one replica is a single point of failure. A leader-election approach works but adds coordination. The claim-based approach is simpler: every instance polls, the database arbitrates, and a crashed worker's claim expires and is reclaimed.

Idempotency must key on the occurrence — "the 09:00 run on 2026-08-18" — not on the attempt, so a retry after a crash does not produce a second execution.
@code sql A scheduler table and the claim query
CREATE TABLE scheduled_jobs (
  id           uuid PRIMARY KEY,
  name         text NOT NULL,
  cron         text NOT NULL,
  timezone     text NOT NULL DEFAULT 'UTC',
  next_run_at  timestamptz NOT NULL,
  claimed_by   text,
  claimed_at   timestamptz,
  enabled      boolean NOT NULL DEFAULT true
);
CREATE INDEX ON scheduled_jobs (next_run_at) WHERE enabled;

CREATE TABLE job_runs (
  job_id       uuid NOT NULL,
  occurrence   timestamptz NOT NULL,     -- ← the SCHEDULED time, not the run time
  status       text NOT NULL,
  started_at   timestamptz, finished_at timestamptz, error text,
  PRIMARY KEY (job_id, occurrence)       -- ← idempotency: one row per occurrence
);
@end
@code ts Claim, execute idempotently, reschedule
async function tick(workerId: string) {
  const claimed = await db.query(`
    WITH due AS (
      SELECT id FROM scheduled_jobs
       WHERE enabled AND next_run_at <= now()
         AND (claimed_at IS NULL OR claimed_at < now() - interval '5 minutes')  -- reclaim stale
       ORDER BY next_run_at
       FOR UPDATE SKIP LOCKED LIMIT 5
    )
    UPDATE scheduled_jobs j SET claimed_by = $1, claimed_at = now()
      FROM due WHERE j.id = due.id RETURNING j.*`, [workerId]);

  for (const job of claimed.rows) {
    const occurrence = job.next_run_at;
    const first = await db.query(
      `INSERT INTO job_runs (job_id, occurrence, status, started_at)
       VALUES ($1,$2,'running',now()) ON CONFLICT DO NOTHING RETURNING 1`, [job.id, occurrence]);
    if (!first.rowCount) { await reschedule(job); continue; }     // already ran → skip

    try { await run(job); await mark(job.id, occurrence, 'succeeded'); }
    catch (e) { await mark(job.id, occurrence, 'failed', e); await alert(job, e); }
    finally { await reschedule(job); }        // compute next_run_at in the job's TIMEZONE
  }
}
@end
@senior
Computing the next occurrence in the job's own timezone is the detail that causes real incidents twice a year: a daily 09:00 job scheduled in UTC drifts by an hour across a daylight-saving transition, and a job that runs "every day at 02:30" can either run twice or not at all on the transition day. Storing the timezone and using a cron library that understands it avoids that. The other point is the stale-claim reclaim window — it is what makes a crashed worker recoverable, and it must be longer than the longest legitimate run or you will get concurrent executions.
@followup
Why not use cron on one machine?
@answer
Because it is a single point of failure with no visibility: if that machine is down or the job fails, nothing tells you, and there is no record of what ran when. It also does not scale to multiple jobs with different concurrency needs, and it lives outside your deployment pipeline so it drifts from the code. The database-backed approach gives you high availability, an audit trail, alerting on failure, and the schedule as code — all for a modest amount of implementation.
@red
- Cron in every replica with no lock.
- Idempotency keyed on the run attempt rather than the occurrence.

### How do you coordinate work across services without distributed transactions?
@short
Sagas with compensations for multi-step business processes, the outbox pattern for atomically publishing intent, and idempotent consumers so retries are safe. The system converges rather than being atomic, and the intermediate states are made visible to users rather than hidden.
@deep
The fundamental constraint is that you cannot atomically commit to your database and to someone else's system. Every pattern here is a way of making that acceptable: commit the intent locally, perform the external effect with at-least-once delivery, and reconcile.

Reconciliation is the safety net that catches everything the patterns miss — a webhook lost, a compensation that failed, a consumer that was down for hours.
@arch The three patterns composed
  ┌── LOCAL TRANSACTION ────────────────────────────────┐
  │  UPDATE orders SET status='paid'                     │
  │  INSERT outbox (type='order.paid', payload, id)      │  ← atomic. No dual write.
  └───────────────────┬──────────────────────────────────┘
                      │ relay (FOR UPDATE SKIP LOCKED)
                      ▼
              broker / queue  (at-least-once)
                      │
        ┌─────────────┼─────────────┬──────────────┐
        ▼             ▼             ▼              ▼
   fulfilment     invoicing     analytics      notifications
   (idempotent    (idempotent   (idempotent    (idempotent
    on event id)   on event id)  on event id)   on event id)
        │
        └── failure → retry with backoff → DLQ → alert → human or compensating action

  RECONCILIATION (hourly/daily): compare the system of record against each
  downstream's state; repair automatically where safe, page where not.
  ↑ This is what catches everything the happy path missed.
@end
@senior
The reconciliation loop is the part I would insist on, because every other mechanism is best-effort: outboxes get stuck, consumers get deployed broken, brokers lose messages during failover, and compensations themselves can fail. A job that compares the system of record to each downstream and repairs or alerts is what turns "eventually consistent" from a hope into a property. It is also the thing that lets you sleep, because a silent divergence discovered by a customer three weeks later is far worse than an alert an hour after it happens.
@followup
How do you make intermediate states acceptable to users?
@answer
Show them honestly. An order that is paid but not yet fulfilled should say so, with an expectation of when it will change — not appear complete or appear broken. Support tooling needs the same visibility so an agent can see where a process is stuck. Users tolerate "we have your payment, your order is being prepared" easily; what they do not tolerate is a status that says one thing while the reality is another, which is what happens when you pretend the operation was atomic.
@red
- Claiming distributed transactions across services.
- No reconciliation to catch what the happy path missed.

### How do you handle idempotency for operations with external side effects?
@short
Separate the decision from the effect: commit the intent transactionally with a unique key, then perform the effect in a worker using that key as the provider's idempotency key, and record completion. A retry at any stage either finds the work already done or repeats it against an idempotent endpoint.
@deep
The difficulty is the gap between deciding and doing. If you call the provider inside the transaction, a timeout leaves you unsure whether it happened while your transaction rolls back. If you call it after committing, a crash between them means it never happens.

The outbox closes the second gap; the provider's idempotency key closes the first.
@code ts The full pattern for "charge the card and record the payment"
// 1. TRANSACTION: decide and record the intent. No external calls.
const intent = await withTransaction(async (tx) => {
  const order = await orders.findForUpdate(orderId, tx);
  if (order.status !== 'pending') return null;                       // already handled
  const row = await payments.insert({ orderId, amountMinor: order.totalMinor,
                                      status: 'requested', idemKey: `pay:${orderId}` }, tx);
  await outbox.publish('payment.requested', { paymentId: row.id }, tx);
  return row;
});

// 2. WORKER: perform the effect, using the SAME key. Safe to retry indefinitely.
async function performCharge(paymentId: string) {
  const p = await payments.find(paymentId);
  if (p.status !== 'requested') return;                              // already done

  const charge = await provider.charge(
    { amount: p.amountMinor, currency: p.currency, source: p.sourceToken },
    { idempotencyKey: p.idemKey });          // ← retry returns the SAME charge, never a second one

  await payments.markSucceeded(p.id, charge.id);
}

// 3. RECONCILE: anything still 'requested' after 15 minutes is queried at the provider
//    and repaired from their authoritative answer.
@end
@senior
Deriving the idempotency key from the business entity rather than generating a fresh one per attempt is the crux: `pay:${orderId}` means every retry, from any layer, converges on the same provider-side operation. A UUID generated at call time would create a new charge on each retry, which is the double-charge bug wearing a disguise. The reconciliation step is what handles the remaining case where the provider succeeded but we never learned about it — and that case is not rare, it is the normal consequence of network failures at scale.
@followup
What if the external API has no idempotency support?
@answer
Then you build it around them: record the attempt with a unique key before calling, and on retry query their API first to check whether the operation already exists — most APIs let you look up by your own reference id, which you pass on the original call. If they support neither, you are left choosing between at-most-once (never retry, risk losing the operation) and at-least-once (retry, risk duplication), and that choice should be made explicitly based on which failure is worse for that operation. Sending an email twice is acceptable; charging twice is not.
@red
- Generating a new idempotency key per retry.
- Calling the external API inside the database transaction.

### How do you design for read-your-writes and monotonic reads?
@short
Route a user's reads to the primary for a short window after they write, or track the write position and only use a replica that has replayed past it. Monotonic reads require sticking a user to one replica within a session so they never see time move backwards.
@deep
These are session guarantees rather than global consistency, and they are what users actually perceive. Global strong consistency is expensive; making a user never see their own write vanish is cheap and covers almost all of the perceived inconsistency.

The precise version uses the write's log position: record it after a write and require any replica serving that user to have replayed at least that far, otherwise fall back to the primary.
@code ts LSN-based read-your-writes — precise, not just time-based
// After any write, record where we are in the WAL for this session
const { rows } = await primary.query('SELECT pg_current_wal_lsn() AS lsn');
await redis.set(`lsn:${userId}`, rows[0].lsn, 'EX', 30);

// On read, choose a replica that has caught up — otherwise use the primary
export async function readFor(userId: string) {
  const required = await redis.get(`lsn:${userId}`);
  if (!required) return replica;                                  // no recent write

  for (const r of replicas) {
    const { rows } = await r.query('SELECT pg_last_wal_replay_lsn() AS lsn');
    if (rows[0].lsn >= required) return r;                        // caught up → safe
  }
  return primary;                                                 // none caught up → primary
}

// Simpler approximation that covers most cases:
//   after a write, pin this user's reads to the primary for 5 seconds.
//   Costs a little primary load; removes the entire class of "my change disappeared".
@end
@senior
The simple time-based version is usually the right engineering trade: it costs a small amount of extra primary load and eliminates the single inconsistency users always notice. The LSN version is precise and worth it when replica lag is variable or when primary capacity is genuinely constrained. What I would avoid is the naive "read from a replica always" configuration, because the resulting bug — a user creates something, is redirected to it, and gets a 404 — looks like a broken application rather than a consistency trade-off, and it generates support tickets rather than understanding.
@followup
What is monotonic read consistency and when does it break?
@answer
It guarantees that a user never sees older data than they have already seen. It breaks when consecutive reads hit different replicas with different lag: a user refreshes and their comment disappears, then reappears. The fix is session affinity to one replica, or tracking the highest position the session has observed and requiring subsequent reads to meet it. It is a small guarantee that removes a disproportionate amount of user confusion.
@red
- Sending all reads to replicas including read-after-write.
- Assuming replica lag is negligible without measuring it.

### How do you test concurrent and distributed behaviour?
@short
Exercise the real concurrency: fire N parallel operations against a real database and assert the invariant held. For distributed behaviour, inject faults — network partitions, latency, killed processes — and verify the system's documented degraded behaviour actually occurs.
@deep
Sequential tests cannot find race conditions, so the test must actually run things in parallel and then check the invariant rather than the sequence. That is both simpler and more robust than trying to orchestrate a specific interleaving.

For distributed failures, deterministic fault injection at the proxy layer is far more repeatable than unplugging things, and it can run in CI.
@code ts Invariant-based concurrency tests, and fault injection
it('never oversells under 50 concurrent purchases of the last unit', async () => {
  await db.products.set('p_1', { stock: 1 });

  const results = await Promise.allSettled(
    Array.from({ length: 50 }, () =>
      request(app).post('/orders').set(auth(user)).send({ sku: 'p_1', qty: 1 })));

  const created = results.filter(r => r.status === 'fulfilled' && r.value.status === 201);
  expect(created).toHaveLength(1);
  expect((await db.products.get('p_1')).stock).toBe(0);        // never negative
});

it('processes a duplicated webhook exactly once under concurrency', async () => {
  const evt = signedEvent({ id: 'evt_1', type: 'payment_intent.succeeded' });
  await Promise.all(Array.from({ length: 10 }, () => post('/webhooks/stripe', evt)));
  await drainQueue();
  expect(await db.orderEvents.count({ to: 'paid' })).toBe(1);
});

// Fault injection with toxiproxy — deterministic, runs in CI
await toxi.addToxic({ type: 'latency', attributes: { latency: 5000 } });   // slow dependency

await toxi.addToxic({ type: 'timeout' });                                  // dependency down
expect(breaker.state).toBe('open');
@end
@senior
Asserting the invariant after real parallel execution is the technique, and it is both simpler and stronger than trying to reproduce a specific interleaving — you do not need to know how the race happens, only that the outcome is wrong. These tests are also fast: fifty parallel requests against a containerised Postgres run in under a second. The fault-injection half is what nobody does and what catches the paths that only run during incidents; a circuit breaker that has never been observed opening is an assumption, not a control.
@followup
How do you test something that only fails at scale?
@answer
Load test with realistic traffic shapes against a production-like environment, and watch for the bend rather than the peak — the point where latency rises non-linearly tells you what the real constraint is. For anything that only manifests with production data distributions, a shadow environment replaying real traffic is the honest answer. And some failures genuinely cannot be reproduced pre-production, which is why the mitigations — feature flags, gradual rollout, fast rollback, good observability — matter as much as the testing.
@red
- Testing concurrency with sequential calls.
- Fault-tolerance code that has never been executed.

### How do you handle clock skew and time in distributed systems?
@short
Never trust a client's clock, never rely on wall-clock comparisons across machines for correctness, and use monotonic clocks for measuring durations. Where ordering matters, use logical clocks or a server-assigned sequence; where expiry matters, compute it server-side.
@deep
Wall clocks drift and jump — NTP corrections can move time backwards, and container clocks can be badly wrong. Using `Date.now()` differences to measure elapsed time can therefore produce negative durations or wrong ones; `process.hrtime.bigint()` or `performance.now()` are monotonic and correct for that purpose.

For ordering across machines, wall clocks are insufficient. Logical sequence numbers assigned by a single authority per entity, or Lamport-style counters, give you a defensible order.
@code ts The three time rules, in code
// 1. DURATIONS: monotonic clock, not wall clock
const t0 = process.hrtime.bigint();
await doWork();
const ms = Number(process.hrtime.bigint() - t0) / 1e6;   // never negative, never jumps

// 2. ORDERING: server-assigned sequence, not client timestamps
const seq = await redis.incr(`room:${roomId}:seq`);       // single authority per room
// ❌ ordering messages by client-supplied `sentAt` → a device with a wrong clock
//    can post messages that appear hours in the past or future

// 3. EXPIRY: computed and enforced server-side
const token = jwt.sign({ sub }, key, { expiresIn: '15m' });   // exp set by the server
// verification allows a small clock tolerance for legitimate skew
jwt.verify(token, key, { clockTolerance: 5 });

// 4. ID GENERATION: time-ordered but collision-safe across machines
const id = uuidv7();       // timestamp prefix + randomness → sortable, no coordination
@end
@senior
The client-clock issue is not theoretical: in a mobile app I have seen devices with clocks days out of sync, and any logic that ordered or expired based on the device's time produced visibly wrong behaviour. The rule I apply is that the client may report its time as information — useful for diagnostics — but the server assigns anything that matters. UUIDv7 is worth mentioning as the modern compromise for identifiers: time-ordered enough to preserve index locality, random enough to avoid coordination, and generatable on the client for offline-first apps.
@followup
Why can't you just use timestamps for ordering events?
@answer
Because two machines' clocks differ, so an event that genuinely happened later can carry an earlier timestamp — which produces an incorrect order that looks authoritative. Even with NTP, skew of milliseconds is normal and enough to matter for high-frequency events. The solutions are a single sequencing authority per entity, logical clocks that capture causality rather than time, or hybrid logical clocks that combine both. Systems like Spanner solve it with atomic clocks and a bounded uncertainty interval, which is a good illustration of how hard the problem is when you genuinely need global ordering.
@red
- Ordering events by client-supplied timestamps.
- Measuring durations with `Date.now()` differences.

### How would you design a system where correctness matters more than availability?
@short
Fail closed, make invariants structural rather than procedural, use strong isolation and explicit locking where needed, log everything with an audit trail, reconcile continuously, and require human approval for irreversible high-value actions. Accept downtime rather than accept incorrect state.
@deep
The design posture inverts most web-scale advice. Caching becomes suspect, eventual consistency becomes unacceptable for the core invariants, and retries become dangerous unless provably idempotent.

The techniques that carry the weight are database constraints that make invalid states unrepresentable, double-entry style modelling for anything financial, and reconciliation that proves the state is correct rather than assuming it.
@code sql A ledger design where the invariant cannot be violated
-- Double entry: every movement is two rows that must sum to zero
CREATE TABLE ledger_entries (
  id           bigserial PRIMARY KEY,
  transfer_id  uuid NOT NULL,
  account_id   uuid NOT NULL REFERENCES accounts(id),
  amount_minor bigint NOT NULL CHECK (amount_minor <> 0),
  currency     char(3) NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON ledger_entries (transfer_id);
CREATE INDEX ON ledger_entries (account_id, created_at DESC);

-- The invariant, enforced by the database at commit time
CREATE CONSTRAINT TRIGGER transfer_balances
AFTER INSERT ON ledger_entries DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION assert_transfer_sums_to_zero();

-- Balances are DERIVED, never stored as a mutable field that can drift
CREATE MATERIALIZED VIEW account_balances AS
SELECT account_id, currency, sum(amount_minor) AS balance_minor
  FROM ledger_entries GROUP BY 1, 2;

-- Continuous proof: recompute and compare against any cached balance
-- Any mismatch is a SEV-1, not a warning.
@end
@senior
Deriving balances from an immutable append-only ledger rather than storing a mutable balance is the structural decision, and it is what makes the system auditable and self-correcting: you can always recompute the truth, and any cached value is a performance optimisation that can be verified. The deferred constraint trigger enforcing that each transfer sums to zero means an unbalanced transfer cannot be committed at all, regardless of application bugs. That is the general principle for correctness-critical systems — encode the invariant where it cannot be bypassed, and prove it continuously rather than trusting the code that maintains it.
@followup
How do you handle a bug that has already produced incorrect state?
@answer
Stop the bleeding first — disable the code path with a flag — then quantify the blast radius by querying for records violating the invariant, then repair with a reviewed, reversible correction script, and finally add the constraint or check that makes the class of error impossible. Every step is logged and, for financial data, the correction is itself a ledger entry rather than an edit, so the history shows what happened and why. Silently fixing rows in a financial system is how you lose the ability to explain your own data.
@red
- Storing a mutable balance as the source of truth.
- Correcting financial data with an in-place update and no audit trail.

# SECTION Real-Time, CRDTs & Collaborative Systems | Deep questions on the WebSocket fan-out and Yjs system you actually built — self-initiated, with no commercial users. Say that once, then defend the engineering properly.

### Compare CRDTs with Operational Transformation.
@short
OT transforms operations against concurrent ones so they can be applied in any order, and historically required a central server to establish a canonical order. CRDTs make the data structure itself commutative so operations merge without transformation or a coordinator. CRDTs are simpler to make correct; OT can produce smaller state.
@deep
OT's difficulty is the transformation functions: for N operation types you need N² transformation cases, and subtle bugs there produce divergence that is extremely hard to debug. Google Docs famously spent years getting theirs right.

CRDTs shift the complexity into the data structure and pay for it with metadata: every element carries an identity, and deletions leave tombstones, so document size grows with edit history rather than with content length.
@code text The trade-off, concretely
  OPERATIONAL TRANSFORMATION
   ✔ compact state — the document is just the text
   ✔ mature in production (Google Docs, Etherpad)
   ✘ needs a central authority to order operations → the server is stateful
   ✘ N² transformation functions; correctness is genuinely hard
   ✘ offline for a long period is difficult (long transformation chains)

  CRDT (Yjs / Automerge)
   ✔ no coordinator needed — merge is commutative, associative, idempotent
   ✔ server can be a DUMB RELAY → stateless, trivially horizontally scalable
   ✔ offline editing merges cleanly on reconnect, arbitrarily long
   ✔ peer-to-peer possible
   ✘ metadata overhead: each element carries client id + clock
   ✘ tombstones accumulate → periodic snapshot compaction required
   ✘ converges deterministically, but not necessarily SEMANTICALLY correctly

  WHY I CHOSE A CRDT: the server never parses the document, so scaling the
  WebSocket layer is just adding instances; and offline-first was a requirement.
@end
@senior
The decisive argument for a CRDT in my design was that it makes the server stateless with respect to document semantics: it relays opaque binary updates and persists them, so horizontal scaling is trivial and a server restart loses nothing. With OT the server holds the canonical operation order, which makes it stateful and makes failover a real design problem. The cost I would name honestly is document growth — Yjs documents accumulate tombstones, so periodic snapshot compaction is mandatory, and without it a heavily edited document becomes slow to load after months.
@followup
What does Yjs actually do to order concurrent insertions?
@answer
It uses a YATA-style algorithm: every inserted item has a unique id of client id plus a logical clock, and a reference to the items it was inserted between. When two clients insert at the same position concurrently, the resulting order is decided deterministically by comparing those ids, so every replica computes the same result without communication. Deletions mark items as deleted rather than removing them, which preserves the positional references other operations depend on — that is why tombstones exist and why compaction is a separate operation.
@red
- Claiming CRDTs remove all conflicts.
- Ignoring document growth from tombstones.

### How do you persist and version CRDT documents?
@short
Append incremental updates for durability and low write latency, periodically collapse them into a snapshot to bound load time, and keep named snapshots separately if the product needs version history. Store large snapshots in object storage rather than in the database row.
@deep
The naive approach — storing the full encoded document on every change — makes writes expensive and grows quadratically with edit count. The append-then-compact approach keeps writes small and load time bounded.

Version history is a distinct feature: Yjs supports capturing a state vector and computing a diff, so a named version is a snapshot plus the ability to reconstruct the document at that point.
@code ts Append, compact, and named versions
// Hot path: append the incremental update. Small, fast, durable.
await db.query(
  `INSERT INTO doc_updates (doc_id, seq, update, created_at) VALUES ($1, $2, $3, now())`,
  [docId, seq, Buffer.from(update)]);

// Compaction: when updates exceed a threshold, collapse to a snapshot
async function compact(docId: string) {
  const rows = await db.query(
    `SELECT seq, update FROM doc_updates WHERE doc_id=$1 ORDER BY seq`, [docId]);

  const doc = new Y.Doc();
  for (const r of rows.rows) Y.applyUpdate(doc, r.update);
  const snapshot = Y.encodeStateAsUpdate(doc);                 // tombstones collapsed

  await withTransaction(async (tx) => {
    await tx.query(`INSERT INTO doc_snapshots (doc_id, seq, snapshot, created_at)
                    VALUES ($1,$2,$3,now())`, [docId, rows.rows.at(-1)!.seq, snapshot]);
    await tx.query(`DELETE FROM doc_updates WHERE doc_id=$1 AND seq <= $2`,
                   [docId, rows.rows.at(-1)!.seq]);
  });
}

// Load: latest snapshot + subsequent updates
const snap = await db.oneOrNone(`SELECT snapshot, seq FROM doc_snapshots
                                  WHERE doc_id=$1 ORDER BY seq DESC LIMIT 1`, [docId]);
const doc = new Y.Doc();
if (snap) Y.applyUpdate(doc, snap.snapshot);
for (const u of await updatesAfter(docId, snap?.seq ?? 0)) Y.applyUpdate(doc, u);

// Named version: store the state vector so you can diff/restore later
await db.query(`INSERT INTO doc_versions (doc_id, name, state_vector, snapshot, created_by)
                VALUES ($1,$2,$3,$4,$5)`,
               [docId, name, Y.encodeStateVector(doc), Y.encodeStateAsUpdate(doc), userId]);
@end
@senior
Compacting inside a transaction that inserts the snapshot and deletes the collapsed updates together is the correctness detail — doing it in two steps risks losing updates if the process dies between them. The other decision is where snapshots live: a document with heavy media or a very long history can produce snapshots of several megabytes, and storing those in a Postgres column bloats the table and slows every query touching it, so object storage with the key in the row is the better shape past a threshold. I would also compact on a background job triggered by update count rather than on the write path, so user-facing latency is unaffected.
@followup
How do you implement undo in a collaborative document?
@answer
With Yjs's `UndoManager`, scoped to the local client's own changes by tracking origin. That is the semantically correct behaviour: undo should revert *your* last edit, not your collaborator's, which is what a naive global undo would do and what users find deeply confusing. The manager tracks which transactions originated locally and inverts only those. Scoping undo correctly is one of those details that separates a collaborative editor that feels right from one that feels broken.
@red
- Storing the full document on every keystroke.
- Global undo that reverts other users' edits.

### How do you scale a WebSocket layer to very large numbers of connections?
@short
Bound per-connection memory, raise file-descriptor limits, subscribe to only the channels each instance actually needs, use a binary protocol, batch and throttle outbound messages, and shard rooms across instances when a single room becomes too large to fan out from one place.
@deep
The limits are memory per connection (buffers and per-socket state, typically tens of kilobytes), file descriptors, and the fan-out cost of large rooms. CPU is rarely the constraint for idle connections but becomes one when broadcasting frequently to many sockets.

Large rooms are the hard case: broadcasting to 50,000 subscribers from one instance serialises the same message 50,000 times. Batching, binary encoding and tiered fan-out are the mitigations.
@code ts Batching and per-socket backpressure
const outbox = new Map<WebSocket, string[]>();

function enqueue(ws: WebSocket, msg: string) {
  // Per-socket backpressure: a slow client must not grow our memory unboundedly
  if (ws.bufferedAmount > 1_000_000) { metrics.increment('ws.slow_client_dropped'); ws.close(1013); return; }
  const buf = outbox.get(ws) ?? [];
  buf.push(msg);
  outbox.set(ws, buf);
}

// Flush on a fixed tick — one syscall per socket per tick instead of per message
setInterval(() => {
  for (const [ws, msgs] of outbox) {
    if (ws.readyState !== ws.OPEN || !msgs.length) continue;
    ws.send(msgs.length === 1 ? msgs[0] : `[${msgs.join(',')}]`);   // batched frame
  }
  outbox.clear();
}, 50);                       // 20 flushes/sec — imperceptible, massively fewer syscalls

// OS limits that actually bind
//   ulimit -n 200000 (container spec)
//   net.core.somaxconn, net.ipv4.tcp_max_syn_backlog
//   per-connection memory: keep per-socket state small; use WeakMap for metadata
@end
@senior
Per-socket backpressure via `bufferedAmount` is the detail that prevents one slow client from taking down an instance: without it, a client on a poor connection accumulates megabytes of unsent data in your process memory, and a few hundred such clients is an OOM. Dropping them with a 1013 "try again later" is the correct behaviour. The batching tick is the other big win — sending twenty frames per second instead of hundreds reduces syscalls dramatically at a latency cost users cannot perceive, and it is the difference between a fan-out that scales and one that pins a CPU.
@followup
How do you handle a room with 100,000 participants?
@answer
Stop treating it as a room. At that size, participation is almost entirely read-only, so the right model is a broadcast fan-out tree or a CDN-backed stream rather than per-socket delivery from one instance: a tier of relay instances each serving a subset, or push through a service designed for broadcast. Presence becomes an aggregate count rather than a member list, and interactive features like typing indicators are disabled or sampled. The design changes qualitatively, not just quantitatively, and recognising that threshold is the point.
@red
- No per-socket backpressure.
- Broadcasting individually to every socket in a very large room.

### How do you secure a real-time system?
@short
Authenticate on the upgrade request and authorise every subscription and every message against the user's permissions — not once at connect. Re-validate periodically because connections are long-lived, propagate revocation so a logged-out session's socket is closed, and rate limit per connection.
@deep
The specific risks are: a client subscribing to a room it should not see, a client sending a message impersonating another user, a token that expires mid-connection but keeps working for hours, and a client flooding the server with messages.

The long-lived nature is the key difference from HTTP: an authorisation decision made at connect time can become stale, so revocation must actively reach the connection.
@code ts Authorisation on subscribe and on message, plus revocation
wss.on('connection', async (ws, req) => {
  const claims = await verifyFromCookieOrHeader(req);      // reject the UPGRADE if invalid
  if (!claims) return ws.close(4401, 'unauthenticated');
  ws.user = { id: claims.sub, tenantId: claims.tid, exp: claims.exp };

  // Long-lived connections need periodic re-validation
  const revalidate = setInterval(async () => {
    if (Date.now() / 1000 > ws.user.exp) return ws.close(4401, 'token_expired');
    if (await revocations.isRevoked(claims.jti, claims.sub)) return ws.close(4401, 'revoked');
  }, 60_000);
  ws.on('close', () => clearInterval(revalidate));

  const limiter = createRateLimiter({ limit: 50, windowMs: 1000 });   // per connection

  ws.on('message', async (raw) => {
    if (!limiter(ws.user.id)) return ws.close(4429, 'rate_limited');
    const msg = MessageSchema.safeParse(JSON.parse(raw.toString()));
    if (!msg.success) return;                                  // ignore malformed

    // ✅ authorise EVERY action against the CONNECTION's identity — never trust
    //    a userId in the payload
    if (msg.data.type === 'subscribe') {
      if (!(await acl.canRead(ws.user, msg.data.roomId))) return ws.close(4403, 'forbidden');
      return join(ws, msg.data.roomId, ws.user.id);
    }
    if (msg.data.type === 'edit') {
      if (!(await acl.canWrite(ws.user, msg.data.roomId))) return;    // silent drop
      return applyUpdate(msg.data.roomId, msg.data.update, ws.user.id);
    }
  });
});

// Revocation reaches live connections
sub.subscribe('auth:revoked');
sub.on('message', (_c, userId) => { for (const ws of socketsByUser.get(userId) ?? []) ws.close(4401); });
@end
@senior
Using the connection's authenticated identity rather than any user id in the message payload is the fundamental rule, and it is violated more often than you would expect because the payload is convenient. The revocation channel is the other piece people miss: a user logs out or is suspended, their HTTP requests start failing, and their WebSocket keeps working for hours because nothing told it. Publishing revocations to a channel that every instance subscribes to and closing the affected sockets closes that gap. Both of these are cheap and both are the kind of thing a security review specifically looks for.
@followup
How do you prevent a malicious client from corrupting a shared document?
@answer
Authorisation on write is the first line — a read-only collaborator's updates are dropped. Beyond that, CRDT updates are opaque binary, so validating their semantic content is hard; what you can do is bound their size, rate limit them, and keep an audit trail of which client id produced which updates so a bad actor's contributions can be identified and reverted from a snapshot. For high-value documents I would also keep periodic named snapshots so there is always a known-good state to restore, because with a CRDT you cannot simply reject a merge after the fact.
@red
- Authorising once at connection time only.
- Trusting a user id supplied in the message body.

### How do you handle presence and awareness across many servers reliably?
@short
TTL-based presence in Redis refreshed by heartbeats, so a crashed instance's users expire without any cleanup process. Aggregate presence into periodic snapshots rather than broadcasting every join and leave, and treat awareness data as ephemeral — never persisted, safely droppable under load.
@deep
The naive design keeps a set of online users and removes members on disconnect. It fails when an instance dies without clean disconnects, leaving ghost users forever, and it fails again when a network partition makes an instance unreachable but alive.

TTL-based presence is self-healing: absence of a heartbeat is the signal, so no explicit cleanup is required and partitions resolve automatically.
@code ts Self-healing presence with bounded fan-out
// Each instance heartbeats for its own connections, in one pipeline
setInterval(async () => {
  const pipe = redis.pipeline();
  const now = Date.now();
  for (const [roomId, users] of localRoomUsers) {
    for (const userId of users) pipe.zadd(`presence:${roomId}`, now, userId);
  }
  await pipe.exec();
}, 20_000);            // TTL semantics: an entry older than 60s is considered gone

// ONE aggregated broadcast per room per interval, not one per join/leave
setInterval(async () => {
  for (const roomId of localSubscribedRooms) {
    await redis.zremrangebyscore(`presence:${roomId}`, 0, Date.now() - 60_000);
    const members = await redis.zrange(`presence:${roomId}`, 0, 199);   // cap the list
    const total = await redis.zcard(`presence:${roomId}`);
    await pub.publish(`room:${roomId}:ephemeral`,
      JSON.stringify({ type: 'presence', members, total }));            // count if > 200
  }
}, 5_000);

// Cursors/typing: throttled at the client, dropped freely under load, never persisted
@end
@senior
Capping the member list and sending a total count beyond that threshold is a small design decision with a large effect: rendering two hundred avatars is already useless to a user, and sending fifty thousand names is a bandwidth problem for no benefit. The aggregated interval broadcast is the other scaling decision — per-event fan-out is O(n) messages for n participants on every join, which is quadratic in a busy room, whereas a fixed-rate snapshot is constant. Both are examples of the general principle for ephemeral data: approximate, bounded and droppable is better than exact and expensive.
@followup
How do you detect a user who has gone away without disconnecting?
@answer
Application-level heartbeats — WebSocket ping/pong frames or an explicit message — with a timeout shorter than the presence TTL. TCP alone will not tell you: a device that loses connectivity abruptly leaves a socket that appears open for minutes until keepalive probes eventually fail. Sending a ping every twenty to thirty seconds and closing the connection after two missed pongs detects it quickly, and it also keeps intermediate proxies and NAT mappings alive, which prevents the connection being killed for idleness.
@red
- Presence sets with no expiry.
- Broadcasting presence on every individual join and leave.

### How do you design offline-first synchronisation in general?
@short
Local database as the source of truth for the UI, a durable outbox for pending mutations, client-generated ids so records exist before the server sees them, idempotent replay with backoff, delta sync with tombstones for deletions, and an explicit conflict policy per data type.
@deep
The pieces that people miss are tombstones and the server clock. Without tombstones, a delta sync cannot express deletions, so deleted records live forever on devices. Without using the server's clock as the sync cursor, device clock skew silently skips records.

Conflict policy must be chosen per data type: append-only telemetry has no conflicts, editable records need last-write-wins or field-level merge, and collaborative text needs a CRDT.
@arch The full sync architecture
  DEVICE
   UI reads ── local SQLite (source of truth for display)
   UI writes ── local write + outbox row {uuid, op, payload, status, attempts}
                 ↑ UI never blocks on the network
   SYNC ENGINE
     push: batch pending outbox rows → POST /sync/push {Idempotency-Key}
           2xx → mark acked, delete   4xx → dead-letter + surface to user
           5xx/timeout → backoff ×2 + jitter, cap 5min
     pull: GET /sync/pull?since=<SERVER cursor>
           → { changed[], deleted[] (tombstones), serverTime }
           store serverTime as the next cursor (NEVER the device clock)

  SERVER
   push:  dedupe on client uuid (unique index) → idempotent replay
          per-record version check → 409 with current state for conflicts
   pull:  index on (tenant_id, updated_at) · tombstone table with the same index
          cap page size; return a cursor, not a timestamp the client computed

  CONFLICT POLICY (declared per entity)
   telemetry points   append-only, dedupe on uuid        → no conflict possible
   user profile       last-write-wins on updated_at      → acceptable, logged
   shared notes       CRDT                                → merges
   order status       server authoritative, client cannot write
@end
@senior
Declaring the conflict policy per entity rather than choosing one globally is the design decision that matters, and writing it into the schema documentation prevents the drift where someone assumes last-write-wins for a field where it silently loses data. The server-clock cursor is the second: I have debugged a sync bug where a device with a clock ten minutes fast never received records written in that window, and it was invisible until a user noticed missing data. Returning `serverTime` and requiring the client to echo it back removes the entire class.
@followup
How do you handle a schema change with clients that are months out of date?
@answer
Additive changes only on the sync payload, tolerant readers on both sides, and a version negotiated at sync time so the server can shape the response for old clients. If a breaking change is unavoidable, the server returns a "full resync required" signal that the client handles by wiping local state and re-downloading — expensive but correct, and far better than silent divergence. I would also enforce a minimum supported client version with a forced-update screen, because supporting arbitrarily old clients forever is not viable.
@red
- No tombstones for deletions.
- Using the device clock as the sync cursor.

### How do you test and debug a real-time collaborative system?
@short
Deterministic multi-client simulation for convergence — apply operations in different orders and assert every replica reaches the same state — plus fault injection for disconnection, reordering and duplication, plus production telemetry with sequence numbers so divergence is detectable.
@deep
Convergence tests are the core: generate random operation sequences, apply them in different permutations across simulated clients, and assert equality. That property-based approach finds ordering bugs that example-based tests miss entirely.

In production, divergence is detected by comparing a document hash across clients periodically — if two clients holding the same document report different hashes, something is wrong and you want to know before a user does.
@code ts Property-based convergence testing and production divergence detection
import fc from 'fast-check';

it('converges regardless of the order updates are applied', () => {
  fc.assert(fc.property(fc.array(fc.record({
    client: fc.integer({ min: 0, max: 2 }),
    op: fc.oneof(fc.record({ t: fc.constant('insert'), i: fc.nat(50), s: fc.string() }),
                 fc.record({ t: fc.constant('delete'), i: fc.nat(50), n: fc.nat(5) })),
  }), { maxLength: 200 }), (ops) => {
    const docs = [new Y.Doc(), new Y.Doc(), new Y.Doc()];
    const updates: Uint8Array[] = [];

    for (const { client, op } of ops) {
      const before = Y.encodeStateVector(docs[client]);
      apply(docs[client], op);
      updates.push(Y.encodeStateAsUpdate(docs[client], before));
    }
    // apply every update to every doc in a SHUFFLED order
    for (const d of docs) for (const u of shuffle(updates)) Y.applyUpdate(d, u);

    const texts = docs.map(d => d.getText('body').toString());
    expect(new Set(texts).size).toBe(1);            // ← all replicas identical
  }));
});

// Production: clients periodically report a document hash; the server compares
ws.send(JSON.stringify({ type: 'state_hash', docId,
                         hash: sha256(Y.encodeStateAsUpdate(doc)), seq: lastSeq }));
// server: two clients at the same seq with different hashes → alert + capture both states
@end
@senior
Production divergence detection is the part that is rarely implemented and is worth the effort: convergence is a theoretical guarantee of the algorithm, but bugs in your integration — an update dropped during a reconnect, a persistence race, a compaction that lost data — break it in practice, and without a hash comparison you find out from a user saying "my colleague sees something different". Capturing both states on mismatch gives you a reproducible case. Property-based testing is the complementary half, because it explores orderings no human would write as a test case.
@followup
How do you debug a report of "my changes disappeared"?
@answer
Start from the client's update log if you have one, and the server's persisted update sequence for that document. The usual causes are: an update produced while disconnected that was never sent because the outbox was not durable, an update sent but lost during a reconnect gap with no resumption, or a compaction bug that dropped updates. Sequence numbers and a per-client update log make each of these distinguishable in minutes; without them it is guesswork. That is why I instrument the sync path heavily even though it adds write volume.
@red
- Only example-based tests for a system whose correctness is about ordering.
- No mechanism to detect divergence in production.

### How would you build a live dashboard that scales to thousands of viewers?
@short
Do not push per-viewer computations. Compute the aggregates once on a fixed interval, publish the result to a channel, and have every viewer receive the same payload. For very large audiences, publish to a CDN-backed stream or use polling with a cached response rather than per-connection delivery.
@deep
The failure mode is treating each viewer as an independent subscriber whose data must be computed and serialised separately — that makes cost proportional to viewers times update rate, which does not scale.

The fix is a fan-out design: one computation, one serialisation, many deliveries. If the payload differs per viewer (per-tenant data), compute per tenant rather than per connection.
@code ts One computation, many deliveries
// A single worker computes each tenant's dashboard payload on an interval
setInterval(async () => {
  const tenants = await activeDashboardTenants();          // only tenants with viewers
  await Promise.all(tenants.map(async (t) => {
    const payload = await computeDashboard(t);             // ONE query per tenant
    const encoded = JSON.stringify(payload);
    await redis.set(`dash:${t}`, encoded, 'EX', 30);       // also serves late joiners + polling
    await pub.publish(`dash:${t}`, encoded);               // fan out to all viewers
  }));
}, 5_000);

// Instances relay the pre-computed payload; zero per-viewer work
sub.on('message', (channel, payload) => {
  for (const ws of viewersByTenant.get(tenantOf(channel)) ?? []) ws.send(payload);
});

// Late joiner gets the cached snapshot immediately, then live updates
ws.send(await redis.get(`dash:${tenantId}`) ?? '{}');

// Very large audiences (public dashboards): skip WebSockets entirely —
// write the payload to object storage, serve via CDN with a 5s TTL, client polls.
@end
@senior
The "only tenants with viewers" filter is the detail that keeps the cost proportional to actual demand rather than to the number of tenants — computing dashboards for customers who are not looking is pure waste, and at scale it dominates. The CDN-polling alternative for public dashboards is worth raising because it inverts the usual instinct: for a read-only, identical-for-everyone payload updated every few seconds, HTTP polling against a cached object is cheaper, simpler and more reliable than maintaining thousands of WebSocket connections, and it degrades gracefully under load.
@followup
When is polling better than pushing?
@answer
When the update rate is low relative to the number of viewers, when the payload is identical across viewers so it can be cached, or when connection state is a burden — mobile clients that background frequently, for example. Polling every five seconds against a CDN-cached response costs almost nothing at the origin and has no connection management, whereas WebSockets cost memory per viewer and require reconnection handling. I would push when updates are frequent and per-user, and poll when they are periodic and shared.
@red
- Computing the same aggregate once per connected viewer.
- WebSockets for a payload that is identical for everyone and changes every 30 seconds.

# SECTION Advanced Frontend Architecture | Senior frontend rounds go here: rendering strategy, boundaries, and cost.

### How do you decide the rendering architecture for a new product?
@short
From the requirements: SEO and first-paint needs, how personalised the content is, how interactive it is, and what the team can operate. Most products end up hybrid — static marketing, server-rendered content pages, and a client-heavy application shell behind login — rather than one strategy everywhere.
@deep
The variables that actually decide it are whether search engines and social previews matter, whether the first paint needs data, how often content changes, and whether the interactive surface is large enough that hydration cost dominates.

The App Router's per-route flexibility means this is a routing decision rather than an application-wide one, which is the right granularity.
@code text A decision table I would actually apply
  SURFACE               STRATEGY                 WHY
  ─────────────────────────────────────────────────────────────────────────────
  marketing pages       static + ISR             SEO, CDN speed, rare changes
  blog / docs           static + on-demand ISR   SEO; publish triggers revalidateTag
  product listing       ISR (tag-invalidated)    SEO + freshness on price/stock change
  product detail        ISR + client stock check price cached, stock read live
  search results        server-rendered dynamic  personalised + indexable
  authenticated app     shell SSR + client fetch no SEO value; interactivity dominates
  admin dashboard       CSR behind auth          no SEO; heavy interaction; cache locally
  checkout              server-rendered dynamic  correctness > cacheability, no staleness

  ANTI-PATTERNS
   • SSR everything → server cost + TTFB for pages that could be static
   • CSR everything → poor LCP, invisible to crawlers, slow on mid-range mobile
   • one strategy chosen at project start and never revisited per route
@end
@senior
The nuance I would add is that stock and price on a product page deserve different treatment: the page can be statically generated and served from the edge while the stock indicator is fetched client-side, because caching stock is a correctness problem while caching the description is free performance. Splitting a page by the freshness requirements of its parts is the technique, and it is what makes a page both fast and correct. I would also state the operational constraint — ISR with several instances needs a shared cache handler, or users see inconsistent staleness at random, which is a genuinely confusing bug.
@followup
How do you handle a page that is mostly static but has a personalised header?
@answer
Keep the page static and render the personalised part on the client, or stream it in a Suspense boundary so the static shell is cached and the personalised fragment is not. What you must not do is mark the whole page dynamic for a user's name in the header — that discards the caching benefit of everything else. Alternatively, if the personalisation is coarse (logged-in versus not, or a locale), varying the cached version on a cookie is cheaper than making it fully dynamic.
@red
- One rendering strategy applied to every route.
- Making a page dynamic for one small personalised element.

### How do you architect state in a large frontend application?
@short
Four separate concerns with four different tools: server cache for API data, URL for navigational and filter state, a store for genuinely global client state, and local component state for everything else. Most complexity comes from putting server data in a client store and then maintaining it by hand.
@deep
The failure pattern is a global store holding fetched data, with manually written loading flags, error flags, refetch logic and invalidation — hundreds of lines reimplementing a query cache badly, and diverging from the server over time.

URL state is the underused one: filters, pagination and selected tabs in the URL are shareable, bookmarkable, survive refresh, work with the back button, and can be read on the server for SSR.
@code tsx URL as state, with typed parsing
// Filters and pagination live in the URL — no store, SSR-readable, shareable
const FiltersSchema = z.object({
  status: z.enum(['all','pending','paid','refunded']).default('all'),
  from: z.coerce.date().optional(),
  page: z.coerce.number().int().min(1).default(1),
  sort: z.enum(['createdAt','total']).default('createdAt'),
});

export function useFilters() {
  const params = useSearchParams();
  const router = useRouter();
  const pathname = usePathname();

  const filters = useMemo(
    () => FiltersSchema.parse(Object.fromEntries(params)), [params]);

  const setFilters = useCallback((patch: Partial<Filters>) => {
    const next = new URLSearchParams(params);
    for (const [k, v] of Object.entries(patch)) {
      v == null || v === '' ? next.delete(k) : next.set(k, String(v));
    }
    if (!('page' in patch)) next.delete('page');           // changing a filter resets paging
    router.replace(`${pathname}?${next}`, { scroll: false });
  }, [params, pathname, router]);

  return { filters, setFilters };
}

// The query key derives from the URL → cache, SSR and sharing all agree
useQuery({ queryKey: orderKeys.list(filters), queryFn: () => api.listOrders(filters) });
@end
@senior
Deriving the query key from the URL state is the design that ties everything together: the server can render the correct data for a shared link, the client cache keys on the same value, and the back button restores both the UI and the correct cached data with no extra work. Resetting the page number when a filter changes is the small detail that prevents the classic "I filtered and got an empty page 7" bug. The broader argument is that each category of state has a natural home, and most state-management pain comes from putting state somewhere it does not belong.
@followup
When does a global store still earn its place?
@answer
For genuinely cross-cutting client state that is not server data and not navigational: an offline mutation queue, a collaborative editor's local UI state, a multi-step wizard's working draft, or a command palette's registry. Those are shared widely, change often, and have no natural URL or server representation. What I would not put there is anything fetched from an API, because the query cache handles that better, or anything that would be more useful in the URL.
@red
- Server data in Redux with hand-written cache invalidation.
- Filter state in a store rather than the URL.

### How do you handle very large data sets in the browser?
@short
Do not send them. Paginate or use cursor-based infinite loading, aggregate on the server, and virtualise whatever genuinely must be rendered locally. When a large local dataset is a real requirement — an offline table, a log viewer — use IndexedDB with an index and query it rather than holding everything in JavaScript memory.
@deep
The costs of a large payload are cumulative: transfer, JSON parse (which blocks the main thread), memory, and render. A 20MB JSON response can block the main thread for hundreds of milliseconds just parsing, before any rendering happens.

For genuinely local datasets, IndexedDB with proper indexes lets you query rather than scan, and a worker keeps the main thread free.
@code ts Querying IndexedDB in a worker, virtualising the result
// worker.ts — parsing and querying off the main thread
import { openDB } from 'idb';

const db = await openDB('logs', 1, {
  upgrade(d) {
    const store = d.createObjectStore('entries', { keyPath: 'id' });
    store.createIndex('byTime', 'ts');
    store.createIndex('byLevelTime', ['level', 'ts']);      // compound index
  },
});

self.onmessage = async ({ data }) => {
  if (data.type === 'query') {
    const range = IDBKeyRange.bound([data.level, data.from], [data.level, data.to]);
    const rows = await db.getAllFromIndex('entries', 'byLevelTime', range, 500);
    self.postMessage({ type: 'rows', rows });               // only what is displayed
  }
};

// main thread: virtualise the 500 rows the worker returned
const v = useVirtualizer({ count: rows.length, estimateSize: () => 32, overscan: 10,
                           getScrollElement: () => ref.current });
@end
@senior
Moving both the parse and the query into a worker is the part that makes this feel fast: IndexedDB's API is asynchronous but the deserialisation and any post-processing still cost main-thread time if done there, and on a mid-range phone that is the difference between a responsive scroll and a janky one. The prior question, though, is always whether the client needs the data at all — server-side aggregation usually beats any client-side technique, and I would push back on a requirement for "load all the data locally" unless offline access is genuinely needed.
@followup
How do you export a large dataset from the browser?
@answer
Ask the server to generate it and hand back a download link, rather than assembling it client-side — the browser is the worst place to build a 200MB CSV. If it must happen client-side, stream it: generate rows incrementally into a `Blob` via a stream, or use the File System Access API where available, so you never hold the whole file in memory. And do the row generation in a worker, because otherwise the tab freezes for the duration.
@red
- Fetching an entire table and filtering in JavaScript.
- Parsing large JSON on the main thread.

### How do you architect a micro-frontend system, and would you?
@short
Only when independent teams need independent deployment of parts of one application — and then with Module Federation or an app-shell composing independently built bundles, a strict contract between them, and shared dependency versions managed deliberately. For a single team it is almost always the wrong trade.
@deep
The costs are real: duplicated dependencies unless carefully shared, cross-application state and routing coordination, inconsistent design unless a shared component library is enforced, and much harder end-to-end testing and debugging.

The benefit is organisational — team autonomy and independent release cycles — so the decision is about team structure, not technology.
@code js Module Federation with the sharing configuration that matters
// host
new ModuleFederationPlugin({
  name: 'shell',
  remotes: {
    orders: 'orders@https://orders.acme.com/remoteEntry.js',
    billing: 'billing@https://billing.acme.com/remoteEntry.js',
  },
  shared: {
    react:       { singleton: true, requiredVersion: '^19.0.0', strictVersion: true },
    'react-dom': { singleton: true, requiredVersion: '^19.0.0', strictVersion: true },
    '@acme/ui':  { singleton: true },                 // design system: ONE instance
  },
});

// Isolate failures — a broken remote must not blank the shell
const Orders = lazy(() => import('orders/OrdersApp').catch(() => ({ default: RemoteUnavailable })));
<ErrorBoundary fallback={<RemoteUnavailable name="Orders" />}>
  <Suspense fallback={<Skeleton />}><Orders /></Suspense>
</ErrorBoundary>

// Contract between shell and remotes: explicit, versioned, minimal
// window.__ACME__ = { user, locale, theme, navigate(path), track(event) }
@end
@senior
`singleton: true` on React is not optional — two React instances produce the "invalid hook call" error and broken context, and it is the single most common micro-frontend failure. Beyond configuration, the point I would make is that micro-frontends solve an organisational problem and introduce a technical one, so I would want to see the organisational pain first: multiple teams blocked on each other's release trains. For one team, a monorepo with good module boundaries gives you the same code organisation with none of the runtime cost, and I would recommend that instead.
@followup
What is the alternative for a large single team?
@answer
A monorepo with enforced module boundaries: feature-sliced packages, a shared design system, and a linter that prevents cross-feature imports. That gives you the code organisation and ownership clarity without runtime composition, duplicated dependencies or cross-bundle debugging. Build performance is handled by task caching and affected-project detection. It scales to a surprisingly large codebase, and the migration path to micro-frontends remains open if team structure later demands it.
@red
- Micro-frontends for a single team.
- Shared React not configured as a singleton.

### How do you make a frontend resilient to backend failure?
@short
Design for degraded states as first-class UI: per-widget error boundaries with retry, stale-while-revalidate so cached data is shown when a refetch fails, optimistic updates with visible rollback, and offline queueing where the product warrants it. A single global error state is an outage; a degraded page is a working product.
@deep
The instinct to show a full-page error on any failure means one non-critical service degrades the entire experience. Isolating failures per data dependency means the user keeps most of the product.

The complementary mechanism is showing stale data with an indicator rather than nothing — for most dashboards, five-minute-old numbers with a "last updated" label are far more useful than an error.
@code tsx Per-widget resilience with stale data and retry
function RevenueCard() {
  const { data, error, isStale, dataUpdatedAt, refetch, isFetching } = useQuery({
    queryKey: ['revenue'],
    queryFn: fetchRevenue,
    staleTime: 60_000,
    retry: (count, err) => count < 3 && err.status >= 500,   // don't retry 4xx
    retryDelay: (i) => Math.min(30_000, 2 ** i * 1000) * (0.5 + Math.random()),
    // keep serving the last good value when a refetch fails
    placeholderData: keepPreviousData,
  });

  if (error && !data) return <WidgetError name="Revenue" onRetry={refetch} />;

  return (
    <Card>
      <Revenue value={data.total} />
      {error && data && (
        <Notice tone="warn">
          Showing data from {formatRelative(dataUpdatedAt)} — couldn’t refresh.
          <button onClick={() => refetch()} disabled={isFetching}>Retry</button>
        </Notice>
      )}
    </Card>
  );
}
@end
@senior
Showing stale data with an explicit "last updated" notice rather than an error is the pattern that most improves perceived reliability, and it is honest — the user knows what they are looking at. The retry predicate matters too: retrying a 4xx is pointless and adds load during an incident, while retrying a 5xx with jittered backoff is helpful. And I would emphasise that the frontend's retry behaviour is part of the backend's load profile: an application where every widget retries aggressively turns a brief backend blip into a self-sustaining traffic spike, which is why jitter and a bounded attempt count are not optional.
@followup
How do you handle a deploy that breaks currently-open sessions?
@answer
Content-hashed chunks mean an open tab can still load its old assets, provided you do not delete them from the CDN immediately — so I keep the previous build's assets. For the case where a chunk genuinely cannot load, I catch `ChunkLoadError` globally and prompt the user to refresh rather than showing a broken screen. For API contract changes, the rule is that the new backend must serve the previous frontend for at least one deployment cycle, which is the same expand-and-contract discipline as schema changes.
@red
- A single global error state for any failure.
- Aggressive retries with no jitter amplifying a backend incident.

### How do you approach frontend security beyond XSS?
@short
A strict Content-Security-Policy with nonces, no tokens in JavaScript-readable storage, careful handling of third-party scripts, protection against clickjacking and open redirects, subresource integrity where you must load external code, and treating any URL or HTML from the server as untrusted.
@deep
CSP is the highest-leverage control because it limits the damage of an XSS you did not prevent — a policy without `unsafe-inline` and with a nonce means an injected script simply does not execute, and `connect-src` limits where data can be exfiltrated to.

Third-party scripts are the underestimated risk: every analytics or chat widget runs with full access to your page, so a compromise of their CDN is a compromise of your application.
@code text A CSP that is actually restrictive, with the reasoning
  Content-Security-Policy:
    default-src 'self';
    script-src 'self' 'nonce-{RANDOM}' 'strict-dynamic';   ← no unsafe-inline/eval
    style-src  'self' 'nonce-{RANDOM}';
    img-src    'self' data: https://cdn.acme.com;
    connect-src 'self' https://api.acme.com https://o1234.ingest.sentry.io;
      ↑ limits where an injected script could exfiltrate to — the key line
    frame-ancestors 'none';                                ← clickjacking
    form-action 'self';                                    ← stops form hijacking
    base-uri 'self';                                       ← stops <base> injection
    object-src 'none';
    upgrade-insecure-requests;
    report-uri /csp-report                                 ← deploy in report-only first

  ALSO
   Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
   X-Content-Type-Options: nosniff
   Referrer-Policy: strict-origin-when-cross-origin      ← stops URL leakage
   Permissions-Policy: camera=(), geolocation=(), microphone=()

  THIRD-PARTY SCRIPTS
   • self-host where possible; otherwise SRI hash + crossorigin
   • load in a sandboxed iframe if they do not need page access
   • audit what each one actually does — they see everything on the page
@end
@senior
`connect-src` is the line that turns CSP from a script-blocking measure into an exfiltration control: even if an attacker executes script, they cannot send the data anywhere you have not allow-listed. Deploying in report-only first is the operational detail — a strict CSP will break something you did not anticipate, and report-only lets you find out without breaking production. On third-party scripts I would be blunt: every one is a supply-chain risk with full page access, so the security review question is not "is this vendor reputable" but "what happens to our users if their CDN is compromised", and subresource integrity is the cheap mitigation.
@followup
How do you protect against a malicious npm dependency?
@answer
Lockfiles with integrity hashes, dependency review on updates, automated vulnerability scanning, and minimising the dependency count — every package is code you are executing with your privileges. For the build pipeline specifically, `npm ci` with a lockfile and disabling install scripts where possible reduces the attack surface, since the common vector is a postinstall script exfiltrating environment variables. At the runtime level, a strict CSP limits what a compromised frontend dependency can do, which is another reason it matters.
@red
- CSP with `unsafe-inline` and `unsafe-eval`.
- Third-party scripts loaded with no integrity check and no review.

### How do you architect for accessibility and internationalisation from the start?
@short
Semantic markup and keyboard operability as a default rather than a retrofit, an accessible component library as the foundation, automated checks in CI, and locale-aware formatting plus ICU messages from day one. Both are far cheaper designed in than added later.
@deep
The structural decisions that matter are: use real interactive elements, manage focus deliberately on navigation and dynamic content, never build a translation string by concatenation, and treat text expansion as a layout constraint since German and Finnish routinely run 30–40% longer than English.

Right-to-left support is a layout architecture decision, not a stylesheet tweak — using logical CSS properties from the start makes it nearly free.
@code css Logical properties make RTL almost free
/* ❌ physical properties break in RTL */
.card { margin-left: 16px; padding-right: 24px; text-align: left; border-left: 2px solid; }

/* ✅ logical properties flip automatically with dir="rtl" */
.card {
  margin-inline-start: 16px;
  padding-inline-end: 24px;
  text-align: start;
  border-inline-start: 2px solid;
}

/* Text expansion: never size containers to the English string */
.button { min-inline-size: 8rem; }   /* not width: 96px */
@end
@code tsx ICU messages and CI gates
// ❌ untranslatable: word order and plural rules differ per language
<span>You have {n} new {n === 1 ? 'message' : 'messages'}</span>

// ✅ ICU handles plural categories the target language actually has
t('inbox.count', { n })
// en: "{n, plural, one {# new message} other {# new messages}}"
// ru: "{n, plural, one {#…} few {#…} many {#…} other {#…}}"

// CI gates that keep both honest
// - jest-axe on component tests, @axe-core/playwright on key journeys
// - a lint rule banning string concatenation in user-facing text
// - a pseudo-locale build (aaaa-expanded) that catches truncation and hardcoded strings
@end
@senior
The pseudo-locale build is the trick I would highlight for internationalisation: rendering the app with artificially lengthened, accented strings immediately reveals hardcoded English, truncated containers and layout that assumes short text — without needing a single real translation. For accessibility, the highest-leverage decision is using an accessible headless component library rather than hand-rolling dropdowns and dialogs, because focus trapping and ARIA semantics are genuinely hard and already solved. Both of these are architecture decisions made once, not ongoing effort.
@followup
How do you handle translations arriving late or incomplete?
@answer
A defined fallback chain — regional locale to base language to the default — with missing keys logged in development and surfaced in a report rather than crashing or rendering the key. I keep the source language as the fallback so a missing translation shows readable English rather than `inbox.count`. And I decouple translation delivery from code deploys where possible, loading catalogues from a service so a translation fix does not require a release, which matters when translations lag features by weeks.
@red
- Accessibility as a pre-launch audit.
- Concatenating translated strings.

### How do you measure and manage frontend performance as an ongoing property?
@short
Real-user monitoring with attribution as the primary signal, lab checks and bundle budgets as CI gates, and a per-route budget that fails the build on regression. Performance is a constraint enforced by the pipeline, not a project that finishes.
@deep
Field data is what Google grades and what users experience, and it differs substantially from lab measurements because of device and network distribution. Attribution data — which element is the LCP, which interaction caused a slow INP — is what makes a metric actionable.

The CI side prevents erosion: without a budget, every feature adds a little and the gains from a performance project are gone within two quarters.
@code js RUM with attribution, plus the CI gates
import { onLCP, onINP, onCLS, onTTFB } from 'web-vitals/attribution';

const send = (m) => navigator.sendBeacon('/rum', JSON.stringify({

  route: matchedRoute(location.pathname),          // ← templated, not the raw path
  // attribution turns a number into a task:
  lcpElement: m.attribution?.element,
  lcpPhase: { ttfb: m.attribution?.timeToFirstByte, load: m.attribution?.resourceLoadDuration },
  inpTarget: m.attribution?.interactionTarget,
  inpPhase: { input: m.attribution?.inputDelay, proc: m.attribution?.processingDuration },
  clsSource: m.attribution?.largestShiftTarget,
  device: navigator.deviceMemory, conn: navigator.connection?.effectiveType,

}));
onLCP(send); onINP(send); onCLS(send); onTTFB(send);

// CI gates
// .size-limit.json  → per-entry budgets, fails the PR on regression
// lighthouse-ci     → fixed device/network profile, thresholds per route
// bundle diff comment on the PR: "+42KB to /dashboard (charting lib)"
@end
@senior
Reporting the templated route rather than the raw path is a small detail that makes the data usable — otherwise every product page is its own row and you cannot aggregate. Segmenting by device memory and connection type is the other one, because an aggregate p75 hides that low-end Android users are having a much worse time, and those are often a large share of the audience. The bundle-diff comment on the pull request is the intervention that changes behaviour: making the cost visible at the moment someone adds a dependency is far more effective than a monthly report nobody reads.
@followup
What do you do when a third-party script is the performance problem?
@answer
Quantify it first — remove it locally and measure the difference, so the conversation is about a number rather than an opinion. Then the options in order: load it lazily after interaction, load it in a worker via Partytown so it does not compete for the main thread, self-host it to remove a connection and gain caching control, or remove it. That last one is a business conversation, and it goes much better with data showing the marketing tag costs 200ms of INP on mobile than with a general complaint about third parties.
@red
- Optimising with lab data only.
- No CI budget, so improvements erode.

# SECTION Security Engineering | Deeper than the checklist: designing systems an attacker cannot easily abuse.

### How do you design an authorisation system that scales with the product?
@short
Model it as a policy function over (actor, resource, action, context) evaluated close to the data, with roles as a convenience over permissions rather than the model itself. For complex relationships — nested teams, shared documents, delegated access — a relationship-based model like Zanzibar's is the right shape.
@deep
Role-based access control breaks down when permissions depend on relationships: "can edit documents in folders they own, or that are shared with a team they belong to". Encoding that as roles produces a combinatorial explosion; encoding it as relationships and rules stays tractable.

Whatever the model, the check must happen where the data is fetched, and it must be centralised so it can be audited and tested exhaustively.
@code ts A policy layer that is exhaustively testable
type Action = 'read' | 'update' | 'delete' | 'refund' | 'export';
type Decision = { allow: true } | { allow: false; reason: string };

const policies: Record<string, (a: Actor, r: Resource, ctx: Ctx) => Decision> = {
  'order:refund': (actor, order, ctx) => {
    if (order.tenantId !== actor.tenantId)          return deny('WRONG_TENANT');
    if (order.status !== 'paid')                    return deny('NOT_REFUNDABLE');
    if (actor.role === 'admin')                     return allow();
    if (actor.role === 'support' && order.totalMinor <= 500_00) return allow();
    if (actor.id === order.userId && ctx.selfServiceRefundsEnabled &&
        daysSince(order.paidAt) <= 14)              return allow();
    return deny('INSUFFICIENT_PRIVILEGE');
  },
};

export function can(actor: Actor, action: Action, resource: Resource, ctx: Ctx): Decision {
  const d = policies[`${resource.type}:${action}`]?.(actor, resource, ctx)
         ?? deny('NO_POLICY');                       // ← default deny
  audit.decision({ actor: actor.id, action, resource: resource.id, ...d });
  return d;
}

// Exhaustive test matrix: every role × every resource state × every action
describe.each(ROLES)('%s', (role) => {
  it.each(ORDER_STATES)('refund on %s order', (state) => {
    expect(can(actorFor(role), 'refund', orderIn(state), ctx)).toMatchSnapshot();
  });
});
@end
@senior
Default-deny plus a snapshot test matrix over every role and state is what makes an authorisation system maintainable: adding a role or a state produces a visible diff of every decision it affects, so a change that accidentally grants access is caught in review rather than in a penetration test. Logging every decision, including denials, is the other half — denial patterns are a strong signal of both bugs and probing. And I would say plainly that the policy layer must be paired with data-layer scoping, because a correct policy on a query that fetches the wrong tenant's row is still a breach.
@followup
When would you adopt a Zanzibar-style relationship model?
@answer
When permissions derive from graph relationships that are expensive to evaluate per request — nested folders, group membership with inheritance, resource sharing with delegation. Zanzibar-style systems (OpenFGA, SpiceDB) store relationship tuples and answer "can user X do Y to Z" with consistent, cached graph traversal. The cost is another service and a new modelling language, so I would adopt it when the relationship logic has genuinely outgrown a policy function — typically when you find yourself writing recursive queries to answer a permission check.
@red
- Roles hardcoded throughout the codebase.
- Authorisation checks that default to allow when no policy matches.

### How do you handle secrets in a way that survives a compromise?
@short
Short-lived credentials issued by an identity provider rather than static secrets, least privilege scoping so a leak is bounded, automated rotation, and detection — secret scanning in CI and in the repository history, plus alerting on unusual credential use. Assume a secret will leak and design for the consequence.
@deep
The strongest control is not having a long-lived secret at all: workload identity (IAM roles, OIDC federation, SPIFFE) issues short-lived credentials tied to the workload's identity, so there is nothing durable to steal.

Where static secrets are unavoidable — third-party API keys — the mitigations are scoping, rotation with overlap, and monitoring for use from unexpected sources.
@code yaml Eliminating static credentials in CI, and scoping what remains
# GitHub Actions → AWS with OIDC. No stored access keys at all.
permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/deploy-api
      aws-region: ap-south-1
      # the role's trust policy restricts WHICH repo and WHICH branch may assume it:
      #   "token.actions.githubusercontent.com:sub": "repo:acme/api:ref:refs/heads/main"

# Runtime: the task role, not environment variables
#   ECS task role → read only THIS service's secrets, write only ITS bucket prefix
{
  "Effect": "Allow",
  "Action": ["secretsmanager:GetSecretValue"],
  "Resource": "arn:aws:secretsmanager:ap-south-1:123:secret:prod/api/*"
}

# Detection
#   gitleaks in pre-commit AND in CI over full history
#   CloudTrail alert: credential used from an unexpected region or principal
#   provider-side: GitHub secret scanning partners notify on leaked provider keys
@end
@senior
The trust-policy condition restricting which repository and branch may assume the role is the detail that makes OIDC federation genuinely secure — without it, any workflow in any repository in the organisation could assume your production deploy role. I have seen that misconfigured. The other point I would make is about response: if a secret leaks, rotation is mandatory and immediate, and history rewriting is largely theatre because forks, caches and crawlers already have it. Designing so that rotation is routine — overlapping keys, automated, tested — is what makes the response fast rather than frightening.
@followup
How do you handle secrets a customer gives you, such as their API keys?
@answer
Encrypt them with envelope encryption under a key you control, store the key id for rotation, restrict decryption to the specific service that needs it, and never log or return them — a masked display plus a rotate action is the correct interface. I would also scope what they can do: ask the customer for the narrowest permissions the integration needs, and document it, because a breach of your system then exposes a limited credential rather than full access to their account. Storing customer credentials is a serious responsibility and it should be visible in the threat model.
@red
- Long-lived cloud access keys stored in CI secrets.
- No trust-policy conditions on a federated role.

### How do you defend against automated abuse — scraping, credential stuffing, card testing?
@short
Layer signals rather than relying on one control: edge rate limiting and bot detection, per-account throttling with progressive friction, device and behavioural signals, and business-logic limits on the specific actions that cost you money. Then monitor for the patterns rather than assuming the controls hold.
@deep
Each abuse type has a distinct signature. Credential stuffing shows many accounts attempted from a distributed source with a low success rate. Card testing shows many small payment attempts with high decline rates. Scraping shows sequential id access or high-volume reads with no writes.

Detection matters more than prevention, because sophisticated actors adapt — the goal is raising cost and reacting quickly, not building an impenetrable wall.
@code ts Detection signals that actually distinguish the abuse types
// CREDENTIAL STUFFING: many accounts, few successes, distributed IPs
const stuffing = await redis.eval(`
  local fails = redis.call('INCR', KEYS[1])                -- failures per IP window
  redis.call('EXPIRE', KEYS[1], 900)
  local accounts = redis.call('SCARD', KEYS[2])            -- distinct accounts tried
  return {fails, accounts}`, 2, `fail:ip:${ip}`, `accts:ip:${ip}`);
if (stuffing.accounts > 10 && stuffing.successRate < 0.05) await requireCaptcha(ip);

// Per-ACCOUNT protection, independent of source IP
await redis.eval(TOKEN_BUCKET, 1, `login:acct:${emailHash}`, 5, 0.05, Date.now(), 1);

// CARD TESTING: many attempts, high decline rate, small amounts
const declines = await payments.recentDeclineRate(userId, '10 minutes');
if (declines.attempts > 5 && declines.rate > 0.6) {
  await flags.set(`payments:blocked:${userId}`, true, '1h');
  await alert.notify('card-testing-suspected', { userId, ...declines });
}

// SCRAPING: sequential access, read-only, high volume
if (isSequentialIdPattern(recentPaths) && writeCount === 0 && readCount > 500)
  await requireCaptcha(ip);

// Business-logic limits on what actually costs money
//   e.g. max 3 OTP sends per hour, max 10 AI generations per day on free tier
@end
@senior
The business-logic limit is the control people skip and it is often the most effective: an attacker who is rate limited but can still trigger 500 SMS sends has cost you real money, whereas a limit of three OTPs per hour per account caps the damage regardless of how clever the evasion is. The other principle is progressive friction rather than binary blocking — a captcha or a delay for suspicious traffic degrades the attacker's economics while barely affecting legitimate users, whereas hard blocks generate support tickets from false positives. And I would emphasise monitoring the metrics that reveal abuse, because the first sign is usually a change in a ratio rather than an alert firing.
@followup
How do you avoid blocking legitimate users?
@answer
Prefer friction over refusal, use account-level signals rather than IP alone (since corporate networks and mobile carriers share addresses widely), and build an appeal path — a support route that can unblock quickly with an audit trail. I also monitor the false-positive rate directly by tracking how many blocked users subsequently succeed after friction, because a control that blocks 2% of real users to stop 0.1% of abuse is a bad trade that nobody notices without that measurement.
@red
- IP-only blocking.
- No business-logic limits on expensive actions.

### How do you approach supply-chain security?
@short
Lockfiles with integrity hashes, automated dependency and vulnerability scanning, minimal dependency count, install scripts disabled where possible, provenance verification for critical packages, and pinned base images with regular rebuilds. The build pipeline itself is part of the attack surface.
@deep
The realistic attack vectors are a compromised maintainer account publishing a malicious version, typosquatting, a dependency confusion attack where a public package shadows an internal name, and a compromised build step exfiltrating secrets.

The build environment is the highest-value target because it holds deployment credentials, which is why short-lived federated credentials and least-privilege build roles matter as much as dependency hygiene.
@code yaml Defences across the pipeline
# 1. Deterministic installs, integrity-checked
- run: npm ci --ignore-scripts        # ← postinstall scripts are the common exfil vector
- run: npm rebuild                    # only rebuild what genuinely needs native compilation

# 2. Vulnerability + license scanning, blocking on high severity
- run: npm audit --audit-level=high
- uses: aquasecurity/trivy-action@master
  with: { scan-type: 'fs', severity: 'HIGH,CRITICAL', exit-code: '1' }

# 3. Dependency confusion: scope internal packages and pin the registry
# .npmrc
#   @acme:registry=https://registry.acme.internal/
#   //registry.acme.internal/:_authToken=${NPM_TOKEN}

# 4. Provenance / SBOM
- run: npm audit signatures            # verify registry signatures
- uses: anchore/sbom-action@v0         # generate an SBOM for the artefact

# 5. Base images pinned by DIGEST, not tag, and rebuilt on a schedule
# FROM node:22-alpine@sha256:abc123...

# 6. The build role can push to ECR and nothing else. No production data access.
@end
@senior
`--ignore-scripts` is the single highest-value line, because the overwhelming majority of malicious npm packages act through a postinstall script that reads environment variables and exfiltrates them — and in a CI environment those variables are deployment credentials. Combining that with short-lived OIDC credentials means even a successful exfiltration yields a token that expires in minutes and is scoped to pushing an image. Pinning base images by digest rather than tag is the other one people miss: `node:22-alpine` is a moving target, so a rebuild can silently change your runtime.
@followup
How do you evaluate whether to add a dependency?
@answer
Maintenance signals — recent releases, responsive issues, more than one maintainer — plus transitive dependency count, install size, and whether the functionality is small enough to write ourselves. A package with sixty transitive dependencies to do date formatting is a poor trade against `Intl`. I also check whether it has native code or install scripts, since both increase risk. The question I ask is what happens if this package is abandoned or compromised, and if the answer is "we would be stuck", that raises the bar considerably.
@red
- Running install scripts in CI with production credentials present.
- Base images referenced by mutable tag.

### How do you design logging and monitoring so an intrusion is detectable?
@short
Log authentication events, authorisation denials, privileged actions, data exports and configuration changes with actor, source and outcome — to an append-only sink in a separate account. Then alert on the patterns that indicate compromise rather than on individual events.
@deep
The value is in detection of anomalies, not in volume. A single failed login is noise; a successful login from a new country followed immediately by a bulk export is a signal.

Separation of the log store matters: an attacker with application access should not be able to delete the evidence, which means the audit sink is written to and not administered by the application's credentials.
@code text Signals worth alerting on, and why each one matters
  AUTHENTICATION
   • successful login from a new country/ASN for a user            → account takeover
   • many failed logins across many accounts from one source       → stuffing
   • MFA disabled shortly after a password change                  → takeover in progress
   • session used from two distant locations within minutes        → token theft

  AUTHORISATION
   • spike in 403/404-on-other-tenant responses for one actor      → probing/IDOR attempt
   • a support account accessing records outside their queue       → insider risk
   • privilege granted outside the normal workflow                 → escalation

  DATA
   • export volume >3× the actor's 30-day baseline                 → exfiltration
   • export outside working hours by a human account               → exfiltration
   • bulk read of sequential ids                                   → scraping

  INFRASTRUCTURE
   • IAM policy change, security group opened to 0.0.0.0/0         → CloudTrail alert
   • new access key created for a service account                  → persistence
   • credential used from an unexpected region                     → stolen credential

  SINK: separate AWS account, write-only from the app, object-locked, 1-year retention.
@end
@senior
Baselining per actor rather than using a global threshold is what makes the export alert usable: a data analyst exporting large volumes daily is normal, and the same volume from a support agent is not. That requires storing a per-actor baseline, which is a small amount of work for a much better signal-to-noise ratio. The separate-account sink is the other structural decision — an attacker who compromises the application should be unable to erase the record of what they did, and that requires the audit destination to be outside the application's blast radius.
@followup
How do you respond to a suspected breach?
@answer
Contain first — revoke the affected credentials and sessions, and disable the vector if identified — then preserve evidence before making changes that destroy it, then investigate scope from the audit logs. In parallel, engage whoever owns legal and communications obligations, because notification requirements have deadlines. The technical instinct is to fix immediately; the correct sequence is contain, preserve, investigate, then remediate, because you cannot determine what was accessed if you have already redeployed and rotated everything without capturing the state.
@red
- Audit logs the application can delete.
- Alerting on raw event counts rather than anomalies.

### How do you handle security in a multi-tenant AI or data product?
@short
Enforce tenant scoping at the data layer for every retrieval, never rely on prompts or application conventions, isolate embeddings and caches per tenant, and treat model outputs as untrusted. The specific risk is cross-tenant leakage through a shared index or a shared cache, which is a breach with a very visible artefact.
@deep
Vector search makes this harder than it looks: an approximate index returns global nearest neighbours, so filtering after retrieval can both leak (if the filter is applied in application code that someone forgets) and under-return (if the filter removes most candidates). Filtering inside the query, ideally with row-level security, is the correct answer.

Caches are the second vector — a semantic cache keyed only on the question will happily serve one tenant's answer to another.
@code sql Tenant isolation that cannot be forgotten
-- RLS on the chunk table: even a raw query cannot cross tenants
ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
ALTER TABLE chunks FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON chunks
  USING (tenant_id = current_setting('app.tenant_id')::uuid);

-- Per-tenant partial index: keeps ANN recall high AND makes leakage structurally hard
CREATE INDEX chunks_hnsw_t1 ON chunks USING hnsw (embedding vector_cosine_ops)
  WHERE tenant_id = '...';       -- for large tenants

-- Application: SET LOCAL inside the transaction (never plain SET behind a pooler)
await client.query('SET LOCAL app.tenant_id = $1', [ctx.tenantId]);
@end
@code ts Cache keys and prompt boundaries that respect tenancy
// ❌ leaks across tenants
const cached = await cache.get(hash(question));

// ✅ tenant is part of the key, always
const cached = await cache.get(`${ctx.tenantId}:${hash(question)}`);

// Retrieved content is DATA — delimit it and strip control sequences
const context = chunks.map(c =>
  `<document id="${c.id}">\n${stripControl(c.content)}\n</document>`).join('\n');

// Test that specifically tries to cross the boundary
it('never returns another tenant’s chunks', async () => {
  const res = await retrieve('confidential revenue figures', { tenantId: TENANT_A });
  expect(res.every(c => c.tenantId === TENANT_A)).toBe(true);
});
@end
@senior
Row-level security is the control I would insist on for this specific product shape, because the consequence of a missed filter is not a bug report — it is one customer seeing another customer's documents quoted back to them by your AI, which is unrecoverable reputationally. Enforcing it in the database means a raw query, an ad-hoc script or a forgetful developer cannot bypass it. The cache-key point is the same principle applied to a different layer, and it is the kind of thing that is obvious once stated and easy to miss when the cache is added later as an optimisation.
@followup
How do you prevent one tenant's data influencing another's model behaviour?
@answer
Do not fine-tune on tenant data unless the model is per-tenant, and do not use one tenant's interactions to build shared retrieval artefacts without explicit consent and isolation. Shared caches, shared few-shot example pools and shared feedback loops are all leakage paths. If a shared model is fine-tuned on aggregate data, that must be disclosed and the data must be genuinely de-identified — and I would be conservative here, because "the model memorised a customer's data" is a failure mode with no clean remediation.
@red
- Filtering by tenant after retrieval rather than in the query.
- Caches keyed without the tenant.

### How do you think about security for internal tools and admin panels?
@short
Treat them as high-value targets, because they concentrate privilege: strong authentication with MFA, least-privilege roles, approval for destructive or high-value actions, comprehensive audit logging, and network restriction. Most damaging incidents involve legitimate internal access, not an external breach.
@deep
Internal tools are often the weakest link because they are built quickly, by the team, for trusted users — so they skip the controls the customer-facing product has. But an admin panel typically allows reading any customer's data, refunding arbitrary amounts and changing permissions.

The controls that matter most are per-action authorisation with amount thresholds, mandatory reasons for privileged actions, and alerting on unusual patterns.
@code ts Admin actions with approval, reason and audit
export async function adminRefund(input: { orderId: string; amountMinor: number; reason: string },
                                  actor: AdminActor) {
  if (input.reason.trim().length < 10)
    throw new BadRequest('REASON_REQUIRED');                     // mandatory, and it is audited

  // Threshold-based approval: routine work is fast, large actions need a second person
  if (input.amountMinor > 25_000_00 && !actor.approvedBy)
    return createApprovalRequest(input, actor);                  // four-eyes principle

  // Just-in-time elevation: no standing superpowers
  if (!(await elevation.isActive(actor.id, 'refunds')))
    throw new Forbidden('ELEVATION_REQUIRED');                   // re-auth + MFA, 30-min window

  const result = await refundOrder({ ...input, actor: { type: 'admin', id: actor.id } });

  await audit.record({ action: 'admin.refund', actor: actor.id, resource: input.orderId,
                       amount: input.amountMinor, reason: input.reason,
                       ip: actor.ip, approvedBy: actor.approvedBy });

  if (await anomaly.isUnusual(actor.id, 'refund', input.amountMinor))
    await alert.notify('unusual-admin-action', { actor: actor.id, ...input });
  return result;
}
@end
@senior
Just-in-time elevation is the control I would advocate most strongly for admin tooling: standing privileges mean a compromised admin session has full power for its lifetime, whereas requiring re-authentication with MFA to enter a thirty-minute elevated window bounds the damage substantially and creates a clear audit signal. The four-eyes threshold is the second — routine small refunds proceed, large ones need a second person, which prevents both fraud and expensive mistakes. And the mandatory reason field is worth more than it looks: it is the field that makes an audit log answer "why", which is the question you will actually be asked.
@followup
Should admin tools be on the public internet?
@answer
Preferably not — restrict to a VPN or an identity-aware proxy so an attacker needs network access as well as credentials. Where that is impractical, enforce MFA, restrict by IP where feasible, apply strict rate limiting, and treat every action as auditable. The general principle is defence in depth: network restriction is not sufficient on its own (an attacker inside the network is a real scenario) but it removes the entire class of opportunistic attacks against a publicly discoverable admin login.
@red
- Admin panels with the same authentication as customer accounts.
- Standing admin privileges with no elevation step.

### How do you handle a security incident end to end?
@short
Contain, preserve evidence, assess scope, remediate, communicate, and learn. The sequence matters — remediation that destroys evidence makes scope assessment impossible, and scope assessment is what determines your notification obligations.
@deep
Containment is not always "shut everything down"; it is stopping the attacker's access while preserving your ability to understand what happened. That usually means revoking credentials and sessions, blocking the vector, and taking a snapshot before rebuilding.

Communication has deadlines. Many data-protection regimes require notification within 72 hours of becoming aware of a breach, so legal and communications must be engaged early, not after the technical work is done.
@code text An incident runbook for a suspected data breach
  T+0   DETECT      alert fires / report received / anomalous pattern observed
                    → declare an incident, assign a commander, open a dedicated channel

  T+5m  CONTAIN     revoke the suspected credentials and ALL sessions for affected accounts
                    block the vector (WAF rule, disable endpoint, feature flag off)
                    ⚠ do NOT redeploy or rotate everything yet — evidence first

  T+15m PRESERVE    snapshot affected instances/volumes
                    export relevant logs to a WORM location before retention expires
                    capture the current state of the audit trail

  T+1h  ASSESS      what was accessible? what was ACCESSED? (audit logs answer this)
                    which customers, which data categories, what volume
                    → this determines notification obligations. Be precise.

  T+2h  ENGAGE      legal + comms + leadership. Clocks may already be running.

  T+4h  REMEDIATE   fix the vulnerability, rotate all potentially exposed credentials,
                    rebuild from known-good images, verify the attacker has no persistence

  T+24h COMMUNICATE affected customers, regulators as required, status page
                    say what happened, what data, what you are doing, what they should do

  T+1w  LEARN       blameless post-mortem: why was this possible, why was it not
                    detected sooner, what CONTROL (not what person) changes
@end
@senior
"Preserve before remediate" is the sequencing point that engineers most often get wrong, because the instinct under pressure is to fix it immediately — and rebuilding the instance destroys the evidence needed to determine whether data was actually accessed rather than merely accessible. That distinction drives your legal obligations and your communication, so it is worth the fifteen minutes. The other point is that the post-mortem must ask why detection took as long as it did, not only how the vulnerability existed — most breaches are found late, and detection latency is usually the more tractable problem.
@followup
What if you cannot determine whether data was accessed?
@answer
Then you must assume it was, and communicate accordingly — which is expensive, and is precisely the argument for having audit logging in place before you need it. The ability to say "we can confirm these twelve records were read and no others" versus "we cannot rule out access to the entire database" is the difference between a contained incident and a company-defining one. I would treat that gap as the top follow-up action, because it converts a future incident from unbounded to bounded.
@red
- Rebuilding compromised systems before capturing evidence.
- Delaying legal and communications engagement until the technical work is done.

# SECTION Performance Engineering at Scale | Making systems fast, and keeping them fast.

### How do you build a performance budget and enforce it?
@short
Define targets per user-visible journey — p95 latency for the API, LCP and INP for the frontend, bundle size per route — measure them continuously in production, and enforce them in CI so a regression fails the build. A budget nobody enforces is a wish.
@deep
Budgets must be per journey rather than global, because an aggregate p95 hides that checkout is slow while a health check is fast. They must also be derived from user impact rather than from what the system currently does, or you enshrine the status quo.

Enforcement has two halves: CI gates catch what is measurable pre-merge (bundle size, lab metrics, query counts), and production monitoring catches what only appears with real data and real users.
@code yaml Budgets as code, enforced in the pipeline
# performance-budget.yml — reviewed like any other contract
journeys:
  checkout:
    api_p95_ms: 400
    api_p99_ms: 1200
    lcp_p75_ms: 2000
    inp_p75_ms: 200
    js_bytes_gzip: 180_000
    db_queries_per_request: 8          # ← catches N+1 before it ships
  dashboard:
    api_p95_ms: 800
    js_bytes_gzip: 320_000
    db_queries_per_request: 15

# CI
- run: npx size-limit                              # fails on bundle regression
- run: npm run test:query-budget                   # asserts queries per endpoint
- run: npx lhci autorun --assert.preset=lighthouse:recommended
- run: node scripts/compare-prod-metrics.js --window 24h --fail-on-regression 10%

# Production: alert when the p75/p95 breaches the budget for 15 minutes
@end
@senior
The query-count budget per endpoint is the gate I would highlight, because N+1 regressions are the most common performance defect and they are invisible in development with small seed data. Asserting "this endpoint issues at most eight queries" in an integration test catches them at the pull request, which is the cheapest possible moment. The other principle is that the budget is a product decision as much as a technical one — a 400ms checkout target should come from evidence about conversion, not from an engineer's preference, which is what makes it defensible when someone wants to add a feature that would breach it.
@followup
What do you do when a feature genuinely cannot fit the budget?
@answer
Make the trade explicit rather than silently exceeding it: present the options — a smaller feature, a different rendering strategy, deferred loading, or accepting a revised budget with the reason recorded. Sometimes the right answer is to raise the budget deliberately for a specific route because the feature is worth it, and that is fine when it is a decision rather than an accident. What I would not accept is exceeding the budget without a decision, because that is how budgets stop meaning anything.
@red
- One global latency target for every endpoint.
- Budgets defined but not enforced anywhere.

### How do you find the real bottleneck in a complex request path?
@short
Distributed tracing with spans for every database query, cache lookup and outbound call, so the waterfall shows where time actually goes. Then confirm with a profile if the time is in your own code rather than in a dependency. Measurement first, hypothesis second, change third.
@deep
The common misdiagnosis is attributing latency to the wrong layer because the evidence was indirect — assuming a slow endpoint is CPU-bound because CPU is high, when CPU is high because of an unrelated background job.

Traces resolve that by attribution: a 900ms request that shows 700ms in a single database span is unambiguous, and so is one showing 200 spans of 3ms each.
@code text Reading a trace, and the diagnosis each shape implies
  SHAPE                                  DIAGNOSIS                 FIX
  ─────────────────────────────────────────────────────────────────────────────────
  one wide DB span                       missing index / bad plan  EXPLAIN, index, stats
  ├──────────────────────────────┤

  many identical small spans             N+1                       batch / IN / DataLoader
  ├─┤├─┤├─┤├─┤├─┤├─┤├─┤├─┤├─┤├─┤

  sequential spans, no overlap           serial awaits             Promise.all
  ├────┤    ├────┤    ├────┤

  gap between spans with no work         event-loop lag or         profile CPU;
  ├──┤          ~~~gap~~~          ├──┤  pool wait                 check pool metrics

  one wide external span                 slow third party          timeout + breaker +
  ├──────────────────────────────┤                                 cache / async

  wide span at the START only            cold start / connection   keep-alive, warm pool
  ├────────┤ then fast

  ALWAYS: compare p50 vs p99 traces. The p99 shape is usually DIFFERENT —
  that is where pool waits, GC pauses and retries show up.
@end
@senior
Comparing p50 and p99 traces separately is the technique I would emphasise, because the median request and the tail request usually fail for different reasons: the median might be dominated by a query, while the tail is dominated by connection-pool waiting or a retry. Optimising the median when your complaint is about the tail is a common waste of effort. The gap-with-no-work shape is the other one worth recognising — an unexplained gap in a trace almost always means the event loop was busy elsewhere or the request was waiting for a connection, both of which are invisible if you only look at spans.
@followup
How do you profile something that only happens in production?
@answer
Continuous profiling at a low sampling rate — Pyroscope, Datadog's profiler, or periodic `--cpu-prof` captures — so you always have a profile from the moment of the problem rather than trying to reproduce it. Combined with `auto_explain` on the database side for slow query plans, that covers the two most common cases. The alternative — reproducing production conditions locally — usually fails because the data distribution and concurrency are what cause the problem.
@red
- Guessing at the bottleneck from resource graphs.
- Optimising the median when the complaint is about the tail.

### How do you optimise a system that is I/O bound versus CPU bound?
@short
Diagnose which it is first — event-loop lag and CPU utilisation separate them. I/O bound means reducing round trips, batching, caching, parallelising and reusing connections. CPU bound means doing less work, moving it off the request path, or moving it to a language or process better suited to it.
@deep
Most web services are I/O bound, and the highest-leverage changes are structural: fewer queries, fewer sequential awaits, connection reuse, and caching. Adding CPU to an I/O-bound service buys nothing.

CPU-bound work in Node is the harder case because of the single thread — the answer is usually to move it rather than to optimise it, unless the hot function is genuinely improvable.
@code ts The two toolkits, and how to tell which you need
// DIAGNOSIS
//   loop lag low + CPU low + latency high   → waiting on I/O (or the pool)
//   loop lag high + CPU high                → CPU bound in JS
//   loop lag low + CPU low + latency high + fs/crypto in the path → thread pool saturated

// I/O-BOUND TOOLKIT
const [a, b, c] = await Promise.all([svcA(), svcB(), svcC()]);       // parallelise
const rows = await db.query('… WHERE id = ANY($1)', [ids]);          // batch
const agent = new https.Agent({ keepAlive: true, maxSockets: 128 }); // reuse connections
await redis.pipeline().get(k1).get(k2).get(k3).exec();               // pipeline
const cached = await cache(key, 300, load);                          // cache
// and: fewer round trips beats faster round trips, every time

// CPU-BOUND TOOLKIT
await pool.run({ buffer }, { transferList: [buffer] });              // worker threads
await queue.add('report', { spec });                                 // move off the path
const stringify = fastJson(schema);                                  // compile the hot path
// and: consider whether the work belongs in the database (SUM/GROUP BY) or
//      in a service written in Go, rather than being optimised in JS
@end
@senior
"Fewer round trips beats faster round trips" is the principle I would state, because it is where the large wins are: turning twenty queries into one is a step change, while making each query 20% faster is marginal. The corollary for CPU work is that the best optimisation is usually relocation — a `SUM` and `GROUP BY` in Postgres beats pulling 200,000 rows into Node to reduce them, both in latency and memory, and it is less code. I would also note that the thread-pool case is the diagnosis people miss, because it presents as I/O-bound symptoms with an idle CPU.
@followup
When would you rewrite a hot service in Go?
@answer
When it is genuinely CPU-bound with high concurrency, where Node's single thread is the structural constraint rather than an implementation detail — a high-throughput transformation service, a real-time aggregation layer, an encoding pipeline. I would want measurements showing that the JavaScript is already reasonably optimised and that CPU is the binding constraint, because rewriting an I/O-bound service in Go buys almost nothing while costing a language boundary in the team. The organisational cost of a second backend language is real and should be part of the decision.
@red
- Adding CPU capacity to an I/O-bound service.
- Micro-optimising JavaScript when the fix is a database index.

### How do you design a caching strategy that survives a cold start?
@short
Assume the cache can be empty at any moment — a deploy, a failover, an eviction storm — and ensure the system still functions, just slower. That means bounded concurrency to the origin, single-flight so a stampede does not multiply, negative caching, and warming for the keys that matter.
@deep
The dangerous state is a system where the database can only handle the traffic because the cache absorbs 95% of it. When the cache empties, the database receives twenty times its normal load and falls over, and the recovery is slow because the cache cannot refill while the origin is saturated.

The defences are single-flight (one recomputation per key), request coalescing, a concurrency cap to the origin, and serving stale data while refreshing.
@code ts Surviving an empty cache
const inflight = new Map<string, Promise<unknown>>();
const originLimit = pLimit(50);                 // hard cap on concurrent origin work

export async function cached<T>(key: string, ttl: number, load: () => Promise<T>): Promise<T> {
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);

  // stale-while-revalidate: serve the old value, refresh in the background
  const stale = await redis.get(`${key}:stale`);
  if (stale) { void refresh(key, ttl, load); return JSON.parse(stale); }

  // single-flight: N concurrent misses for the same key → ONE origin call
  const existing = inflight.get(key) as Promise<T> | undefined;
  if (existing) return existing;

  const p = originLimit(load)
    .then(async (v) => {
      await redis.multi()
        .set(key, JSON.stringify(v), 'EX', ttl + jitter())
        .set(`${key}:stale`, JSON.stringify(v), 'EX', ttl * 10)   // stale copy lives longer
        .exec();
      return v;
    })
    .finally(() => inflight.delete(key));

  inflight.set(key, p);
  return p;
}

// Warming: after a deploy, prefetch the top-N keys by traffic before taking load
await Promise.all(topKeys.slice(0, 500).map(k => originLimit(() => cached(k, TTL, loaders[k]))));
@end
@senior
The long-lived stale copy is the piece that makes a cold start survivable: even when the primary key expires, there is a slightly older value to serve while exactly one request refreshes, so the origin sees one request per key rather than thousands. Combined with a hard concurrency cap to the origin, the worst case becomes "slower" rather than "down". The question I always ask of a caching design is what happens when Redis restarts — if the answer is "the database falls over", the cache is load-bearing infrastructure and needs the same availability treatment as the database, or the design needs to change.
@followup
How do you warm a cache after a deploy?
@answer
Prefetch the highest-traffic keys before the instance passes its readiness check, so it does not receive traffic with an empty local cache. For a shared Redis this matters less, because a rolling deploy does not clear it — the cold-start problem is mainly about Redis restarts and about in-process caches. I derive the warm list from actual traffic data rather than guessing, and I bound the warming work so a deploy does not itself become a load spike on the origin.
@red
- A system that cannot survive an empty cache.
- No single-flight, so every miss multiplies by concurrency.

### How do you optimise database performance for a read-heavy workload?
@short
Index for the actual queries, cache aggressively with correct invalidation, use read replicas for anything that tolerates lag, pre-aggregate expensive computations, and reduce the data returned. Then verify with plans and buffer statistics rather than assuming.
@deep
The order matters because each step is cheaper than the next: an index costs nothing to run, a cache costs memory and complexity, a replica costs money and introduces lag, and a denormalised read model costs ongoing maintenance.

Index-only scans are the specific target for hot read paths — including the selected columns means the heap is never touched, which can be several times faster.
@code sql The read-optimisation ladder, with the measurement at each step
-- 1. INDEX for the query, and verify an Index Only Scan
CREATE INDEX CONCURRENTLY ON orders (tenant_id, status, created_at DESC)
  INCLUDE (total_minor, currency);
EXPLAIN (ANALYZE, BUFFERS) SELECT …;      -- want: "Index Only Scan", Heap Fetches: 0
-- Heap Fetches > 0 means the visibility map is stale → vacuum more aggressively

-- 2. RETURN LESS
SELECT id, total_minor, status FROM orders …   -- not SELECT * with a 4KB jsonb column

-- 3. PRE-AGGREGATE what is recomputed constantly
CREATE MATERIALIZED VIEW tenant_daily AS SELECT … GROUP BY …;
CREATE UNIQUE INDEX ON tenant_daily (tenant_id, d);
REFRESH MATERIALIZED VIEW CONCURRENTLY tenant_daily;

-- 4. REPLICA for anything tolerant of lag (reports, search, exports)
--    with read-your-writes routed to the primary

-- 5. MEASURE the cache hit ratio and the working set
SELECT sum(heap_blks_hit)::float / NULLIF(sum(heap_blks_hit + heap_blks_read), 0)
  FROM pg_statio_user_tables;               -- want > 0.99 for OLTP
@end
@senior
`Heap Fetches: 0` in an index-only scan is the detail worth checking rather than assuming: Postgres can only skip the heap if the visibility map says the page is all-visible, which requires vacuum to have run since the last modification. On a frequently updated table you can add a covering index, see "Index Only Scan" in the plan, and still be doing heap fetches on most rows — so the optimisation silently does not apply. Tuning autovacuum for that table is the fix, and it is the kind of thing that only shows up when you read the plan carefully.
@followup
When do read replicas stop helping?
@answer
When the workload is write-heavy, because replicas replay every write and therefore do not reduce write load at all — they add to it. They also stop helping when replication lag becomes large enough that reads must go to the primary anyway for correctness, which happens under heavy write load or during a large backfill. At that point the answers are partitioning, archiving, moving analytics to a different store, or reducing write amplification, not more replicas.
@red
- Adding replicas to solve a write bottleneck.
- Assuming a covering index gives index-only scans without checking heap fetches.

### How do you handle a workload with extreme traffic spikes?
@short
Absorb what you can at the edge with caching, queue what does not need to be synchronous, shed load with priority when capacity is exceeded, and scale ahead of the spike where it is predictable. Autoscaling alone is too slow for a step change, so the design must degrade gracefully rather than rely on adding capacity in time.
@deep
Autoscaling reacts on a timescale of minutes — metric collection, threshold evaluation, instance start, warm-up — while a flash sale spike arrives in seconds. So the system must survive the gap.

The techniques are: pre-scale for known events, keep a queue in front of anything that can be asynchronous, cache the read path aggressively so most of the spike never reaches the origin, and shed the least valuable traffic first.
@arch Handling a known spike (a sale launching at 20:00)
  BEFORE (T−30m)
   • pre-scale app tier and workers to the expected peak; do not rely on autoscaling
   • warm caches: product pages, inventory snapshots, config
   • raise DB connection headroom; verify pool arithmetic at the new instance count
   • freeze deploys; confirm rollback is one command
   • dashboards up, on-call briefed, runbook open

  DURING
   • CDN absorbs product pages (s-maxage + stale-while-revalidate)
   • inventory reads from Redis; DECREMENTS are atomic in Postgres (correctness)
   • checkout is NEVER shed; recommendations/search/analytics shed first
   • queue: order confirmation emails, analytics, webhooks → async
   • virtual waiting room if demand exceeds capacity → controlled admission,
     which is far better UX than everyone getting timeouts

  AFTER
   • drain queues, verify reconciliation, scale down gradually
   • post-event review: what bent first? that is next quarter's work
@end
@senior
The virtual waiting room is the technique that most improves the outcome of a genuine over-demand event: admitting users at the rate you can serve, with a position indicator, converts a total failure where nobody can buy into a slower experience where everybody eventually can. It is also honest with users, which matters for trust. The other point is that autoscaling is a cost optimisation, not a spike defence — for a known event you pre-scale, and for an unknown one you rely on caching, queuing and shedding, because instances cannot start fast enough.
@followup
How do you decide what to shed first?
@answer
By business value, decided in advance and encoded as endpoint classes: checkout and payment never shed, browsing degrades to cached content, and recommendations, search suggestions and analytics shed first. That requires a conversation with product rather than an engineering judgement, and the outcome should be a table in the runbook so the decision is not being made at 20:05 during the incident. The implementation is a middleware that checks a load signal and rejects low-priority requests quickly with a 503 and a `Retry-After`.
@red
- Relying on autoscaling to handle a step-change spike.
- No priority classification, so critical and optional traffic degrade together.

### How do you optimise for cost as well as latency?
@short
Measure cost per request or per tenant, find the dominant contributors, and attack them with the same rigour as latency — usually caching, right-sizing, storage lifecycle and eliminating data transfer. Cost and performance often align, because doing less work is both cheaper and faster.
@deep
The largest costs in a typical stack are compute that is over-provisioned for a peak that rarely arrives, database instances sized for the worst query rather than the workload, data transfer through NAT gateways and across availability zones, storage that nobody expires, and observability with high-cardinality labels.

AI features are the newer category and behave differently — cost scales with usage in a way that can grow ten times overnight.
@code text Cost per request, and the lever for each contributor
  MEASURE FIRST: attribute cost per endpoint and per tenant
   compute $/request  = (instance-hours × rate) / requests
   db $/request       = share of DB cost weighted by pg_stat_statements total_exec_time
   egress $/request   = bytes out × rate  (CDN vs origin vs NAT)
   ai $/request       = tokens × model rate  (already labelled per feature/tenant)

  TYPICAL DOMINANT CONTRIBUTORS AND FIXES
   over-provisioned compute   → right-size from p95, use Graviton, scale to zero non-prod
   oversized DB               → right-size; move reporting to a replica; index properly
   NAT gateway egress         → VPC endpoints (free for S3), co-locate chatty services
   cross-AZ transfer          → keep chatty pairs in one AZ where availability allows
   log/metric volume          → sample successes, drop unused labels, tier retention
   S3 with no lifecycle       → Intelligent-Tiering, expire old exports/temp objects
   AI tokens                  → prompt caching, output caps, model routing, semantic cache

  ALIGNMENT: caching, batching and returning less data all reduce cost AND latency.
  CONFLICT: replicas and multi-AZ increase cost to buy availability — that is a
            deliberate purchase, not waste.
@end
@senior
Attributing database cost by weighting the instance bill with each query's share of total execution time is a technique worth mentioning, because it turns "the database is expensive" into "this one endpoint accounts for 40% of database time", which is actionable in the same way a latency trace is. The broader framing I would give is that cost is an engineering metric, not a finance one — the people who can reduce it are the ones writing the queries — and making it visible per service and per feature changes behaviour far more effectively than a spending policy.
@followup
How do you avoid optimising cost at the expense of reliability?
@answer
By treating reliability spend as a deliberate purchase with a stated benefit — multi-AZ, replicas, headroom above p95 — and only cutting what is genuinely waste: idle non-production environments, unattached volumes, unsampled logs, over-provisioned instances that never approach their limits. I would also be explicit that removing headroom is a reliability decision disguised as a cost decision, so it should be made with the same care as any other change to the failure envelope, not quietly during a cost-reduction exercise.
@red
- Cutting headroom without recognising it as a reliability decision.
- Optimising cost without attribution data.

# SECTION Architecture & Staff-Level Judgement | The questions with no correct answer, where the reasoning is the assessment.

### How do you evaluate an architectural decision?
@short
By what it costs and what it buys, expressed as reversibility, blast radius, operational burden and the specific change it makes easier. I write a short decision record with the options, the trade-offs, the choice, and the conditions that would make me revisit it — so the reasoning survives the decision.
@deep
The single most useful lens is reversibility. A decision that is cheap to undo — a library behind an adapter, a caching layer — deserves a quick judgement and an experiment. A decision that is expensive to undo — a datastore, a shard key, a public API contract, a language — deserves analysis, prototyping and explicit agreement.

The second lens is who pays. An architecture that is elegant but requires the team to operate three new systems is a cost paid every day by people who did not choose it.
@code text A decision record that is actually useful later
  ADR-014: Outbox pattern for external side effects
  STATUS: accepted (2026-03) · supersedes ADR-009

  CONTEXT
    Calling Stripe inside the order transaction caused pool exhaustion under load
    (connections held for the duration of an 8s external call) and produced
    inconsistent state when the call succeeded but the transaction rolled back.

  OPTIONS CONSIDERED
    A. Call the provider after commit           — simple; loses the call if we crash
    B. Two-phase commit                          — unsupported by the provider
    C. Outbox table + relay worker (CHOSEN)      — atomic intent, at-least-once effect
    D. Event bus with transactional producer     — same guarantees, +1 system to operate

  DECISION: C. Same guarantees as D with no additional infrastructure. We already
    operate Postgres; we do not operate Kafka.

  CONSEQUENCES
    + no external calls inside transactions → pool pressure resolved
    + effects are retryable and observable (outbox table is queryable)
    − eventual consistency for emails/webhooks (seconds) — accepted, documented in UX
    − relay is a new component to monitor (lag, DLQ)

  REVISIT IF: we need cross-service event fan-out to >3 consumers, or relay lag
    becomes user-visible. Then D becomes the better trade.
@end
@senior
The "revisit if" clause is what distinguishes a decision record from documentation: it states the evidence that would change the answer, which means a future engineer can evaluate whether conditions have changed rather than either blindly following or blindly rewriting. The other habit is naming the option you did not take and why — most architectural arguments recur every eighteen months, and having the previous reasoning written down converts a debate into a review. I would also stress the operational cost line, because "we already operate Postgres; we do not operate Kafka" is frequently the deciding factor and it is rarely written down.
@followup
How do you handle a decision you disagree with that has already been made?
@answer
Commit and execute well, while making the risks visible in writing so they are shared rather than privately held. If new evidence emerges — the predicted problem materialises, or the constraints change — that is the moment to reopen it, with data rather than with a restatement of the original argument. Continuing to relitigate a settled decision is corrosive; documenting the conditions under which it should be revisited is constructive, and it is the same "revisit if" discipline applied to a decision I did not make.
@red
- Architectural decisions with no recorded reasoning.
- Evaluating options without considering operational cost.

### How do you decide when to rewrite versus refactor?
@short
Refactor by default. Rewrite only when the existing system cannot meet a requirement it must meet — a fundamental architectural constraint, not accumulated mess — and even then, strangle it incrementally rather than building a replacement in parallel and cutting over.
@deep
The case against big-bang rewrites is empirical: they take longer than estimated, the old system keeps changing during the rewrite, the new system rediscovers undocumented behaviour the hard way, and the business gets no value until the switch.

The strangler-fig approach delivers value continuously: route new functionality to the new implementation, migrate existing functionality piece by piece, and retire the old system when nothing calls it.
@code text When a rewrite is justified, and how to do it anyway incrementally
  REFACTOR when: the problems are structure, naming, coupling, test coverage,
                 duplication — anything reachable by incremental change.

  REWRITE when:  a REQUIREMENT cannot be met by the current architecture, e.g.
                 • single-tenant design must become multi-tenant
                 • a data model that cannot express a now-essential invariant
                 • a runtime or framework that is end-of-life with no upgrade path
                 • performance characteristics that are structural, not incidental

  EVEN THEN — strangle, do not big-bang:
    1. put a facade in front of the old system (routing layer / adapter)
    2. build the new implementation behind the SAME interface
    3. route ONE low-risk capability to it; shadow-compare against the old
    4. migrate capability by capability, always shippable, always reversible
    5. retire the old system when nothing routes to it

  RED FLAG: "we will rewrite it in 3 months and switch over" — the old system will
  have changed by then, and the estimate is optimistic by a factor nobody predicts.
@end
@senior
The distinction I would draw is between problems that are *incidental* — mess, duplication, poor naming, missing tests, all of which refactoring reaches — and problems that are *structural*, where the architecture cannot express what is now required. Only the second justifies a rewrite, and it is much rarer than people claim. I would also point out that the strangler approach is available even for a genuine rewrite, and choosing it means the business gets value throughout and you can stop at any point with something working — which is the property that makes the risk acceptable.
@followup
How do you convince stakeholders to fund a large refactor?
@answer
By expressing it as the cost being paid now rather than as an aesthetic improvement: this module adds two days to every payments change, caused four of the last nine bugs, and is modified in most pull requests. Then propose it incrementally, folded into feature work, so there is no large budget line to approve and value is delivered continuously. A request for a three-month refactor sprint is usually refused and should be; a plan to extract one component per sprint alongside features is usually accepted because the risk is bounded.
@red
- Proposing a rewrite for a codebase that is merely messy.
- A rewrite plan with no incremental delivery.

### How do you design a system when the requirements are uncertain?
@short
Optimise for changeability rather than for a predicted future: clear boundaries, adapters at the edges, data models that capture facts rather than derived conclusions, and deliberate deferral of decisions that are expensive to reverse. Build the simplest thing that works, but do not close doors unnecessarily.
@deep
The trap is speculative generality — building an abstraction for a requirement that never materialises, which costs complexity now and usually turns out to be the wrong abstraction anyway.

The complementary trap is closing doors: choosing a shard key, a public API contract, or a data model that cannot represent an obvious future need. Those are the decisions to think hard about, precisely because they are expensive to reverse.
@code text Which decisions to defer, and which to get right now
  DECIDE NOW (expensive to reverse)
   • what the data model MEANS — record facts, not conclusions
     ✔ store (paid_at, amount_minor, currency, provider, intent_id)
     ✘ store only a boolean is_paid — you can derive it, but not the reverse
   • identifier strategy (UUIDv7 vs int) — changing it later rewrites everything
   • tenancy model — retrofitting multi-tenancy is a rewrite
   • public API contract — external consumers make it permanent
   • money representation — integer minor units + currency, always

  DEFER (cheap to add later)
   • caching layer, search engine, queue technology
   • microservice extraction (keep the module boundary, defer the process boundary)
   • sharding, multi-region, read replicas
   • which specific vendor — behind an adapter, so switching is one module

  NEVER BUILD SPECULATIVELY
   • a plugin system for one plugin
   • an abstraction with one implementation and no second one in sight
   • configurability for a value that has never changed
@end
@senior
"Record facts, not conclusions" is the principle I would lead with, because it is the data-modelling decision that most determines future flexibility: storing when and how something was paid lets you derive any conclusion later, while storing a boolean throws away information you cannot recover. That is also why event logs and ledgers are so resilient to changing requirements. The complementary discipline is refusing speculative abstraction — the cost of adding an abstraction when you need it is almost always lower than the cost of carrying the wrong one for two years, and the second implementation is what tells you what the abstraction should be.
@followup
How do you avoid over-engineering?
@answer
By requiring a concrete, named reason for each layer of indirection — a second implementation that exists or is committed, a specific failure mode being defended against, a specific change being made easier. "It might be useful" is not a reason. I also prefer to write the simple version first and extract the abstraction on the second use, because two examples reveal the right shape and one does not. And in review I ask what would be deleted if a requirement went away, since machinery nobody can point at a purpose for is the definition of over-engineering.
@red
- Building for hypothetical scale or hypothetical requirements.
- Deferring decisions that are expensive to reverse.

### How do you introduce a significant technical change into an established team?
@short
Start from the problem rather than the technology, prototype on something real to produce evidence, involve the people who will maintain it, roll out incrementally with an escape hatch, and document the decision. A change nobody else understands or wants is a liability regardless of its technical merit.
@deep
The failure pattern is technology-first advocacy: someone introduces a tool they like, the team does not understand it, and it becomes an unmaintained island. The person who introduced it leaves and the tool becomes a permanent tax.

The successful pattern is problem-first with evidence: this specific pain, this measured improvement on a real slice, this migration path, this rollback plan.
@code text Introducing TypeScript to a JavaScript team — the same shape works for anything
  1. NAME THE PROBLEM, WITH DATA
     "38% of Sentry errors last quarter were type errors — undefined property access
      and wrong argument types. That is ~11 incidents and ~3 days of engineering."

  2. PROTOTYPE ON SOMETHING REAL
     Convert the payments module (highest risk, highest value). Measure: errors in
     that module before and after. Not a toy example — a module people care about.

  3. INVOLVE THE MAINTAINERS
     Pair with two engineers during the prototype. They become advocates or they
     surface the objection that kills it — both outcomes are useful.

  4. INCREMENTAL, REVERSIBLE ROLLOUT
     allowJs, strict:false, leaf-first. The build never breaks. Any step can stop.

  5. MAKE THE NEW WAY THE EASY WAY
     Templates, generators, lint rules, editor config. If the good path needs
     discipline, it will not hold.

  6. DOCUMENT AND TEACH
     ADR + a 30-minute session + a written migration guide. Then hand ownership
     to someone else — if only you can maintain it, it has not landed.
@end
@senior
Step six is the one that determines whether the change survives: handing ownership to someone else, deliberately, is what converts "your project" into "how we work". I have seen good technical changes fail purely because they remained one person's responsibility. Step one is the other critical part — leading with the measured problem rather than the technology means the discussion is about whether the problem is worth solving, which is a conversation you can win, rather than about tooling preference, which is a conversation nobody wins.
@followup
What if the team resists?
@answer
Understand the objection rather than overcoming it — resistance is usually informed: they have been burned by a similar change, they see a maintenance cost you have not accounted for, or the timing is genuinely wrong. Sometimes that changes my mind, which is a good outcome. If the objection is unfamiliarity, the answer is a smaller first step and more pairing. If the team is genuinely against it after a fair hearing, I would not push it through, because a change the team does not own will not be maintained, and the technical benefit does not survive that.
@red
- Introducing technology because it is interesting.
- Remaining the only person who can maintain the change.

### How do you balance delivery speed against engineering quality?
@short
By recognising that they are the same thing over any horizon longer than a few weeks — quality is what keeps you fast. The real trade is about which specific quality investments to make now, and that depends on the expected lifetime and blast radius of the code.
@deep
Some things are non-negotiable regardless of deadline because their failure is expensive and their cost is small: input validation, authorisation checks, idempotency on money, not logging secrets, and the ability to roll back. Others are genuinely negotiable early: comprehensive test coverage on a prototype, perfect abstractions, and full observability on a feature that may be deleted.

Making that distinction explicitly, and stating what you are deferring, is the professional version of "moving fast".
@code text What I never cut, and what I defer deliberately
  NEVER CUT (cheap now, catastrophic later)
   • authorisation scoped to the record and tenant
   • input validation at the boundary
   • idempotency on anything touching money
   • secrets out of code and logs
   • the ability to roll back (flags, reversible migrations, image retention)
   • enough observability to know it is broken

  DEFER DELIBERATELY, AND SAY SO
   • exhaustive test coverage on a feature that may not survive a month
   • extracting an abstraction before a second use
   • performance work before there is traffic
   • perfect error messages / edge-case polish
   • documentation beyond a README, for a prototype

  MAKE THE DEBT VISIBLE
   "Shipping without pagination on the admin list. Fine up to ~1,000 records;
    it will need a cursor after that. Ticket ENG-482, owner me, due before launch."
   ← that is engineering judgement. Silent omission is not.
@end
@senior
The distinction that matters is between deferring deliberately with a record and omitting silently. A team that says "we are skipping X because of Y, here is the ticket and the threshold at which it becomes urgent" is making an engineering decision; a team that just does not do it is accumulating unknown risk. I would also push back on the framing itself in an interview: sustained speed comes from good tests, fast feedback and safe deployment, so a team that has traded those away for short-term speed is slower within a quarter — and being able to make that argument with evidence is more useful than agreeing to cut corners gracefully.
@followup
What do you do when a deadline requires cutting something you said you never cut?
@answer
Push back once, clearly, with the specific consequence — "shipping without authorisation scoping means any customer can read any other customer's orders" — because that is a different category of decision from cutting test coverage. If the answer is still to ship, I would want that decision made by someone accountable for the risk and recorded in writing, and I would reduce the blast radius instead: ship behind a flag to internal users only, or to one pilot customer. There is almost always a way to satisfy the deadline without shipping the unsafe thing to everyone.
@red
- Treating speed and quality as inherently opposed.
- Cutting authorisation or validation for a deadline.

### How do you approach a system you have inherited that nobody understands?
@short
Establish observability first so you can see what it does, then map the boundaries — inputs, outputs, dependencies, data stores — then write characterisation tests around the behaviour you must preserve. Only then change anything, in small reversible steps.
@deep
The mistake is changing before understanding, which produces regressions in behaviour nobody documented and users depended on. Characterisation tests capture the current behaviour, quirks included, so a change that alters it becomes visible.

Observability is the prerequisite for everything: if you cannot see what the system does in production, you cannot safely change it or know whether your change helped.
@code text A plan for taking ownership of an opaque system
  WEEK 1 — SEE IT
   • add structured logging with a request id if absent
   • add metrics: request rate, error rate, latency per endpoint
   • add tracing for database and external calls
   • find or create a dashboard. Watch it for a few days before touching anything.

  WEEK 2 — MAP IT
   • inputs: who calls it, how often, with what
   • outputs: what it writes, what it calls, what depends on it
   • data: schema, sizes, growth rate, retention
   • deployment: how it ships, how it rolls back, what config it needs
   • draw it. One diagram everyone can read.

  WEEK 3 — PIN IT DOWN
   • characterisation tests around the behaviour you must not break —
     including the weird behaviour, because someone depends on it
   • record the "why is this like this?" questions. Some have answers; ask around.

  WEEK 4+ — CHANGE IT
   • smallest useful improvement first, behind a flag, measured
   • fix the thing that pages people at night before the thing that annoys you
   • write down what you learn as you go — you are the last person who will
     ever see this with fresh eyes
@end
@senior
"Fix the thing that pages people before the thing that annoys you" is the prioritisation I would emphasise, because the instinct on inheriting a messy system is to clean up the code that offends you, when the highest-value change is usually removing an operational burden. That also builds trust with the team who lived with it. And the note about being the last person to see it with fresh eyes is genuine advice: your confusion in the first month is a resource, and writing it down produces the onboarding document that never otherwise gets written.
@followup
What if the system needs to change urgently and there is no time for this?
@answer
Then compress it rather than skip it: add just enough observability to see the specific behaviour you are changing, write characterisation tests for just that path, and make the change behind a flag with a fast rollback. That might be a day rather than a month, and it is the difference between a change you can reverse confidently and one that produces an outage you cannot diagnose. The one step I would never skip is the ability to roll back, because it is what makes everything else recoverable.
@red
- Changing an unfamiliar system before you can observe it.
- Rewriting for elegance instead of fixing the operational pain.

### How do you scope and sequence a large project?
@short
Find the thinnest end-to-end slice that delivers real value, ship it, then expand. Sequence by risk — do the uncertain and irreversible parts early while there is time to change course — and keep every intermediate state shippable so the project can be stopped or repriorised without waste.
@deep
Sequencing by risk rather than by dependency order is the key move: building the easy parts first feels productive and defers the discovery of the problem that changes the plan. The uncertain integration, the performance question, the unclear requirement — those belong in week one, often as a timeboxed spike.

Vertical slices beat horizontal layers: a working thin path through every layer teaches you far more than a complete data layer with no consumer.
@code text Sequencing a payments integration for a new market
  ❌ HORIZONTAL (feels organised, learns nothing until the end)
     week 1-2  build the full data model
     week 3-4  build all the API endpoints
     week 5-6  build the UI
     week 7    integrate with the provider  ← the risk was here all along

  ✅ VERTICAL, RISK-FIRST
     day 1-2   SPIKE: does the provider's mandate flow fit our order state machine?
               (the answer changes the whole plan — find out now)
     week 1    thinnest end-to-end slice: ONE payment method, happy path only,
               real provider sandbox, real webhook, real database write
               → demoable, and it validates every layer
     week 2    failure paths: declines, duplicates, out-of-order webhooks
     week 3    reconciliation + observability  ← before more features, not after
     week 4    second payment method (now cheap — the shape is proven)
     week 5    admin tooling, refunds
     each week: shippable behind a flag. The project can stop at any point
     with something working and valuable.
@end
@senior
Putting reconciliation and observability in week three rather than at the end is the sequencing decision I would defend hardest, because they are what make the system operable — and they are always the first thing cut when a project runs late, which is exactly when you need them most. The spike on day one is the other principle: the question "does their mandate flow fit our state machine?" could invalidate weeks of work, so it is worth two days to find out before committing. Sequencing by risk is uncomfortable because it front-loads the hard parts, and that is precisely why it works.
@followup
How do you handle a project that is running late?
@answer
Re-scope rather than re-estimate: identify what can ship now and what can follow, and present options with their consequences rather than a new date alone. Because every slice is shippable, there is usually a version that delivers most of the value on time. I raise it as soon as I know, not at the deadline, and I am specific about what changed — a discovered integration complexity is a different conversation from underestimating known work, and being honest about which it was preserves credibility for the next estimate.
@red
- Building horizontally, integrating last.
- Deferring observability and reconciliation to the end.

### What do you do when you disagree with the industry consensus?
@short
Hold the position if the reasoning is sound and the context differs, but hold it with evidence and with humility about what the consensus is protecting against. Most consensus exists because of failures the advocate has not personally experienced, so understanding the failure is the prerequisite for departing from it.
@deep
Context genuinely varies. Microservices, event sourcing, GraphQL, Kubernetes and CQRS are all correct in some contexts and expensive mistakes in others, and the consensus rarely carries the context with it.

The professional version is to state the trade-off explicitly and to define what would change your mind — the same "revisit if" discipline as any architectural decision.
@code text Positions I would defend against the reflex answer, with the reasoning
  CONSENSUS                          MY POSITION IN CONTEXT
  ──────────────────────────────────────────────────────────────────────────────
  "microservices scale better"       a modular monolith scales further than most
                                     teams need; distribution is a cost you should
                                     be able to name a benefit for
  "always use an ORM"                ORMs for CRUD, raw SQL for the 20% that matters;
                                     hidden queries are worse than visible SQL
  "NoSQL for flexible schemas"       Postgres JSONB gives flexibility AND constraints;
                                     schema flexibility is rarely the actual problem
  "never use a monorepo"             monorepos are excellent when one team owns the
                                     stack; the tooling cost is real but bounded
  "cache everything"                 caching a query that is slow for a fixable reason
                                     hides the bug and creates a cold-start cliff
  "you must have 100% coverage"      coverage of risk, not of lines; mock-heavy tests
                                     with high coverage prove very little

  IN EVERY CASE: state what the consensus is protecting against, say why that
  does not apply here, and name what would change my mind.
@end
@senior
Stating what the consensus protects against is the part that makes a dissenting position credible rather than contrarian: "microservices exist so teams can deploy independently; we have one team and one release train, so we would pay the cost without the benefit — if we grow to four teams with conflicting cadences, I would revisit it". That shows you understand the rule before departing from it. The failure mode on both sides is cargo-culting: adopting a pattern because it is standard, or rejecting one because it is fashionable, without engaging with the problem it solves.
@followup
How do you know when you are wrong?
@answer
By defining in advance what evidence would change my position, and then actually looking for it. If I argued against extracting services and module boundaries keep being violated in review, that is the evidence, and I should say so rather than defend the original position. I also weight the opinions of people who have operated the thing I have only read about — the consensus usually encodes operational pain that a design discussion cannot convey, and being wrong about that is expensive.
@red
- Rejecting consensus without understanding what it protects against.
- Adopting patterns because they are standard, without a problem to solve.

### How do you think about build versus buy for infrastructure?
@short
Buy commodity capability, build differentiation. The question is not licence cost but total cost of ownership including the engineer-months to build, operate, secure and maintain it for three years — and the opportunity cost of those engineers not building the product.
@deep
The systematic error is underestimating operation. Building a queue is a week; running one reliably for three years — durability, monitoring, scaling, dead-letter handling, upgrades, on-call knowledge — is a continuous cost that never appears in the original estimate.

The counterweight is vendor risk: pricing changes, acquisitions, shutdowns and lock-in. The mitigation is an adapter boundary so switching is a contained project.
@code text The full-cost comparison, including what people leave out
  EXAMPLE: job queue
   BUILD (Postgres-backed)          BUY (SQS)
   ────────────────────────────────────────────────────────────────
   initial      ~1 week              ~1 day
   retries/DLQ  ~3 days              included
   monitoring   ~2 days              CloudWatch, included
   scaling      your problem         managed
   on-call      your team            AWS
   3-yr ops     ~1 week/yr           ~0
   cost         DB capacity          ~$0.40 / million requests
   VERDICT      fine at low volume; SQS wins as soon as volume or reliability
                requirements grow — and Postgres queues stay attractive precisely
                because you already operate Postgres

  ALWAYS, whichever you choose:
   • wrap it behind YOUR interface → switching is one module, not a rewrite
   • know the exit cost before you commit
   • check the pricing curve at 10× current volume, not at today's volume

  BUILD when: it IS the product · vendor pricing breaks at your scale ·
              compliance forbids the vendor · the requirement is genuinely unusual
  BUY when:   commodity · security-critical (payments, auth) · needs 24/7 expertise
              you do not have · time to market matters more than unit cost
@end
@senior
Checking the pricing curve at ten times current volume is the practical discipline, because vendor pricing that is trivial at launch can dominate the cost base at scale — per-seat, per-event and per-gigabyte models all have that shape. Knowing the exit cost before committing is the complement: if migrating away would take six months, that is a strategic dependency and should be a conscious decision. And the adapter boundary is the cheap insurance that makes most of this reversible, which is why I apply it even to vendors I expect to keep.
@followup
When have you regretted a buy decision?
@answer
The pattern I would describe is a managed service chosen for speed whose pricing model did not match how usage grew — per-record or per-event pricing that was negligible in the pilot and significant at scale — combined with an integration that had leaked into the application rather than sitting behind an adapter, so migrating was a project rather than a swap. The lesson was to model the cost curve at projected scale before committing, and to enforce the adapter boundary even when the vendor's SDK is convenient to use directly.
@red
- Comparing licence cost against build cost without operational cost.
- Integrating a vendor's SDK throughout the codebase.

# SECTION Testing, Delivery & Operational Excellence | The senior view of quality: not more tests, but the right guarantees.

### How do you design a test strategy for a complex system?
@short
Map the failure modes that would actually hurt, then choose the cheapest test that would catch each. That produces a portfolio — unit tests for logic, integration tests for wiring and data, contract tests for boundaries, property tests for invariants, and a small number of end-to-end journeys — rather than a coverage target.
@deep
Coverage measures which lines executed, not which failures are prevented. A suite with 90% coverage that mocks the database proves the mocks work.

The useful framing is: for each way this system can hurt someone, what is the cheapest reliable detection? Sometimes the answer is a test; sometimes it is a database constraint, a type, or an alert — and those are often better because they cannot be forgotten.
@code text Failure modes mapped to the cheapest control
  FAILURE MODE                        CHEAPEST RELIABLE CONTROL
  ──────────────────────────────────────────────────────────────────────────────
  wrong price calculated              unit test (pure function, exhaustive cases)
  order created in wrong tenant       integration test + RLS policy  ← constraint > test
  double charge on retry              integration test (concurrent duplicates)
                                      + UNIQUE(provider, intent_id)  ← constraint
  webhook processed twice             integration test with replayed signed fixture
  out-of-order webhook regresses      integration test + guarded UPDATE … WHERE status=
  N+1 introduced                      query-count assertion in the endpoint test
  breaking API change                 schema diff in CI (oasdiff), not a test
  bundle regression                   size-limit budget in CI
  auth check forgotten on new route   authorisation matrix test, generated per route
  migration locks the table           lock_timeout + rehearsal on a prod-size snapshot
  dependency vulnerability            automated scanning, not a test
  service degrades when Redis is down fault injection in CI (toxiproxy)

  NOTE how many are NOT tests. Constraints and types prevent; tests detect.
  Prefer prevention where it is available.
@end
@senior
"Constraints prevent, tests detect" is the framing I would lead with, because a unique index on the payment intent id makes double-charging structurally impossible regardless of how the code evolves, while a test only catches it if someone remembers to keep the test relevant. So my first question about a failure mode is whether the type system or the database can make it unrepresentable, and only if not do I reach for a test. That also produces a smaller, faster, more durable suite, which is what keeps people running it.
@followup
How do you decide how much testing is enough?
@answer
By risk and by change frequency: code that handles money, auth or personal data gets thorough testing including adversarial cases; code that is stable and low-consequence gets less. I also weight how quickly a failure would be detected another way — a bug that would be obvious on the first page load needs less test investment than one that silently mis-charges customers for a month. The honest answer is that "enough" is a judgement, and stating the reasoning is more useful than quoting a percentage.
@red
- A coverage percentage as the definition of enough.
- Tests where a constraint would prevent the problem entirely.

### How do you test a system with many external dependencies?
@short
Layer it: unit tests with the dependency stubbed at your own adapter interface, integration tests with HTTP intercepted and realistic recorded payloads including error cases, and a small number of tests against the provider's sandbox running outside the main CI path. Never call live third-party APIs in CI.
@deep
Recorded payloads are important because hand-written fixtures drift from reality. Capturing real responses — with secrets scrubbed — and replaying them keeps the tests honest about the actual shape.

The adapter boundary is what makes this tractable: because the domain talks to your interface rather than the vendor's SDK, most tests need a simple fake rather than an HTTP-level mock.
@code ts Three layers, and the contract test that keeps fakes honest
// LAYER 1 — domain tests use a FAKE adapter. Fast, no HTTP.
const fake: PaymentProvider = {
  name: 'stripe',
  createIntent: async () => ({ intentId: 'pi_test', clientSecret: 'cs_test' }),
  verifyWebhook: async () => ({ eventId: 'evt_1', event: { kind: 'succeeded', … } }),
  refund: async () => ({ refundId: 're_1' }),
};

// LAYER 2 — adapter tests replay RECORDED provider responses (secrets scrubbed)
nock('https://api.stripe.com')
  .post('/v1/payment_intents')
  .reply(200, fixtures.paymentIntentCreated);            // captured from the sandbox
nock('https://api.stripe.com')
  .post('/v1/refunds')
  .reply(402, fixtures.cardDeclined);                    // ← error cases matter most

// LAYER 3 — CONTRACT TEST against the sandbox, run nightly (not on every PR)
//   catches provider changes that fixtures cannot: new required fields,
//   changed error shapes, renamed enums
it('sandbox: created intent matches our parsed shape', async () => {
  const real = await liveStripe.paymentIntents.create({ amount: 100, currency: 'inr' });
  expect(() => IntentSchema.parse(adapter.toDomain(real))).not.toThrow();
});

// Keeping fakes honest: the SAME suite runs against both the fake and the recorded
// adapter, so a fake that drifts from reality fails.
@end
@senior
Running one shared suite against both the fake and the recorded adapter is the technique that prevents the classic problem where the fake diverges from reality and the tests become fiction. The nightly sandbox contract test is the other half — it catches provider-side changes that no fixture can, and running it outside the pull-request path means a provider outage does not block merges. I would emphasise the error fixtures particularly: the happy path is what everyone tests and the declined card, the rate limit and the malformed webhook are what actually break in production.
@followup
How do you test third-party webhooks?
@answer
Sign fixtures with the real HMAC using a test secret, so the signature-verification path — including the raw-body handling — is genuinely exercised rather than stubbed. Then test the adversarial cases: duplicate delivery, out-of-order delivery, an invalid signature, and an event type you do not handle. Provider CLIs that replay real deliveries into a local endpoint are excellent for validating the shapes during development, and I capture those payloads as fixtures for CI.
@red
- Calling live third-party APIs from CI.
- Stubbing signature verification rather than signing fixtures.

### How do you use property-based testing?
@short
For invariants that must hold across all inputs rather than for specific examples — a parser that must round-trip, a merge that must converge, a pricing function that must never produce a negative total. The library generates inputs and shrinks failures to a minimal reproduction.
@deep
The value is finding the inputs you would not have thought of: empty arrays, unicode surrogate pairs, values at boundaries, and unusual orderings. Shrinking is what makes failures actionable — instead of a 200-element failing case you get the smallest one that still fails.

It complements example-based tests rather than replacing them: examples document intent, properties explore the space.
@code ts Properties worth asserting
import fc from 'fast-check';

// 1. Round-trip: encoding then decoding must return the original
it('cursor encoding round-trips', () => {
  fc.assert(fc.property(fc.record({ ts: fc.date(), id: fc.uuid() }), (c) => {
    expect(decodeCursor(encodeCursor(c))).toEqual(c);
  }));
});

// 2. Invariant: a total can never be negative, whatever the discounts
it('order total is never negative', () => {
  fc.assert(fc.property(
    fc.array(fc.record({ priceMinor: fc.nat(1_000_000), qty: fc.integer({ min: 1, max: 99 }) })),
    fc.option(fc.record({ pct: fc.float({ min: 0, max: 1 }), maxOffMinor: fc.nat(500_000) })),
    (items, coupon) => {
      const t = priceOrder(items, coupon ?? undefined);
      expect(t.totalMinor).toBeGreaterThanOrEqual(0);
      expect(t.discountMinor).toBeLessThanOrEqual(t.subtotalMinor);
    }));
});

// 3. Commutativity: CRDT updates converge regardless of application order
// 4. Idempotency: applying the same webhook twice equals applying it once
it('webhook application is idempotent', () => {
  fc.assert(fc.asyncProperty(arbitraryEvent(), async (e) => {
    const once = await applyToFreshDb(e);
    const twice = await applyToFreshDb(e, e);
    expect(twice).toEqual(once);
  }));
});
@end
@senior
Idempotency and convergence are the two properties where this technique earns its place decisively, because both are statements about all possible orderings and duplications — exactly the space example-based tests cannot cover. The pricing invariant is the other one I would highlight, because "the total is never negative" is the kind of property that a specific combination of a percentage discount, a cap and a rounding rule can violate in a way nobody would think to test. The cost is that these tests are slower and occasionally flaky if the generators are too broad, so I use them for genuine invariants rather than everywhere.
@followup
How do you handle a property test that fails intermittently?
@answer
Capture the failing seed — fast-check reports it — and add it as a regression test with that exact input, so the specific case is deterministic while the property continues exploring. If the intermittency comes from the test itself rather than the code (shared state, timing), that is a test bug and I fix it rather than reducing the generator. What I would not do is loosen the property to make it pass, because the property is the specification.
@red
- Property tests for behaviour that is not actually invariant.
- Loosening a property to make a genuine failure disappear.

### How do you approach continuous deployment safely?
@short
Small changes, comprehensive automated verification, deployment decoupled from release via feature flags, progressive rollout with automatic rollback on error-rate or latency breach, and observability good enough to detect a problem within minutes. Safety comes from small blast radius and fast recovery, not from more manual gates.
@deep
Manual approval gates create the illusion of safety while making changes larger and less frequent, which increases risk per deployment. The counter-intuitive finding from delivery research is that teams deploying more often have lower change-failure rates, because each change is smaller and the pipeline is exercised constantly.

The prerequisite is that rollback is fast and reliable, which must be tested rather than assumed.
@code yaml A pipeline where safety is automated, not manual
on: { push: { branches: [main] } }
jobs:
  verify:
    steps:
      - run: npm ci --ignore-scripts
      - run: npm run lint && npx tsc --noEmit
      - run: npm run test:unit
      - run: npm run test:integration          # real Postgres via testcontainers
      - run: npm run test:security             # authorisation matrix
      - run: npx size-limit                    # bundle budget
      - run: npm audit --audit-level=high

  deploy:
    needs: verify
    steps:
      - run: ./deploy.sh --canary 10           # 10% of traffic
      - run: sleep 300
      - run: ./compare.sh --window 5m --baseline 1h \
               --max-error-delta 0.5 --max-p99-delta 200 --max-payment-decline-delta 2
      - run: ./deploy.sh --promote 100
      - if: failure()
        run: ./deploy.sh --rollback && ./notify.sh "auto-rollback: metrics breach"

# The feature itself ships DISABLED. Release = flipping a flag, separately,
# to internal users → 1% → 10% → 100%, each step reversible in seconds.
@end
@senior
Separating deployment from release is the decision that makes continuous deployment safe: code reaches production many times a day with the feature disabled, so a deployment is a low-risk event, and turning the feature on is a separate, instantly reversible action. That also means a problem discovered at 1% of users is fixed by a flag flip rather than by a deploy. The automated comparison against a baseline is the other essential — a human watching a dashboard for five minutes after every deploy does not scale and does not happen at 2am, whereas an automated check with an automatic rollback does.
@followup
What must be true before you can deploy continuously?
@answer
A trustworthy automated test suite, fast and reliable rollback, feature flags for anything risky, observability that detects problems within minutes, and backwards-compatible database changes. Missing any of those makes continuous deployment reckless rather than modern. If a team wants to get there, I would build those prerequisites in that order — starting with rollback, because it is what makes every subsequent risk survivable.
@red
- Manual approval gates as the primary safety mechanism.
- Continuous deployment without fast rollback.

### How do you manage database changes in a continuously deployed system?
@short
Every migration is backwards-compatible with the running code, additive changes deploy separately from the code that uses them, destructive changes wait until the previous code version is fully retired, and migrations run as a separate step with a lock timeout and a rehearsal against production-sized data.
@deep
The binding constraint is that during a rolling deploy both versions run against the same schema, so any change must be valid for both. That rules out renames, type narrowings and drops in a single step.

The operational constraint is locking: a migration that cannot get its lock queues every subsequent query behind it, which is why `lock_timeout` is non-negotiable.
@code text The migration rules, as a checklist enforced in review
  ALWAYS SAFE (deploy any time)
   • ADD COLUMN nullable (or with a non-volatile default, PG11+)
   • CREATE INDEX CONCURRENTLY  (outside a transaction)
   • ADD CONSTRAINT … NOT VALID, then VALIDATE separately
   • CREATE TABLE / new enum VALUE (at the end)

  NEVER IN ONE STEP
   • RENAME column/table            → add new, dual-write, backfill, switch, drop
   • change a column TYPE           → same expand/contract dance
   • ADD NOT NULL directly          → NOT VALID check, backfill, VALIDATE, then SET
   • DROP column still referenced   → wait a full release after the code stops using it
   • CREATE INDEX (non-concurrent)  → locks writes for the duration

  ALWAYS
   • SET lock_timeout = '3s'  → fail fast rather than queueing every query
   • SET statement_timeout    → bound the migration itself
   • backfills in BATCHES, outside the migration transaction, throttled
   • rehearse on a restored production-size snapshot; record the timing
   • review the generated SQL — ORMs generate destructive migrations routinely
@end
@senior
Rehearsing on a production-sized restore is the practice that prevents the classic incident: a migration that takes twelve milliseconds on development data takes forty minutes on fifty million rows, and nobody finds out until it is running against production. Recording the rehearsal timing in the pull request makes the risk visible to reviewers. The `lock_timeout` line is the other one I would treat as mandatory, because it converts "the site is down for six minutes" into "the migration failed, retry in a quieter window", which is an entirely different kind of day.
@followup
How do you roll back a deployment that included a migration?
@answer
You roll back the code, not the schema — which works because the migration was additive and the previous code version does not know about the new column. That is exactly why destructive changes are deferred: dropping a column in the same release as the code change makes rollback impossible. If data was genuinely corrupted rather than merely changed, recovery is point-in-time restore, which is why testing restores matters more than taking backups. The design principle is that every deployment must be reversible by reverting code alone.
@red
- Renaming a column in a single migration.
- Migrations that have never been rehearsed at production scale.

### How do you build an on-call practice that people can sustain?
@short
Few enough pages that sleep is normal, every page actionable with a runbook, rotation that shares knowledge rather than concentrating it, compensation or time back for out-of-hours work, and a strict discipline of turning every incident into a control that prevents recurrence. Unsustainable on-call is a systems problem, not a stamina problem.
@deep
The metric to manage is pages per person per week, and specifically out-of-hours pages. Anything above roughly one or two a week erodes people and, more dangerously, trains them to dismiss alerts.

The lever is alert quality: delete alerts that never lead to action, convert cause-based alerts to symptom-based ones, and route non-urgent signals to a ticket queue.
@code text An on-call health review I would run monthly
  METRICS
   pages per person per week          target ≤ 2, out-of-hours ≤ 1
   % pages that led to an action      target > 80%   ← below that, alerts are noise
   median time to acknowledge / fix
   % incidents with a completed post-mortem and SHIPPED follow-ups
   repeat incidents (same cause twice) ← the most damning metric

  FOR EACH ALERT THAT FIRED
   did a human do something different because of it?
     no  → tune the threshold, convert to a ticket, or DELETE it
     yes → is the runbook accurate? update it now, while it is fresh

  STRUCTURE
   • every paging alert has an owner, a runbook link and a stated user impact
   • non-urgent signals go to a queue reviewed in business hours, never a page
   • follow-up actions from post-mortems are scheduled work, not backlog decoration
   • rotate deliberately so knowledge spreads; pair a newer engineer with the primary
   • compensate out-of-hours work — otherwise the cost is invisible and never fixed
@end
@senior
The percentage of pages that led to an action is the metric I would put at the top, because it directly measures alert quality, and alert quality is what determines whether a real incident gets noticed. A rotation where 60% of pages are ignorable has already failed, regardless of how good the tooling is. The other point is that repeat incidents are the strongest signal that post-mortem follow-ups are not being done — and if they are not being scheduled as real work, the post-mortem process is theatre and I would rather fix that than run more of them.
@followup
How do you handle an on-call rotation on a small team?
@answer
Reduce the load rather than distribute the pain: aggressively tune alerts, invest in automatic recovery for the failures that recur, and be explicit about what is genuinely urgent overnight versus what can wait until morning. On a small team the honest answer may be that some services do not warrant 24/7 response, and stating that as a service-level decision — with the business — is better than an implicit expectation that someone is always watching. Compensation and time back matter more, not less, when the pool of people is small.
@red
- On-call with no compensation and no alert hygiene.
- Post-mortem actions that are never scheduled.

### How do you run a blameless post-mortem that actually improves things?
@short
Establish a factual timeline, ask why the failure was possible and why detection took as long as it did, produce a small number of specific scheduled actions with owners, and share it widely. Blameless means focusing on the conditions rather than the person, because the person was responding rationally to the system they were in.
@deep
Two questions matter more than the rest: what made this class of failure possible, and what made it hard to detect. Most post-mortems answer the first and skip the second, but detection latency is usually the more tractable problem and the higher-leverage fix.

Actions must be specific and scheduled. "Be more careful with migrations" is not an action; "add `lock_timeout` to the migration runner and rehearse on a production snapshot in CI" is.
@code text A post-mortem template that produces change
  TITLE     Checkout unavailable for 6 minutes — blocking migration
  IMPACT    ~2,400 failed checkouts, ~₹—— in delayed revenue, 11 support tickets
  DETECTED  automated alert, T+90s   (good — not by a customer)

  TIMELINE (facts, timestamps, no interpretation)
   14:02  migration ALTER TABLE orders ADD NOT NULL deployed
   14:02  the statement waited for ACCESS EXCLUSIVE behind a 40s report query
   14:03  every subsequent query on `orders` queued behind the pending lock
   14:03  p99 alert fired; on-call acknowledged at 14:04
   14:07  pg_cancel_backend on the migration → locks released, recovery in ~30s
   14:08  error rate normal

  WHY WAS IT POSSIBLE
   • migrations ran with no lock_timeout
   • ADD NOT NULL was used directly instead of NOT VALID + VALIDATE
   • the migration was tested against a 5k-row dev table, not production scale

  WHY WAS DETECTION/RECOVERY NOT FASTER
   • no runbook entry for "identify and cancel a blocking migration" —
     the responder spent 3 of the 6 minutes finding the right query

  ACTIONS (owner, date, ticket — NOT "be careful")
   1. lock_timeout=3s in the migration runner        @ana   this week   ENG-731
   2. lint rule: reject ADD NOT NULL / non-concurrent CREATE INDEX  @sam  ENG-732
   3. CI: rehearse migrations on a restored prod snapshot  @ana  2 weeks  ENG-733
   4. runbook: blocking-migration diagnosis + cancel commands  @sam  today  ENG-734

  WHAT WENT WELL   alerting caught it in 90s; rollback was not needed; comms were clear
@end
@senior
Asking why detection and recovery were not faster, as a separate question from why the failure happened, is the addition that most improves post-mortems — in this example three of the six minutes were spent finding a command, and a runbook entry is a cheaper, more reliable fix than any amount of care. The "what went well" section is also worth keeping: it reinforces the investments that paid off, which is how you justify continuing to make them. And listing owners and tickets is what separates a post-mortem that changes the system from one that documents an event.
@followup
What if the incident was clearly caused by one person's mistake?
@answer
Then the question is why the system allowed a single person's ordinary mistake to cause an outage. A missing lock timeout, an absent lint rule, a deploy pipeline with no verification, a migration untested at scale — those are the causes, and the person merely encountered them first. Naming the individual changes nothing except making everyone less likely to report the next incident honestly, which is the opposite of what you need. I would say that explicitly in the meeting if the tone drifts, because the culture is set in exactly those moments.
@red
- Post-mortems that identify a person as the root cause.
- Actions like "be more careful" with no owner or date.

### How do you measure engineering effectiveness?
@short
Delivery metrics that reflect flow and stability — deployment frequency, lead time from commit to production, change-failure rate, and time to restore — plus qualitative signals from the team. Never individual output metrics like lines of code or commits, which are trivially gamed and measure the wrong thing.
@deep
The four delivery metrics are useful because they are outcomes rather than activity, and because improving them requires improving the system: better tests, faster pipelines, safer deploys, better observability.

They are diagnostic rather than targets. Deployment frequency rising because the team is shipping smaller safer changes is good; rising because they are splitting one change into six deploys to hit a number is not.
@code text What I would track, and what I would refuse to track
  FLOW
   deployment frequency          → how often does value reach users?
   lead time (commit → prod)     → how long is the feedback loop?
  STABILITY
   change failure rate           → what proportion of deploys cause a problem?
   time to restore               → how quickly do we recover?
  HEALTH
   % capacity on unplanned work  → is reliability debt eating delivery?
   on-call pages per person      → is this sustainable?
   flaky test rate               → is the suite trusted?

  QUALITATIVE (equally important)
   • do engineers feel able to ship safely?
   • can a new joiner ship in their first week?
   • do people avoid touching certain parts of the codebase? (which, and why?)

  REFUSE TO TRACK PER PERSON
   lines of code · commits · story points · PRs merged · hours
   → all trivially gamed, all measure activity rather than outcome, all damage
     collaboration the moment they are used for evaluation
@end
@senior
The percentage of capacity going to unplanned work is the metric I find most actionable in practice, because it is the one that explains why a team feels slow: if 40% of every sprint is absorbed by incidents and interruptions, no amount of estimation discipline will help, and the fix is reliability investment. That is also an argument a business stakeholder understands. On individual metrics I would be firm — the moment they are used for evaluation, behaviour optimises for the metric rather than the outcome, and the collaboration that makes teams effective is the first casualty.
@followup
How do you improve lead time?
@answer
Look at where the time actually goes between commit and production: waiting for review, waiting for CI, waiting for a manual gate, or batching into a release. Each has a different fix — smaller pull requests and review expectations, parallelised and cached CI, automated verification replacing manual approval, and continuous deployment replacing release trains. Measuring the breakdown rather than the total is what makes it improvable, and usually one stage dominates.
@red
- Individual productivity metrics.
- Treating delivery metrics as targets rather than diagnostics.

### How do you keep a system maintainable over years, not months?
@short
Boundaries that are enforced mechanically, decisions recorded with their reasoning, dependencies kept current continuously rather than in large jumps, observability treated as part of the feature, and knowledge distributed deliberately so no component has a single owner.
@deep
Systems decay in predictable ways: boundaries erode because nothing enforces them, dependencies age until upgrading is a project, decisions are forgotten so nobody dares change anything, and knowledge concentrates until one person is a bottleneck.

Each has a mechanical counter — a linter, an ADR, automated dependency updates, and rotation — which is why maintainability is more about process than about code style.
@code text The mechanisms that fight each decay mode
  DECAY                          MECHANISM
  ────────────────────────────────────────────────────────────────────────────
  boundaries erode               dependency-cruiser / eslint-boundaries in CI
                                 → cross-feature imports fail the build
  dependencies age               Renovate with grouped, automerged patch updates;
                                 majors as scheduled work. Small hops, never a
                                 two-year jump.
  decisions forgotten            ADRs in the repo with a "revisit if" clause
  knowledge concentrates         rotation, pairing on unfamiliar areas,
                                 runbooks written by the person who resolved it
  tests become untrusted         quarantine flaky tests immediately; track the rate
  observability rots             dashboards reviewed in post-mortems; alerts pruned
  performance erodes             CI budgets (bundle size, query counts, lighthouse)
  security drifts                automated scanning + a scheduled threat-model review

  THE COMMON PATTERN: every one is a mechanical gate, not a good intention.
  Anything that relies on people remembering will decay.
@end
@senior
"Anything that relies on people remembering will decay" is the principle I would state, and it is why I push for gates in CI rather than guidelines in a wiki. The dependency point is worth emphasising specifically: teams that update continuously do small, boring upgrades, while teams that defer end up with a two-year jump that is a project nobody wants to own — and then they are stuck on an unsupported runtime with unpatched vulnerabilities. Automated grouped patch updates with a good test suite makes that a non-event, which is a large long-term saving for a small ongoing cost.
@followup
What is the first thing you would fix on a codebase that has decayed?
@answer
The feedback loop — whatever makes changes slow or frightening. Usually that is a slow or untrusted test suite, or the absence of a reliable rollback, because both mean every change carries unbounded risk and people therefore batch changes, which makes each one riskier. Fixing that first makes every subsequent improvement cheaper and safer. Cleaning up code before you can change it confidently is the wrong order, however tempting the mess is.
@red
- Maintainability as a matter of code style.
- Dependency upgrades deferred until they become a project.
